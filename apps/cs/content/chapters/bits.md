이 책은 장면 하나를 처음부터 끝까지 따라갑니다. **지금 읽고 있는 이 페이지**입니다. 이 페이지는 어딘가의 서버에서 출발해 바다와 통신사를 건너 내 컴퓨터에 왔고, 운영체제와 브라우저를 거쳐 화면의 픽셀이 되었습니다. 맨 아래의 "학습 완료"를 누르면 그 기록이 디스크에 남습니다. 장마다 이 장면의 한 구간을 확대해서 봅니다.

1장은 가장 작은 곳에서 시작합니다. 이 페이지는 컴퓨터 안에서 어떤 모습일까요? 브라우저가 받은 이 페이지의 파일을 그대로 열어 보면 맨 앞은 이렇게 생겼습니다.

![이 페이지의 HTML 파일 맨 앞 16바이트. 위는 우리가 읽는 글자, 가운데는 컴퓨터가 실제로 가진 값(16진수), 아래는 그중 한 바이트를 비트로 편 것입니다](bits-page-bytes.svg)

글자도, 색도, 진행 막대의 숫자도 없습니다. 0과 1이 늘어선 줄뿐입니다. 이 장은 이 줄을 숫자로, 글자로, 색으로, 파일로 읽어 내는 약속을 차례로 봅니다. 왜 하필 0과 1인지부터 시작합니다.

## 왜 하필 0과 1인가

컴퓨터 부품은 수십억 개의 [[트랜지스터]]로 되어 있습니다. 트랜지스터는 전기로 여닫는 아주 작은 스위치입니다. 스위치는 켜짐과 꺼짐 두 상태를 가장 확실하게 구분합니다. 전압을 열 단계로 나눠 0부터 9까지 표현할 수도 있겠지만, 전선에는 늘 잡음이 섞이고 온도에 따라 전압이 조금씩 흔들립니다. 열 단계면 3.4V가 3인지 4인지 헷갈리지만, 두 단계면 "대략 높다" "대략 낮다"만 보면 되니 잡음에 강합니다.

![전압을 열 단계로 나누면 잡음 조금에도 칸을 넘어가지만, 두 단계로 나누면 웬만큼 흔들려도 높은지 낮은지는 분명합니다](bits-noise.svg)

그래서 컴퓨터는 모든 것을 두 가지 상태의 나열로 적습니다. 이 한 자리를 [[비트]](bit, binary digit)라고 부르고, 0과 1로 씁니다. 0과 1은 전압, 자기장의 방향(하드디스크), 빛이 있고 없음(광섬유), 전하가 갇혀 있는지(SSD) 등 무엇으로든 만들 수 있습니다. 이 페이지도 서버의 SSD에서는 갇힌 전하로, 바다 밑 광섬유에서는 빛의 깜빡임으로, 내 컴퓨터의 메모리에서는 전압으로 있었습니다. 물리적인 방법은 달라도 위에서 보면 똑같이 0과 1입니다.

이렇게 "아래가 어떻게 생겼는지 몰라도 위에서 쓸 수 있게 감싸는 것"을 추상화라고 합니다. 이 책 전체가 추상화를 한 층씩 쌓아 올리는 이야기입니다.

비트 하나로는 두 가지밖에 못 나타냅니다. 그럼 비트를 몇 개씩 묶어야 쓸모가 생길까요?

잡음으로 비트가 뒤집히는 일을 완전히 막을 수는 없으니, 뒤집혔는지 알아채는 장치를 덧붙입니다. 가장 단순한 것이 [[패리티 비트]]입니다. 데이터의 1이 짝수 개가 되도록 비트 하나를 더 붙여 두면, 한 비트가 뒤집혔을 때 1의 개수가 홀수가 되어 알아챕니다. 어느 비트인지는 모르고, 두 비트가 함께 뒤집히면 놓칩니다. 검사 비트를 여러 개 겹치게 두면 몇 번째 비트가 뒤집혔는지까지 알아내 바로잡을 수 있는데, 그 대표가 [[해밍 코드]]입니다. 서버의 ECC 메모리(2장)가 이렇게 한 비트 오류를 고치고, 10장의 이더넷 FCS(CRC)는 고치지는 못해도 여러 비트의 오류를 잘 찾아냅니다.

:::quiz parity 짝수 패리티를 쓰는 7비트 데이터 `1011001`에 붙일 패리티 비트는? (0 또는 1)
= 0

**0**입니다. 1이 네 개(1, 1, 1, 1)로 이미 짝수이니 0을 붙입니다. 받는 쪽에서 1의 개수가 홀수로 바뀌어 있으면 어딘가 한 비트가 뒤집힌 것입니다.
:::

## 비트를 묶으면: 바이트와 용량 단위

비트를 n개 붙이면 2ⁿ가지를 구분합니다. 2비트는 4가지, 8비트는 256가지, 32비트는 약 43억 가지입니다.

비트 8개를 묶은 것을 [[바이트]]라고 부릅니다. 메모리와 파일은 바이트 단위로 주소를 매기고 읽고 씁니다. "이 파일은 3바이트다"라고 할 수는 있어도 "3비트 반이다"라고 할 수는 없습니다. [[CPU]]가 한 번에 다루기 좋은 크기는 [[워드]]라고 하는데, 요즘 컴퓨터는 대부분 64비트(8바이트) 워드를 씁니다. "64비트 운영체제"라는 말이 여기서 나옵니다.

이 페이지의 HTML 파일은 4만 바이트 남짓입니다. 이걸 "40KB"라고 쓸지 "39KiB"라고 쓸지에서 함정이 하나 생깁니다. 킬로(k)는 원래 1000인데, 컴퓨터는 2의 거듭제곱을 좋아해서 1024를 킬로라고 부르던 습관이 있습니다. 이 둘을 구분하려고 1024 단위에는 KiB, MiB, GiB처럼 i를 붙입니다.

| 표기 | 뜻 | 바이트 수 |
| --- | --- | --- |
| 1 KB | 킬로바이트 (10진) | 1,000 |
| 1 KiB | 키비바이트 (2진) | 1,024 |
| 1 GB | 기가바이트 (10진) | 1,000,000,000 |
| 1 GiB | 기비바이트 (2진) | 1,073,741,824 |

운영체제마다 이 단위를 다르게 씁니다. 그래서 같은 512GB SSD가 컴퓨터마다 다르게 보입니다.

| | Windows | macOS | Linux |
| --- | --- | --- | --- |
| 파일 탐색기의 "GB" | 사실은 GiB (1024³) | 진짜 GB (1000³, 2009년 Snow Leopard부터) | 프로그램마다 다름. `ls -h`, `df -h`는 1024, `df -H`는 1000 |
| 512GB SSD가 보이는 크기 | 약 476GB | 약 512GB (실제로는 포맷에 쓰인 만큼 빠짐) | 도구에 따라 476G 또는 512G |

디스크 회사는 10진 GB로 팔고 Windows는 2진으로 나눠 보여 주니, 약 7% 차이가 "사라진 용량"처럼 보이는 것입니다. 실제로 사라진 것은 없습니다.

이 페이지가 네트워크를 건너올 때는 단위가 또 바뀝니다. 네트워크 속도는 바이트가 아니라 **비트**로 셉니다. 100Mbps 인터넷은 초당 100메가비트이고, 8로 나누면 초당 12.5메가바이트입니다. 기가 인터넷(1Gbps)으로 1GB 파일을 받는 데 1초가 아니라 이론상 최소 8초가 걸리는 이유입니다. 실제로는 [[헤더]]와 재전송 때문에 더 걸립니다.

:::quiz disk-units 1TB라고 적힌 외장 디스크를 Windows에 꽂았더니 931GB로 보입니다. 가장 정확한 설명은?
- [ ] 포맷하면서 약 7%가 파일 시스템 정보로 쓰여서
- [ ] 제조사가 실제보다 크게 적어 팔아서
- [x] 제조사는 1000 단위로, Windows는 1024 단위로 나눠 보여 줘서
- [ ] Windows가 숨김 파일 공간을 미리 잡아 둬서

단위가 다르기 때문입니다. 10¹² 바이트를 1024³으로 나누면 약 931이 나오고, Windows는 이걸 "GB"라고 적습니다. 포맷에도 공간이 조금 쓰이긴 하지만 7%나 되지는 않습니다.
:::

## 바이트를 사람이 읽으려면: 2진수와 16진수

맨 앞 그림의 가운데 줄에 `3C 21 64 6F`처럼 적힌 것이 바이트 값입니다. 이 표기를 읽으려면 수 체계 두 가지를 알아야 합니다.

우리가 쓰는 10진수는 자리마다 10배씩 커집니다. 345는 3×100 + 4×10 + 5×1입니다. [[2진수]]는 자리마다 2배씩 커집니다. `1011`은 1×8 + 0×4 + 1×2 + 1×1 = 11입니다.

10진수를 2진수로 바꿀 때는 2로 계속 나누고 나머지를 아래에서부터 읽습니다. 13 → 6 나머지 1 → 3 나머지 0 → 1 나머지 1 → 0 나머지 1, 아래부터 읽으면 `1101`입니다. 손으로 몇 번 해 보면 금방 익습니다. 2의 거듭제곱(1, 2, 4, 8, 16, 32, 64, 128, 256, 512, 1024)은 외워 두면 평생 씁니다.

2진수는 길어서 사람이 읽기 힘듭니다. 그래서 [[16진수]]를 씁니다. 16진수는 0~9 다음에 A(10), B(11), C(12), D(13), E(14), F(15)를 씁니다. 16진수 한 자리는 정확히 2진수 네 자리(4비트)와 같아서, 바이트 하나는 16진수 두 자리로 딱 떨어집니다. 이 페이지 첫 글자 `<`의 바이트 `3C`는 `0011 1100`이고, 10진수로는 60입니다.

| 2진수 | 16진수 | 10진수 |
| --- | --- | --- |
| `0000 0000` | `00` | 0 |
| `0000 1111` | `0F` | 15 |
| `1010 0101` | `A5` | 165 |
| `1111 1111` | `FF` | 255 |

16진수는 개발하면서 매일 봅니다.

- CSS 색 `#FF8800`은 빨강 `FF`(255), 초록 `88`(136), 파랑 `00`(0)입니다. 세 바이트가 그대로 적혀 있습니다. 이 글자의 색 `#141418`도 거의 검은 세 바이트입니다.
- [[MAC 주소]] `3c:22:fb:12:34:56`은 6바이트를 16진수로 적은 것입니다.
- [[IPv6]] 주소 `2001:db8::1`도 16진수입니다.
- 오류 메시지의 메모리 주소 `0x7ffeefbff5c8`, Git 커밋 해시 `6edb0f5`도 16진수입니다.

코드에서는 `0x`를 앞에 붙여 16진수, `0b`를 붙여 2진수를 씁니다. JS에서도 `0xff === 255`, `0b1010 === 10`이고, `(255).toString(16)`은 `"ff"`, `parseInt("ff", 16)`은 255입니다.

:::quiz hex-to-dec 이 페이지 맨 앞 바이트 중 `6D`(글자 `m`)는 10진수로 얼마일까요?
= 109

`6`은 6 × 16 = 96, `D`는 13이니 96 + 13 = **109**입니다. 2진수로는 `0110 1101`입니다. ASCII에서 109번이 소문자 `m`입니다.
:::

이제 바이트 하나를 읽을 수 있습니다. 그런데 바이트는 0~255뿐입니다. 이 페이지의 진행 막대가 "−3"이나 "0.25" 같은 수를 다뤄야 한다면 어떻게 적을까요?

## 정수: 부호 없는 수와 2의 보수

8비트로는 0부터 255까지 256개의 수를 셀 수 있습니다. 이렇게 0부터 세는 정수를 **부호 없는 정수**라고 합니다. 이미지의 색 채널, 바이트 값이 그렇습니다.

음수는 어떻게 할까요? 맨 앞 비트를 부호로 쓰는 방법이 떠오르지만, 그러면 +0과 −0이 따로 생기고 덧셈 회로도 복잡해집니다. 그래서 거의 모든 컴퓨터는 [[2의 보수]]를 씁니다. 어떤 수의 음수는 "모든 비트를 뒤집고 1을 더한 것"입니다. 5 = `0000 0101`을 뒤집으면 `1111 1010`, 1을 더하면 `1111 1011`이 −5입니다.

이렇게 하면 `5 + (-5)`를 그냥 2진 덧셈으로 계산해도 `0000 0101 + 1111 1011 = 1 0000 0000`이 되고, 8비트를 넘친 맨 앞 1은 버려져 0이 됩니다. 뺄셈을 덧셈 회로로 할 수 있으니 하드웨어가 단순해집니다. 8비트 부호 있는 정수의 범위는 −128부터 127까지입니다.

![8비트 값 256개를 계량기처럼 원으로 놓은 모습. 같은 비트가 부호 없는 정수로는 128~255, 2의 보수로는 −128~−1입니다. 127에서 한 칸 더 가면 −128로 넘어갑니다](bits-twos-complement.svg)

정해진 비트 수를 넘으면 [[오버플로]]가 일어납니다. 위 그림의 원에서 127 다음 칸이 −128인 것처럼, 계량기가 9999 다음에 0000으로 돌아가는 것과 같습니다. 2038년 문제가 유명한 예입니다. 1970년 1월 1일부터 흐른 초를 부호 있는 32비트 정수에 담던 시스템은 2038년 1월 19일에 이 값이 넘쳐 1901년으로 돌아갑니다. 요즘 운영체제는 64비트로 시간을 세서 이 문제를 피합니다.

JS에서도 오버플로를 직접 볼 수 있습니다.

```js 브라우저 콘솔
const a = new Int8Array([127]);
a[0] += 1;          // -128: 넘쳐서 한 바퀴 돕니다
new Uint8Array([300])[0];        // 44: 300 - 256
new Uint8ClampedArray([300])[0]; // 255: 넘치면 끝에 붙습니다 (캔버스 픽셀이 이 타입입니다)
```

:::quiz twos-minus-one 8비트 2의 보수에서 `1111 1111`은 어떤 수일까요?
- [x] −1
- [ ] −127
- [ ] 255
- [ ] −128

−1입니다. `0000 0001`(1)을 뒤집으면 `1111 1110`, 1을 더하면 `1111 1111`입니다. 같은 비트를 부호 없는 정수로 읽으면 255가 되고, −128은 `1000 0000`입니다. 비트는 같아도 어떤 약속으로 읽느냐에 따라 값이 달라집니다.
:::

## 실수: 부동소수점

진행 막대가 25%만큼 차 있다는 0.25, 읽는 데 걸리는 시간 같은 실수는 [[부동소수점]]으로 적습니다. 과학 표기법 6.02 × 10²³처럼, 수를 "유효 숫자"와 "몇 자리 옮길지"로 나눠 적는 방식입니다. 거의 모든 컴퓨터가 [[IEEE 754]]라는 표준을 따릅니다.

![64비트 배정밀도 실수의 구조. 부호 1비트, 지수 11비트, 가수 52비트입니다. 0.1은 가수에서 1001이 끝없이 반복되다 52비트에서 잘립니다](bits-float.svg)

문제는 2진법으로 끝나지 않는 소수가 있다는 것입니다. 10진법에서 1/3이 0.333…으로 끝나지 않듯, 2진법에서는 0.1이 `0.0001100110011…`으로 끝없이 반복됩니다. 52비트에서 잘라야 하니 0.1은 정확히 0.1이 아니라 아주 조금 다른 값으로 저장됩니다. 그 오차가 더해지면서 `0.1 + 0.2`가 `0.30000000000000004`가 됩니다. 이건 JS의 버그가 아니라 IEEE 754를 쓰는 모든 언어에서 똑같이 일어납니다. 0.25는 2진법으로 `0.01`이라 정확히 담깁니다.

JS의 `number`는 언제나 이 64비트 double입니다. 그래서 몇 가지 규칙이 따라 나옵니다.

- 정수를 정확히 담을 수 있는 한계는 가수 52비트 + 숨은 1비트 = 53비트입니다. `Number.MAX_SAFE_INTEGER`가 2⁵³ − 1 = 9007199254740991인 이유입니다. 이보다 큰 ID(트위터, 디스코드의 ID 등)는 문자열이나 `BigInt`로 다룹니다.
- 돈은 소수로 계산하지 않습니다. 원 단위 정수나 센트 단위 정수로 바꿔 계산하고 화면에 보일 때만 나눕니다.
- 소수 비교는 `===` 대신 `Math.abs(a - b) < Number.EPSILON`처럼 오차를 허용합니다.
- IEEE 754에는 특별한 값이 있습니다. `Infinity`, `-Infinity`, `NaN`(숫자가 아님), 그리고 `-0`입니다. `NaN === NaN`이 `false`인 것도 표준이 그렇게 정했기 때문입니다.

소수점 위치를 미리 정해 두고 정수로 다루는 방식도 있습니다. 이걸 [[고정 소수점]]이라고 합니다. 돈을 `12.34`달러가 아니라 `1234`센트라는 정수로 저장하는 것이 그렇습니다. 다룰 수 있는 범위는 좁지만 덧셈과 뺄셈에 오차가 없어서, 금액은 부동소수점 대신 가장 작은 단위의 정수로 다룹니다.

:::quiz float-exact 다음 중 JS의 `number`에 **정확히** 담기는 값은?
- [ ] 0.1
- [ ] 0.3
- [ ] 2⁵³ + 1
- [x] 0.75

0.75입니다. 0.75 = 1/2 + 1/4라 2진법으로 `0.11`에서 끝납니다. 0.1과 0.3은 2진법에서 끝없이 반복되어 근삿값으로 저장되고, 2⁵³ + 1은 53비트 정밀도를 넘어 2⁵³과 구분되지 않습니다.
:::

숫자는 이렇게 적습니다. 그런데 이 페이지의 대부분은 숫자가 아니라 한글입니다. 글자는 어떻게 바이트가 될까요?

## 글자: 문자 인코딩

글자도 숫자로 적습니다. "A는 65, B는 66"처럼 글자마다 번호를 붙이는 약속을 [[문자 인코딩]]이라고 합니다.

### ASCII에서 유니코드까지

1960년대에 만든 [[ASCII]]는 7비트로 128개 글자를 정했습니다. 영어 알파벳, 숫자, 기호, 그리고 줄바꿈 같은 제어 문자입니다. `A`는 65(`0x41`), `a`는 97(`0x61`), `0`은 48(`0x30`)입니다. 대문자와 소문자가 정확히 32(비트 하나) 차이 나도록 배치해서, 비트 하나만 뒤집으면 대소문자가 바뀝니다. 이 페이지 맨 앞의 `<!doctype html>`이 그림처럼 한 글자에 한 바이트였던 것도 ASCII 글자라서입니다.

128개로는 한글도 한자도 못 적습니다. 그래서 나라마다 따로 인코딩을 만들었습니다. 한국은 EUC-KR과 이를 넓힌 CP949(Windows 한국어판의 기본 인코딩)를 썼습니다. 같은 바이트가 인코딩마다 다른 글자를 뜻하니, 다른 인코딩으로 읽으면 "뷁똠" 같은 글자가 나옵니다. 이게 한글이 깨지는 현상입니다.

이 혼란을 끝내려고 [[유니코드]]가 나왔습니다. 유니코드는 세상의 모든 글자에 번호(코드 포인트)를 하나씩 붙인 표입니다. `A`는 U+0041, `가`는 U+AC00, `😀`는 U+1F600입니다. 유니코드는 "번호표"일 뿐이고, 이 번호를 바이트로 어떻게 적을지는 따로 정합니다. 그 방법이 UTF-8, UTF-16입니다.

### UTF-8과 UTF-16

![같은 글자 세 개가 번호(코드 포인트)를 거쳐 바이트가 되는 두 가지 방법. UTF-8은 1·3·4바이트, UTF-16은 2·2·4바이트를 씁니다](bits-utf8.svg)

[[UTF-8]]은 글자에 따라 1~4바이트를 씁니다. ASCII 글자는 1바이트로 예전과 똑같이 적히고, 한글 한 글자는 3바이트, 이모지는 4바이트입니다. 이 책 제목의 "컴퓨터"는 `EC BB B4 ED 93 A8 ED 84 B0`, 9바이트입니다. 영어 문서는 ASCII와 완전히 같아서 호환이 좋고, 웹 페이지의 98% 이상이 UTF-8입니다. 이 페이지 맨 위의 `<meta charset="utf-8">`이 바로 "이 바이트들을 UTF-8로 읽으라"는 약속입니다.

[[UTF-16]]은 2바이트 또는 4바이트를 씁니다. 자주 쓰는 글자(한글 포함)는 2바이트이고, 이모지처럼 번호가 큰 글자는 2바이트짜리 두 개(서로게이트 쌍)로 적습니다. JS 문자열과 Windows 내부, Java가 UTF-16을 씁니다. 그래서 이 페이지는 UTF-8로 도착했다가, 브라우저가 JS에 넘길 때는 UTF-16 문자열이 됩니다.

```js 브라우저 콘솔
"가".length;                          // 1: UTF-16 코드 유닛 1개
"😀".length;                          // 2: 서로게이트 쌍
[..."😀"].length;                     // 1: 코드 포인트 단위로 나누면 1
new TextEncoder().encode("가").length; // 3: UTF-8로는 3바이트
new TextEncoder().encode("😀").length; // 4
```

`length`가 이모지에서 2가 나오는 이유, `slice`가 이모지를 반으로 잘라 깨진 글자를 만드는 이유가 이것입니다. 글자 단위로 자르려면 `[...str]`을 쓰고, 👨‍👩‍👧처럼 여러 코드 포인트가 합쳐진 글자까지 정확히 다루려면 `Intl.Segmenter`를 씁니다.

:::quiz utf8-bytes "가😀"를 UTF-8로 보내면 모두 몇 바이트일까요?
= 7 | 7바이트

"가"는 3바이트, "😀"는 4바이트라 합쳐서 **7바이트**입니다. 같은 문자열의 JS `length`는 3입니다. JS는 UTF-16 코드 유닛을 세서 "가"는 1, "😀"는 서로게이트 쌍이라 2이기 때문입니다.
:::

### 한글 파일 이름이 자모로 쪼개지는 이유

유니코드에서 "한"은 완성형 글자 하나(U+D55C)로 적을 수도 있고, "ㅎ + ㅏ + ㄴ" 세 자모를 이어 적을 수도 있습니다. 앞을 NFC, 뒤를 NFD라고 합니다. 화면에서는 똑같이 보이지만 바이트는 다릅니다.

macOS는 파일 이름을 NFD로 저장하는 경우가 많고, Windows와 Linux는 대개 NFC를 씁니다. 그래서 Mac에서 만든 "보고서.pdf"를 Windows에 옮기거나 웹에 올리면 "ㅂㅗㄱㅗㅅㅓ.pdf"처럼 자모가 풀려 보입니다. 파일 업로드를 받는 웹 서비스라면 `name.normalize("NFC")`로 맞춰 저장하는 게 안전합니다.

## 줄바꿈도 바이트입니다

맨 앞 그림의 마지막 바이트 `0A`는 글자가 아니라 줄바꿈입니다. 텍스트 파일의 줄바꿈도 문자인데, 운영체제마다 다른 문자를 씁니다.

| | Windows | macOS, Linux |
| --- | --- | --- |
| 줄바꿈 | CR LF (`\r\n`, 바이트 `0D 0A`) | LF (`\n`, 바이트 `0A`) |
| 유래 | 타자기: 줄 처음으로(CR) + 한 줄 아래로(LF) | 유닉스가 LF 하나로 정함 |

Windows에서 저장한 셸 스크립트를 Linux 서버에서 실행하면 `/bin/bash^M: bad interpreter` 같은 오류가 납니다. 줄 끝에 남은 `\r`(`^M`)이 명령의 일부로 읽히기 때문입니다. Git의 `core.autocrlf` 설정과 저장소의 `.gitattributes`가 이 차이를 맞춰 주고, 에디터 오른쪽 아래의 "CRLF/LF" 표시가 지금 파일이 어느 쪽인지 알려 줍니다.

## 바이트의 순서: 엔디언

여기까지는 한 바이트짜리 값만 봤습니다. 이 페이지가 네트워크를 건너올 때 붙는 [[헤더]]에는 포트 번호 443처럼 2바이트, 4바이트짜리 숫자가 들어갑니다. 2바이트 이상인 수를 적을 때는 큰 자리 바이트를 앞에 둘지 뒤에 둘지 정해야 합니다. 이 순서를 [[엔디언]]이라고 합니다.

![`0x12345678`을 메모리 네 칸에 적는 두 가지 순서. 빅 엔디언은 큰 자리(12)부터, 리틀 엔디언은 작은 자리(78)부터 놓습니다](bits-endian.svg)

요즘 PC와 휴대폰의 CPU(x86, ARM)는 리틀 엔디언입니다. 반대로 인터넷 [[프로토콜]]은 빅 엔디언으로 적기로 약속했습니다. 이걸 [[네트워크 바이트 순서]]라고 부릅니다. 그래서 프로그램은 네트워크로 숫자를 보내기 전에 순서를 바꿉니다. JS의 `DataView`는 기본이 빅 엔디언이고 `getUint32(0, true)`처럼 마지막 인자로 리틀 엔디언을 고릅니다. 바이너리 파일이나 웹소켓 바이너리 메시지를 읽을 때 이 인자를 틀리면 엉뚱한 숫자가 나옵니다.

:::quiz endian-port 포트 번호 443(`0x01BB`)을 네트워크 바이트 순서로 보내면 선 위에 어떤 순서로 실릴까요?
- [ ] `BB 01`
- [x] `01 BB`
- [ ] `10 BB`
- [ ] `BB 10`

`01 BB`입니다. 네트워크 바이트 순서는 빅 엔디언이라 큰 자리 바이트 `01`이 먼저 갑니다. 리틀 엔디언 CPU의 메모리에는 `BB 01`로 놓여 있으니, 보내기 전에 순서를 뒤집습니다.
:::

## 그림, 소리, 파일도 결국 바이트

이 페이지가 화면에 그려지면 글자는 픽셀이 됩니다. 픽셀은 빨강·초록·파랑 세 채널에 각 8비트(0~255)를 써서 약 1677만 가지 색을 냅니다. 투명도(알파)까지 4바이트입니다. 그래서 1920×1080 화면 한 장을 압축 없이 펼치면 1920 × 1080 × 4 ≈ 8.3MB입니다. 200KB짜리 JPEG라도 브라우저가 화면에 그리려면 이만큼 메모리를 씁니다. 큰 이미지 여러 장이 휴대폰 브라우저를 느리게 만드는 이유입니다.

소리는 공기의 떨림을 1초에 44,100번 재서 각각을 16비트 정수로 적습니다(CD 음질). 1초에 44,100 × 2바이트 × 2채널 ≈ 176KB입니다. MP3, AAC는 사람이 잘 못 듣는 부분을 버려 이를 10분의 1 이하로 줄입니다.

결국 [[파일]]은 바이트를 한 줄로 늘어놓은 것입니다. 파일 안에는 "나는 이미지다"라는 표시가 따로 없고, 맨 앞 몇 바이트를 약속된 값으로 시작하는 관례만 있습니다. 이걸 [[매직 넘버]]라고 합니다. PNG는 `89 50 4E 47`(뒤 세 바이트가 ASCII로 "PNG"), PDF는 `25 50 44 46`("%PDF"), ZIP은 `50 4B`("PK")로 시작합니다. HTML에는 정해진 매직 넘버가 없지만, 이 페이지처럼 `<!doctype html>`로 시작하는 것이 관례입니다.

| | Windows | macOS | Linux |
| --- | --- | --- | --- |
| 파일 종류를 무엇으로 아는가 | 주로 확장자 (`.exe`, `.txt`) | 확장자 + 내부 형식 정보(UTI) | 확장자는 관례일 뿐. 실행 여부는 권한, 내용은 `file` 명령이 매직 넘버로 판별 |
| 확장자 기본 표시 | 숨김 (그래서 `사진.jpg.exe` 같은 속임수가 통함) | 숨김 | 그대로 보임 |

웹에서는 확장자 대신 [[MIME 타입]](`image/png`, `text/html`)으로 종류를 알려 줍니다. 서버가 이 페이지를 보낼 때도 "이건 `text/html`이고 UTF-8이다"라는 꼬리표를 붙입니다. 이걸 틀리게 보내면 브라우저가 CSS 파일을 적용하지 않거나 HTML을 내려받기로 처리합니다. 이 이야기는 14장에서 다시 나옵니다.

## 다시 장면으로: "학습 완료"를 누르면

이 장 맨 아래의 "학습 완료"를 누르면 무엇이 저장될까요? 이 사이트의 JS는 브라우저 저장소(`localStorage`)에 `mlnl-cs:progress`라는 이름으로 이런 글자를 씁니다.

```js
{"bits:s:intro":1}
```

이 장에서 본 것이 모두 들어 있습니다. 체크했다/안 했다는 비트 하나면 되지만, 실제로는 JSON이라는 글자 약속으로 적힌 18글자이고, JS 안에서는 UTF-16 문자열이며, 디스크에 내려갈 때는 바이트가 됩니다. 숫자 `1`조차 여기서는 정수가 아니라 글자 `1`(`0x31`)입니다.

그럼 이 바이트들은 컴퓨터 안 어디에 있을까요? 지금 이 페이지의 4만 바이트는 메모리 어딘가에 있고, 체크 기록은 SSD 어딘가에 있고, CPU가 그 사이를 오가며 계산합니다. 2장은 이 바이트들이 사는 곳, 컴퓨터의 부품들로 들어갑니다.

## 프론트엔드와 이어지는 곳

- `ArrayBuffer`는 바이트 덩어리, `Uint8Array` 같은 `TypedArray`와 `DataView`는 그 바이트를 어떤 단위와 엔디언으로 읽을지 정하는 창입니다. 파일 업로드, 이미지 처리, 웹소켓 바이너리 메시지, WebAssembly가 모두 이걸 씁니다.
- 비트 연산자(`&`, `|`, `^`, `~`, `<<`, `>>`, `>>>`)는 피연산자를 32비트 정수로 바꿔 계산합니다. `x | 0`이 소수점을 버리고, 2³¹보다 큰 수에서 엉뚱한 값이 나오는 이유입니다.
- React의 내부 플래그처럼 여러 참/거짓을 정수 하나에 담을 때 [[비트 마스크]]를 씁니다. `flags & HAS_EFFECT`로 확인하고 `flags | HAS_EFFECT`로 켭니다.
- `btoa`, `atob`의 [[Base64]]는 바이트를 글자 64종으로만 적어서, 글자만 오갈 수 있는 곳(URL, JSON, 이메일)에 바이너리를 싣는 방법입니다. 3바이트가 4글자가 되니 크기가 약 33% 늘어납니다.

## 용어 정리

:::terms
- 비트 (bit) — 0 또는 1 하나를 담는 정보의 가장 작은 단위입니다. n비트로 2ⁿ가지를 구분합니다.
- 바이트 (byte) — 비트 8개 묶음. 메모리와 파일은 바이트 단위로 주소를 매기고 읽고 씁니다. 0~255 또는 16진수 `00`~`FF`.
- 워드 (word) — CPU가 한 번에 가장 자연스럽게 다루는 크기. 요즘 컴퓨터는 64비트(8바이트)입니다.
- 2진수 (binary) — 자리마다 2배씩 커지는 수 체계. 0과 1만 씁니다.
- 16진수 (hexadecimal) — 0~9와 A~F를 쓰는 수 체계. 한 자리가 정확히 4비트라 바이트를 두 자리로 적기 좋습니다. 코드에서는 `0x`를 붙입니다.
- KiB와 KB — KiB는 1024바이트, KB는 1000바이트. Windows는 1024 단위를 GB라고 표시하고 macOS는 1000 단위를 씁니다.
- 2의 보수 (two's complement) — 음수를 "모든 비트를 뒤집고 1을 더한 값"으로 적는 방식. 뺄셈을 덧셈 회로로 할 수 있어 거의 모든 CPU가 씁니다.
- 오버플로 (overflow) — 계산 결과가 정해진 비트 수를 넘쳐 엉뚱한 값으로 돌아가는 현상. 8비트 부호 있는 정수에서 127 + 1 = −128.
- 부동소수점 (floating point) — 실수를 부호, 지수, 가수로 나눠 적는 방식. 넓은 범위를 다루는 대신 대부분의 소수를 정확히 담지 못합니다.
- IEEE 754 — 부동소수점 표준. JS의 `number`는 이 표준의 64비트 배정밀도입니다.
- 문자 인코딩 (character encoding) — 글자와 바이트를 서로 바꾸는 약속. 보낸 쪽과 읽는 쪽의 인코딩이 다르면 글자가 깨집니다.
- ASCII — 영어 알파벳, 숫자, 기호, 제어 문자 128개를 7비트로 정한 인코딩. UTF-8의 첫 128글자와 같습니다.
- 유니코드 (Unicode) — 세상의 모든 글자에 번호(코드 포인트, `U+AC00` 같은)를 붙인 표준. 번호를 바이트로 적는 방법은 UTF-8, UTF-16이 따로 정합니다.
- UTF-8 — 유니코드를 1~4바이트로 적는 방식. ASCII와 호환되고 웹의 표준입니다. 한글 한 글자는 3바이트.
- UTF-16 — 유니코드를 2바이트 또는 4바이트(서로게이트 쌍)로 적는 방식. JS 문자열, Windows 내부, Java가 씁니다.
- NFC와 NFD — 한글을 완성형 한 글자로 적는 방식(NFC)과 자모를 나눠 적는 방식(NFD). 보기에는 같아도 바이트가 달라서 파일 이름이 깨져 보이는 원인이 됩니다.
- CRLF와 LF — 줄바꿈 문자. Windows는 `\r\n`, macOS와 Linux는 `\n`을 씁니다.
- 엔디언 (endianness) — 여러 바이트로 된 수를 메모리에 놓는 순서. 큰 자리부터면 빅 엔디언, 작은 자리부터면 리틀 엔디언입니다.
- 네트워크 바이트 순서 (network byte order) — 인터넷 프로토콜이 헤더의 숫자를 적기로 정한 순서. 빅 엔디언입니다.
- 파일 (file) — 이름이 붙은 바이트의 나열. 그 바이트를 무엇으로 읽을지는 형식(이미지, 텍스트 등)의 약속에 달려 있습니다.
- 매직 넘버 (magic number) — 파일 형식을 알리려고 파일 맨 앞에 두는 약속된 바이트. PNG는 `89 50 4E 47`로 시작합니다.
- 비트 마스크 (bit mask) — 여러 참/거짓 값을 정수 하나의 비트들에 담고, `&`, `|`, `^`로 꺼내고 켜고 뒤집는 기법.
- Base64 — 바이트를 영문자, 숫자, `+`, `/` 64종 글자로만 적는 방법. 글자만 오갈 수 있는 곳에 바이너리를 싣습니다. 크기가 약 4/3배가 됩니다.
- 패리티 비트 (parity bit) — 데이터의 1의 개수가 짝수(또는 홀수)가 되도록 덧붙이는 비트 하나. 한 비트가 뒤집혔는지 알아챕니다.
- 해밍 코드 (Hamming code) — 검사 비트 여러 개를 겹치게 두어, 어느 비트가 뒤집혔는지 찾아 바로잡는 오류 정정 부호입니다.
- 고정 소수점 (fixed-point) — 소수점 위치를 미리 정해 두고 정수로 저장하는 방식. 금액을 센트 단위 정수로 다루는 것이 예입니다.
:::

## 직접 해보기

:::practice hexdump 파일을 바이트로 열어 보기
이 장 맨 앞 그림을 직접 만들어 봅니다. 이 페이지를 저장해 16진수로 열고, 텍스트 파일과 PNG 이미지도 열어 봅니다. 텍스트 파일에서는 글자가 ASCII 코드로, PNG에서는 맨 앞의 `89 50 4E 47`이 보여야 합니다.

```sh macOS · Linux
curl -s https://cs.mlnl.site/bits/ | xxd | head -3   # 이 페이지의 맨 앞
echo "Hi 가" > hi.txt
xxd hi.txt
# 00000000: 4869 20ea b080 0a    Hi ....
# H=48 i=69 공백=20, 가=ea b0 80 (UTF-8 3바이트), 줄바꿈=0a

xxd -l 16 아무이미지.png
file 아무이미지.png
```

```powershell Windows (PowerShell)
"Hi 가" | Out-File -Encoding utf8 hi.txt
Format-Hex hi.txt
# 맨 앞에 EF BB BF가 붙어 있을 수 있습니다. UTF-8 BOM이라는 표시입니다
Format-Hex 아무이미지.png | Select-Object -First 1
```
:::

:::practice console 콘솔에서 숫자와 글자의 한계 확인하기
이 페이지에서 개발자 도구 콘솔을 열고 아래를 하나씩 쳐 봅니다. 결과가 왜 그렇게 나오는지, 이 장의 어느 절로 설명되는지 적어 봅니다. 마지막 줄은 파트 하나를 "학습 완료"로 체크한 뒤에 쳐 봅니다.

```js 브라우저 콘솔

```

:::practice crlf 줄바꿈 차이 눈으로 보기
VS Code 오른쪽 아래의 `LF`/`CRLF` 표시를 눌러 같은 파일을 두 방식으로 저장하고 각각 바이트로 열어 봅니다. 줄 끝이 `0a`인지 `0d 0a`인지 확인합니다. 내 저장소에 `.gitattributes`가 있는지, `git config core.autocrlf` 값은 무엇인지도 확인합니다.
:::

:::practice disk 내 디스크 용량을 두 단위로 계산하기
내 컴퓨터 디스크의 전체 용량을 운영체제가 보여 주는 숫자로 확인하고, 바이트 수로 바꾼 뒤 1000³과 1024³으로 각각 나눠 봅니다.

```sh macOS
diskutil info / | grep -E "Container Total Space|Disk Size"
df -H /   # 1000 단위
df -h /   # 1024 단위
```

```powershell Windows (PowerShell)
Get-Volume -DriveLetter C | Select-Object Size, SizeRemaining
# Size는 바이트입니다. 1e9와 1GB(=1024³)로 각각 나눠 보세요
(Get-Volume -DriveLetter C).Size / 1e9
(Get-Volume -DriveLetter C).Size / 1GB
```
:::

## 장 전체 문제

:::quiz progress-bytes 이 사이트가 저장하는 `{"bits:s:intro":1}`에서 마지막 숫자 `1`은 디스크에 어떤 바이트로 적힐까요?
- [ ] `01` (정수 1)
- [ ] `00 00 00 01` (32비트 정수 1)
- [ ] `3F F0 00 00 00 00 00 00` (실수 1.0)
- [x] `31` (글자 "1")

글자 "1"의 바이트 `31`입니다. JSON은 숫자도 글자로 적는 약속이라, 값이 숫자여도 저장될 때는 ASCII 글자 `1`(48 + 1 = 49 = `0x31`)이 됩니다. 같은 "1"이라도 어떤 약속으로 적느냐에 따라 바이트가 완전히 다릅니다.
:::

:::quiz mojibake 한글 CSV 파일을 엑셀에서 열었더니 "뷁똠" 같은 글자가 나옵니다. 가장 가능성이 높은 원인은?
- [ ] 파일이 중간에 잘려서 마지막 바이트가 사라졌다
- [x] UTF-8로 저장된 파일을 다른 인코딩(CP949)으로 읽었다
- [ ] 줄바꿈이 CRLF가 아니라 LF여서
- [ ] 파일 이름이 NFD로 저장돼서

인코딩이 어긋났기 때문입니다. 바이트는 멀쩡한데 읽는 쪽이 다른 약속으로 해석해서 엉뚱한 글자가 나옵니다. 줄바꿈이나 파일 이름의 NFD는 내용 글자를 바꾸지 않습니다.
:::

## 스스로 점검

:::qa 16진수 `0xC0`는 10진수로 얼마이고, 2진수로는 어떻게 적나요?
`C`는 12, `0`은 0이므로 12 × 16 + 0 = 192입니다. 16진수 한 자리가 4비트이니 `C` = `1100`, `0` = `0000`, 합쳐서 `1100 0000`입니다. 192는 사설 IP `192.168.x.x`의 첫 바이트이기도 합니다.
:::

:::qa 8비트 2의 보수로 −1은 어떻게 적히나요? 왜 그렇게 적으면 편한가요?
1 = `0000 0001`을 뒤집으면 `1111 1110`, 1을 더하면 `1111 1111`입니다. 여기에 1을 더하면 `1 0000 0000`이 되고 넘친 비트를 버리면 0이 되니, 덧셈 회로 하나로 음수 계산까지 됩니다.
:::

:::qa `0.1 + 0.2 !== 0.3`인 이유를 한 문장으로 설명해 보세요. 돈 계산은 어떻게 해야 하나요?
0.1과 0.2는 2진법에서 끝나지 않는 소수라 64비트 부동소수점에 근삿값으로 저장되고, 그 오차가 더해져 0.3의 근삿값과 달라집니다. 돈은 가장 작은 단위(원, 센트)의 정수로 계산합니다.
:::

:::qa "가😀"를 UTF-8로 보내면 몇 바이트이고, JS의 `length`는 얼마인가요?
UTF-8로는 3 + 4 = 7바이트입니다. JS 문자열은 UTF-16이라 "가"는 1, "😀"는 서로게이트 쌍 2, 합쳐서 `length`는 3입니다.
:::

:::qa 같은 1TB 외장 디스크가 Windows에서는 931GB로, macOS에서는 1TB로 보입니다. 왜인가요?
제조사와 macOS는 1TB = 10¹² 바이트로 세고, Windows는 1024⁴로 나눈 값(TiB)을 "TB"라고 표시합니다. 10¹² / 1024³ ≈ 931이라 GB로 보면 931GB입니다. 용량이 사라진 것이 아니라 단위가 다릅니다.
:::

:::qa 서버에 올린 셸 스크립트가 `bad interpreter: /bin/bash^M` 오류를 냅니다. 원인과 해결은?
Windows에서 CRLF로 저장되어 첫 줄 끝에 `\r`이 붙었고, 셸이 `/bin/bash\r`라는 프로그램을 찾다가 실패한 것입니다. 에디터에서 LF로 바꿔 저장하거나 `sed -i 's/\r$//' 파일`로 지우고, `.gitattributes`에 `*.sh text eol=lf`를 적어 다시 생기지 않게 합니다.
:::
