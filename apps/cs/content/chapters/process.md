5장은 이상한 장면으로 끝났습니다. 브라우저 아이콘은 한 번 눌렀는데 작업 관리자에는 Chrome이 수십 개 떠 있고, CPU 코어는 8개뿐인데 실행 중인 프로그램은 수백 개입니다. 지금 이 페이지를 보여 주고 있는 브라우저를 펼쳐 보면 이렇게 생겼습니다.

![이 페이지를 띄운 브라우저의 속. 실행 파일은 하나지만 프로세스가 여럿이고, 이 페이지를 맡은 렌더러 안에는 다시 스레드가 여럿입니다. 이 모든 것을 커널이 코어 몇 개에 번갈아 올립니다](process-browser.svg)

이 장은 이 그림을 위에서 아래로 내려갑니다. 왜 하나의 프로그램이 여러 프로세스로 도는지, 운영체제가 적은 코어를 어떻게 잘게 쪼개 모두가 동시에 도는 것처럼 보이게 하는지, 한 프로세스 안의 여러 스레드가 같은 데이터를 건드리면 무슨 일이 생기는지를 봅니다. 마지막에는 이 페이지의 "다 읽었어요" 클릭이 렌더러의 메인 스레드에서 어떻게 처리되는지, 이벤트 루프로 이어집니다.

## 프로그램과 프로세스

디스크에 있는 `node` 실행 파일은 **프로그램**입니다. 그걸 실행해서 메모리에 올라와 돌고 있는 것이 [[프로세스]]입니다. 터미널 세 개에서 `node`를 실행하면 프로그램은 하나, 프로세스는 셋입니다. 셋은 각자 자기 메모리, 자기 변수, 자기 열린 파일을 가지며 서로의 메모리를 볼 수 없습니다.

운영체제는 프로세스마다 번호, [[PID]]를 붙입니다. 프로세스를 띄운 프로세스는 부모가 되고, 부모의 PID를 PPID라고 합니다. 3장에서 본 첫 프로세스(launchd, systemd)에서 시작해 모든 프로세스가 부모-자식 나무로 이어져 있습니다.

| | Windows | macOS | Linux |
| --- | --- | --- | --- |
| 그림으로 보기 | 작업 관리자 (Ctrl+Shift+Esc), Process Explorer | 활성 상태 보기 | 시스템 모니터, `htop` |
| 명령으로 보기 | `Get-Process`, `tasklist` | `ps aux`, `top` | `ps aux`, `top`, `htop` |
| 나무 모양으로 | Process Explorer | `pstree` (brew) | `pstree`, `ps -ef --forest` |

## 브라우저 하나에 프로세스가 여럿인 이유

Chrome을 띄우면 작업 관리자에 Chrome 프로세스가 수십 개 보입니다. 역할별로 나뉘어 있습니다.

| 프로세스 | 하는 일 |
| --- | --- |
| 브라우저 프로세스 | 주소창, 탭, 북마크 같은 바깥 화면. 다른 프로세스들을 관리 |
| 렌더러 프로세스 | 웹 페이지 하나(정확히는 사이트 하나)의 HTML, CSS, JS를 처리. 샌드박스 안에서 돎 |
| GPU 프로세스 | 모든 탭의 화면 그리기를 GPU에 맡김 |
| 네트워크 서비스 | 모든 네트워크 요청 처리 |
| 확장 프로그램, 유틸리티 | 확장마다, 오디오 등 |

사이트마다 렌더러 프로세스를 따로 두는 것을 [[사이트 격리]]라고 합니다. 2018년 CPU의 설계 결함(Spectre)으로 같은 프로세스 안의 다른 사이트 메모리를 몰래 읽을 수 있다는 게 알려진 뒤 강화되었습니다. 운영체제의 프로세스 벽을 보안 경계로 쓰는 것입니다. 탭 하나가 "앗, 이런!"으로 죽어도 브라우저가 멀쩡한 이유도 같습니다. Chrome에서 Shift+Esc를 누르면 Chrome 자체의 작업 관리자로 이 프로세스들을 볼 수 있습니다.

같은 브라우저 실행 파일에서 나온 프로세스들이지만, 운영체제 눈에는 서로 남입니다. 그럼 운영체제는 이 프로세스 하나하나를 어떻게 구분해 기억할까요?

## 운영체제가 프로세스마다 기억하는 것

커널은 프로세스마다 기록 카드를 하나씩 둡니다. 이걸 [[PCB]](프로세스 제어 블록)라고 합니다. Linux에서는 `task_struct`, Windows에서는 `EPROCESS`라는 구조체입니다. 카드에는 이런 것들이 적혀 있습니다.

- PID, 부모 PID, 어느 사용자의 프로세스인지
- 지금 상태(실행 중, 대기 중 등)
- 멈췄을 때의 레지스터 값과 프로그램 카운터 (다시 이어서 실행하려면 필요)
- 메모리 지도: 이 프로세스의 주소 공간이 실제 RAM 어디에 있는지 (7장)
- 열린 파일과 소켓 목록 (8장)
- 우선순위, CPU를 얼마나 썼는지

프로세스를 "실행 중인 프로그램"이라고 하지만, 운영체제 입장에서 프로세스는 이 카드와 그 카드가 가리키는 자원 묶음입니다.

## 프로세스의 상태

프로세스는 대부분의 시간을 CPU를 쓰지 않고 기다리면서 보냅니다. 키 입력을, 디스크를, 네트워크 응답을 기다립니다.

![프로세스의 상태와 옮겨 가는 길. 실행 중일 수 있는 것은 코어 수만큼뿐이고, 대부분은 대기 상태에서 무언가를 기다립니다](process-states.svg)

- **준비(ready)**: 당장이라도 실행할 수 있는데 코어가 비기를 기다립니다.
- **실행(running)**: 지금 코어 위에서 돌고 있습니다. 동시에 이 상태인 프로세스(정확히는 스레드)는 코어 수를 넘을 수 없습니다.
- **대기(waiting, blocked)**: 입출력 같은 일이 끝나기를 기다립니다. 기다리는 동안은 CPU를 쓰지 않습니다.

`top`이나 `ps`의 상태 칸에서 `R`은 실행 또는 준비, `S`는 잠든(대기) 상태입니다. 대부분이 `S`입니다. 컴퓨터에 프로세스가 수백 개 있어도 느려지지 않는 이유는, 그중 대부분이 잠들어 있기 때문입니다.

## 코어보다 많은 프로세스: 컨텍스트 스위칭

코어 하나는 한 번에 하나만 실행합니다. 운영체제는 코어를 수 밀리초씩 잘라 프로세스들에게 돌아가며 줍니다. 이 한 조각을 [[타임 슬라이스]]라고 합니다. 너무 빨리 바뀌어서 사람 눈에는 동시에 도는 것처럼 보입니다.

실행 중인 프로세스를 멈추고 다른 프로세스를 돌리는 것을 [[컨텍스트 스위칭]]이라고 합니다.

1. 타이머 인터럽트나 시스템 콜로 CPU가 커널에 들어옵니다.
2. 커널이 지금 프로세스의 레지스터와 프로그램 카운터를 그 PCB에 저장합니다.
3. 스케줄러가 다음 프로세스를 고릅니다.
4. 그 프로세스의 PCB에서 레지스터를 되살리고, 메모리 지도를 그 프로세스 것으로 바꿉니다.
5. 사용자 모드로 돌아가면, 그 프로세스는 멈췄던 바로 그 명령어부터 이어서 실행합니다.

![코어 하나가 이 페이지의 렌더러와 메신저 앱을 번갈아 돌리는 모습. 타이머 인터럽트로 커널이 끼어들어 지금 값을 PCB에 저장하고, 다음 프로세스의 값을 되살립니다](process-context-switch.svg)

스위칭 자체는 몇 마이크로초면 끝나지만 숨은 비용이 있습니다. 새 프로세스의 데이터는 CPU 캐시에 없으니 한동안 캐시 미스가 이어집니다(2장의 지역성). 그래서 스위칭이 너무 잦으면 실제 일보다 바꾸는 데 시간을 더 씁니다.

:::quiz switch-save 컨텍스트 스위칭 때 커널이 PCB에 저장해 두지 **않아도** 되는 것은?
- [ ] 프로그램 카운터
- [ ] 레지스터 값
- [x] 그 프로세스가 쓰던 CPU 캐시의 내용
- [ ] 어느 메모리 지도를 쓰는지

CPU 캐시의 내용입니다. 캐시는 RAM의 복사본일 뿐이라 저장할 필요가 없고, 다음에 그 프로세스가 돌 때 다시 채워집니다. 그 다시 채우는 시간이 스위칭의 숨은 비용입니다. 프로그램 카운터와 레지스터는 저장하지 않으면 멈췄던 곳부터 이어 갈 수 없습니다.
:::

그런데 준비 상태인 프로세스가 여럿이면, 다음 조각은 누구에게 줘야 할까요?

## 누구에게 CPU를 줄까: 스케줄링

[[스케줄러]]는 준비 상태의 프로세스 중 누구에게 코어를 줄지 정하는 커널의 부분입니다. 목표가 서로 부딪칩니다. 마우스와 키보드에 바로 반응해야 하고(응답성), 전체 일을 많이 끝내야 하고(처리량), 누구도 너무 오래 굶기면 안 됩니다(공정성).

교과서에 나오는 기본 방법들입니다.

| 방법 | 규칙 | 장단점 |
| --- | --- | --- |
| FCFS | 먼저 온 순서대로 끝날 때까지 | 단순하지만 긴 작업 뒤의 짧은 작업이 한참 기다림 |
| SJF | 짧은 작업부터 | 평균 대기 시간이 가장 짧지만 작업 길이를 미리 알기 어렵고 긴 작업이 굶음 |
| [[라운드 로빈]] | 타임 슬라이스씩 돌아가며 | 공평하고 응답이 좋음. 슬라이스 크기가 중요 |
| 우선순위 | 우선순위 높은 것부터 | 중요한 일을 먼저. 낮은 것이 굶지 않게 나이 들면 올려 줌 |
| 다단계 피드백 큐 | 여러 우선순위 줄. CPU를 오래 쓰면 아래 줄로 | 대화형 작업은 위에, 계산 작업은 아래로 저절로 나뉨 |

실제 운영체제는 이것들을 섞은 자기만의 스케줄러를 씁니다.

| | Windows | macOS | Linux |
| --- | --- | --- | --- |
| 방식 | 우선순위 기반 선점형. 앞에 띄운 창의 프로세스와 입력을 받은 스레드의 우선순위를 잠깐 올려 줌 | 우선순위 + QoS 등급 (사용자 상호작용, 백그라운드 등). 등급에 따라 성능 코어와 효율 코어를 고름 | 오래 쓴 CFS를 2023년(6.6)부터 EEVDF로 교체. 각자 받아야 할 몫에 비해 덜 쓴 쪽을 먼저 |
| 우선순위 바꾸기 | 작업 관리자 → 세부 정보 → 우선 순위 설정 | `nice`, `renice`, `taskpolicy` | `nice`, `renice`, `chrt` |

현대 운영체제는 모두 [[선점형 스케줄링]]을 씁니다. 프로세스가 스스로 양보하지 않아도 타이머 인터럽트로 강제로 빼앗을 수 있다는 뜻입니다. 옛 Windows 3.1과 Mac OS 9는 프로그램이 스스로 양보해야 했고(협력형), 한 프로그램이 멈추면 컴퓨터 전체가 멈췄습니다.

표의 SJF와 우선순위 방식에는 같은 약점이 있습니다. 짧거나 급한 일이 계속 들어오면 길거나 덜 급한 일은 끝없이 밀립니다. 이걸 [[기아]](starvation)라고 하고, 기다린 시간만큼 우선순위를 조금씩 올려 주는 [[에이징]](aging)으로 막습니다.

교과서는 스케줄러를 셋으로 나누기도 합니다. 어떤 작업을 메모리에 올려 실행 후보로 받을지 정하는 장기 스케줄러, 메모리가 모자랄 때 일부 프로세스를 통째로 디스크로 내려 보내는 중기 스케줄러, 준비 상태 중 누구에게 지금 코어를 줄지 정하는 단기 스케줄러입니다. 요즘 PC와 서버의 운영체제에서 실제로 늘 도는 것은 단기 스케줄러이고, 이 절의 스케줄러가 그것입니다.

:::quiz preempt 다른 탭의 페이지가 무한 루프에 빠졌는데도 이 페이지는 스크롤되고 체크박스도 눌립니다. 가장 큰 이유 두 가지를 묶은 것은?
- [x] 탭마다 렌더러 프로세스가 다르고, 커널이 타이머 인터럽트로 CPU를 빼앗아 다른 프로세스에 줘서
- [ ] 무한 루프는 CPU를 쓰지 않는 대기 상태라서
- [ ] 브라우저가 무한 루프를 감지해 즉시 그 코드를 지워서
- [ ] 이 페이지의 JS가 GPU에서 따로 돌아서

프로세스가 나뉘어 있고 스케줄링이 선점형이기 때문입니다. 무한 루프를 도는 렌더러는 자기 코어 시간을 다 쓰지만, 타임 슬라이스가 끝나면 커널이 빼앗아 이 페이지의 렌더러에게도 차례를 줍니다. 같은 렌더러 안의 메인 스레드였다면 이야기가 다릅니다(이 장 끝의 이벤트 루프).

## 프로세스 만들기: fork와 exec, CreateProcess

새 프로세스를 만드는 방법은 유닉스 계열과 Windows가 크게 다릅니다.

**유닉스 계열(macOS, Linux)** 은 두 단계입니다.

1. [[fork]]: 지금 프로세스를 통째로 복제합니다. 메모리, 열린 파일, 환경 변수까지 똑같은 자식이 생깁니다. `fork`는 한 번 불렀는데 두 번 돌아옵니다. 부모에게는 자식의 PID가, 자식에게는 0이 돌아오고, 그걸로 서로 다른 길을 갑니다.
2. [[exec]]: 자식이 자기 메모리를 버리고 새 프로그램의 실행 파일로 갈아 끼웁니다. PID는 그대로입니다.

통째로 복제하면 느릴 것 같지만, 실제로는 메모리를 바로 복사하지 않고 둘이 같은 메모리를 보다가 누군가 쓰려고 할 때만 그 부분을 복사합니다. 이게 7장의 [[copy-on-write]]입니다.

셸이 `ls`를 실행하는 과정이 바로 이것입니다. 셸이 `fork`로 자기를 복제하고, 자식이 `exec("ls")`로 `ls`가 되고, 셸(부모)은 자식이 끝나기를 기다렸다가 다음 명령을 받습니다. 둘로 나뉘어 있어서, 자식이 `exec` 전에 출력을 파일로 돌리거나(`>`) 환경 변수를 바꾸는 일을 쉽게 할 수 있습니다.

**Windows** 는 `CreateProcess` 한 번에 "이 실행 파일로 새 프로세스를 만들어라"를 합니다. 복제 단계가 없습니다. 그래서 Windows에서는 프로세스를 만드는 비용이 상대적으로 크고, 프로세스를 많이 띄우는 유닉스식 프로그램(예전 Git, 셸 스크립트)이 Windows에서 느리게 느껴지곤 합니다.

Node의 `child_process.spawn("ls")`는 운영체제에 맞춰 이 둘 중 하나를 부릅니다. 브라우저가 새 탭의 렌더러를 띄울 때도 결국 이 시스템 콜들을 부릅니다. Linux의 Chrome은 미리 띄워 둔 작은 프로세스를 `fork`해서 렌더러를 빨리 만듭니다.

## 곁가지: 프로세스 끝내기, 종료 코드, 좀비, 고아

프로세스는 끝날 때 숫자 하나를 남깁니다. [[종료 코드]]입니다. 0은 성공, 0이 아니면 실패라는 약속이 있습니다. CI가 테스트 실패를 아는 방법이 이것입니다. `vitest`가 실패하면 1로 끝나고, CI는 그걸 보고 빨간불을 켭니다.

| | 직전 명령의 종료 코드 보기 |
| --- | --- |
| macOS · Linux (bash, zsh) | `echo $?` |
| Windows PowerShell | `$LASTEXITCODE` |
| Windows cmd | `echo %ERRORLEVEL%` |
| Node에서 정하기 | `process.exit(1)` 또는 `process.exitCode = 1` |

자식이 끝나도 부모가 그 종료 코드를 읽어 가기(`wait`) 전까지 커널은 자식의 PCB를 지우지 못합니다. 이렇게 끝났지만 거둬지지 않은 프로세스를 [[좀비 프로세스]]라고 합니다. 하나하나는 작지만 쌓이면 PID가 바닥납니다.

부모가 먼저 끝나면 자식은 [[고아 프로세스]]가 됩니다. 유닉스 계열에서는 PID 1이 고아를 입양해 대신 거둬 줍니다. Docker 컨테이너 안에서는 내 앱이 PID 1이 되는데, 보통의 앱은 이 일을 하도록 만들어지지 않았습니다. 그래서 자식 프로세스를 많이 띄우는 앱은 `docker run --init`이나 `tini`로 작은 PID 1을 따로 둡니다.

## 시그널: 프로세스에 보내는 짧은 알림

탭을 닫으면 브라우저 프로세스가 그 렌더러를 끝냅니다. 이처럼 프로세스에게 "이제 그만"이라고 알리는 방법이 있습니다. 이 페이지를 보낸 서버를 새 버전으로 바꿀 때도 같은 방법을 씁니다.

[[시그널]]은 커널이나 다른 프로세스가 프로세스에 보내는 번호 하나짜리 알림입니다. 프로세스는 시그널마다 핸들러를 달아 원하는 일을 하거나, 기본 동작(대개 종료)을 따릅니다.

| 시그널 | 언제 오나 | 기본 동작 | 막을 수 있나 |
| --- | --- | --- | --- |
| [[SIGINT]] (2) | 터미널에서 Ctrl+C | 종료 | 예 |
| [[SIGTERM]] (15) | `kill PID`, `docker stop`, systemd가 서비스를 멈출 때 | 종료 | 예. 정리하고 끝내라는 정중한 부탁 |
| [[SIGKILL]] (9) | `kill -9 PID`, 메모리 부족으로 커널이 죽일 때 | 즉시 종료 | 아니요. 정리할 기회가 없음 |
| SIGHUP (1) | 터미널이 닫힘. 데몬에게는 "설정을 다시 읽어라" 관례 | 종료 | 예 |
| SIGCHLD | 자식 프로세스가 끝남 | 무시 | 예 |
| SIGSEGV (11) | 허락되지 않은 메모리에 접근 (7장) | 종료 + 코어 덤프 | 사실상 아니요 |

서버를 배포할 때 시그널이 중요합니다. 새 버전으로 바꾸려고 옛 서버를 멈출 때, 먼저 SIGTERM을 보내 "새 요청은 그만 받고, 처리 중인 요청은 끝내고, DB 연결을 닫고 나가라"고 부탁합니다. 정해진 시간(Docker는 10초) 안에 안 끝나면 SIGKILL로 강제로 끝냅니다. Node 서버라면 이렇게 받습니다.

```js server.js
const server = app.listen(3000);
process.on("SIGTERM", () => {
  server.close(() => process.exit(0)); // 새 연결을 그만 받고, 지금 연결이 끝나면 종료
});
```

컨테이너 안에서 PID 1인 프로세스는 핸들러를 달지 않은 시그널이 기본 동작을 하지 않고 무시됩니다. 그래서 핸들러 없는 Node 앱은 `docker stop`에 반응하지 않고 10초를 꽉 채운 뒤 SIGKILL로 죽습니다. 배포가 매번 10초씩 걸린다면 이걸 의심합니다.

Windows에는 POSIX 시그널이 없습니다. Ctrl+C는 콘솔 이벤트로 전달되고, 강제 종료는 `TerminateProcess`(작업 관리자의 "작업 끝내기")입니다. Node는 Windows에서도 Ctrl+C를 `SIGINT`처럼 받게 흉내 내 주지만, `SIGTERM`을 보내는 방법은 없습니다.

## 스레드: 프로세스 안의 실행 흐름

프로세스 안에서 독립적으로 실행되는 흐름 하나를 [[스레드]]라고 합니다. 모든 프로세스는 스레드를 적어도 하나 가지고 있고(메인 스레드), 더 만들 수 있습니다. 스케줄러가 코어에 올리는 단위는 사실 프로세스가 아니라 스레드입니다.

| | 프로세스 | 스레드 |
| --- | --- | --- |
| 메모리 | 각자 따로. 서로 못 봄 | 같은 프로세스의 스레드끼리 공유 |
| 각자 가진 것 | 주소 공간, 열린 파일, PID | 레지스터, 프로그램 카운터, 콜 스택 |
| 만들고 바꾸는 비용 | 큼 | 작음 (메모리 지도를 안 바꿔도 됨) |
| 하나가 죽으면 | 그 프로세스만 | 보통 프로세스 전체가 죽음 |
| 데이터 주고받기 | IPC가 필요 (아래 절) | 그냥 같은 변수를 읽고 씀. 그래서 위험함 |

스레드는 메모리를 공유하니 데이터를 주고받기 쉽고 가볍습니다. 대신 서로를 망가뜨릴 수 있습니다. 프로세스는 무겁지만 안전합니다. 브라우저가 탭마다 프로세스를 따로 쓰는 건 안전을 고른 것이고, 그 프로세스 안에서 여러 스레드로 일을 나누는 건 속도를 고른 것입니다. 맨 앞 그림에서 이 페이지의 렌더러 안 점선 상자가 바로 그 스레드들입니다. `app.js`를 돌리는 메인 스레드와 스크롤을 맡는 컴포지터 스레드가 같은 메모리를 보며 함께 일합니다.

같은 메모리를 여럿이 함께 쓴다는 것은 편하지만 위험합니다. 그 위험을 보기 전에 말 두 개를 정리합니다.

| | 멀티프로세스 | 멀티스레드 |
| --- | --- | --- |
| 메모리 | 프로세스마다 따로 | 한 프로세스의 메모리를 함께 씀 |
| 만들기와 전환 | 무거움 (주소 공간을 새로) | 가벼움 |
| 데이터 나누기 | IPC가 필요 (아래 절) | 그냥 같은 변수를 읽음. 대신 동기화가 필요 |
| 하나가 죽으면 | 나머지는 멀쩡 | 프로세스 전체가 함께 죽음 |
| 예 | Chrome의 탭마다 렌더러 | 렌더러 안의 메인 스레드, 합성 스레드, 워커 |

Chrome이 탭마다 프로세스를 나눈 것은 안전과 안정을 위해 무게를 감수한 선택이고, 한 탭 안의 일을 스레드로 나눈 것은 가볍게 함께 일하기 위한 선택입니다.

## 동시성과 병렬성

두 말은 자주 섞여 쓰이지만 다릅니다.

- **[[동시성]]**(concurrency): 여러 일을 번갈아 조금씩 진행해서, 한 기간 동안 여러 일이 함께 진행 중인 상태. 코어 하나로도 됩니다. 요리사 한 명이 국을 끓이는 동안 채소를 써는 것입니다.
- **[[병렬성]]**(parallelism): 여러 일이 같은 순간에 진짜로 동시에 실행되는 것. 코어가 여러 개 있어야 합니다. 요리사 두 명이 각자 요리하는 것입니다.

JS의 메인 스레드는 동시성은 있지만 병렬성은 없습니다. `fetch` 세 개를 동시에 보내 놓고 기다리는 건 동시성이고, 그 응답들을 처리하는 JS 코드는 한 번에 하나씩 돕니다.

## 같은 메모리를 함께 쓰면: 경쟁 조건

두 스레드가 같은 변수 `count`에 1씩 더한다고 해 봅니다. `count++`는 한 줄이지만 CPU에서는 세 단계입니다. 읽고, 더하고, 씁니다.

![두 스레드가 같은 `count`에 1씩 더할 때 순서가 엇갈린 경우. 둘 다 5를 읽어 6을 쓰니, 한 번의 덧셈이 사라집니다](process-race.svg)

실행 순서에 따라 결과가 달라지는 이런 상황을 [[경쟁 조건]]이라고 합니다. 매번 일어나지 않고 가끔, 그것도 테스트할 때는 안 일어나고 사용자가 많을 때 일어나서 가장 찾기 어려운 버그입니다. 공유 데이터를 건드리는 코드 구간을 [[임계 구역]]이라고 하고, 한 번에 하나의 실행 흐름만 들어가게 해야 합니다.

경쟁 조건은 스레드가 없는 JS에서도 생깁니다. 메모리 수준이 아니라 논리 수준에서입니다.

- 두 탭이 동시에 `localStorage`의 값을 읽어 1을 더하고 씁니다. 이 책을 탭 두 개로 열어 두고 각각 체크하면 생길 수 있는 일입니다. 그래서 이 사이트의 `app.js`는 체크할 때마다 저장된 기록을 새로 읽은 뒤 쓰고, 다른 탭이 쓰면 `storage` 이벤트를 받아 화면을 맞춥니다.
- 서버에서 두 요청이 동시에 "재고 확인 → 재고 차감"을 하면, 둘 다 재고가 1개 남았다고 보고 2개를 팝니다.
- `await` 사이에 다른 이벤트 핸들러가 끼어들어 상태를 바꿉니다. React에서 늦게 도착한 검색 응답이 최신 응답을 덮어쓰는 버그가 대표적입니다.

## 막는 방법: 원자적 연산, 뮤텍스, 세마포어

- **[[원자적 연산]]**: CPU가 "읽고 더하고 쓰기"를 중간에 끼어들 수 없게 한 번에 해 주는 명령어입니다. 가장 유명한 것이 비교 후 교환(CAS, "값이 아직 5면 6으로 바꿔라")입니다. JS에서도 `SharedArrayBuffer`와 `Atomics.add`로 씁니다.
- **[[뮤텍스]]**(mutex, 상호 배제): 임계 구역 앞의 자물쇠. 먼저 잠근 스레드만 들어가고, 나머지는 풀릴 때까지 기다립니다. 화장실 열쇠 하나와 같습니다.
- **[[세마포어]]**: 정해진 수만큼만 들어가게 하는 계수기. 열쇠가 N개인 셈입니다. DB 연결 풀이 연결 10개를 나눠 쓰게 하는 것이 그 예입니다.
- **데이터베이스 트랜잭션과 잠금**: 서버의 재고 문제는 DB가 행을 잠그거나 "재고가 1 이상일 때만 차감"을 한 문장으로 처리해 풉니다.
- **JS의 논리적 경쟁**: 늦게 온 응답을 무시하도록 `AbortController`로 이전 요청을 취소하거나, 요청 번호를 비교합니다.

여러 스레드가 함께 쓰는 자원을 건드리는 코드 구간을 [[임계 영역]]이라고 합니다. 위의 `count++`가 들어 있는 줄이 그렇습니다. 임계 영역을 제대로 지키려면 세 가지가 필요하다고 정리합니다. 한 번에 하나만 들어간다(상호 배제), 아무도 안에 없으면 기다리던 누군가는 들어갈 수 있다(진행), 그리고 한 스레드가 영원히 기다리지는 않는다(한정 대기). 뮤텍스와 세마포어는 이 세 가지를 지키는 도구입니다.

:::quiz race-fix 두 스레드가 `count++`를 동시에 하다 값이 하나씩 사라집니다. 이 문제를 **고치지 못하는** 방법은?
- [ ] `count++` 전체를 뮤텍스로 감싸기
- [ ] 원자적 덧셈 명령어(`Atomics.add` 같은)로 바꾸기
- [ ] 한 스레드만 `count`를 바꾸고 다른 스레드는 그 스레드에 부탁하게 하기
- [x] `count++`를 `count += 1`로 바꿔 쓰기

`count += 1`은 고쳐 주지 못합니다. 쓰는 모양만 다를 뿐 CPU에서는 똑같이 읽기, 더하기, 쓰기 세 단계라 그 사이에 끼어들 수 있습니다. 나머지는 모두 세 단계를 한 번에 하나만 하게 만드는 방법입니다.
:::

## 서로 기다리다 멈추는 것: 데드락

잠금을 쓰면 새 문제가 생깁니다. 스레드 A가 자물쇠 1을 잡고 자물쇠 2를 기다리는데, 스레드 B는 자물쇠 2를 잡고 자물쇠 1을 기다립니다. 둘 다 영원히 기다립니다. 이걸 [[데드락]](교착 상태)이라고 합니다. 좁은 다리 양쪽에서 차 두 대가 마주 보고 서서 서로 비키기를 기다리는 모습입니다.

데드락은 네 조건이 모두 맞을 때 생깁니다.

1. **상호 배제**: 자원을 한 번에 하나만 쓸 수 있음
2. **점유와 대기**: 자원 하나를 쥔 채로 다른 자원을 기다림
3. **비선점**: 남이 쥔 자원을 강제로 빼앗을 수 없음
4. **순환 대기**: 기다림이 원을 이룸

![데드락. 두 스레드가 각자 자물쇠 하나를 쥔 채 상대의 자물쇠를 기다려 원이 생겼습니다](process-deadlock.svg)

하나만 깨면 막을 수 있습니다. 실무에서 가장 흔한 방법은 "자물쇠는 항상 정해진 순서로 잡는다"로 순환 대기를 깨는 것, 그리고 "일정 시간 못 잡으면 포기하고 다시 시도한다"로 대기를 끊는 것입니다. 데이터베이스는 데드락을 스스로 찾아내 한쪽 트랜잭션을 실패시킵니다.

## 프로세스끼리 대화하기: IPC

프로세스는 서로의 메모리를 못 보니, 데이터를 주고받으려면 운영체제가 마련한 통로를 써야 합니다. 이걸 [[IPC]](프로세스 간 통신)라고 합니다.

| 방법 | 어떻게 | 예 |
| --- | --- | --- |
| [[파이프]] | 한쪽이 쓰면 다른 쪽이 읽는 단방향 통로 | 셸의 `cat log \| grep error` |
| 이름 있는 파이프 | 파일 시스템에 이름이 있는 파이프 | Windows의 `\\.\pipe\…`, 유닉스의 FIFO |
| [[유닉스 도메인 소켓]] | 같은 컴퓨터 안의 프로세스끼리 쓰는 소켓. 파일 경로로 찾음 | `/var/run/docker.sock` (docker 명령이 Docker 데몬과 대화), PostgreSQL 로컬 접속 |
| TCP 소켓 (localhost) | 네트워크 소켓을 같은 컴퓨터 안에서 | 개발 서버와 브라우저, 이 사이트의 Caddy와 컨테이너들 |
| 공유 메모리 | 두 프로세스가 같은 RAM 조각을 보게 함 | 빠르지만 동기화가 필요. Chrome이 렌더러와 GPU 프로세스 사이에 씀 |
| 시그널 | 번호 하나짜리 알림 | 위의 SIGTERM |

맨 앞 그림의 선들도 IPC입니다. "다 읽었어요" 클릭은 먼저 브라우저 프로세스가 받고, IPC 메시지로 이 페이지의 렌더러에 넘깁니다. 렌더러가 무언가를 받아야 할 때도 네트워크 서비스에 IPC로 부탁합니다. Chrome은 이 메시지 통로를 Mojo라고 부르고, 아래에서는 운영체제의 파이프와 공유 메모리를 씁니다.

셸 파이프는 매일 쓰는 IPC입니다. `ps aux | grep node | wc -l`은 프로세스 세 개를 띄우고 파이프 두 개로 이어, 앞 프로세스의 출력이 다음 프로세스의 입력으로 흐르게 합니다. 세 프로세스는 병렬로 돌고, 파이프가 가득 차거나 비면 커널이 알아서 재우고 깨웁니다.

## JS는 스레드 하나로 어떻게 여러 일을 하나: 이벤트 루프

브라우저의 JS는 메인 스레드 하나에서 돕니다. 그런데 클릭에 반응하면서 타이머도 돌리고 네트워크 응답도 받습니다. 비결은 [[이벤트 루프]]입니다.

1. JS 코드는 콜 스택에서 끝까지 실행됩니다. 실행 중에는 다른 JS가 끼어들지 않습니다.
2. `fetch`, `setTimeout`, 이벤트 리스너처럼 기다려야 하는 일은 JS 엔진 바깥(브라우저의 다른 스레드, 운영체제)에 맡깁니다. JS는 기다리지 않고 다음 줄로 갑니다.
3. 맡긴 일이 끝나면 그 콜백이 [[태스크 큐]]에 줄을 섭니다.
4. 콜 스택이 비면, 이벤트 루프가 먼저 [[마이크로태스크]](Promise의 `then`, `await` 다음 코드)를 모두 실행하고, 그다음 태스크 큐에서 하나를 꺼내 실행합니다.
5. 브라우저는 그 사이사이에 화면을 다시 그립니다(대략 16ms마다, 26장).

![이 페이지에서 "다 읽었어요"를 눌렀을 때. 클릭은 IPC로 렌더러에 와서 태스크 큐에 줄을 서고, 콜 스택이 비면 꺼내져 `app.js`의 핸들러가 실행됩니다. 그동안 다른 JS는 끼어들지 못합니다](process-event-loop.svg)

그래서 JS가 오래 걸리는 계산을 하면 그동안 클릭도, 타이머도, 화면 그리기도 멈춥니다. 페이지가 "얼어붙는" 이유입니다. 50ms 넘게 메인 스레드를 잡는 작업을 긴 작업(long task)이라고 하고, 웹 성능 지표 INP가 나빠지는 주 원인입니다.

:::quiz long-task "다 읽었어요"의 `change` 핸들러 안에서 2초 걸리는 계산을 한다면, 그 2초 동안 이 페이지에서 무슨 일이 생길까요?
- [ ] 계산은 다른 코어에서 돌고 페이지는 평소처럼 반응한다
- [ ] 커널이 타임 슬라이스마다 계산을 끊고 다른 클릭 핸들러를 실행해 준다
- [x] 다른 클릭이나 타이머의 핸들러가 기다리고, 진행 막대도 2초 뒤에야 바뀐다
- [ ] 브라우저가 계산을 Web Worker로 옮겨 준다

다른 JS와 화면 갱신이 2초 동안 밀립니다. 커널은 렌더러 프로세스와 다른 프로세스 사이에서는 CPU를 나눠 주지만, 메인 스레드 안의 JS 작업 순서는 이벤트 루프가 정합니다. 지금 돌고 있는 핸들러가 끝나야 다음 태스크를 꺼내고 화면을 그립니다. 오래 걸리는 계산은 직접 Web Worker로 옮기거나 잘게 나눠야 합니다.
:::

메인 스레드 하나로는 모자란 일도 있습니다.

Node도 같은 생각으로 돕니다. libuv의 이벤트 루프가 타이머, 입출력 완료, `setImmediate`를 단계별로 돌며 콜백을 실행합니다. 수천 개의 연결을 스레드 하나로 처리할 수 있는 건, 연결 대부분이 대기 상태라 그동안 다른 연결의 콜백을 돌릴 수 있기 때문입니다. 대신 CPU를 오래 쓰는 계산 하나가 모든 연결을 멈춥니다.

진짜 병렬 실행이 필요하면 스레드를 따로 씁니다. 브라우저에서는 [[Web Worker]], Node에서는 `worker_threads`입니다. 이들은 메모리를 기본적으로 공유하지 않고 메시지(`postMessage`)로 대화하니, 스레드이지만 프로세스처럼 안전하게 쓰도록 설계되어 있습니다.

## 다시 장면으로: 클릭 한 번이 지나간 곳들

맨 앞 그림을 위에서 아래로 따라가 봅니다. 브라우저 실행 파일 하나에서 브라우저 프로세스가 뜨고, 그 프로세스가 사이트마다 렌더러를, 화면을 위해 GPU 프로세스를, 요청을 위해 네트워크 서비스를 띄웠습니다. 각각은 PCB를 가진 프로세스이고, 커널의 스케줄러가 이들의 스레드를 몇 개뿐인 코어에 몇 밀리초씩 번갈아 올립니다. 대부분은 대기 상태에서 무언가를 기다립니다.

"다 읽었어요"를 누르면 브라우저 프로세스가 클릭을 받아 IPC로 이 페이지의 렌더러에 넘깁니다. 렌더러의 메인 스레드는 이를 태스크 큐에 세웠다가 콜 스택이 비면 `app.js`의 핸들러를 실행하고, 진행 막대를 바꾸고, 다음 프레임에 화면을 다시 그립니다. 다른 탭이 같은 기록을 쓸 수 있으니 쓰기 전에 다시 읽습니다.

여기서 새로운 질문이 생깁니다. 렌더러가 수십 개이고 각자 자기 메모리를 쓰는데, 서로의 메모리는 어떻게 못 보게 막을까요? 이 페이지의 4만 바이트와 `app.js`가 만든 JS 객체는 RAM의 어디에 있을까요? 탭을 많이 열면 컴퓨터가 왜 느려질까요? 7장의 메모리 이야기입니다.

## 프론트엔드와 이어지는 곳

- 긴 계산은 Web Worker로 옮기거나, 잘게 나눠 중간중간 메인 스레드를 양보합니다(`scheduler.yield()`, `setTimeout`). 메인 스레드를 오래 잡으면 INP가 나빠집니다.
- `Promise.then`과 `setTimeout(…, 0)` 중 무엇이 먼저 실행되는지는 마이크로태스크와 태스크의 순서로 정해집니다.
- 검색창의 늦은 응답이 최신 결과를 덮는 버그는 논리적 경쟁 조건입니다. 이전 요청을 `AbortController`로 취소합니다.
- 서버를 배포하는 쪽이라면 SIGTERM 핸들러를 달아 우아하게 끝냅니다. Docker의 PID 1 문제를 기억합니다.
- 개발 서버가 안 꺼지고 포트를 붙잡고 있으면, 그 PID를 찾아 끝냅니다(16장의 `lsof -i :3000`).

## 용어 정리

:::terms
- 프로세스 (process) — 실행 중인 프로그램. 자기만의 주소 공간, 열린 파일, 하나 이상의 스레드를 가집니다.
- PID (Process ID) — 운영체제가 프로세스마다 붙이는 번호. 부모 프로세스의 번호는 PPID라고 합니다.
- PCB (Process Control Block) — 커널이 프로세스마다 두는 기록. 상태, 저장된 레지스터, 메모리 지도, 열린 파일 목록이 들어 있습니다.
- 타임 슬라이스 (time slice) — 스케줄러가 스레드 하나에 한 번에 주는 CPU 시간. 보통 수 밀리초입니다.
- 컨텍스트 스위칭 (context switching) — 실행 중인 스레드의 레지스터를 저장하고 다른 스레드의 것을 되살려 CPU를 넘기는 일입니다.
- 스케줄러 (scheduler) — 준비된 스레드 중 누구에게 CPU 코어를 줄지 정하는 커널의 부분입니다.
- 라운드 로빈 (round robin) — 준비된 작업들에 타임 슬라이스씩 돌아가며 CPU를 주는 스케줄링 방법입니다.
- 선점형 스케줄링 (preemptive scheduling) — 실행 중인 프로세스가 양보하지 않아도 운영체제가 타이머 인터럽트로 CPU를 빼앗을 수 있는 방식입니다.
- fork — 유닉스 계열에서 지금 프로세스를 복제해 자식 프로세스를 만드는 시스템 콜. 부모와 자식에게 각각 다른 값을 돌려줍니다.
- exec — 지금 프로세스의 내용을 새 프로그램으로 갈아 끼우는 시스템 콜. PID는 그대로입니다.
- 종료 코드 (exit code) — 프로세스가 끝날 때 남기는 숫자. 0은 성공, 그 밖은 실패를 뜻합니다.
- 좀비 프로세스 (zombie process) — 끝났지만 부모가 종료 코드를 거둬 가지 않아 PCB만 남은 프로세스입니다.
- 고아 프로세스 (orphan process) — 부모가 먼저 끝난 프로세스. 유닉스 계열에서는 PID 1이 입양합니다.
- 시그널 (signal) — 커널이나 다른 프로세스가 프로세스에 보내는 번호 하나짜리 알림. 핸들러로 받거나 기본 동작을 따릅니다.
- SIGINT — Ctrl+C로 보내는 시그널. 기본 동작은 종료입니다.
- SIGTERM — 정리하고 끝내라는 정중한 종료 시그널. `kill`, `docker stop`, systemd가 기본으로 보냅니다.
- SIGKILL — 받는 즉시 강제 종료되는 시그널(9번). 막거나 정리할 수 없습니다.
- 스레드 (thread) — 프로세스 안의 실행 흐름 하나. 같은 프로세스의 스레드끼리 메모리를 공유하고, 각자 레지스터와 콜 스택을 가집니다.
- 동시성 (concurrency) — 여러 일을 번갈아 진행해 한 기간에 함께 진행 중인 상태. 코어 하나로도 됩니다.
- 병렬성 (parallelism) — 여러 일이 같은 순간에 여러 코어에서 실제로 동시에 실행되는 것입니다.
- 경쟁 조건 (race condition) — 여러 실행 흐름이 공유 데이터를 다룰 때, 실행 순서에 따라 결과가 달라지는 버그입니다.
- 임계 구역 (critical section) — 공유 데이터를 건드려서 한 번에 하나의 실행 흐름만 들어가야 하는 코드 구간입니다.
- 원자적 연산 (atomic operation) — 중간에 다른 실행 흐름이 끼어들 수 없게 한 번에 끝나는 연산. 비교 후 교환(CAS)이 대표적입니다.
- 뮤텍스 (mutex) — 한 번에 하나만 임계 구역에 들어가게 하는 자물쇠입니다.
- 세마포어 (semaphore) — 정해진 수만큼만 동시에 들어가게 하는 계수기. 연결 풀의 크기 제한이 그 예입니다.
- 데드락 (deadlock) — 둘 이상의 실행 흐름이 서로가 쥔 자원을 기다리며 영원히 멈춘 상태입니다.
- IPC (Inter-Process Communication) — 프로세스끼리 데이터를 주고받는 방법. 파이프, 소켓, 공유 메모리, 시그널 등이 있습니다.
- 파이프 (pipe) — 한 프로세스의 출력을 다른 프로세스의 입력으로 잇는 단방향 통로. 셸의 `|`입니다.
- 유닉스 도메인 소켓 (Unix domain socket) — 같은 컴퓨터 안의 프로세스끼리 파일 경로로 찾아 쓰는 소켓. `docker.sock`이 그 예입니다.
- 이벤트 루프 (event loop) — 할 일 큐에서 콜백을 하나씩 꺼내 실행하는 반복. JS가 스레드 하나로 여러 일을 처리하는 방법입니다.
- 태스크 큐 (task queue) — 타이머, 이벤트, 입출력 완료 콜백이 실행을 기다리며 줄 서는 곳입니다.
- 마이크로태스크 (microtask) — Promise 콜백처럼, 지금 태스크가 끝나자마자 다음 태스크보다 먼저 실행되는 작은 작업입니다.
- Web Worker — 브라우저에서 메인 스레드와 따로 JS를 실행하는 스레드. 메시지로만 대화합니다.
- 사이트 격리 (site isolation) — 브라우저가 사이트마다 다른 렌더러 프로세스를 써서 서로의 메모리를 볼 수 없게 하는 구조입니다.
- 기아 (starvation) — 우선순위가 낮거나 긴 작업이 다른 작업에 계속 밀려 CPU나 자원을 끝없이 받지 못하는 상태입니다.
- 에이징 (aging) — 오래 기다린 작업의 우선순위를 조금씩 올려 기아를 막는 방법입니다.
- 임계 영역 (critical section) — 여러 스레드나 프로세스가 함께 쓰는 자원을 다루는 코드 구간. 한 번에 하나만 들어가야 합니다.
:::

아래 서버를 띄우고 다른 터미널에서 SIGTERM과 SIGKILL을 각각 보내 차이를 봅니다. SIGKILL에서는 정리 메시지가 나오지 않아야 합니다.

```js graceful.js
const http = require("node:http");
const server = http.createServer((req, res) => setTimeout(() => res.end("ok\n"), 3000));
server.listen(3000, () => console.log("PID", process.pid));
process.on("SIGTERM", () => {
  console.log("SIGTERM: 새 연결을 그만 받고 정리합니다");
  server.close(() => { console.log("끝"); process.exit(0); });
});
```

```sh macOS · Linux
node graceful.js &
curl localhost:3000 & sleep 0.5; kill -TERM %1   # 응답 "ok"를 준 뒤 끝나는지
node graceful.js & sleep 0.5; kill -KILL %1      # 바로 죽는지
```
:::

:::practice race 경쟁 조건을 일부러 만들고 고치기
워커 4개가 같은 공유 메모리의 숫자에 100만 번씩 1을 더합니다. 그냥 더하면 400만이 안 나오고, `Atomics.add`를 쓰면 정확히 400만이 나옵니다.

```js race.mjs
import { Worker, isMainThread, workerData } from "node:worker_threads";
if (isMainThread) {
  const shared = new Int32Array(new SharedArrayBuffer(4));
  const useAtomics = process.argv[2] === "atomic";
  await Promise.all(Array.from({ length: 4 }, () =>
    new Promise((r) => new Worker(new URL(import.meta.url), { workerData: { shared, useAtomics } }).on("exit", r))));
  console.log(useAtomics ? "Atomics:" : "그냥:", shared[0]);
} else {
  const { shared, useAtomics } = workerData;
  for (let i = 0; i < 1e6; i++) useAtomics ? Atomics.add(shared, 0, 1) : shared[0]++;
}
```

```sh 터미널
node race.mjs          # 400만보다 작게 나옵니다
node race.mjs atomic   # 정확히 4000000
```
:::

:::practice block 메인 스레드를 막아 보기
아무 웹 페이지의 콘솔에서 3초 동안 메인 스레드를 잡아 두고, 그 사이 페이지를 스크롤하거나 버튼을 눌러 봅니다. 그다음 Performance 패널에서 같은 걸 녹화해 빨간 긴 작업 표시를 찾습니다.

```js 브라우저 콘솔
setTimeout(() => console.log("타이머"), 0);
Promise.resolve().then(() => console.log("마이크로태스크"));
const end = Date.now() + 3000;
while (Date.now() < end) {}
console.log("동기 코드 끝");
// 출력 순서: 동기 코드 끝 → 마이크로태스크 → 타이머
```
:::

:::practice chrome-tasks 브라우저의 프로세스 세어 보기
Chrome에서 Shift+Esc(Mac은 창 메뉴 → 작업 관리자)를 열고, 탭을 서로 다른 사이트로 세 개, 같은 사이트로 세 개 열어 렌더러 프로세스가 어떻게 늘어나는지 봅니다. 운영체제의 작업 관리자나 활성 상태 보기에서도 같은 프로세스들을 찾아봅니다.
:::

## 장 전체 문제

:::quiz one-program-many 브라우저 아이콘을 한 번 눌렀을 뿐인데 활동 모니터에 Chrome 관련 프로세스가 20개 넘게 보입니다. 맞는 설명은?
- [ ] 아이콘을 누를 때마다 운영체제가 실행 파일을 여러 번 복사해서
- [ ] 코어 수만큼 프로세스를 띄워야 브라우저가 돌 수 있어서
- [ ] 스레드를 운영체제가 프로세스로 잘못 표시해서
- [x] 브라우저가 안전과 안정성을 위해 사이트, GPU, 네트워크 같은 역할마다 프로세스를 따로 띄워서

역할과 사이트마다 프로세스를 나눴기 때문입니다. 프로그램(실행 파일)은 하나지만 프로세스는 여럿이고, 프로세스끼리는 메모리가 갈라져 있어 한 탭이 죽거나 악성 사이트가 다른 사이트의 메모리를 엿보는 일을 막습니다.
:::

:::quiz output-order 다음 코드는 어떤 순서로 출력될까요? `setTimeout(() => log("A")); queueMicrotask(() => log("B")); Promise.resolve().then(() => log("D")); log("C");` (띄어쓰기 없이 네 글자로)
= CBDA | C B D A | C,B,D,A

**CBDA**입니다. 지금 실행 중인 코드의 C가 먼저입니다. 콜 스택이 비면 마이크로태스크 큐를 줄 선 순서대로 모두 비우니 B, D가 이어지고, 그다음에야 태스크 큐의 `setTimeout` 콜백 A가 나옵니다. 스스로 점검의 질문과 같은 규칙이지만 마이크로태스크가 둘일 때도 순서가 지켜지는지 확인하는 문제입니다.
:::

## 스스로 점검

:::qa 프로그램과 프로세스의 차이를, `node`를 터미널 세 개에서 실행한 상황으로 설명해 보세요.
프로그램은 디스크의 `node` 실행 파일 하나이고, 실행할 때마다 각자 주소 공간, PID, 열린 파일을 가진 프로세스가 생겨 세 개가 됩니다. 셋은 서로의 메모리를 볼 수 없습니다.
:::

:::qa 컨텍스트 스위칭이 일어나는 과정과 숨은 비용은?
타이머 인터럽트 등으로 커널에 들어와 지금 스레드의 레지스터를 PCB에 저장하고, 스케줄러가 고른 스레드의 레지스터와 메모리 지도를 되살려 이어서 실행합니다. 스위칭 자체보다 새 스레드의 데이터가 캐시에 없어 생기는 캐시 미스가 숨은 비용입니다.
:::

:::qa 셸이 `ls`를 실행할 때 `fork`와 `exec`가 각각 무슨 일을 하나요? Windows는 어떻게 다르나요?
`fork`로 셸 자신을 복제한 자식을 만들고, 자식이 `exec`로 자기 내용을 `ls` 프로그램으로 바꿉니다. 부모 셸은 `wait`로 자식이 끝나길 기다립니다. Windows는 `CreateProcess` 한 번으로 새 실행 파일의 프로세스를 바로 만듭니다.
:::

:::qa `docker stop`을 하면 Node 컨테이너가 10초 뒤에야 꺼집니다. 왜이고, 어떻게 고치나요?
컨테이너 안에서 Node가 PID 1이라, 핸들러를 달지 않은 SIGTERM이 기본 동작(종료)을 하지 않고 무시됩니다. Docker는 10초를 기다린 뒤 SIGKILL을 보냅니다. `process.on("SIGTERM")` 핸들러를 달거나, `docker run --init`으로 시그널을 전달해 주는 작은 PID 1을 둡니다.
:::

:::qa 스레드끼리 데이터를 주고받기는 쉬운데, 왜 위험한가요?
같은 메모리를 공유해서 그냥 같은 변수를 읽고 쓰면 되지만, 읽고-바꾸고-쓰는 사이에 다른 스레드가 끼어들면 결과가 실행 순서에 따라 달라지는 경쟁 조건이 생깁니다. 뮤텍스나 원자적 연산으로 임계 구역을 보호해야 합니다.
:::

:::qa 데드락의 네 조건은 무엇이고, 실무에서 가장 흔히 쓰는 예방법은?
상호 배제, 점유와 대기, 비선점, 순환 대기입니다. 자물쇠를 항상 같은 순서로 잡아 순환 대기를 깨는 방법, 정해진 시간 안에 못 잡으면 포기하고 다시 시도하는 방법을 많이 씁니다.
:::

:::qa 다음 코드의 출력 순서는? `setTimeout(() => log("A"), 0); Promise.resolve().then(() => log("B")); log("C");`
C, B, A입니다. 동기 코드가 먼저 끝까지 실행되고, 콜 스택이 비면 마이크로태스크(B)를 모두 실행한 뒤 태스크 큐의 타이머 콜백(A)을 실행합니다.
:::
