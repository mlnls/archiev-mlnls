summary: IP가 컴퓨터까지 데려다준 패킷을 어느 프로그램에 줄지 정하는 포트와 소켓을 봅니다. 사라지고 뒤섞이는 패킷 위에서 믿을 수 있는 연결을 만드는 TCP(3-way 핸드셰이크, 재전송, 흐름 제어, 혼잡 제어, 연결 종료), 가볍게 보내고 마는 UDP, 둘의 장점을 합친 QUIC까지. `ECONNREFUSED`와 `ETIMEDOUT`이 무슨 뜻인지도 여기서 정확히 알게 됩니다.
---

11장은 서버의 네트워크 카드에 닿은 패킷을 두고 두 가지를 물으며 끝났습니다. 서버에는 Caddy, SSH 서버, 블로그 API가 함께 돌고 있는데 이 패킷은 누구의 것일까요? 그리고 IP는 패킷이 사라지거나 순서가 바뀌어도 책임지지 않는데, 이 페이지의 HTML은 어떻게 한 글자도 빠지지 않고 도착할까요? 답은 IP 헤더 바로 안쪽, TCP 헤더에 적혀 있습니다.

![서버의 커널은 TCP 헤더의 받는 포트(443)를 보고 Caddy의 소켓에 데이터를 넘깁니다. 거꾸로 HTML은 바이트마다 번호가 붙어 나가서, 하나가 사라지면 다시 받아 빈칸을 채운 뒤 순서대로 브라우저에 건넵니다](transport-scene.svg)

이 두 문제를 푸는 층이 [[전송 계층]]입니다. 첫째 문제는 포트로, 둘째 문제는 TCP로 풉니다. 둘째 문제가 필요 없는 경우를 위해 UDP도 있습니다. 전송 계층은 라우터가 아니라 양 끝 컴퓨터의 커널에서만 동작합니다. 길 위의 라우터들은 IP 헤더까지만 보니까요.

## 포트: 컴퓨터 안의 문 번호

IP 주소가 건물 주소라면 [[포트]]는 그 건물 안의 호수입니다. 0부터 65535까지의 16비트 번호이고, TCP와 UDP 헤더에 받는 포트와 보내는 포트가 적혀 있습니다. 커널은 받는 포트 번호를 보고 그 포트를 쓰고 있는 프로그램에 데이터를 넘깁니다.

| 범위 | 이름 | 예 |
| --- | --- | --- |
| 0~1023 | [[잘 알려진 포트]] | 22 SSH, 25 SMTP, 53 DNS, 80 HTTP, 443 HTTPS |
| 1024~49151 | 등록된 포트 | 3000 (Node 개발 서버 관례), 3306 MySQL, 5173 Vite, 5432 PostgreSQL, 6379 Redis, 8080 (대체 HTTP) |
| 49152~65535 | 동적 포트 | 클라이언트가 연결할 때 임시로 받는 번호 |

브라우저가 `https://naver.com`에 접속하면 받는 포트는 443(주소에 안 적어도 HTTPS의 기본값), 보내는 포트는 운영체제가 그때그때 빈 번호를 골라 줍니다. 이걸 [[임시 포트]]라고 합니다. 응답은 이 임시 포트로 돌아와서 그 브라우저의 그 연결에 닿습니다. 임시 포트 범위는 운영체제마다 다릅니다. Windows와 macOS는 49152~65535, Linux는 기본 32768~60999입니다.

:::quiz ephemeral 브라우저가 이 페이지의 서버에 연결할 때 서버 쪽 포트는 443입니다. 노트북 쪽 포트는 누가 정할까요?
- [ ] 서버가 정해서 SYN+ACK로 알려 준다
- [x] 노트북의 운영체제가 빈 번호를 골라 준다
- [ ] 늘 443으로 같다
- [ ] 공유기가 DHCP로 나눠 준다

노트북의 운영체제가 임시 포트 범위에서 빈 번호를 골라 줍니다. 연결마다 다른 번호를 쓰기 때문에 같은 서버로 연결을 여럿 열어도 응답이 섞이지 않습니다. 공유기는 NAT를 하며 바깥쪽 포트를 다시 붙일 뿐입니다(11장).
:::

## 소켓: 연결의 양 끝

프로그램이 네트워크를 쓰려면 커널에 [[소켓]]을 만들어 달라고 합니다. 소켓은 통신의 한쪽 끝을 나타내는 커널 객체이고, 프로그램 쪽에서는 8장의 파일 디스크립터 하나로 보입니다. 그래서 소켓도 `read`, `write`로 읽고 씁니다.

TCP 연결 하나는 다섯 가지 값, [[5-튜플]]로 구분됩니다.

```text
(TCP, 192.168.0.23, 51000, 142.250.207.46, 443)
 프로토콜, 내 IP, 내 포트, 상대 IP, 상대 포트
```

이 다섯 개 중 하나만 달라도 다른 연결입니다. 그래서 서버는 443번 포트 하나로 연결 수만 개를 동시에 받을 수 있습니다. 클라이언트마다 IP나 포트가 다르니 5-튜플이 모두 다르기 때문입니다.

서버와 클라이언트가 소켓을 쓰는 순서는 이렇습니다. 4장의 시스템 콜 목록에 있던 이름들입니다.

```text
서버                                   클라이언트
socket()   소켓 만들기
bind()     이 IP, 이 포트에 붙이기
listen()   연결을 받을 준비 (LISTEN 상태)
                                       socket()
                                       connect(서버 IP, 443) ── 3-way 핸드셰이크 ──▶
accept()   새 연결이 오면, 그 연결 전용의
           새 소켓을 돌려줌
read()/write()  ◀────────── 데이터 ──────────▶  write()/read()
close()                                close()
```

`listen`하는 소켓은 연결을 받기만 하는 접수 창구이고, 실제 대화는 `accept`가 연결마다 돌려주는 새 소켓으로 합니다. Node의 `server.listen(3000)`이 socket, bind, listen을, `connection` 이벤트가 accept를 감싼 것입니다. 16장에서 이 시스템 콜들을 직접 써서 서버를 열어 봅니다.

:::quiz five-tuple 서버가 443번 포트 하나로 연결 수만 개를 동시에 받을 수 있는 이유는?
- [ ] 연결이 올 때마다 커널이 443번을 잠깐 다른 번호로 바꿔 줘서
- [ ] 한 번에 한 연결씩 아주 빨리 돌아가며 처리해서
- [x] 연결은 양쪽 IP와 포트를 합친 5-튜플로 구분되어, 클라이언트가 다르면 다른 연결이라서
- [ ] 443번은 잘 알려진 포트라 제한이 없어서

5-튜플이 다르면 다른 연결입니다. 서버 쪽 IP와 포트가 같아도 클라이언트의 IP나 포트가 다르면 커널은 각각을 다른 연결로 보고, `accept`가 연결마다 새 소켓을 돌려줍니다.
:::

## TCP가 약속하는 것

[[TCP]](Transmission Control Protocol)는 믿을 수 없는 IP 위에 믿을 수 있는 통로를 만듭니다.

- **연결형**: 데이터를 보내기 전에 양쪽이 연결을 맺고, 끝나면 끊습니다.
- **신뢰성**: 사라진 데이터는 다시 보내서 빠짐없이 전달합니다.
- **순서 보장**: 보낸 순서대로 프로그램에 넘깁니다.
- **바이트 스트림**: 메시지의 경계가 없는 바이트의 흐름입니다. 100바이트를 두 번 보내도, 받는 쪽은 200바이트를 한 번에 받거나 50, 150으로 나눠 받을 수 있습니다.
- **흐름 제어와 혼잡 제어**: 받는 쪽과 네트워크가 감당할 만큼만 보냅니다.
- **양방향**: 연결 하나로 양쪽이 동시에 보내고 받습니다.

바이트 스트림이라는 점이 실무에서 중요합니다. TCP는 "메시지 하나"라는 개념이 없으니, 위층 프로토콜이 경계를 따로 정해야 합니다. HTTP가 `Content-Length` 헤더로 본문 길이를 알리고, WebSocket이 메시지마다 길이가 적힌 프레임을 두는 이유입니다.

TCP가 데이터에 헤더를 붙인 단위를 [[세그먼트]]라고 부릅니다. 헤더의 주요 칸입니다.

| 칸 | 내용 |
| --- | --- |
| 보내는 포트, 받는 포트 | 각 16비트 |
| [[시퀀스 번호]] | 이 세그먼트의 첫 바이트가 전체 흐름에서 몇 번째인지 |
| 확인 응답 번호 | "여기까지 잘 받았고, 다음엔 이 번호를 기다린다" |
| 플래그 | [[SYN]] (연결 시작), [[ACK]] (확인 응답 번호가 유효함), [[FIN]] (보낼 것 끝), [[RST]] (연결 강제 종료) 등 |
| 윈도 크기 | 받는 쪽이 지금 더 받을 수 있는 양 (흐름 제어) |
| 체크섬 | 헤더와 데이터가 망가지지 않았는지 |

:::quiz bytestream 서버가 TCP 소켓에 `write`로 100바이트를 두 번 보냈습니다. 받는 쪽의 `read`에 대해 맞는 것은?
- [ ] 반드시 100바이트씩 두 번에 나눠 받는다
- [ ] 200바이트를 반드시 한 번에 받는다
- [ ] 두 번째 100바이트가 먼저 올 수도 있다
- [x] 순서는 지켜지지만, 몇 바이트씩 끊겨 오는지는 정해져 있지 않다

TCP는 바이트 스트림이라 순서는 지키지만 메시지 경계는 지키지 않습니다. 200바이트가 한 번에 올 수도, 50과 150으로 올 수도 있습니다. 그래서 HTTP는 `Content-Length`로, WebSocket은 프레임 길이로 경계를 따로 정합니다.
:::

## 연결 맺기: 3-way 핸드셰이크

TCP 연결은 세 번의 메시지로 맺습니다. 이걸 [[3-way 핸드셰이크]]라고 합니다.

![노트북과 서버가 SYN, SYN+ACK, ACK를 주고받으며 각자의 시작 번호를 확인합니다. 9장 맨 앞 그림의 왕복 2가 이것이고, 세 번째 ACK와 함께 바로 데이터(TLS)를 보냅니다](transport-handshake.svg)

세 번인 이유는 양쪽이 각자 시작 번호를 정하고, 상대가 그 번호를 받았는지 서로 확인해야 하기 때문입니다. 시작 번호를 0이 아니라 무작위로 고르는 건, 이전 연결의 늦게 도착한 패킷이 새 연결에 섞이거나 공격자가 번호를 맞혀 끼어드는 걸 막으려는 것입니다.

핸드셰이크에는 왕복 한 번(1 RTT)이 듭니다. 서울에서 미국 서버로 연결하면 데이터를 한 바이트도 보내기 전에 130ms를 씁니다. DevTools Network 탭의 "Initial connection"이 이 시간입니다. 연결을 재사용하고(아래 keep-alive), 미리 맺어 두는(`<link rel="preconnect">`) 최적화가 있는 이유입니다.

SYN만 잔뜩 보내고 답하지 않아 서버가 반쯤 열린 연결로 메모리를 채우게 만드는 공격을 SYN 플러드라고 합니다. 요즘 운영체제는 SYN 쿠키라는 방법으로 핸드셰이크가 끝나기 전까지 상태를 저장하지 않아 이를 버팁니다.

:::quiz syn-ack 클라이언트가 `SYN, seq=7000`을 보냈습니다. 서버가 돌려보내는 SYN+ACK의 확인 응답 번호(ack)는?
= 7001

**7001**입니다. 확인 응답 번호는 "다음에 기다리는 번호"입니다. SYN은 번호 하나를 차지하므로 7000을 받았으니 다음은 7001이라고 답합니다.
:::

## 순서 번호와 확인 응답

TCP는 보내는 모든 바이트에 번호를 붙입니다. 받는 쪽은 "몇 번 바이트까지 빠짐없이 받았으니 다음엔 몇 번을 달라"는 [[ACK]]를 보냅니다.

- 순서가 뒤바뀌어 도착하면, 받는 쪽은 앞의 빈칸이 채워질 때까지 뒤의 데이터를 버퍼에 들고 기다렸다가 순서대로 프로그램에 넘깁니다.
- 같은 데이터가 두 번 오면 번호를 보고 하나를 버립니다.
- 보내는 쪽은 ACK가 오지 않은 데이터를 지우지 않고 들고 있다가, 필요하면 다시 보냅니다.

## 사라진 데이터 되찾기: 재전송

보낸 세그먼트의 ACK가 정해진 시간 안에 오지 않으면, 보내는 쪽은 사라졌다고 보고 다시 보냅니다. 이게 [[재전송]]입니다. 기다리는 시간(재전송 타임아웃)은 지금까지 잰 RTT를 보고 정합니다. 가까운 서버면 짧게, 먼 서버면 길게 기다립니다.

시간이 다 갈 때까지 기다리면 느리니 지름길도 있습니다. 받는 쪽은 빈칸이 생기면 계속 "아직 1001번을 기다린다"는 같은 ACK를 보냅니다. 보내는 쪽이 같은 ACK를 세 번 더 받으면 시간을 기다리지 않고 바로 그 부분을 다시 보냅니다(빠른 재전송). 받는 쪽이 "1001~2000은 빠졌지만 2001~5000은 받았다"고 구체적으로 알리는 SACK 옵션도 있습니다.

순서 보장에는 대가가 있습니다. 앞의 세그먼트 하나가 사라지면, 그 뒤 데이터가 이미 도착해 있어도 빈칸이 채워질 때까지 프로그램은 아무것도 받지 못합니다. 줄 맨 앞의 한 명 때문에 뒷사람이 모두 멈추는 것을 [[헤드 오브 라인 블로킹]]이라고 합니다. 14장에서 HTTP/2가 TCP 연결 하나에 요청 여러 개를 섞어 보내는데, 패킷 하나가 사라지면 모든 요청이 함께 멈추는 문제가 이것이고, HTTP/3가 QUIC으로 옮겨 간 이유입니다.

:::quiz hol 서버가 보낸 세그먼트 1~5 가운데 2번만 사라지고 3, 4, 5번은 도착했습니다. 브라우저가 지금 소켓에서 읽을 수 있는 것은?
- [x] 1번만
- [ ] 1, 3, 4, 5번
- [ ] 아무것도 없음
- [ ] 1~5번 전부 (2번은 비워 둔 채로)

1번만입니다. TCP는 순서대로만 넘기므로 3, 4, 5번은 커널 버퍼에서 2번이 다시 올 때까지 기다립니다. 이것이 헤드 오브 라인 블로킹이고, HTTP/3가 QUIC으로 옮겨 간 이유입니다.
:::

## 받는 쪽이 넘치지 않게: 흐름 제어

빠른 서버가 느린 휴대폰에 마구 보내면, 휴대폰의 수신 버퍼가 넘쳐 데이터를 버리게 됩니다. 그래서 받는 쪽은 ACK를 보낼 때마다 "지금 내 버퍼에 이만큼 여유가 있다"는 [[수신 윈도]] 크기를 함께 알립니다. 보내는 쪽은 ACK를 받지 못한 데이터가 이 크기를 넘지 않게 보냅니다. 이게 [[흐름 제어]]입니다. 프로그램이 데이터를 읽어 가지 않아 버퍼가 가득 차면 윈도가 0이 되고, 보내는 쪽은 멈춥니다. 8장의 스트림에서 말한 backpressure가 네트워크 수준에서 일어나는 것입니다.

## 네트워크가 넘치지 않게: 혼잡 제어

받는 쪽이 여유가 있어도, 중간의 라우터들이 붐비면 패킷이 큐에서 넘쳐 버려집니다. 모두가 재전송까지 하면 더 붐벼서 아무도 못 보내는 상태가 됩니다. 1986년 인터넷은 실제로 이렇게 거의 멈췄습니다. 그 뒤 TCP에 [[혼잡 제어]]가 들어갔습니다.

보내는 쪽은 네트워크가 감당할 양을 스스로 추측해 [[혼잡 윈도]]로 들고 있고, 이 값과 수신 윈도 중 작은 만큼만 한 번에 보냅니다.

1. **[[슬로 스타트]]**: 새 연결은 작게 시작합니다. 요즘은 세그먼트 10개(약 14KB)입니다. ACK가 돌아올 때마다 늘려서, RTT마다 대략 두 배가 됩니다.
2. **혼잡 회피**: 어느 정도 커지면 조심스럽게, RTT마다 조금씩 늘립니다.
3. **손실을 만나면**: 네트워크가 붐빈다고 보고 윈도를 크게 줄였다가 다시 늘립니다.

![혼잡 윈도가 왕복마다 바뀌는 모습. 처음 몇 번은 두 배씩 늘고, 손실을 만나면 줄였다가 조금씩 다시 늘립니다. 숫자는 흐름을 보여 주려고 고른 예입니다](transport-cwnd.svg)

윈도를 어떻게 늘리고 줄일지는 알고리즘마다 다릅니다. Windows, macOS, Linux 모두 기본으로 CUBIC을 쓰고, Google이 만든 BBR은 손실 대신 측정한 대역폭과 RTT로 속도를 정해 손실이 잦은 무선망에서 강합니다.

프론트엔드에 바로 쓰이는 결과가 있습니다. 새 연결의 첫 왕복에는 약 14KB만 보낼 수 있습니다. 그래서 첫 화면에 꼭 필요한 HTML과 CSS를 14KB 안쪽으로 줄이면, 연결 직후 한 번의 왕복으로 첫 화면을 그릴 재료가 다 옵니다. "14KB 규칙"이라고 부르는 최적화입니다. 같은 이유로, 새 연결 여러 개보다 이미 데워진(윈도가 커진) 연결 하나를 재사용하는 편이 빠릅니다.

:::quiz slow-start 새 연결의 혼잡 윈도가 14KB이고 손실 없이 왕복마다 두 배가 된다면, 세 번째 왕복에서 한 번에 보낼 수 있는 양은 몇 KB일까요?
= 56 | 56kb

14 → 28 → **56KB**입니다. 처음 세 번의 왕복으로 모두 98KB를 보낼 수 있습니다. 새 연결은 느리게 시작하니, 이미 윈도가 커진 연결을 재사용하는 편이 빠릅니다.
:::

## 연결 끊기: FIN, TIME_WAIT, RST

TCP는 양방향이라 끊을 때도 각자 "나는 보낼 게 끝났다"를 알립니다. 한쪽이 [[FIN]]을 보내고 상대가 ACK하고, 상대도 다 보낸 뒤 FIN을 보내고 이쪽이 ACK합니다. 네 번의 메시지라 4-way 종료라고 부릅니다.

먼저 끊은 쪽은 마지막 ACK를 보낸 뒤 바로 사라지지 않고 잠시(운영체제에 따라 30초~4분) [[TIME_WAIT]] 상태로 머뭅니다. 마지막 ACK가 사라졌을 때 상대가 다시 보낼 FIN에 답하고, 늦게 도착한 옛 연결의 패킷이 같은 5-튜플의 새 연결에 섞이지 않게 하려는 것입니다. 짧은 연결을 엄청나게 많이 맺고 끊는 클라이언트는 TIME_WAIT가 쌓여 임시 포트가 바닥나기도 합니다. 연결을 재사용하면 피할 수 있습니다.

정중한 종료와 달리 [[RST]]는 "이 연결은 없던 걸로"라는 즉시 종료입니다. 상대가 갑자기 죽었거나, 없는 연결에 데이터가 왔거나, 아무도 듣지 않는 포트에 SYN이 왔을 때 보냅니다.

이 동작들이 우리가 매일 보는 오류 메시지의 정체입니다.

| 오류 | 실제로 일어난 일 | 흔한 원인 |
| --- | --- | --- |
| [[ECONNREFUSED]] (연결 거부) | SYN을 보냈더니 RST가 돌아옴 | 그 포트에서 듣는 프로그램이 없음. 서버가 꺼졌거나 포트 번호가 틀림 |
| [[ETIMEDOUT]] (시간 초과) | SYN을 보냈는데 아무 답이 없음 | 방화벽이 패킷을 조용히 버림, 주소가 틀림, 서버가 멈춤 |
| [[ECONNRESET]] (연결 재설정) | 연결 중에 상대가 RST를 보냄 | 상대 프로세스가 죽음, 프록시나 로드 밸런서의 시간 초과 |
| EHOSTUNREACH | 목적지로 가는 길이 없음 | 라우팅 문제, 네트워크 끊김 |
| EPIPE | 이미 닫힌 연결에 썼음 | 상대가 먼저 끊었는데 계속 씀 |
| EADDRINUSE | 이미 쓰이고 있는 포트에 bind하려 함 | 같은 서버가 이미 떠 있음 (16장) |

"거부"와 "시간 초과"의 차이만 알아도 디버깅이 빨라집니다. 거부는 "그 컴퓨터까지는 갔는데 그 포트에 아무도 없다", 시간 초과는 "가는 길이나 문 앞에서 막혔다"입니다.

![거부는 RST라는 답이 와서 바로 끝나고, 시간 초과는 답이 없어 기다리다 끝납니다](transport-errors.svg)

:::quiz refused `curl https://example.com:8443`이 기다림 없이 바로 "Connection refused"로 끝났습니다. 여기서 알 수 있는 것은?
- [ ] 방화벽이 SYN을 조용히 버렸다
- [ ] 서버가 너무 느려서 응답을 기다리다 포기했다
- [x] 그 컴퓨터까지는 닿았는데 8443번에서 듣는 프로그램이 없다
- [ ] 서버의 인증서가 만료되었다

RST가 돌아왔다는 뜻입니다. 패킷은 그 컴퓨터까지 갔고, 커널이 "그 포트에는 아무도 없다"고 답했습니다. 방화벽이 버리면 답이 없어 시간 초과가 나고, 인증서 문제는 연결이 맺어진 뒤 TLS에서 납니다.
:::

## TCP 상태

`netstat`이나 `ss`로 연결을 보면 상태가 나옵니다. 자주 보는 것들입니다.

| 상태 | 뜻 |
| --- | --- |
| LISTEN | 서버가 연결을 기다리는 중 |
| SYN_SENT | 클라이언트가 SYN을 보내고 답을 기다리는 중 |
| ESTABLISHED | 연결되어 데이터를 주고받는 중 |
| CLOSE_WAIT | 상대는 끊었는데 내 프로그램이 아직 `close`를 안 함 |
| TIME_WAIT | 내가 먼저 끊고 잠시 기다리는 중 |

[[CLOSE_WAIT]]가 계속 쌓이면 내 프로그램의 버그입니다. 상대가 연결을 끝냈는데 프로그램이 소켓을 닫지 않아 파일 디스크립터가 새고 있다는 뜻이고, 결국 `EMFILE`로 이어집니다.

:::quiz close-wait 서버에서 `ss -tan`을 보니 CLOSE_WAIT 상태가 수천 개 쌓여 계속 늘어납니다. 가장 먼저 의심할 것은?
- [ ] 클라이언트들이 FIN을 보내지 않는다
- [ ] 네트워크가 혼잡해서 ACK가 사라진다
- [ ] TIME_WAIT가 너무 짧게 설정되었다
- [x] 내 프로그램이 상대가 끊은 소켓을 `close`하지 않는다

CLOSE_WAIT는 상대가 FIN을 보내 끊었는데 내 프로그램이 아직 소켓을 닫지 않은 상태입니다. 쌓인다면 내 코드가 소켓을 새게 두는 것이고, 결국 파일 디스크립터가 바닥나 `EMFILE`이 납니다.
:::

## 연결 재사용: keep-alive와 연결 풀

핸드셰이크에 RTT가 들고, 새 연결은 슬로 스타트로 느리게 시작하니, 연결은 맺어 두고 여러 번 쓰는 게 이득입니다. HTTP는 응답 뒤에도 연결을 닫지 않고 다음 요청에 재사용합니다. 이게 HTTP [[keep-alive]]입니다(14장). 서버 쪽 프로그램도 데이터베이스나 다른 API와의 연결을 미리 여러 개 맺어 두고 돌려 쓰는데, 이걸 [[연결 풀]]이라고 합니다.

TCP 자체에도 keepalive라는 기능이 있어 헷갈립니다. 이건 오랫동안 조용한 연결에 작은 탐색 패킷을 보내 상대가 아직 살아 있는지 확인하는 기능입니다. 이름은 같지만 하는 일이 다릅니다.

작은 데이터를 보낼 때 TCP는 조금 모아서 보내려고 잠깐 기다립니다(Nagle 알고리즘). 대량 전송에는 효율적이지만, 키 입력이나 게임처럼 작은 메시지를 바로 보내야 하면 지연이 됩니다. 그래서 실시간 프로그램과 많은 HTTP 서버는 `TCP_NODELAY` 옵션으로 이걸 끕니다.

## UDP: 보내고 끝

[[UDP]](User Datagram Protocol)는 TCP가 하는 일을 거의 하지 않습니다. 헤더는 8바이트(보내는 포트, 받는 포트, 길이, 체크섬)가 전부입니다. 연결도, 재전송도, 순서 보장도, 흐름 제어도 없습니다. 보낸 [[데이터그램]] 하나가 그대로 하나로 도착하거나, 사라집니다. 대신 메시지의 경계가 지켜지고, 핸드셰이크 없이 바로 보내니 빠릅니다.

| | TCP | UDP |
| --- | --- | --- |
| 연결 | 핸드셰이크로 맺음 | 없음 |
| 신뢰성 | 재전송으로 보장 | 없음. 사라지면 끝 |
| 순서 | 보장 | 없음 |
| 단위 | 바이트 스트림 (경계 없음) | 데이터그램 (경계 있음) |
| 헤더 | 20바이트 이상 | 8바이트 |
| 쓰는 곳 | 웹(HTTP/1.1, HTTP/2), SSH, 이메일, 데이터베이스 | DNS, 화상 통화, 게임, 실시간 방송, DHCP, 시간 맞추기(NTP), QUIC |

UDP를 쓰는 이유는 "늦게 오는 데이터는 안 오느니만 못한" 경우가 있어서입니다. 화상 통화에서 0.5초 전의 음성 패킷을 재전송받아 봐야 쓸모가 없습니다. 그냥 건너뛰는 게 낫습니다. 게임도 지난 위치 대신 새 위치가 중요합니다. DNS는 질문과 답이 패킷 하나로 끝나니 연결을 맺는 비용이 아깝습니다. 9장 맨 앞 그림의 왕복 1, 이 페이지의 이름을 묻는 질문도 UDP 패킷 하나로 갑니다. 신뢰성이 필요하면 그 프로그램이 필요한 만큼만 UDP 위에 직접 만듭니다.

## QUIC: UDP 위에 다시 만든 TCP

TCP는 40년 넘게 고쳐 왔지만 바꾸기가 아주 어렵습니다. 운영체제 커널 안에 있어서 모든 사용자의 OS가 업데이트되어야 하고, 길 위의 방화벽과 NAT 장비들이 "TCP는 이렇게 생겼다"고 가정하고 있어 새 기능을 넣으면 패킷이 막히곤 합니다.

그래서 Google이 UDP 위에 새 전송 프로토콜을 만들었고, 2021년 [[QUIC]](RFC 9000)으로 표준이 되었습니다. QUIC은 TCP가 하던 일(연결, 재전송, 혼잡 제어)을 다 하면서 몇 가지를 고쳤습니다.

- **사용자 공간에서 동작**: 커널이 아니라 브라우저와 서버 프로그램 안에 구현되어 있어, 앱 업데이트만으로 개선을 배포합니다. 길 위의 장비에는 그냥 UDP로 보입니다.
- **TLS 1.3이 들어 있음**: 연결과 암호화 핸드셰이크를 합쳐 1 RTT면 데이터를 보내기 시작하고, 다시 접속할 때는 0 RTT로 바로 보냅니다(14장).
- **스트림마다 독립**: 연결 하나에 여러 스트림을 두되, 한 스트림의 패킷이 사라져도 다른 스트림은 멈추지 않습니다. TCP의 헤드 오브 라인 블로킹이 없습니다.
- **연결 ID**: 연결을 5-튜플이 아니라 ID로 구분해서, Wi-Fi에서 LTE로 바뀌어 IP가 바뀌어도 연결이 이어집니다.

HTTP/3가 바로 QUIC 위의 HTTP입니다. Google, YouTube, Cloudflare, Meta는 이미 대부분의 트래픽을 QUIC으로 보냅니다. 브라우저는 처음에는 TCP로 접속하고, 서버가 응답 헤더(`Alt-Svc`)로 "HTTP/3도 된다"고 알려 주면 다음 요청부터 QUIC으로 옮겨 갑니다. 이 사이트 앞의 Caddy도 HTTP/3를 기본으로 켜 두지만, 서버 방화벽이 UDP 443을 막고 있으면 브라우저는 그냥 TCP를 계속 씁니다.

:::quiz migrate 휴대폰이 Wi-Fi에서 LTE로 바뀌어 IP 주소가 바뀌었는데도 HTTP/3 연결은 끊기지 않았습니다. 이유는?
- [x] QUIC은 연결을 5-튜플이 아니라 연결 ID로 구분해서
- [ ] LTE와 Wi-Fi가 같은 IP를 나눠 써서
- [ ] TCP가 바뀐 IP를 자동으로 다시 연결해서
- [ ] 서버가 휴대폰의 MAC 주소로 연결을 알아봐서

연결 ID 덕분입니다. TCP는 5-튜플 중 IP 하나만 바뀌어도 다른 연결이라 새로 맺어야 합니다. QUIC은 패킷마다 연결 ID를 실어 보내므로 주소가 바뀌어도 같은 연결로 이어 갑니다. MAC 주소는 첫 홉을 넘어가지 않습니다.
:::

## 다시 장면으로: 연결 하나가 이 페이지를 실어 오기까지

맨 앞 그림은 이제 이렇게 읽힙니다. 브라우저가 소켓을 만들어 `connect`를 부르자, 노트북의 운영체제가 임시 포트를 골라 SYN을 보냈습니다. 서버에서는 443번을 `listen`하던 Caddy가 핸드셰이크를 마친 연결을 `accept`로 받아 이 연결만의 소켓을 얻었습니다. 그 뒤 HTML은 1460바이트씩 번호가 붙은 세그먼트로 쪼개져 왔습니다. 처음에는 14KB만, 왕복마다 두 배로 늘려 가며 보냈고, 사라진 조각은 다시 받아 빈칸을 채운 뒤 순서대로 브라우저에 건넸습니다. 같은 연결로 CSS와 `app.js`도 이어서 받습니다.

그런데 하나를 건너뛰었습니다. `connect`를 부르려면 54.116.117.190이라는 IP 주소를 알아야 합니다. 주소창에 적은 건 `cs.mlnl.54-116-117-190.sslip.io`라는 이름뿐이었습니다. 이 이름은 언제, 누구에게 물어서 숫자가 되었을까요? 9장 그림의 왕복 1, 이 모든 일보다 먼저 일어난 일이 13장의 DNS입니다.

## 프론트엔드와 이어지는 곳

- 개발 서버에 붙지 못할 때 `ECONNREFUSED`면 서버가 안 떠 있거나 포트가 틀린 것이고, `ETIMEDOUT`이면 방화벽이나 주소 문제입니다.
- DevTools Network 탭에서 Connection ID 칸을 켜면 요청들이 같은 연결을 재사용하는지 보입니다. "Initial connection"이 있는 요청만 새 연결을 맺은 것입니다.
- 첫 화면에 필요한 HTML과 핵심 CSS는 압축 후 14KB 안쪽을 목표로 합니다.
- WebSocket은 TCP 위에 메시지 경계를 만든 프로토콜이고, WebRTC의 음성·영상은 UDP 위에서 갑니다. WebTransport는 QUIC 위에서 갑니다.
- 서버에서 외부 API를 부를 때 매번 새 연결을 맺지 말고 연결을 재사용합니다. Node의 `fetch`(undici)는 기본으로 연결 풀을 씁니다.

## 용어 정리

:::terms
- 전송 계층 (transport layer) — 양 끝 컴퓨터의 프로그램과 프로그램 사이에서 데이터를 전달하는 계층. 포트로 프로그램을 구분하고, TCP는 신뢰성까지 맡습니다.
- 포트 (port) — 한 컴퓨터 안에서 통신하는 프로그램을 구분하는 0~65535의 번호입니다.
- 잘 알려진 포트 (well-known port) — 0~1023번 포트. 80(HTTP), 443(HTTPS), 22(SSH)처럼 표준 서비스에 정해져 있습니다.
- 임시 포트 (ephemeral port) — 클라이언트가 연결할 때 운영체제가 임시로 골라 주는 보내는 쪽 포트입니다.
- 소켓 (socket) — 네트워크 통신의 한쪽 끝을 나타내는 커널 객체. 프로그램은 파일 디스크립터로 다룹니다.
- 5-튜플 (5-tuple) — 프로토콜, 내 IP, 내 포트, 상대 IP, 상대 포트. TCP 연결 하나를 구분하는 다섯 값입니다.
- TCP (Transmission Control Protocol) — 연결을 맺고 재전송, 순서 보장, 흐름 제어, 혼잡 제어로 믿을 수 있는 바이트 스트림을 만드는 전송 계층 프로토콜입니다.
- 세그먼트 (segment) — TCP 헤더를 붙인 데이터 단위입니다.
- 시퀀스 번호 (sequence number) — TCP가 보내는 바이트마다 붙이는 번호. 순서 맞추기와 빠진 데이터 찾기에 씁니다.
- SYN — TCP 연결을 시작하자는 표시(플래그). 시작 시퀀스 번호를 알립니다.
- ACK — "여기까지 받았다"는 확인 응답 표시와 번호입니다.
- FIN — "나는 보낼 데이터가 끝났다"는 TCP 연결 종료 표시입니다.
- RST — 연결을 즉시 끊는 TCP 표시. 아무도 듣지 않는 포트에 연결하면 이걸 받습니다.
- 3-way 핸드셰이크 (three-way handshake) — SYN, SYN+ACK, ACK 세 메시지로 TCP 연결을 맺는 과정. 1 RTT가 듭니다.
- 재전송 (retransmission) — 확인 응답이 오지 않은 데이터를 다시 보내는 것입니다.
- 헤드 오브 라인 블로킹 (head-of-line blocking) — 앞의 데이터 하나가 늦거나 사라져서 뒤의 데이터까지 모두 기다리는 현상입니다.
- 수신 윈도 (receive window) — 받는 쪽이 지금 더 받을 수 있다고 알리는 데이터 양입니다.
- 흐름 제어 (flow control) — 받는 쪽의 버퍼가 넘치지 않게 보내는 양을 수신 윈도 안으로 제한하는 것입니다.
- 혼잡 제어 (congestion control) — 네트워크가 붐비지 않게 보내는 쪽이 전송 속도를 스스로 조절하는 것입니다.
- 혼잡 윈도 (congestion window) — 네트워크가 감당할 거라고 보내는 쪽이 추측한, 한 번에 보낼 수 있는 데이터 양입니다.
- 슬로 스타트 (slow start) — 새 TCP 연결이 작은 혼잡 윈도로 시작해 RTT마다 두 배로 늘려 가는 단계. 첫 왕복에는 약 14KB를 보냅니다.
- TIME_WAIT — 먼저 연결을 끊은 쪽이 늦게 오는 패킷을 처리하려고 잠시 머무는 TCP 상태입니다.
- CLOSE_WAIT — 상대는 연결을 끊었는데 내 프로그램이 아직 소켓을 닫지 않은 상태. 쌓이면 프로그램의 버그입니다.
- ECONNREFUSED — 연결하려는 포트에서 아무도 듣고 있지 않아 RST를 받았다는 오류입니다.
- ETIMEDOUT — 연결 요청이나 데이터에 정해진 시간 안에 아무 답이 없다는 오류. 방화벽이 패킷을 버리는 경우가 흔합니다.
- ECONNRESET — 연결 도중 상대가 RST로 연결을 끊었다는 오류입니다.
- keep-alive — HTTP에서 응답 뒤에도 TCP 연결을 닫지 않고 다음 요청에 재사용하는 것. TCP에는 같은 이름의 생존 확인 기능도 있습니다.
- 연결 풀 (connection pool) — 미리 맺어 둔 연결 여러 개를 돌려 쓰는 구조. 데이터베이스와 HTTP 클라이언트가 씁니다.
- UDP (User Datagram Protocol) — 연결, 재전송, 순서 보장 없이 데이터그램을 보내기만 하는 가벼운 전송 계층 프로토콜입니다.
- 데이터그램 (datagram) — UDP처럼 독립적으로 보내지는 메시지 단위. 경계가 지켜집니다.
- QUIC — UDP 위에서 연결, 재전송, 혼잡 제어, TLS 1.3 암호화, 독립 스트림을 제공하는 전송 프로토콜. HTTP/3가 씁니다.
:::

## 직접 해보기

:::practice listen 내 컴퓨터에서 듣고 있는 포트 찾기
지금 내 컴퓨터에서 연결을 기다리고 있는 포트와 그 프로그램을 모두 찾아봅니다. 개발 서버를 하나 띄우고 목록에 생기는지 확인합니다. 각 포트가 어느 주소(`127.0.0.1`, `*`, `::`)에서 듣고 있는지도 봅니다. 그 차이는 16장에서 다룹니다.

```sh macOS
lsof -iTCP -sTCP:LISTEN -n -P
```

```sh Linux
ss -tlnp
```

```powershell Windows (PowerShell)
Get-NetTCPConnection -State Listen | Sort-Object LocalPort | Select-Object LocalAddress, LocalPort, OwningProcess, @{n="Name";e={(Get-Process -Id $_.OwningProcess).ProcessName}}
```
:::

:::practice handshake Wireshark로 TCP 한 생애 보기
Wireshark에서 `tcp.port == 80`으로 걸러 놓고 `curl http://example.com`을 실행합니다. SYN, SYN+ACK, ACK, HTTP 요청과 응답, FIN, ACK를 차례로 찾고, 각 패킷의 시퀀스 번호와 확인 응답 번호가 어떻게 이어지는지 적습니다. 통계 메뉴의 Flow Graph로 보면 이 장의 그림과 같은 모양이 나옵니다.
:::

:::practice errors ECONNREFUSED와 ETIMEDOUT 만들어 보기
아무도 듣지 않는 내 컴퓨터의 포트와, 패킷을 버리는 주소로 각각 연결해 오류가 어떻게 다르고 얼마나 걸리는지 봅니다. `10.255.255.1`은 대부분의 집 네트워크에서 응답이 없는 주소입니다.

```js errors.mjs
import net from "node:net";
function tryConnect(host, port) {
  const t = Date.now();
  const s = net.connect({ host, port, timeout: 5000 });
  s.on("connect", () => { console.log(host, port, "연결됨"); s.end(); });
  s.on("timeout", () => { console.log(host, port, "시간 초과", Date.now() - t, "ms"); s.destroy(); });
  s.on("error", (e) => console.log(host, port, e.code, Date.now() - t, "ms"));
}
tryConnect("127.0.0.1", 9);         // 거부: 바로 실패
tryConnect("10.255.255.1", 80);     // 시간 초과: 기다리다 실패
tryConnect("example.com", 80);      // 성공
```
:::

:::practice states 연결 상태 늘어놓기
브라우저로 사이트 몇 개를 연 직후와 1분 뒤에 TCP 연결 상태를 세어 봅니다. ESTABLISHED와 TIME_WAIT가 어떻게 변하는지 봅니다.

```sh macOS
netstat -an -p tcp | awk '{print $6}' | sort | uniq -c | sort -rn
```

```sh Linux
ss -tan | awk 'NR>1 {print $1}' | sort | uniq -c | sort -rn
```

```powershell Windows (PowerShell)
Get-NetTCPConnection | Group-Object State | Select-Object Count, Name
```
:::

:::practice udp UDP로 메시지 주고받기
UDP 서버와 클라이언트를 Node로 만들어, 연결 없이 데이터그램이 오가는 걸 봅니다. 서버를 끈 채로 클라이언트를 보내 보면 TCP와 달리 아무 오류 없이 사라지는 것도 확인합니다.

```js udp.mjs
import dgram from "node:dgram";
const server = dgram.createSocket("udp4");
server.on("message", (msg, from) => console.log("받음:", msg.toString(), "보낸 곳:", from.address, from.port));
server.bind(41234, () => {
  const client = dgram.createSocket("udp4");
  for (const word of ["하나", "둘", "셋"]) client.send(word, 41234, "127.0.0.1");
  setTimeout(() => { client.close(); server.close(); }, 200);
});
```
:::

## 장 전체 문제

:::quiz caddy-sockets 이 페이지를 여는 동안 서버의 Caddy가 가진 TCP 소켓에 대해 맞는 것은?
- [ ] 443번 LISTEN 소켓 하나로 모든 브라우저와 대화한다
- [x] 443번 LISTEN 소켓이 하나 있고, 연결마다 `accept`가 돌려준 소켓이 따로 있다
- [ ] 연결마다 443이 아닌 새 포트를 열어 브라우저에 알려 준다
- [ ] 공유기마다 소켓이 하나씩 있어서 같은 집의 기기들은 소켓을 나눠 쓴다

LISTEN 소켓은 접수 창구이고, 실제 대화는 `accept`가 연결마다 돌려주는 소켓으로 합니다. 이 소켓들은 모두 서버 쪽 포트가 443이고, 상대 IP와 포트로 구분됩니다. 같은 집의 노트북과 휴대폰도 NAT가 바깥쪽 포트를 다르게 붙이니 서로 다른 연결입니다.
:::

:::quiz html-rtts 이 페이지의 HTML이 압축해서 40KB라고 합니다. 새 연결의 혼잡 윈도가 14KB에서 시작해 왕복마다 두 배가 된다면, HTML을 다 보내는 데 데이터 왕복이 최소 몇 번 필요할까요? TLS가 차지하는 양은 무시합니다.
= 2 | 2번 | 두번

**2번**입니다. 첫 왕복에 14KB, 둘째 왕복에 28KB를 보내 모두 42KB가 되니 40KB가 다 갑니다. HTML이 14KB 안쪽이었다면 한 번이면 됐습니다. 핸드셰이크와 TLS의 왕복은 따로 듭니다.
:::

## 스스로 점검

:::qa 서버의 443번 포트 하나로 수만 개의 연결을 동시에 받을 수 있는 이유는?
TCP 연결은 프로토콜, 양쪽 IP, 양쪽 포트의 5-튜플로 구분됩니다. 서버 쪽 IP와 포트는 같아도 클라이언트마다 IP나 임시 포트가 달라 연결마다 5-튜플이 다르고, 커널은 `accept` 때마다 연결별 소켓을 따로 만듭니다.
:::

:::qa 3-way 핸드셰이크에서 각 메시지가 하는 일과, 이게 웹 성능에 주는 영향은?
SYN으로 클라이언트가 시작 번호를 알리고, SYN+ACK로 서버가 그걸 받았다고 확인하며 자기 시작 번호를 알리고, ACK로 클라이언트가 서버의 번호를 확인합니다. 데이터를 보내기 전에 1 RTT가 들어서, 먼 서버일수록 새 연결이 비쌉니다. 연결 재사용과 preconnect로 줄입니다.
:::

:::qa `ECONNREFUSED`와 `ETIMEDOUT`의 차이를 패킷 수준에서 설명하고, 각각 무엇을 먼저 의심해야 하나요?
ECONNREFUSED는 SYN에 RST가 돌아온 것으로, 컴퓨터까지는 닿았지만 그 포트에서 듣는 프로그램이 없다는 뜻입니다. 서버가 떠 있는지, 포트 번호가 맞는지 봅니다. ETIMEDOUT은 아무 답도 없는 것으로, 방화벽이 패킷을 버리거나 주소나 경로가 틀린 경우를 먼저 봅니다.
:::

:::qa 흐름 제어와 혼잡 제어는 각각 무엇을 보호하나요?
흐름 제어는 받는 쪽의 버퍼가 넘치지 않게(수신 윈도), 혼잡 제어는 중간 네트워크의 라우터들이 넘치지 않게(혼잡 윈도) 보내는 양을 제한합니다. 실제로 보내는 양은 둘 중 작은 쪽입니다.
:::

:::qa 서버에서 `CLOSE_WAIT` 상태의 연결이 계속 늘어납니다. 무엇이 문제인가요?
상대는 연결을 끝냈는데 내 프로그램이 소켓을 `close`하지 않고 있다는 뜻입니다. 응답을 다 쓴 뒤 연결을 닫지 않거나 오류 경로에서 정리를 빠뜨린 버그이고, 내버려 두면 파일 디스크립터가 바닥나 `EMFILE`이 납니다.
:::

:::qa 화상 통화와 게임이 TCP 대신 UDP를 쓰는 이유는? HTTP/3는 왜 UDP 위의 QUIC을 쓰나요?
늦게 도착한 옛 데이터는 쓸모가 없어서, 재전송을 기다리느라 멈추는 것보다 잃어버리고 넘어가는 편이 낫기 때문입니다. HTTP/3는 신뢰성이 필요하지만, 커널과 길 위 장비 때문에 바꾸기 어려운 TCP 대신 UDP 위에서 연결, 암호화, 독립 스트림을 새로 구현해 헤드 오브 라인 블로킹과 느린 핸드셰이크를 없앴습니다.
:::
