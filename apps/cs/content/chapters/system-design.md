23장은 블로그 API의 요청 수 제한에 붙은 주석 하나로 끝났습니다. "프로세스 하나로 도는 개인 서버라 메모리로 충분합니다." 이 블로그의 사용자가 1000배로 늘면 무엇이 먼저 무너지고, 무엇을 바꿔야 할까요?

![지금의 서버 한 대와, 1000배가 되었을 때의 모양. 진한 칸은 앱이 안에 품고 있던 상태이고, 서버를 늘리려면 앱 밖의 공유 저장소로 옮겨야 합니다](system-design-scene.svg)

17장까지 서버 한 대 위에 여러 프로그램을 띄우는 법을 봤습니다. 이 사이트 같은 개인 서비스는 그걸로 충분합니다. 하지만 사용자가 늘면 한 대로는 버틸 수 없고, 그 한 대가 죽으면 서비스 전체가 멈춥니다. 이 장은 서비스가 커질 때 생기는 문제와 그 해결책들을 봅니다. 면접의 "시스템 설계" 질문이 이 내용이고, 앞 장들의 거의 모든 개념이 여기서 다시 쓰입니다.

## 한 대에서 수백만 명까지

전형적인 웹 서비스가 커 가는 순서를 따라가 봅니다. 각 단계는 앞 단계에서 생긴 병목 하나를 푸는 것입니다.

1. **서버 한 대**: 웹 서버, 앱, 데이터베이스가 한 컴퓨터에. 이 사이트가 지금 이 단계입니다.
2. **데이터베이스 분리**: 앱과 DB가 CPU와 메모리를 다투지 않게 DB를 다른 서버로(21장).
3. **캐시**: 자주 읽는 데이터를 Redis에 두어 DB 읽기를 줄입니다(17장).
4. **CDN**: 정적 파일을 사용자 가까이에서 줍니다(17장).
5. **앱 서버 여러 대 + 로드 밸런서**: 앱을 무상태로 만들고 여러 대로 늘립니다(이 장).
6. **DB 읽기 복제본**: 읽기를 복제본으로 나눕니다(22장).
7. **메시지 큐와 워커**: 오래 걸리는 일을 요청 밖으로 뺍니다(17장).
8. **샤딩**: 쓰기와 데이터 양이 DB 한 대를 넘으면 나눕니다(22장).
9. **여러 리전**: 다른 대륙의 사용자와 데이터센터 전체의 장애에 대비합니다(15장).

중요한 건 순서입니다. 처음부터 9단계로 시작하면 복잡함만 늘고 얻는 게 없습니다. 실제로 측정해서 병목이 보일 때 그 병목만 풉니다.

:::quiz first-step 이 블로그의 글 목록 API가 요즘 느려졌습니다. 가장 먼저 할 일은?
- [ ] 데이터베이스를 샤딩한다
- [x] 어디가 느린지 측정해서, 찾은 병목 하나만 푼다
- [ ] 마이크로서비스로 나눈다
- [ ] 여러 리전에 서버를 둔다

측정이 먼저입니다. 느린 이유가 인덱스가 빠진 쿼리 하나일 수도, N+1일 수도(21장) 있습니다. 병목이 보이기 전에 큰 구조를 들이면 복잡함만 늘어납니다.
:::

## 확장: 더 크게, 또는 더 많이

부하가 늘었을 때 대응하는 방법은 둘입니다.

| | [[수직 확장]] (scale up) | [[수평 확장]] (scale out) |
| --- | --- | --- |
| 방법 | 서버를 더 큰 것으로 (CPU, 메모리 더) | 서버를 더 여러 대로 |
| 장점 | 코드를 바꿀 필요 없음. 단순 | 한계가 거의 없음. 한 대가 죽어도 버팀 |
| 단점 | 한계가 있고 큰 서버는 비쌈. 그 한 대가 죽으면 끝 | 앱이 여러 대에서 돌 수 있게 설계해야 함 |

수평 확장을 하려면 앱 서버가 [[무상태|무상태 서버]]여야 합니다. 요청 사이의 상태(세션, 업로드 파일, 메모리 캐시)를 앱 서버 안에 두면, 다음 요청이 다른 서버로 갔을 때 그 상태가 없습니다(17장의 "로그인이 자꾸 풀림"). 상태는 DB, Redis, 오브젝트 스토리지 같은 공유 저장소로 빼고, 앱 서버는 언제 지우고 새로 띄워도 되는 소모품으로 만듭니다. 그러면 로드 밸런서 뒤에 몇 대든 붙이고 뗄 수 있습니다.

:::quiz split-limit 블로그 API를 로드 밸런서 뒤에 3대로 늘렸더니, "로그인은 IP마다 15분에 8번"이던 제한이 사실상 24번이 되었습니다. 이유는?
- [ ] 로드 밸런서가 IP를 바꿔서
- [ ] 서버가 늘면 15분이 5분으로 줄어서
- [x] 계수기가 각 프로세스의 메모리에 있어서 서버마다 따로 세서
- [ ] 쿠키가 서버마다 달라서

서버마다 따로 셉니다. 요청이 세 서버에 흩어지면 각자 8번씩 허락합니다. 계수기를 Redis 같은 공유 저장소로 옮겨야 모든 서버가 같은 숫자를 봅니다.
:::

:::quiz cookie-scales 반대로 API를 여러 대로 늘려도 관리자 로그인은 풀리지 않습니다. 이유는?
- [x] 쿠키가 서명된 토큰이라, 같은 비밀 키를 가진 서버라면 어느 서버든 서명만 확인하면 되어서
- [ ] 로드 밸런서가 같은 사용자를 늘 같은 서버로 보내서
- [ ] 세션이 SQLite에 저장되어 있어서
- [ ] 브라우저가 서버마다 쿠키를 따로 보내서

서명된 토큰이기 때문입니다. 서버에 세션 저장소가 없으니 어느 서버가 받아도 같은 비밀 키로 HMAC을 다시 계산해 확인합니다. 처음부터 무상태로 만든 부분은 늘릴 때 손댈 것이 없습니다.
:::

## 가용성: 얼마나 안 멈추나

[[가용성]]은 서비스가 정상적으로 쓰일 수 있는 시간의 비율입니다. 보통 9의 개수로 말합니다.

| 가용성 | 1년에 멈춰도 되는 시간 | 한 달에 |
| --- | --- | --- |
| 99% (two nines) | 3.65일 | 7.2시간 |
| 99.9% | 8.8시간 | 43분 |
| 99.99% | 53분 | 4.3분 |
| 99.999% | 5분 | 26초 |

9를 하나 늘릴 때마다 비용과 복잡도가 크게 늘어납니다. 그래서 서비스마다 목표를 정합니다(SLO). 개인 블로그에 99.99%는 필요 없지만 결제 시스템에는 필요합니다.

가용성의 적은 [[단일 장애 지점]](SPOF)입니다. 그게 죽으면 전체가 멈추는 하나뿐인 부품입니다. 이 사이트에서는 Lightsail 서버 한 대, 그 위의 Caddy 하나가 단일 장애 지점입니다. 없애려면 같은 일을 하는 것을 둘 이상 두고(이중화), 하나가 죽으면 다른 쪽이 자동으로 넘겨받게 합니다(장애 조치). 로드 밸런서 뒤의 여러 앱 서버, DB 주 서버와 복제본, 여러 가용 영역이 그 예입니다. 로드 밸런서 자체도 둘 이상 둡니다.

:::quiz uptime-month 가용성 목표가 99.9%라면 30일짜리 한 달에 최대 몇 분까지 멈춰도 될까요? (분, 반올림)
= 43 | 43분

30일 × 24시간 × 60분 × 0.001 = 43.2분, 약 **43분**입니다. 서버 재시작과 배포가 몇 번 겹치면 금방 쓰는 시간이라, 무중단 배포(17장)가 필요해집니다.
:::

:::quiz not-spof 이 사이트에서 단일 장애 지점이 아닌 것은?
- [ ] Lightsail 가상 머신
- [ ] 모든 요청을 받는 Caddy 컨테이너
- [ ] 이 책을 내보내는 nginx 컨테이너
- [x] 배포를 맡는 GitHub Actions

GitHub Actions입니다. 멈추면 새 배포를 못 할 뿐, 이미 떠 있는 사이트는 계속 돕니다. 나머지는 하나뿐이라, 멈추면 사이트의 전부나 일부가 멈춥니다.
:::

## 분산 시스템은 왜 어려운가

서버가 여러 대가 되는 순간 [[분산 시스템]]이 됩니다. 여러 컴퓨터가 네트워크로 메시지를 주고받으며 하나처럼 동작하는 시스템입니다. 한 컴퓨터 안에서는 당연하던 것들이 사라집니다.

- **네트워크는 믿을 수 없습니다.** 메시지가 사라지고, 늦고, 두 번 오고, 순서가 바뀝니다(11장, 12장).
- **"응답이 없다"가 무슨 뜻인지 모릅니다.** 상대가 죽었는지, 느린지, 요청은 처리했는데 응답만 사라졌는지 구분할 수 없습니다.
- **일부만 고장 납니다.** 한 컴퓨터는 전부 돌거나 전부 멈추지만, 분산 시스템은 일부 서버만 죽거나 일부 회선만 끊깁니다.
- **시계가 맞지 않습니다.** 서버마다 시계가 조금씩 다르고 NTP로 맞춰도 오차가 있어서, "어느 일이 먼저 일어났나"를 시각으로 정하기 어렵습니다.

1990년대에 정리된 "분산 컴퓨팅의 오류"라는 목록이 있습니다. 네트워크는 믿을 수 있다, 지연은 0이다, 대역폭은 무한하다, 네트워크는 안전하다… 처음 분산 시스템을 만드는 사람이 무심코 하는 가정들이고, 전부 틀렸습니다.

## CAP 정리와 일관성

데이터를 여러 서버에 복제하면(22장) 피할 수 없는 선택이 생깁니다. 서버 사이의 네트워크가 끊겨 둘로 갈라졌다고 해 봅니다(네트워크 분할). 양쪽에 각각 쓰기 요청이 오면?

- **일관성을 고르면**: 다른 쪽과 확인할 수 없으니 요청을 거절합니다. 틀린 값은 주지 않지만, 그동안 서비스 일부가 멈춥니다.
- **가용성을 고르면**: 양쪽이 각자 받아 처리합니다. 서비스는 계속되지만, 두 쪽의 데이터가 잠시 달라지고 나중에 합쳐야 합니다.

이게 [[CAP 정리]]입니다. 일관성(Consistency), 가용성(Availability), 분할 내성(Partition tolerance) 중 둘만 가질 수 있다고 흔히 말하지만, 정확히는 "네트워크 분할은 언젠가 반드시 일어나니, 그때 일관성과 가용성 중 무엇을 지킬지 골라야 한다"는 뜻입니다. 분할이 없을 때도 "지연 시간과 일관성 중 무엇을 우선하나"를 고르게 되는데, 이걸 덧붙여 PACELC라고 부르기도 합니다.

![네트워크가 끊긴 동안 양쪽에 쓰기가 오면, 거절해서 일관성을 지키거나 받아서 가용성을 지키거나 둘 중 하나를 고릅니다](system-design-cap.svg)

일관성에도 단계가 있습니다.

| 일관성 | 뜻 | 예 |
| --- | --- | --- |
| [[강한 일관성]] | 쓰기가 끝나면 그 뒤의 모든 읽기가 새 값을 봄. 한 대처럼 동작 | 은행 잔액, 재고, 비밀번호 변경 |
| 자기 쓰기 읽기 | 적어도 내가 쓴 건 나에게 바로 보임 | 내가 쓴 글이 내 목록에 바로 보이게 (22장의 복제 지연 대책) |
| [[최종적 일관성]] | 지금은 서로 다를 수 있지만, 새 쓰기가 멈추면 결국 같아짐 | 좋아요 수, 조회 수, 피드, DNS(13장의 TTL 캐시) |

모든 데이터에 강한 일관성이 필요한 건 아닙니다. 좋아요 수가 몇 초 늦게 맞아도 괜찮지만 송금은 그러면 안 됩니다. 데이터마다 필요한 일관성을 고르는 것이 설계입니다.

:::quiz pick-cap 네트워크가 갈라진 동안 "좋아요 수"와 "계좌 잔액"에 쓰기가 들어옵니다. 각각 무엇을 지키는 것이 알맞을까요?
- [ ] 둘 다 가용성: 서비스가 멈추면 안 되니까
- [ ] 둘 다 일관성: 틀린 숫자는 늘 나쁘니까
- [ ] 좋아요는 일관성, 잔액은 가용성
- [x] 좋아요는 가용성(나중에 맞춤), 잔액은 일관성(잠시 거절)

좋아요 수는 몇 초 틀려도 괜찮지만, 잔액이 틀리면 돈이 두 번 나갑니다. 데이터마다 필요한 일관성을 고르는 것이 설계입니다.
:::

## 실패에 대비하는 습관: 타임아웃, 재시도, 서킷 브레이커

분산 시스템에서는 다른 서비스를 부르는 모든 호출이 실패할 수 있다고 보고 코드를 짭니다.

**[[타임아웃]]**: 모든 네트워크 호출에 기다릴 시간의 한계를 둡니다. 타임아웃이 없으면 응답하지 않는 서버 하나 때문에 요청을 처리하던 스레드와 연결이 끝없이 붙잡혀, 결국 내 서비스까지 멈춥니다. `fetch`는 기본 타임아웃이 없으니 `AbortSignal.timeout(3000)`을 붙입니다.

**재시도와 [[지수 백오프]]**: 일시적인 실패는 다시 하면 됩니다. 하지만 바로, 계속 다시 하면 이미 힘든 서버를 더 괴롭힙니다. 그래서 1초, 2초, 4초, 8초처럼 기다리는 시간을 두 배씩 늘리고, 여기에 무작위 값을 섞어 모든 클라이언트가 같은 순간에 몰려 재시도하지 않게 합니다. 그리고 재시도해도 되는 요청인지 확인합니다. 14장의 멱등한 요청이거나 멱등성 키가 있어야 합니다.

```js
async function withRetry(fn, tries = 4) {
  for (let i = 0; ; i++) {
    try { return await fn(); }
    catch (e) {
      if (i >= tries - 1) throw e;
      const wait = 2 ** i * 500 * (0.5 + Math.random());   // 지수 백오프 + 무작위
      await new Promise((r) => setTimeout(r, wait));
    }
  }
}
await withRetry(() => fetch(url, { signal: AbortSignal.timeout(3000) }));
```

**[[서킷 브레이커]]**: 집의 누전 차단기처럼, 어떤 서비스로의 호출이 계속 실패하면 한동안 아예 호출하지 않고 바로 실패(또는 대체 응답)를 돌려줍니다. 죽어 가는 서비스를 더 두드리지 않고, 내 쪽 자원도 아낍니다. 잠시 뒤 몇 개만 시험 삼아 보내 보고, 성공하면 다시 연결합니다.

이 셋이 없으면 장애가 퍼집니다. 서비스 하나가 느려지면 그걸 부르는 서비스의 연결이 쌓이고, 그 서비스도 느려지고, 결국 전체가 무너집니다. 이걸 연쇄 장애라고 합니다.

:::quiz no-timeout 블로그 API가 외부 서비스를 `fetch`로 부르는데 타임아웃이 없습니다. 그 서비스가 연결은 받고 응답하지 않으면?
- [x] 요청마다 기다리는 연결이 쌓여 결국 내 API도 느려지거나 멈춘다
- [ ] `fetch`가 30초 뒤에 알아서 실패한다
- [ ] Node가 그 요청을 다른 서비스로 보낸다
- [ ] 아무 영향이 없다

쌓입니다. `fetch`에는 기본 타임아웃이 없어서 응답하지 않는 상대를 계속 기다립니다. 남의 장애가 내 장애로 번지는 연쇄 장애의 시작이라, `AbortSignal.timeout()`으로 기다릴 한계를 둡니다.
:::

- [x] 같은 순간에 실패한 클라이언트들이 같은 순간에 몰려 다시 보내지 않게 하려고

몰림을 흩뜨리기 위해서입니다. 서버가 잠깐 멈췄다 살아날 때 수천 클라이언트가 정확히 1초, 2초, 4초 뒤에 함께 다시 보내면 살아나자마자 다시 쓰러집니다.

## 요청 수 제한의 알고리즘

23장의 [[요청 수 제한]]은 어떻게 셀까요? 흔한 방법 두 가지입니다.

- **고정 창**: 1분마다 계수기를 0으로 초기화. 단순하지만 59초와 1분 1초에 몰아 보내면 짧은 시간에 두 배를 보낼 수 있습니다.
- **[[토큰 버킷]]**: 버킷에 토큰이 일정 속도로 채워지고(초당 10개, 최대 100개), 요청마다 하나씩 씁니다. 토큰이 없으면 429. 평소 속도는 지키면서 잠깐의 몰림은 허락합니다. 가장 많이 쓰는 방법이고, 20장의 슬라이딩 윈도로 세는 방법도 있습니다.

서버가 여러 대면 계수기를 공유해야 하니 보통 Redis에 둡니다.

:::quiz window-edge 이 API의 댓글 제한은 IP마다 처음 요청부터 10분 동안 20번입니다. 9분 59초에 20번, 10분 1초에 20번을 보내면?
- [ ] 두 번째 20번은 모두 막힌다
- [ ] 두 번째 20번 중 절반만 통과한다
- [x] 2초 사이에 40번이 모두 통과한다
- [ ] 처음 20번부터 막힌다

모두 통과합니다. 고정 창은 창이 끝나는 순간 계수기를 비우니, 창 경계에 몰아 보내면 짧은 시간에 두 배를 보냅니다. 토큰 버킷이나 슬라이딩 윈도는 이 몰림을 막습니다.
:::

## 데이터를 나눌 때: 일관된 해싱

22장의 샤딩이나 캐시 서버 여러 대에 키를 나눌 때, `hash(key) % 서버 수`로 정하면 서버를 하나 늘리는 순간 거의 모든 키의 자리가 바뀝니다. 캐시라면 한꺼번에 모두 미스가 나서 DB가 폭주합니다.

[[일관된 해싱]]은 해시 값의 범위를 원으로 생각하고, 서버들도 원 위의 점에 놓은 뒤, 각 키는 원을 따라 시계 방향으로 처음 만나는 서버에 둡니다. 서버를 하나 더하면 그 서버 바로 앞 구간의 키만 옮겨 가고 나머지는 그대로입니다. CDN, 분산 캐시, Cassandra와 DynamoDB 같은 분산 데이터베이스가 이 방법을 씁니다.

![`% 서버 수`는 서버를 하나 더하면 대부분의 키가 옮겨 가지만, 일관된 해싱은 새 서버 바로 앞 구간의 키만 옮깁니다](system-design-hash-ring.svg)

:::quiz rehash 키를 `hash % 서버 수`로 나누던 캐시 서버를 3대에서 4대로 늘리면, 키의 대략 몇 %가 자리를 옮길까요?
= 75 | 75% | 약75

약 **75%**입니다. 3과 4로 나눈 나머지가 같은 키는 대략 네 개 중 하나뿐입니다. 캐시라면 대부분이 한꺼번에 미스가 나서 DB로 몰립니다. 일관된 해싱이면 약 25%, 새 서버 몫만 옮깁니다.
:::

## 합의: 여러 대가 하나의 답에 동의하기

DB 주 서버가 죽었을 때 복제본 중 누가 새 주 서버가 될지, 설정 값의 최신본이 무엇인지를 여러 서버가 같은 답으로 정해야 할 때가 있습니다. 네트워크가 끊기고 서버가 죽는 와중에도 엇갈린 결정을 내리지 않게 하는 방법이 [[합의 알고리즘]]입니다. 가장 널리 쓰이는 것이 Raft입니다. 서버들 중 과반수의 표를 얻은 하나가 리더가 되고, 리더가 받은 변경은 과반수가 받았다고 답해야 확정됩니다. 과반수를 쓰기 때문에 서버 5대 중 2대가 죽어도 동작하고, 네트워크가 둘로 갈라져도 과반수 쪽만 결정을 내려 두 리더가 생기지 않습니다. Kubernetes가 상태를 저장하는 etcd, 여러 분산 데이터베이스가 Raft를 씁니다.

:::quiz raft-quorum 서버 5대로 이루어진 Raft 클러스터는 몇 대까지 죽어도 계속 결정을 내릴 수 있을까요?
= 2 | 2대

**2대**입니다. 결정에는 과반수(3대)의 동의가 필요하니 3대가 살아 있으면 됩니다. 그래서 이런 클러스터는 3대, 5대처럼 홀수로 만듭니다.
:::

## 모놀리스와 마이크로서비스

서비스의 코드를 어떻게 나눌지도 설계의 큰 결정입니다.

| | [[모놀리스]] | [[마이크로서비스]] |
| --- | --- | --- |
| 모양 | 앱 하나에 모든 기능 | 기능마다 따로 배포하는 작은 서비스들이 네트워크로 대화 |
| 장점 | 단순함. 함수 호출로 대화, 트랜잭션 하나로 묶기 쉬움, 배포 하나 | 팀마다 독립적으로 개발과 배포, 기능별로 따로 확장, 한 서비스의 장애가 덜 퍼짐 |
| 단점 | 코드가 커지면 팀끼리 부딪치고 배포가 무거워짐 | 분산 시스템의 모든 어려움(이 장)이 생김. 운영 도구와 사람이 많이 필요 |

마이크로서비스는 기술 문제라기보다 조직 문제를 풉니다. 수백 명이 한 코드에서 부딪치는 회사에서 팀을 독립시키는 방법입니다. 작은 팀은 잘 나눈 모놀리스(모듈러 모놀리스)로 시작하는 게 거의 늘 낫습니다. 이 저장소는 그 중간쯤입니다. 한 저장소(모노레포)에서 공통 코드(`packages/`)를 나눠 쓰면서, 앱마다 따로 컨테이너로 배포합니다.

- [ ] 처음부터 Kubernetes와 서비스 메시

모놀리스입니다. 마이크로서비스는 팀끼리 부딪치는 큰 조직의 문제를 푸는 대신 분산 시스템의 어려움을 모두 들여옵니다. 모듈 경계를 잘 나눠 두면 나중에 필요한 부분만 떼어 낼 수 있습니다.

## 어림 계산으로 설계 검토하기

설계를 정하기 전에 대략적인 숫자를 계산해 보면 무엇이 문제가 될지 미리 보입니다. 2장과 9장의 숫자표가 여기서 쓰입니다.

> **예: 하루 사용자 100만 명이 하루 10번씩 글 목록을 보는 서비스**
>
> - 요청 수: 1000만 번 ÷ 86,400초 ≈ 초당 116번. 피크는 평균의 3~5배로 보면 초당 500번.
> - 응답 크기: 글 20개 × 1KB = 20KB. 초당 500번 × 20KB = 초당 10MB = 80Mbps. 서버 한 대의 회선으로 감당 가능.
> - DB: 목록 쿼리가 인덱스로 5ms라면 DB 연결 하나가 초당 200번. 초당 500번이면 연결 몇 개면 됨. 캐시를 쓰면 더 여유.
> - 저장 공간: 하루 새 글 1만 개 × 2KB = 20MB/일 = 1년에 7GB. 이미지가 따로 있다면 그쪽이 훨씬 큼 → 오브젝트 스토리지.
>
> 결론: 앱 서버 2대(이중화) + DB 하나와 복제본 하나 + 캐시 + 이미지는 CDN으로 충분. 샤딩은 필요 없음.

1초 = 약 10⁵ 단위로 세면 편합니다(하루 86,400초 ≈ 10⁵). 하루 100만 번 요청은 초당 약 10번, 하루 10억 번은 초당 약 1만 번입니다.

## 다시 장면으로: 1000배가 되면

맨 앞 그림의 진한 칸들이 답입니다. 요청 수 계수기는 프로세스 메모리에 있어서 서버를 늘리면 따로 셉니다. SQLite 파일은 그 서버의 볼륨에만 있고 쓰기를 하나씩 받습니다. 그리고 그 모든 것이 VM 한 대 위에 있습니다. 수평으로 늘리려면 이 상태들을 앱 밖으로 옮깁니다. 계수기는 Redis로 옮겨 토큰 버킷으로 세고, 데이터는 여러 앱 서버가 함께 쓰는 DB 서버로, 이미지는 오브젝트 스토리지로 옮깁니다. 이 저장소의 DB 클라이언트는 이미 원격 DB의 주소와 토큰을 받을 수 있게 되어 있습니다. 관리자 쿠키처럼 처음부터 무상태로 만든 부분은 손댈 것이 없습니다. 이 책은 더 쉽습니다. 정적 HTML이라 CDN 앞에 두기만 하면 1000배도 버팁니다.

그런데 "옮긴다"는 말은 코드를 고친다는 뜻입니다. 요청 수 제한을 Redis로 바꾸려면 API 코드를 몇 군데나 고쳐야 할까요? 이 저장소에서는 다행히 한 곳입니다. `RateLimiter`는 `security.ts`에만 있고, API는 어디서든 `allow(키)` 하나로만 부릅니다. 데이터베이스도 `packages/db`가 감싸고 있어서 API는 `listComments` 같은 함수만 압니다. 바꾸기 쉬운 코드는 어떻게 생겼고, 어떻게 그렇게 만들까요? 25장의 이야기입니다.

## 곁가지: 시스템 설계 질문에 답하는 순서

1. **요구 사항을 묻습니다.** 무엇을 하는 시스템인지(기능), 사용자 수와 데이터 양, 읽기와 쓰기 비율, 지연 시간과 일관성 요구(비기능).
2. **어림 계산을 합니다.** 초당 요청, 저장 공간, 대역폭.
3. **큰 그림을 그립니다.** 클라이언트, 로드 밸런서, 앱, 캐시, DB, 큐, CDN, 오브젝트 스토리지 중 필요한 것을 이어 그립니다.
4. **데이터 모델과 API를 정합니다.** 테이블과 키(21장), 엔드포인트(17장).
5. **병목과 장애를 파고듭니다.** 어디가 먼저 터질지, 단일 장애 지점은 어디인지, 일관성은 어디서 강해야 하는지.
6. **장단점을 말합니다.** 정답은 없고 거래만 있습니다. 무엇을 얻고 무엇을 포기했는지 설명할 수 있으면 됩니다.

## 프론트엔드와 이어지는 곳

- 프론트엔드도 분산 시스템의 한 노드입니다. API 호출에 타임아웃을 두고, 일시적 실패에 백오프 재시도를 하고(TanStack Query가 기본으로 합니다), 실패하면 대체 화면을 보여 줍니다.
- 낙관적 업데이트와 오프라인 지원은 최종적 일관성을 받아들이는 설계입니다. 화면이 잠시 서버와 다를 수 있고, 나중에 맞춥니다.
- 화면에 보이는 숫자(좋아요, 조회 수)는 대개 최종적 일관성이라 몇 초 늦어도 괜찮지만, 결제 금액과 재고는 서버의 최신 값을 다시 확인합니다.
- 429를 받으면 `Retry-After` 헤더만큼 기다렸다 다시 보냅니다.

## 용어 정리

:::terms
- 수직 확장 (scale up) — 서버 한 대의 CPU, 메모리를 늘려 더 많은 부하를 받는 것입니다.
- 수평 확장 (scale out) — 같은 서버를 여러 대로 늘려 부하를 나누는 것입니다.
- 무상태 서버 (stateless server) — 요청 사이의 상태를 자기 안에 두지 않아 어느 서버가 요청을 받아도 같게 처리하는 서버. 수평 확장의 조건입니다.
- 가용성 (availability) — 서비스가 정상적으로 쓰일 수 있는 시간의 비율. 99.9%처럼 9의 개수로 말합니다.
- 단일 장애 지점 (single point of failure) — 그 하나가 고장 나면 전체가 멈추는 부품이나 서버입니다.
- 분산 시스템 (distributed system) — 여러 컴퓨터가 네트워크로 메시지를 주고받으며 하나처럼 동작하는 시스템입니다.
- CAP 정리 (CAP theorem) — 네트워크 분할이 일어났을 때 분산 시스템은 일관성과 가용성 중 하나를 포기해야 한다는 정리입니다.
- 강한 일관성 (strong consistency) — 쓰기가 끝나면 그 뒤의 모든 읽기가 새 값을 보는, 한 대처럼 동작하는 일관성입니다.
- 최종적 일관성 (eventual consistency) — 지금은 복제본마다 다를 수 있지만 새 쓰기가 멈추면 결국 같아지는 일관성입니다.
- 타임아웃 (timeout) — 응답을 기다릴 시간의 한계. 넘으면 실패로 보고 자원을 풉니다.
- 지수 백오프 (exponential backoff) — 실패한 요청을 다시 보낼 때 기다리는 시간을 두 배씩 늘리는 방법. 무작위 값을 함께 섞습니다.
- 서킷 브레이커 (circuit breaker) — 계속 실패하는 서비스로의 호출을 한동안 막고 바로 실패를 돌려줘 장애가 퍼지지 않게 하는 장치입니다.
- 토큰 버킷 (token bucket) — 일정 속도로 채워지는 토큰을 요청마다 하나씩 쓰게 해 평균 속도를 제한하고 잠깐의 몰림은 허락하는 알고리즘입니다.
- 일관된 해싱 (consistent hashing) — 키와 서버를 해시 원 위에 놓아, 서버를 더하거나 뺄 때 일부 키만 자리를 옮기게 하는 분배 방법입니다.
- 합의 알고리즘 (consensus algorithm) — 고장과 네트워크 문제 속에서도 여러 서버가 하나의 값에 동의하게 하는 알고리즘. Raft, Paxos.
- 모놀리스 (monolith) — 서비스의 모든 기능을 하나의 앱으로 만들고 배포하는 구조입니다.
- 마이크로서비스 (microservices) — 기능마다 따로 배포하는 작은 서비스들로 나누고 네트워크로 대화하게 하는 구조입니다.
:::

## 직접 해보기

:::practice estimate 어림 계산 연습
다음 서비스의 초당 요청 수(평균, 피크), 1년 저장 공간, 필요한 대역폭을 계산하고, 서버 구성을 한 문단으로 제안합니다: "하루 사용자 50만 명이 하루 평균 사진 2장을 올리고(장당 2MB), 피드를 20번 보는(한 번에 사진 10장의 썸네일, 장당 50KB) 사진 공유 앱." 어디가 가장 먼저 병목이 될지(DB, 저장소, 대역폭) 적습니다.
:::

:::practice retry 타임아웃과 백오프 재시도 직접 보기
절반 확률로 실패하고 가끔 아주 느리게 답하는 서버를 띄우고, 이 장의 `withRetry`와 `AbortSignal.timeout`으로 호출해 몇 번째에 성공하는지, 기다린 시간이 어떻게 늘어나는지 로그로 봅니다. 타임아웃을 빼면 느린 응답에서 무슨 일이 생기는지도 확인합니다.

```js flaky.mjs
import http from "node:http";
http.createServer((req, res) => {
  const r = Math.random();
  if (r < 0.4) { res.statusCode = 503; return res.end("busy"); }
  if (r < 0.5) return setTimeout(() => res.end("slow ok"), 10_000);
  res.end("ok");
}).listen(4000);
```
:::

:::practice token-bucket 토큰 버킷 만들기
초당 5개 채워지고 최대 10개인 토큰 버킷을 클래스로 만들고, 1초에 20번 요청이 몰리는 상황과 0.2초마다 꾸준히 오는 상황에서 몇 번이 허락되는지 시뮬레이션합니다. 그다음 이 버킷을 Node 서버에 붙여, 넘치면 429와 `Retry-After` 헤더를 돌려주게 합니다.
:::

:::practice spof 이 사이트의 단일 장애 지점 찾기
17장의 이 사이트 구조 그림을 보고 단일 장애 지점을 모두 찾아 적습니다(서버, Caddy, 디스크, DNS 서비스, GitHub Actions, 레지스트리 등). 각각이 죽으면 사용자에게 무엇이 안 되는지, 없애려면 무엇이 필요하고 비용이 얼마나 드는지 표로 만듭니다. 그리고 개인 사이트에 어디까지가 합리적인지 결론을 냅니다.
:::

## 스스로 점검

:::qa 앱 서버를 수평 확장하려면 무엇을 바꿔야 하나요?
앱을 무상태로 만들어야 합니다. 세션은 DB나 Redis로, 업로드 파일은 오브젝트 스토리지로, 메모리 캐시는 공유 캐시로 빼서 어느 서버가 요청을 받아도 같은 결과가 나오게 하고, 앞에 로드 밸런서를 둡니다.
:::

:::qa CAP 정리를 "둘 중 하나를 고른다"는 관점으로 정확히 설명해 보세요.
네트워크 분할은 피할 수 없으니, 분할이 일어났을 때 다른 쪽과 확인할 수 없는 요청을 거절해 일관성을 지킬지, 각자 받아 처리해 가용성을 지키고 나중에 데이터를 맞출지 골라야 한다는 뜻입니다.
:::

:::qa 실패한 요청을 바로, 계속 재시도하면 무엇이 문제이고, 어떻게 고치나요?
이미 과부하인 서버에 요청이 더 몰려 회복을 막고, 모든 클라이언트가 같은 시각에 재시도하면 파도처럼 몰립니다. 지수 백오프로 간격을 늘리고 무작위 값을 섞고, 재시도 횟수에 한계를 두고, 멱등한 요청만 재시도합니다.
:::

:::qa 서버 하나가 느려지자 그걸 부르던 서비스들까지 줄줄이 멈췄습니다. 무엇이 빠졌을까요?
타임아웃이 없거나 너무 길어서 느린 호출이 연결과 스레드를 계속 붙잡았고, 서킷 브레이커가 없어 실패가 쌓이는데도 계속 호출했을 가능성이 큽니다. 모든 외부 호출에 짧은 타임아웃과 서킷 브레이커, 대체 응답을 둡니다.
:::

:::qa `hash(key) % N`으로 캐시 서버를 나누다가 서버를 하나 늘리면 무슨 일이 생기고, 일관된 해싱은 이를 어떻게 줄이나요?
N이 바뀌면 거의 모든 키의 서버가 바뀌어 캐시가 한꺼번에 비고 DB로 요청이 몰립니다. 일관된 해싱은 키와 서버를 원 위에 두고 시계 방향으로 가장 가까운 서버에 키를 두니, 새 서버가 들어간 구간의 키만 옮겨 갑니다.
:::

:::qa 5명짜리 팀이 새 서비스를 마이크로서비스로 시작하는 건 좋은 선택인가요?
대개 아닙니다. 마이크로서비스는 팀 간 독립을 얻는 대신 네트워크 실패, 분산 트랜잭션, 배포와 관측 도구 같은 분산 시스템의 비용을 치릅니다. 작은 팀은 모듈을 잘 나눈 모놀리스로 시작해, 정말 나눌 이유가 생긴 부분만 떼어 내는 편이 낫습니다.
:::
