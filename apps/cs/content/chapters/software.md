## 프로그래밍 패러다임

같은 문제도 어떤 관점으로 코드를 짜느냐에 따라 모양이 달라집니다. 이 관점을 [[프로그래밍 패러다임]]이라고 합니다. JS와 TypeScript는 셋을 모두 섞어 쓸 수 있는 언어입니다.

| 패러다임 | 프로그램을 보는 눈 | 예 |
| --- | --- | --- |
| 절차형 | 순서대로 실행되는 명령과 그걸 묶은 함수 | C, 셸 스크립트, 이 사이트의 빌드 스크립트 |
| [[객체 지향 프로그래밍]] | 데이터와 그 데이터를 다루는 동작을 묶은 객체들이 서로 메시지를 주고받음 | Java, C#, Swift, JS 클래스 |
| [[함수형 프로그래밍]] | 값을 받아 값을 돌려주는 함수들의 조합. 상태를 바꾸지 않음 | Haskell, Elm, React의 컴포넌트와 훅, Redux의 리듀서 |

### 객체 지향의 네 가지 기둥

- **[[캡슐화|객체 캡슐화]]**: 데이터와 그걸 다루는 동작을 묶고, 내부를 숨기고 정해진 메서드로만 바꾸게 합니다. 18장의 `Queue` 클래스가 `#items`를 숨기고 `push`, `shift`만 보여 주는 것처럼. 숨긴 내부는 바깥을 깨뜨리지 않고 바꿀 수 있습니다.
- **[[상속]]**: 기존 클래스를 물려받아 새 클래스를 만듭니다. 편하지만 부모를 바꾸면 모든 자식이 흔들려서, 요즘은 "상속보다 조합"을 권합니다. React가 클래스 상속 대신 컴포넌트 조합과 훅으로 기능을 나누는 이유입니다.
- **[[다형성]]**: 같은 메시지에 객체마다 다르게 반응합니다. `shape.area()`를 부르면 원은 원의 넓이를, 사각형은 사각형의 넓이를 계산합니다. 부르는 쪽은 구체적인 종류를 몰라도 됩니다.
- **[[추상화]]**: 필요한 것만 드러내고 세부를 감춥니다. 이 책 전체가 추상화의 층입니다. 파일은 디스크 블록의, 소켓은 네트워크 카드의 추상화였습니다(4장).

### 함수형의 핵심 생각

- **[[순수 함수]]**: 같은 입력에 늘 같은 출력을 돌려주고, 바깥의 아무것도 바꾸지 않는(부수 효과가 없는) 함수입니다. 테스트하기 쉽고, 결과를 캐시해도 안전하고(20장의 메모이제이션), 병렬로 돌려도 안전합니다(6장).
- **[[불변성]]**: 값을 고치지 않고 바꾼 새 값을 만듭니다. `[...arr, x]`, `{...obj, done: true}`. React가 상태 변화를 "이전 값과 참조가 다른가"로 빠르게 알아내려면 불변이어야 합니다.
- **고차 함수와 조합**: 함수를 인자로 받거나 돌려주는 함수. `map`, `filter`, `reduce`, 커스텀 훅, 미들웨어가 그렇습니다. 작은 함수를 이어 붙여 큰 일을 합니다.

부수 효과(네트워크, 파일, DOM, 시간, 무작위)는 없앨 수 없습니다. 함수형 스타일은 그걸 없애는 게 아니라 가장자리로 밀어 둡니다. React가 렌더링은 순수하게 하고 부수 효과는 `useEffect`와 이벤트 핸들러에 모으라고 하는 것이 이 생각입니다.

:::quiz pure 순수 함수는 어느 것일까요?
- [ ] `() => Date.now()`
- [x] `(a, b) => a + b`
- [ ] `(x) => { console.log(x); return x; }`
- [ ] `() => ++count` (바깥의 `count`를 늘림)

`(a, b) => a + b`입니다. 같은 입력에 늘 같은 값을 돌려주고 바깥을 바꾸지 않습니다. 시각을 읽거나, 화면에 찍거나, 바깥 변수를 바꾸면 부수 효과가 있는 함수입니다.
:::

:::quiz same-ref React에서 `state.items.push(x); setItems(state.items);`를 했더니 화면이 바뀌지 않습니다. 이유는?
- [ ] `push`는 비동기라서
- [ ] 배열은 상태로 쓸 수 없어서
- [x] 같은 배열(같은 참조)을 다시 넣어 React가 바뀐 게 없다고 판단해서
- [ ] `setItems`는 숫자만 받아서

같은 참조이기 때문입니다. React는 이전 값과 새 값이 같은 객체인지로 변화를 빠르게 판단합니다. `setItems([...items, x])`처럼 새 배열을 만들어야 합니다(불변성).
:::

## 결합도와 응집도

좋은 구조를 판단하는 가장 기본적인 두 잣대입니다.

- **[[응집도]]**: 한 모듈 안의 것들이 얼마나 하나의 목적으로 모여 있나. 높을수록 좋습니다. `utils.ts`에 날짜, 문자열, API 호출이 다 들어 있으면 응집도가 낮습니다.
- **[[결합도]]**: 모듈끼리 얼마나 서로에 기대나. 낮을수록 좋습니다. 한 모듈을 고쳤는데 다른 열 군데가 깨진다면 결합도가 높은 것입니다.

"관련된 것은 모으고, 관련 없는 것은 떼어 놓는다." 아래의 원칙과 패턴은 대부분 이 한 문장을 구체적으로 푸는 방법입니다.

:::quiz utils-cohesion `utils.ts` 한 파일에 날짜 포맷, API 호출, 문자열 자르기, 로그인 확인이 모두 들어 있습니다. 무엇이 낮은 상태일까요?
- [x] 응집도
- [ ] 결합도
- [ ] 다형성
- [ ] 추상화

응집도가 낮습니다. 서로 상관없는 일들이 한 모듈에 모여 있어서, 어느 하나를 고치러 들어가도 나머지를 다 읽게 됩니다. 이 API는 보안에 관한 것은 `security.ts`에, 데이터에 관한 것은 `packages/db`에 모아 두었습니다.
:::

## SOLID

객체 지향 설계의 다섯 원칙의 머리글자입니다. 클래스가 아니라 함수와 컴포넌트에도 그대로 들어맞습니다.

| 원칙 | 뜻 | 프론트엔드에서 |
| --- | --- | --- |
| [[단일 책임 원칙]] (S) | 모듈은 한 가지 이유로만 바뀌어야 한다 | 데이터 가져오기, 상태 관리, 그리기를 한 컴포넌트에 다 넣지 않고 훅과 컴포넌트로 나눔 |
| 개방-폐쇄 원칙 (O) | 기능을 더할 때 기존 코드를 고치지 않고 확장할 수 있어야 한다 | 버튼에 종류가 추가될 때마다 `if`를 늘리지 않고 `variant`나 `children`으로 받음 |
| 리스코프 치환 원칙 (L) | 자식 타입은 부모 타입 자리에 넣어도 똑같이 동작해야 한다 | `<Button>`을 감싼 `<SubmitButton>`이 `onClick`, `disabled`를 똑같이 존중 |
| 인터페이스 분리 원칙 (I) | 쓰지 않는 기능에 기대게 하지 않는다 | 컴포넌트에 거대한 `user` 객체 대신 필요한 `name`, `avatarUrl`만 props로 |
| [[의존성 역전 원칙]] (D) | 구체적인 것이 아니라 추상(인터페이스)에 기댄다 | 컴포넌트가 `fetch`를 직접 부르지 않고 주입받은 `api.getPosts()`에 기댐 → 테스트에서 가짜로 바꿀 수 있음 |

원칙은 목표가 아니라 도구입니다. 작은 코드에 모든 원칙을 적용하면 오히려 읽기 어려운 층만 늘어납니다. 고치기 어려움을 실제로 느낄 때 꺼내 씁니다.

:::quiz depends-on 블로그 API의 라우트가 `RateLimiter`에 대해 기대는 것은?
- [ ] 안의 `hits` Map의 모양
- [ ] 10,000개가 넘으면 비우는 규칙
- [ ] 창의 길이를 계산하는 방법
- [x] `allow(key)`를 부르면 참이나 거짓이 돌아온다는 것

겉으로 드러난 `allow(key)` 하나입니다. 안의 `Map`은 `private`으로 숨겨져 있어서(캡슐화), 그 속을 Redis로 바꿔도 라우트가 기대는 약속은 그대로입니다.
:::

## 디자인 패턴

자주 나오는 설계 문제에 대한 이름 붙은 해법을 [[디자인 패턴]]이라고 합니다. 1994년 "GoF"라 불리는 네 저자의 책이 23가지를 정리했습니다. 이름을 알면 "여기 옵저버 패턴 쓰자"처럼 짧게 대화할 수 있습니다. 프론트엔드에서 이미 매일 쓰고 있는 것들 위주로 봅니다.

| 패턴 | 푸는 문제 | 이미 쓰고 있는 곳 |
| --- | --- | --- |
| [[싱글턴]] | 인스턴스가 하나만 있어야 함 | ES 모듈은 한 번만 실행되니 `export const queryClient = new QueryClient()`가 사실상 싱글턴 |
| [[팩토리]] | 무엇을 만들지 고르는 일을 한곳에 모음 | `createStore()`, `createRoot()`, 조건에 따라 다른 객체를 만드는 함수 |
| [[옵저버 패턴]] | 한 곳의 변화를 여러 곳에 알림 | `addEventListener`, `EventTarget`, Redux·Zustand의 `subscribe`, RxJS, 6장의 이벤트 |
| [[전략 패턴]] | 알고리즘을 바꿔 끼움 | `sort`에 넘기는 비교 함수(20장), 결제 수단별 처리 함수, 로드 밸런싱 방식(17장) |
| [[어댑터 패턴]] | 맞지 않는 인터페이스를 맞춤 | 서버 응답을 화면용 모양으로 바꾸는 함수, 여러 결제 SDK를 같은 모양으로 감싸기, libuv(8장) |
| [[데코레이터 패턴]] | 원래 것을 감싸 기능을 덧붙임 | 고차 컴포넌트, `withRetry(fn)`(24장), 미들웨어, Express·Hono의 `app.use` |
| [[컴포지트 패턴]] | 낱개와 묶음을 똑같이 다룸 | DOM과 React 트리(19장). 컴포넌트 하나든 컴포넌트 묶음이든 똑같이 `children`으로 |
| [[프록시 패턴]] | 대리인이 접근을 가로채 제어 | JS `Proxy`, Vue와 MobX의 반응형 상태, 17장의 리버스 프록시도 같은 생각 |
| [[템플릿 메서드 패턴|템플릿 메서드]] | 순서의 뼈대는 위에서 정하고 단계별 내용만 아래에서 채움 | 테스트 프레임워크가 `beforeEach` → 테스트 → `afterEach` 순서를 정하고 우리는 내용만 채움, React 클래스 컴포넌트의 생명주기 메서드 |
| 퍼사드 | 복잡한 하위 시스템 앞에 단순한 창구 | `fetch` 감싼 `api.get()`, 여러 훅을 묶은 커스텀 훅 |

### 의존성 주입

[[의존성 주입]]은 모듈이 필요한 것을 직접 만들지 않고 바깥에서 받는 것입니다. 의존성 역전 원칙을 실천하는 가장 흔한 방법입니다.

```ts
// 직접 만들면: 테스트에서 진짜 네트워크를 부를 수밖에 없음
function loadPosts() { return fetch("/api/posts").then((r) => r.json()); }

// 주입받으면: 테스트에서는 가짜를, 운영에서는 진짜를 넣음
function makePostService(http: { get(url: string): Promise<unknown> }) {
  return { load: () => http.get("/api/posts") };
}
```

React의 Context는 컴포넌트 트리에 의존성을 주입하는 장치입니다. 테마, 로그인 정보, API 클라이언트를 Provider로 넣어 주면, 깊은 곳의 컴포넌트가 직접 만들지 않고 받아 씁니다.

:::quiz observer `button.addEventListener("click", handler)`는 어떤 패턴일까요?
- [ ] 싱글턴
- [x] 옵저버
- [ ] 팩토리
- [ ] 어댑터

옵저버입니다. 버튼(주체)이 클릭이라는 변화를 등록된 함수들(관찰자)에게 알립니다. Redux와 Zustand의 `subscribe`도 같은 모양입니다.
:::

:::quiz di-test 함수가 `fetch`를 직접 부르는 대신 `http` 객체를 인자로 받게(의존성 주입) 바꾸면, 테스트에서 무엇이 좋아질까요?
- [x] 가짜 `http`를 넣어 네트워크 없이, 원하는 응답과 실패를 마음대로 만들어 테스트할 수 있다
- [ ] 함수가 더 빨리 실행된다
- [ ] 타입 검사가 필요 없어진다
- [ ] 운영에서 `fetch`를 쓰지 않아도 된다

가짜를 끼울 수 있게 됩니다. 테스트에서는 정해진 값을 돌려주는 가짜를, 운영에서는 진짜 `fetch`를 감싼 것을 넣습니다. 함수는 둘을 구분하지 않습니다.
:::

## 화면 구조의 패턴: MVC에서 단방향 흐름까지

화면이 있는 프로그램은 오래전부터 "데이터"와 "보여 주기"와 "입력 처리"를 나눠 왔습니다.

- **[[MVC]]**: 모델(데이터와 규칙), 뷰(보여 주기), 컨트롤러(입력을 받아 모델을 바꾸기). 서버 쪽 웹 프레임워크(Rails, Spring MVC)가 이 구조입니다.
- **MVVM**: 뷰가 뷰 모델의 상태에 묶여(바인딩) 자동으로 갱신됩니다. Vue, Angular, SwiftUI가 비슷합니다.
- **[[단방향 데이터 흐름]]**: 상태 → 화면, 사용자 행동 → 액션 → 새 상태 → 화면, 한 방향으로만 흐릅니다. Facebook이 Flux로 정리했고 React, Redux, Elm이 이 구조입니다. 데이터가 어디서 바뀌었는지 추적하기 쉬운 것이 장점입니다.

```text
   ┌──────── 액션 (클릭, 응답 도착) ────────┐
   ▼                                     │
 상태 ──(순수 함수: reducer)──▶ 새 상태 ──▶ 화면 (순수 함수: 컴포넌트)
```

서버 쪽 코드도 비슷하게 층으로 나눕니다. 라우트(HTTP를 받고), 서비스(업무 규칙), 저장소(DB 접근). 17장의 API 서버를 이렇게 나누면, 업무 규칙을 HTTP나 DB 없이 테스트할 수 있습니다.

## 테스트

코드가 원하는 대로 동작하는지 사람이 매번 눌러 보는 대신 코드로 확인하는 것이 자동 테스트입니다. 무엇을 얼마나 넓게 확인하느냐에 따라 나뉩니다.

| 종류 | 확인하는 범위 | 속도 | 예 |
| --- | --- | --- | --- |
| [[단위 테스트]] | 함수나 컴포넌트 하나 | 아주 빠름 | `formatPrice(1000)`이 `"1,000원"`인지 |
| [[통합 테스트]] | 여러 부분이 함께 | 중간 | 폼을 채우고 제출하면 API 호출과 화면 변화가 맞는지 |
| [[E2E 테스트]] | 진짜 브라우저로 사용자 흐름 전체 | 느림 | 로그인 → 글쓰기 → 목록에 보이는지 (Playwright) |

빠르고 많은 단위 테스트를 바닥에, 느린 E2E는 꼭 필요한 흐름에만 두는 것을 테스트 피라미드라고 합니다. 프론트엔드에서는 "사용자처럼 쓰는" 통합 테스트(Testing Library)가 가장 가성비가 좋다는 의견(테스트 트로피)도 많습니다.

테스트하기 어려운 의존성(네트워크, 시간, 무작위)은 가짜로 바꿔 끼웁니다. 이 가짜들을 통틀어 [[테스트 더블]]이라고 하고, 정해진 값을 돌려주는 스텁, 호출을 기록하고 확인하는 목(mock) 등이 있습니다. 위의 의존성 주입이 이걸 쉽게 해 줍니다.

[[TDD]](테스트 주도 개발)는 테스트를 먼저 쓰는 방식입니다. 실패하는 테스트를 쓰고(빨강), 통과할 만큼만 코드를 짜고(초록), 구조를 다듬습니다(리팩터). 이 순환을 짧게 반복합니다. 늘 이렇게 할 필요는 없지만, 규칙이 분명한 함수(계산, 파싱, 변환)에는 아주 잘 맞습니다. 이 사이트의 마크다운 변환기와 빌드도 vitest 테스트로 확인합니다.

:::quiz e2e 실제 브라우저를 띄워 "로그인 → 글쓰기 → 목록에 보이는지"를 처음부터 끝까지 확인하는 테스트의 종류는? (영어 약자)
= E2E | e2e

**E2E**(End-to-End) 테스트입니다. 가장 실제와 가깝지만 느리고 잘 깨지니, 꼭 지켜야 할 흐름 몇 개에만 둡니다. 함수 하나는 단위 테스트, 몇 부분을 함께는 통합 테스트로 확인합니다.
:::

## 리팩터링과 기술 부채

[[리팩터링]]은 동작은 그대로 두고 구조만 고치는 것입니다. 이름을 바꾸고, 함수를 나누고, 중복을 합칩니다. 테스트가 있어야 "동작은 그대로"를 확인하며 안심하고 할 수 있습니다.

급하게 만드느라 남겨 둔 구조적 문제를 [[기술 부채]]라고 부릅니다. 빚처럼 당장은 빠르게 해 주지만, 갚지 않으면 이자(고칠 때마다 드는 추가 시간)가 쌓입니다. 일부러 진 빚은 나쁘지 않습니다. 기록해 두고 갚을 계획이 있으면 됩니다.

읽는 사람이 바로 이해할 수 있게 쓴 코드를 흔히 클린 코드라고 부릅니다. 이름이 하는 일을 말하고, 함수는 한 가지만 하고, 같은 지식이 두 군데 적혀 있지 않은 코드입니다. 이 장의 원칙들을 한 문장으로 줄인 말이라고 보면 됩니다.

일하는 방식에도 이름이 붙어 있습니다. 애자일은 몇 달 계획하고 한 번에 내놓는 대신, 1~2주 단위로 작게 만들어 보여 주고 고치기를 되풀이하는 방식입니다. DevOps는 개발과 운영을 다른 팀의 일로 나누지 않고, CI/CD(17장), 모니터링, 자동화로 "만든 사람이 돌리고 고친다"를 가능하게 하는 문화와 도구를 말합니다. 이 저장소의 테스트, 자동 배포, 롤백이 그 작은 예입니다.

## Git은 안에서 어떻게 동작하나

Git은 매일 쓰지만 안을 들여다보면 이 책의 개념들로 만든 깔끔한 자료구조입니다.

**내용 주소 저장소**: Git은 모든 것을 내용의 해시(14장, SHA-1, 새 저장소는 SHA-256도 가능)를 이름으로 삼아 `.git/objects`에 저장합니다. 같은 내용은 같은 이름이니 한 번만 저장되고, 내용이 한 비트라도 바뀌면 이름이 바뀌니 변조를 알아챕니다. 객체는 세 종류입니다.

| 객체 | 담는 것 |
| --- | --- |
| blob | 파일 내용 (이름 없이 내용만) |
| tree | 디렉터리: 이름 → blob 또는 tree의 해시 목록 (8장의 디렉터리와 같은 모양) |
| commit | 최상위 tree의 해시, 부모 커밋의 해시, 작성자, 시각, 메시지 |

**커밋은 DAG입니다**: 커밋이 부모 커밋의 해시를 담고 있으니, 커밋들은 19장의 DAG를 이룹니다. 커밋의 해시에 부모의 해시가 들어가니, 과거의 커밋 하나를 몰래 바꾸면 그 뒤의 모든 해시가 바뀝니다.

![이 장의 Git 예. 커밋은 부모 해시로 이어진 DAG이고, 브랜치와 HEAD는 커밋 하나를 가리키는 이름표입니다](software-git.svg)

**브랜치는 포인터입니다**: 브랜치는 커밋 해시 하나를 적은 작은 파일(`.git/refs/heads/main`)일 뿐입니다. 그래서 브랜치를 만드는 건 순식간이고, `HEAD`는 "지금 어느 브랜치에 있나"를 가리키는 포인터입니다.

**머지와 리베이스**: 두 갈래를 합칠 때, 머지는 두 부모를 가진 새 커밋을 만들고(DAG에 합류점), 리베이스는 한쪽 커밋들을 다른 쪽 끝에 새로 다시 만들어 붙입니다(새 해시가 생김). 이미 남과 나눈 커밋을 리베이스하면 남이 가진 해시와 어긋나서, 공유한 브랜치는 리베이스하지 않는 것이 규칙입니다. 합칠 때 Git은 두 갈래의 공통 조상을 찾아 세 버전(공통 조상, 내 것, 남의 것)을 비교하고(3-way 머지), 줄 단위 차이는 20장의 diff 알고리즘으로 구합니다.

`git reflog`는 HEAD가 지나간 자리를 모두 기록해 둡니다. 브랜치를 잘못 지웠거나 리셋으로 커밋을 잃은 것 같아도, 객체는 한동안 남아 있어 reflog로 대부분 되찾을 수 있습니다.

### 브랜치 전략과 커밋 규칙

여럿이 한 저장소를 쓰면 브랜치를 어떻게 나누고 합칠지 약속이 필요합니다. 이걸 [[브랜치 전략]]이라고 합니다.

| 전략 | 모양 | 맞는 곳 |
| --- | --- | --- |
| Git Flow | `main`, `develop`, 기능별 `feature/*`, 출시 준비 `release/*`, 긴급 수정 `hotfix/*` | 버전을 정해 출시하는 앱, 설치형 소프트웨어 |
| GitHub Flow | `main` 하나와 짧게 사는 기능 브랜치, PR로 리뷰하고 합치면 바로 배포 | 자주 배포하는 웹 서비스 |
| 트렁크 기반 | 모두가 `main`에 작게 자주 합치고, 덜 된 기능은 기능 플래그로 숨김 | 큰 팀, 하루에도 여러 번 배포 |

이 저장소는 GitHub Flow입니다. 기능 브랜치에서 작업하고, PR을 열면 CI가 검사하고, `main`에 합쳐지면 바뀐 앱만 배포됩니다(17장). PR 제목과 커밋 메시지에는 `[CS/feature] 26장 쓰기`처럼 어느 앱의 어떤 종류의 변경인지 적는 규칙이 있고, CI가 이 형식을 검사합니다(`packages/conventions`). 바깥에서 많이 쓰는 비슷한 규칙으로 `feat:`, `fix:`처럼 적는 Conventional Commits가 있습니다. 형식이 정해져 있으면 기록을 훑거나 바뀐 내용을 모아 출시 노트를 만들기 쉽습니다.

:::quiz branch-cost Git에서 새 브랜치를 만들 때 실제로 일어나는 일은?
- [ ] 저장소의 모든 파일을 새 폴더에 복사한다
- [ ] 지금까지의 커밋을 모두 새로 만든다
- [x] 커밋 해시 하나를 적은 작은 파일을 만든다
- [ ] 원격 저장소에 새 저장소를 만든다

해시 하나를 적은 파일입니다. 그래서 브랜치는 몇 개를 만들어도 순식간이고 공간도 거의 들지 않습니다. 커밋과 파일 내용은 이미 해시 이름으로 저장되어 있으니 복사할 것이 없습니다.
:::

:::quiz shared-rebase 이미 푸시해서 동료가 받아 간 브랜치를 리베이스하고 강제로 푸시하면?
- [ ] 아무 일도 없다. 내용이 같으니까
- [ ] Git이 동료의 브랜치도 자동으로 고쳐 준다
- [ ] 리베이스는 푸시한 브랜치에는 동작하지 않는다
- [x] 커밋들이 새 해시로 다시 만들어져, 동료가 가진 옛 커밋과 어긋난다

새 해시가 됩니다. 리베이스는 커밋을 다른 부모 위에 새로 만들고, 부모가 바뀌면 해시도 바뀝니다. 동료의 브랜치는 옛 해시를 가리키고 있으니 합칠 때 같은 변경이 두 번 들어가는 등 꼬입니다.
:::

## 버전 번호의 약속: 시맨틱 버저닝

라이브러리의 버전 번호 `2.14.3`에는 약속이 담겨 있습니다. 이것이 [[시맨틱 버저닝]]입니다.

| 자리 | 올리는 때 | 예 |
| --- | --- | --- |
| 주 (MAJOR) `2` | 기존 사용자의 코드를 깨뜨리는 변경 | API 이름 변경, 기능 제거 |
| 부 (MINOR) `14` | 깨뜨리지 않고 기능을 더함 | 새 옵션 추가 |
| 수 (PATCH) `3` | 깨뜨리지 않는 버그 수정 | 오류 수정 |

`package.json`의 범위 표기는 이 약속에 기댑니다. `^2.14.3`은 2.x 중 2.14.3 이상(주 버전은 고정), `~2.14.3`은 2.14.x 중 2.14.3 이상입니다. 하지만 사람이 하는 약속이라 가끔 깨집니다. 그래서 23장에서 본 잠금 파일이 실제로 설치된 정확한 버전을 고정하고, 업데이트는 테스트를 돌리며 따로 합니다. `0.x` 버전은 "아직 안정되지 않음"이라 부 버전에서도 깨질 수 있습니다.

:::quiz caret `package.json`에 `"^2.14.3"`이라고 적었을 때 설치될 수 있는 버전은?
- [ ] `3.0.0`
- [x] `2.15.0`
- [ ] `2.14.2`
- [ ] `1.99.0`

`2.15.0`입니다. `^`는 주 버전을 고정하고 2.14.3 이상을 허락합니다. 3.0.0은 깨지는 변경일 수 있어 빠지고, 2.14.2와 1.99.0은 더 낮습니다. 실제로 어느 것이 깔렸는지는 잠금 파일이 고정합니다.
:::

## 다시 장면으로: 7부를 마치며

맨 앞 그림의 답은 "거의 한 곳"입니다. 라우트는 `allow(키)`라는 겉모양에만 기대고 속을 모르니, `RateLimiter` 안의 `Map`을 Redis로 바꾸면 됩니다. Redis에 묻는 일은 네트워크를 건너는 비동기라, 부르는 세 곳에 `await`을 붙이는 정도만 따라 고치면 됩니다. 데이터베이스도 같습니다. API는 `listComments` 같은 함수만 알고 SQL과 연결은 `packages/db` 안에 있습니다. 관련된 것은 모으고(응집도) 서로는 겉모양으로만 기대게(낮은 결합도) 한 덕분입니다. 고친 뒤에는 `apps/api/test`와 `packages/db/test`의 테스트가 동작이 그대로인지 확인하고, CI는 바뀐 패키지와 그것에 기대는 패키지만 골라 다시 돌립니다(19장의 의존 그래프).

7부는 여기서 끝납니다. 이 서비스를 공격하는 쪽, 키우는 쪽, 고치는 쪽에서 차례로 봤습니다. 이제 처음으로 돌아갈 차례입니다. 1장에서 이 페이지는 바이트였습니다. 그 바이트가 서버의 SSD에서 출발해 커널과 Caddy와 nginx를 지나고, 네트워크를 건너, 브라우저 안에서 픽셀이 되기까지 어떤 길을 걸을까요? 마지막 26장은 이 책 전체를 요청 하나로 처음부터 끝까지 따라갑니다.

## 프론트엔드와 이어지는 곳

- 컴포넌트가 너무 커지면 "이 컴포넌트가 바뀌는 이유가 몇 가지인가"(단일 책임)를 세어 보고, 데이터 가져오기는 훅으로, 표현은 작은 컴포넌트로 나눕니다.
- 서버 응답 모양을 화면 곳곳에서 직접 쓰지 않고 한 곳(어댑터)에서 화면용 모양으로 바꾸면, API가 바뀌어도 고칠 곳이 하나입니다.
- 렌더링은 순수하게, 부수 효과는 이벤트 핸들러와 이펙트에. React의 Strict Mode가 이펙트를 두 번 실행하는 건 이 규칙을 어긴 곳을 찾아 주려는 것입니다.
- 커밋은 작게, 메시지는 "왜"를 적고, 공유한 브랜치는 리베이스하지 않습니다.

## 용어 정리

:::terms
- 프로그래밍 패러다임 (programming paradigm) — 프로그램을 어떤 단위와 관점으로 구성할지에 대한 방식. 절차형, 객체 지향, 함수형 등.
- 객체 지향 프로그래밍 (object-oriented programming) — 데이터와 그 동작을 묶은 객체들이 메시지를 주고받는 방식으로 프로그램을 짜는 패러다임입니다.
- 객체 캡슐화 (encapsulation) — 데이터와 동작을 묶고 내부를 숨겨 정해진 창구로만 다루게 하는 것입니다.
- 상속 (inheritance) — 기존 클래스의 데이터와 동작을 물려받아 새 클래스를 만드는 것입니다.
- 다형성 (polymorphism) — 같은 메시지나 인터페이스에 객체의 종류마다 다르게 반응하는 성질입니다.
- 추상화 (abstraction) — 필요한 것만 드러내고 복잡한 세부를 감추는 것입니다.
- 함수형 프로그래밍 (functional programming) — 상태를 바꾸지 않는 순수 함수들의 조합으로 프로그램을 짜는 패러다임입니다.
- 순수 함수 (pure function) — 같은 입력에 늘 같은 출력을 돌려주고 바깥 상태를 바꾸지 않는 함수입니다.
- 불변성 (immutability) — 값을 고치지 않고, 바꾼 내용을 담은 새 값을 만드는 성질입니다.
- 응집도 (cohesion) — 한 모듈 안의 요소들이 하나의 목적으로 얼마나 모여 있는지. 높을수록 좋습니다.
- 결합도 (coupling) — 모듈끼리 서로에게 얼마나 기대는지. 낮을수록 고치기 쉽습니다.
- 단일 책임 원칙 (single responsibility principle) — 모듈은 한 가지 이유로만 바뀌어야 한다는 SOLID의 첫 원칙입니다.
- 의존성 역전 원칙 (dependency inversion principle) — 구체적인 구현이 아니라 추상에 기대야 한다는 SOLID의 원칙입니다.
- 디자인 패턴 (design pattern) — 자주 나오는 설계 문제에 대한 이름 붙은 재사용 가능한 해법입니다.
- 싱글턴 (singleton) — 인스턴스를 하나만 만들고 어디서나 그것을 쓰게 하는 패턴입니다.
- 팩토리 (factory) — 어떤 객체를 만들지 고르고 만드는 일을 한 함수나 객체에 모으는 패턴입니다.
- 옵저버 패턴 (observer pattern) — 한 대상의 변화를 구독한 여러 관찰자에게 알리는 패턴. 이벤트 리스너와 상태 구독이 이것입니다.
- 전략 패턴 (strategy pattern) — 알고리즘을 갈아 끼울 수 있게 따로 떼어 넘겨주는 패턴입니다.
- 어댑터 패턴 (adapter pattern) — 서로 맞지 않는 인터페이스 사이에서 모양을 맞춰 주는 패턴입니다.
- 데코레이터 패턴 (decorator pattern) — 원래 객체나 함수를 감싸 기능을 덧붙이는 패턴. 고차 컴포넌트, 미들웨어.
- 컴포지트 패턴 (composite pattern) — 낱개와 묶음을 같은 인터페이스로 다뤄 트리 구조를 만드는 패턴입니다.
- 프록시 패턴 (proxy pattern) — 대리 객체가 원래 객체로의 접근을 가로채 제어하는 패턴입니다.
- 의존성 주입 (dependency injection) — 모듈이 쓸 의존성을 스스로 만들지 않고 바깥에서 넘겨받는 것입니다.
- MVC (Model-View-Controller) — 데이터(모델), 보여 주기(뷰), 입력 처리(컨트롤러)를 나누는 구조입니다.
- 단방향 데이터 흐름 (unidirectional data flow) — 상태가 화면을 만들고, 행동이 액션을 통해 새 상태를 만드는 한 방향의 흐름. React, Redux의 구조입니다.
- 단위 테스트 (unit test) — 함수나 컴포넌트 하나를 따로 떼어 확인하는 테스트입니다.
- 통합 테스트 (integration test) — 여러 부분이 함께 맞물려 동작하는지 확인하는 테스트입니다.
- E2E 테스트 (end-to-end test) — 실제 브라우저와 서버로 사용자 흐름 전체를 확인하는 테스트입니다.
- 테스트 더블 (test double) — 테스트에서 진짜 의존성 대신 쓰는 가짜 객체. 스텁, 목, 스파이 등.
- TDD (Test-Driven Development) — 실패하는 테스트를 먼저 쓰고, 통과시키고, 다듬기를 반복하는 개발 방식입니다.
- 리팩터링 (refactoring) — 동작은 그대로 두고 코드의 구조를 개선하는 것입니다.
- 기술 부채 (technical debt) — 빠르게 가려고 남겨 둔 구조적 문제. 갚지 않으면 이후 변경 비용이 쌓입니다.
- 시맨틱 버저닝 (semantic versioning) — 주.부.수 버전 번호로 변경이 호환되는지를 약속하는 규칙입니다.
- 템플릿 메서드 패턴 (template method pattern) — 일의 순서(뼈대)는 위에서 정해 두고, 단계별 내용만 아래에서 채우게 하는 패턴입니다.
- 브랜치 전략 (branching strategy) — 여럿이 한 저장소에서 브랜치를 어떻게 나누고 합치고 배포할지 정한 약속. Git Flow, GitHub Flow, 트렁크 기반 개발 등이 있습니다.
:::

## 직접 해보기

:::practice git-objects Git 객체를 손으로 열어 보기
연습용 저장소를 만들고 커밋 하나를 한 뒤, `.git/objects` 안의 blob, tree, commit을 `git cat-file`로 열어 서로 해시로 어떻게 이어져 있는지 따라갑니다. 같은 내용의 파일 두 개가 같은 blob 하나를 가리키는지도 확인합니다.

```sh 터미널
mkdir git-inside && cd git-inside && git init -q
echo "hello" > a.txt && echo "hello" > b.txt && git add . && git commit -qm "첫 커밋"
git cat-file -p HEAD                 # commit: tree 해시, 작성자, 메시지
git cat-file -p "HEAD^{tree}"        # tree: a.txt, b.txt가 같은 blob 해시
git cat-file -p "$(git rev-parse HEAD:a.txt)"
cat .git/HEAD .git/refs/heads/*      # 브랜치는 해시 한 줄짜리 파일
find .git/objects -type f | head
```
:::

:::practice pure 순수 함수로 바꾸기
아래 함수가 왜 순수하지 않은지 세 가지를 찾고, 같은 일을 하는 순수 함수와 부수 효과를 맡는 바깥 함수로 나눕니다. 나눈 순수 함수에 단위 테스트를 vitest로 두세 개 써 봅니다.

```js
let total = 0;
function addToCart(item) {
  total += item.price;                               // 바깥 상태를 바꿈
  document.querySelector("#total").textContent = total; // DOM을 바꿈
  localStorage.setItem("total", total);              // 저장소를 바꿈
  return total;
}
```
:::

:::practice patterns 내 코드에서 패턴 찾기
지금 작업 중인 프론트엔드 프로젝트에서 이 장의 패턴 표에 있는 패턴을 다섯 개 이상 찾아, 파일 이름과 함께 "어떤 문제를 그 패턴으로 풀고 있는지"를 한 줄씩 적습니다. 결합도가 높다고 느끼는 곳 하나를 골라, 어댑터나 의존성 주입으로 어떻게 떼어 낼 수 있을지도 적습니다.
:::

:::practice tdd TDD로 작은 함수 만들기
"초 단위 숫자를 `1시간 2분 3초` 형식으로 바꾸는 함수"를 TDD로 만듭니다. 0초, 59초, 60초, 3661초, 음수 같은 경우를 테스트로 하나씩 먼저 쓰고, 통과할 만큼만 코드를 고치는 순환을 반복합니다. 끝나고 테스트가 몇 개였고 어느 경우에서 설계가 바뀌었는지 적습니다.
:::

## 장 전체 문제

:::quiz swap-redis 24장에서 정한 대로 요청 수 계수기를 Redis로 옮깁니다. 이 저장소에서 고칠 곳으로 가장 맞는 것은?
- [ ] 라우트마다 Redis 호출을 직접 써 넣는다
- [ ] `packages/db`에 계수기 테이블을 만든다
- [x] `RateLimiter`의 속을 Redis로 바꾸고, 비동기가 된 `allow`를 부르는 세 곳에 `await`을 붙인다
- [ ] Caddy 설정을 고친다

`RateLimiter` 안입니다. 겉모양이 `allow(키)`로 같으니 부르는 쪽은 `await`만 더하면 됩니다. 라우트마다 Redis를 직접 부르면 같은 규칙이 세 곳에 흩어져, 다음에 바꿀 때 또 세 곳을 고쳐야 합니다.
:::

:::quiz turbo-filter `packages/db`의 코드를 고친 PR에서 CI가 다시 타입 검사하고 테스트하는 것은?
- [ ] 저장소 전체
- [ ] `packages/db`만
- [x] `packages/db`와 그것을 쓰는 `apps/api`
- [ ] `apps/blog`만

바뀐 패키지와 그것에 기대는 패키지입니다. Turborepo가 의존 그래프를 따라 `db`를 쓰는 `api`까지 골라냅니다. `blog`와 `cs`는 `db`에 기대지 않으니 다시 돌리지 않습니다.
:::

## 스스로 점검

:::qa 결합도와 응집도를 각각 한 문장으로 설명하고, 좋은 설계는 어느 쪽인가요?
응집도는 한 모듈 안의 것들이 하나의 목적으로 모인 정도, 결합도는 모듈끼리 서로에게 기대는 정도입니다. 좋은 설계는 응집도가 높고 결합도가 낮아서, 한 가지를 고칠 때 한 곳만 바뀝니다.
:::

:::qa React가 상태를 불변으로 다루라고 하는 이유는?
상태가 바뀌었는지를 내용을 다 비교하지 않고 참조가 달라졌는지만 보고 빠르게 판단하기 때문입니다. 배열을 직접 고치면 참조가 같아 바뀐 걸 알아채지 못해 화면이 갱신되지 않고, `memo`와 `useMemo`의 비교도 틀어집니다.
:::

:::qa `addEventListener`, Redux의 `subscribe`, 브라우저의 `MutationObserver`가 공통으로 쓰는 패턴은?
옵저버 패턴입니다. 관찰 대상에 콜백을 구독으로 등록해 두면, 대상이 바뀌거나 사건이 일어날 때 등록된 관찰자들에게 알려 줍니다.
:::

:::qa 의존성 주입이 테스트를 쉽게 만드는 이유는?
모듈이 네트워크나 DB 같은 의존성을 직접 만들지 않고 바깥에서 받으니, 테스트에서는 진짜 대신 정해진 값을 돌려주는 가짜(테스트 더블)를 넣어 빠르고 예측 가능하게 확인할 수 있습니다.
:::

:::qa Git에서 브랜치를 만드는 게 순식간인 이유와, 과거 커밋을 몰래 바꿀 수 없는 이유는?
브랜치는 커밋 해시 하나를 적은 작은 파일(포인터)이라 만들 때 복사할 것이 없습니다. 커밋은 부모 커밋의 해시를 담고 자기 이름도 내용의 해시라서, 과거 커밋 하나를 바꾸면 그 뒤 모든 커밋의 해시가 바뀌어 드러납니다.
:::

:::qa `"react": "^18.2.0"`은 어떤 버전까지 설치될 수 있나요? 그런데도 잠금 파일이 필요한 이유는?
주 버전 18은 고정하고 18.2.0 이상의 18.x를 허락합니다. 시맨틱 버저닝은 사람이 지키는 약속이라 부 버전이나 수 버전에서도 가끔 깨지고, 설치하는 날마다 다른 버전이 깔리면 재현이 안 되니, 잠금 파일로 실제 설치된 정확한 버전과 해시를 고정합니다.
:::
