25장은 처음으로 돌아가며 끝났습니다. 1장에서 이 페이지는 바이트였습니다. 그 바이트가 서버의 SSD에서 출발해 네트워크를 건너고, 브라우저 안에서 픽셀이 되기까지 어떤 길을 걸을까요? 면접에서 가장 자주 나오는 질문, "주소창에 URL을 치고 엔터를 누르면 무슨 일이 일어나나요?"의 답이기도 합니다. 이 책의 장들은 모두 그 답의 한 토막이었습니다.

![엔터에서 픽셀까지. 위 두 줄은 앞의 장들에서 하나씩 본 것이고, 진한 칸인 레이아웃, 페인트, 합성은 이 장에서 처음 자세히 봅니다](journey-scene.svg)

이 장은 이 그림을 왼쪽 위에서부터 시간 순서로 따라갑니다. 앞에서 본 단계는 짧게 짚으며 어느 장을 펼치면 되는지 적고, 아직 보지 않은 브라우저 안쪽, 받은 바이트가 화면의 픽셀이 되는 과정은 자세히 봅니다.

## 0ms: 키를 누르는 순간

키보드의 스위치가 닫히면 키보드 컨트롤러가 USB로 신호를 보내고, 운영체제는 인터럽트를 받아 키 입력 이벤트를 만듭니다(4장). 창 관리자가 그 이벤트를 지금 앞에 있는 브라우저 창에 건네고, 브라우저 프로세스의 UI 스레드가 받습니다(6장). 글자를 칠 때마다 주소창은 방문 기록과 북마크에서 후보를 찾아 보여 줍니다. Chrome의 방문 기록은 SQLite 파일입니다(21장).

엔터를 누르면 브라우저는 먼저 이것이 주소인지 검색어인지 정합니다. `cs.mlnl.cloud`는 점이 있고 알려진 최상위 도메인으로 끝나니 주소로 봅니다. 스킴을 적지 않았으니 요즘 브라우저는 `https://`를 먼저 시도합니다. 이 도메인을 전에 방문해 HSTS 헤더(14장)를 받았다면 `http://`는 아예 쓰지 않습니다. 그리고 이 주소를 보여 줄 렌더러 프로세스를 미리 띄워 두기 시작합니다(6장의 사이트 격리).

:::quiz hsts-first 주소창에 `cs.mlnl.cloud`만 치고 엔터를 눌렀습니다. 브라우저가 `http://`로 한 번 묻지도 않고 처음부터 `https://`로 가는 경우는?
- [ ] 서버가 80번 포트를 닫아 두었을 때
- [x] 전에 이 도메인에서 HSTS 헤더를 받았거나, 도메인이 브라우저의 HSTS 목록에 있을 때
- [ ] DNS 답에 HTTPS라고 적혀 있을 때
- [ ] 공유기가 HTTPS만 허락할 때

HSTS 덕분입니다. 이 사이트의 Caddy는 응답마다 `Strict-Transport-Security`를 붙이니, 한 번 방문한 브라우저는 1년 동안 처음부터 `https://`로 갑니다. 그 전이라면 요즘 브라우저는 `https://`를 먼저 시도해 보고 안 될 때만 `http://`로 내려갑니다.
:::

## 이름에서 연결까지: 왕복 세 번

여기부터는 9장 맨 앞 그림의 왕복 네 번 가운데 세 번입니다.

1. **이름을 IP로**(13장). 브라우저 캐시, 운영체제 캐시와 hosts 파일을 보고, 없으면 DHCP로 받은 DNS 서버에 UDP 53번으로 묻습니다. 통신사의 재귀 리졸버가 루트, `.cloud`, 가비아의 네임서버에 차례로 물어 `54.116.117.190`을 받아 옵니다. 이 질문 패킷 하나도 공유기까지 가려면 공유기의 MAC 주소가 필요하니, ARP 캐시에 없으면 ARP부터 합니다(10장).
2. **연결 맺기**(12장). 운영체제가 임시 포트를 골라 SYN을 보냅니다. 패킷은 공유기의 NAT에서 보내는 주소가 바뀌고, 라우터 열몇 개를 지나며 IP 헤더만 읽히고, 구간마다 새 프레임에 실립니다(9~11장).
3. **암호 맞추기**(14장). ClientHello에 SNI로 `cs.mlnl.cloud`를, ALPN으로 `h2`를 적어 보냅니다. Caddy가 인증서를 내밀면 브라우저는 루트 인증 기관까지 서명을 확인하고 대칭키를 만듭니다.
4. **요청**(14장). 마지막 TLS 메시지와 함께 `GET /` 요청이 HTTP/2 프레임으로 갑니다. 헤더에는 `Host`, 받을 수 있는 압축 방식, 언어가 실립니다. 이 사이트는 쿠키를 쓰지 않으니 쿠키는 없습니다.

처음 방문이라면 여기까지 왕복이 네 번 듭니다. 서울 안이라면 다 합쳐 100ms 안쪽입니다. 두 번째 방문부터는 DNS가 캐시에서 끝나고, 같은 탭 안에서 다음 장으로 넘어갈 때는 이미 열린 연결을 그대로 씁니다.

## 서버 안에서

요청을 담은 패킷이 서버의 네트워크 카드에 닿으면, 카드가 DMA로 RAM에 써 넣고 인터럽트를 겁니다(8장). 커널의 TCP 스택이 조각을 순서대로 맞추고, 443번 포트의 소켓을 들고 있는 Caddy를 epoll로 깨웁니다(8·12장).

[[Caddy]]는 TLS를 풀고 `Host: cs.mlnl.cloud`를 보고 `reverse_proxy mlnl-cs:80` 줄을 고릅니다(17장). `mlnl-cs`라는 이름은 Docker 네트워크 안의 작은 DNS 서버(`127.0.0.11`)에 물어 컨테이너의 IP로 바꿉니다(13장). Caddy는 nginx 컨테이너와 새로 연결을 맺거나 맺어 둔 연결을 다시 써서 평범한 HTTP 요청을 보냅니다.

nginx는 경로 `/`를 `/usr/share/nginx/html/index.html` 파일로 바꿉니다. 이 파일은 자주 읽히니 커널의 페이지 캐시에 이미 있고, nginx는 `sendfile`로 디스크를 거치지 않고 페이지 캐시에서 소켓으로 바로 보냅니다(8·17장). 응답에는 `Cache-Control: no-cache`가 붙습니다(14장). 돌아오는 길에 Caddy가 zstd로 압축하고 HSTS를 붙입니다. 이 일이 서버 안에서는 1ms 남짓입니다. 이 페이지에서 시간이 드는 곳은 서버가 아니라 거리입니다.

:::quiz docker-dns Caddy가 `reverse_proxy mlnl-cs:80`을 따라가려고 `mlnl-cs`라는 이름의 IP를 물을 때, 묻는 곳은?
- [ ] 가비아의 네임서버
- [ ] 통신사의 재귀 리졸버
- [x] Docker 네트워크 안의 작은 DNS 서버 (`127.0.0.11`)
- [ ] 서버의 `/etc/hosts`만

Docker의 내장 DNS입니다. 같은 Docker 네트워크에 붙은 컨테이너의 이름을 그 컨테이너의 IP로 풀어 줍니다. `mlnl-cs`는 인터넷의 이름이 아니니 바깥 DNS는 모릅니다. 컨테이너가 죽었다면 이 질문이 실패하고, Caddy는 502를 돌려줍니다(17장).
:::

## 돌아와서: 바이트에서 문서로

응답 패킷은 같은 길을 거꾸로 돌아와, 노트북의 네트워크 카드와 커널을 지나 브라우저 프로세스의 소켓에 닿습니다. 브라우저 프로세스는 TLS를 풀고 HTTP/2 프레임을 모아 응답 헤더를 읽습니다. `Content-Type: text/html`이니 문서로 보여 줄 것이고, 그래서 아까 띄워 둔 렌더러 프로세스에 본문을 IPC로 넘깁니다(6장). 여기서부터는 그 렌더러의 메인 스레드가 맡습니다.

1. **압축 풀기와 글자로 바꾸기.** zstd를 풀고, `charset=utf-8`대로 바이트를 글자로 해독합니다(1장).
2. **토큰으로 자르기.** `<`, 태그 이름, 속성, 글자를 읽어 "여는 태그 `main`", "글자 '컴퓨터…'" 같은 토큰으로 자릅니다.
3. **DOM 나무 만들기.** 토큰을 차례로 받아 노드를 만들고 부모 자식으로 이어 19장 맨 앞의 DOM 나무를 짓습니다. HTML 파서는 닫는 태그가 빠져도 정해진 규칙대로 고쳐 가며 짓습니다.

파서는 나무를 짓다가 다른 자원을 만납니다. 이 페이지의 `<head>`에는 글꼴 CSS(`cdn.jsdelivr.net`), 이 책의 `style.css`, 그리고 `defer`가 붙은 `app.js`가 있습니다. 브라우저는 파싱을 계속하면서 이 파일들을 미리 요청합니다. 이 책의 CSS와 JS는 같은 출처라 이미 열린 연결에 실려 오고, 글꼴 CSS는 다른 출처라 DNS 조회와 연결을 따로 합니다. 그래서 HTML에 `<link rel="preconnect" href="https://cdn.jsdelivr.net">`을 넣어 그 연결을 미리 맺게 했습니다(13장).

스크립트에는 함정이 있습니다. 아무 표시 없는 `<script src>`를 만나면, 파서는 그 파일을 받아 실행할 때까지 멈춥니다. 스크립트가 `document.write`로 문서를 바꿀 수도 있기 때문입니다. 이걸 피하는 표시가 둘입니다.

| | 받는 동안 파싱 | 실행 시점 | 실행 순서 |
| --- | --- | --- | --- |
| 표시 없음 | 멈춤 | 받자마자 | 문서 순서 |
| `defer` | 계속 | 파싱이 다 끝난 뒤 | 문서 순서 |
| `async` | 계속 | 받자마자 (파싱 도중일 수 있음) | 먼저 받은 것부터 |

이 책의 `app.js`는 `defer`라서 파싱을 막지 않고, DOM이 다 지어진 뒤에 문제와 진행 막대를 찾아 붙습니다(19장의 `querySelectorAll`). CSS는 반대로 [[렌더 차단 리소스]]입니다. CSS가 오기 전에 그리면 꾸밈 없는 글자가 번쩍였다가 다시 그려지니, 브라우저는 `<head>`의 CSS를 다 받을 때까지 첫 화면을 그리지 않고 기다립니다.

:::quiz parser-block `<head>`에 `defer`도 `async`도 없는 `<script src="big.js">`가 있고, 그 파일을 받는 데 1초가 걸립니다. 그동안 일어나는 일은?
- [ ] 파싱은 계속되고, 파일이 오면 그때 실행한다
- [x] HTML 파싱이 멈춰서 그 아래 내용의 DOM이 1초 동안 지어지지 않는다
- [ ] 브라우저가 스크립트를 건너뛰고 나중에 실행하지 않는다
- [ ] CSS 다운로드도 멈춘다

파싱이 멈춥니다. 스크립트가 문서를 바꿀 수 있으니 파서는 실행이 끝날 때까지 기다립니다. 그래서 스크립트는 `defer`를 붙이거나 `</body>` 바로 앞에 둡니다. 다른 파일의 다운로드는 미리 보기 스캐너 덕분에 계속됩니다.
:::

## 렌더링: DOM에서 픽셀까지

DOM은 "무엇이 있는가"일 뿐, 어디에 어떤 크기와 색으로 그릴지는 아직 모릅니다. CSS도 파싱해서 규칙들의 나무인 [[CSSOM]]을 만들고, 둘을 합쳐 화면에 그리기까지 몇 단계를 더 거칩니다. HTML, CSS, JS를 받아 첫 픽셀을 그리기까지의 이 길을 [[중요 렌더링 경로]]라고 부릅니다.

![HTML과 CSS가 각자 나무가 되고, 합쳐져 레이아웃, 페인트, 합성을 거쳐 화면이 됩니다. 아래는 바꾸는 속성에 따라 어느 단계부터 다시 하는지입니다](journey-render.svg)

1. **스타일 계산.** DOM의 노드마다 CSSOM의 규칙을 맞춰 보고 최종 스타일을 정합니다. `display: none`인 노드는 그리지 않으니 빼고, `::before` 같은 가상 요소는 더합니다. 그렇게 화면에 그릴 것만 남긴 나무를 [[렌더 트리]]라고 합니다.
2. **레이아웃.** 화면 너비에서 시작해 나무를 따라 내려가며 상자마다 위치와 크기를 계산합니다. 글자가 몇 줄로 접히는지, 표의 칸이 몇 픽셀인지가 여기서 정해집니다. 위치나 크기에 영향을 주는 것이 바뀌어 이 계산을 다시 하는 것을 [[리플로우]]라고 합니다.
3. **페인트.** 상자마다 "여기에 이 색 사각형, 저기에 이 글자"라는 그리기 명령 목록을 만들고, 그 명령을 픽셀로 바꿉니다. 색이나 그림자처럼 위치와 상관없는 것만 바뀌어 이 단계부터 다시 하는 것을 [[리페인트]]라고 합니다.
4. **합성.** 브라우저는 페이지를 한 장으로 그리지 않고 여러 [[레이어]]로 나눠 그립니다. 고정된 헤더, `transform`으로 움직이는 요소, 동영상처럼 따로 움직일 만한 것들이 각자 레이어가 됩니다. 마지막에 합성 스레드가 레이어들을 GPU로 겹쳐 한 장의 화면을 만듭니다(2장). 이 단계가 [[합성]]입니다.

여기까지 끝나면 첫 화면이 뜹니다. 레이어를 나눠 두는 이유가 4단계에 있습니다. 레이어 하나가 움직이기만 하면 레이아웃과 페인트를 다시 할 필요 없이 GPU가 레이어의 위치만 바꿔 다시 겹치면 됩니다. 2장에서 "CSS `transform`과 `opacity` 애니메이션이 부드러운 이유"라고 미뤄 두었던 답이 이것입니다.

:::quiz render-tree `display: none`인 요소와 `visibility: hidden`인 요소는 렌더 트리에 어떻게 들어갈까요?
- [ ] 둘 다 렌더 트리에 없다
- [ ] 둘 다 렌더 트리에 있다
- [ ] `display: none`만 있고 `visibility: hidden`은 없다
- [x] `display: none`은 빠지고, `visibility: hidden`은 자리를 차지한 채 들어간다

`display: none`은 그리지도 자리를 차지하지도 않으니 빠집니다. `visibility: hidden`은 보이지만 않을 뿐 레이아웃에서 자리를 차지하니 렌더 트리에 남습니다. 그래서 `display`를 바꾸면 리플로우가 일어나고, `visibility`만 바꾸면 페인트부터 다시 합니다.
:::

:::quiz composite-only 다음 중 레이아웃도 페인트도 다시 하지 않고 합성만으로 처리될 수 있는 변경은?
- [ ] `width: 200px` → `300px`
- [ ] `top: 0` → `100px`
- [ ] `color: black` → `red`
- [x] `transform: translateX(0)` → `translateX(100px)`

`transform`입니다. 그 요소가 자기 레이어에 있으면 GPU가 레이어를 옮겨 겹치기만 하면 됩니다. `width`와 `top`은 위치와 크기를 바꾸니 레이아웃부터, `color`는 페인트부터 다시 합니다. 그래서 움직이는 애니메이션은 `top`, `left` 대신 `transform`으로 만듭니다.
:::

## 16ms의 한 프레임

첫 화면이 뜬 뒤에도 브라우저는 계속 그립니다. 화면은 1초에 60번(60Hz) 새로 고쳐지니, 브라우저도 16.7ms마다 한 장을 내놓아야 매끄럽게 보입니다. 이 시간 안에 렌더러의 메인 스레드는 6장의 이벤트 루프를 한 바퀴 돌며 차례로 일합니다. 작업 하나(클릭 처리 같은 JS) → 마이크로태스크 → `requestAnimationFrame` 콜백 → 스타일 → 레이아웃 → 페인트, 그리고 합성은 합성 스레드가 따로 합니다.

![한 프레임 안의 일. JS가 오래 붙잡으면 그 프레임에 낼 장을 놓쳐 화면이 멈칫합니다](journey-frame.svg)

JS 작업 하나가 50ms를 넘으면 [[롱 태스크]]라고 부릅니다. 그동안 메인 스레드는 다른 아무것도 못 하니, 스크롤과 클릭이 밀리고 프레임이 빠집니다. 무거운 계산은 쪼개거나(작업 사이사이 브라우저에 차례를 넘김) Web Worker로 보냅니다(6장).

레이아웃을 쓸데없이 여러 번 하게 만드는 흔한 실수도 있습니다. 브라우저는 스타일을 바꿔도 레이아웃을 바로 하지 않고 프레임 끝에 한 번에 몰아서 합니다. 그런데 바꾼 직후에 `offsetHeight`, `getBoundingClientRect()`처럼 위치를 읽으면, 맞는 값을 주려고 그 자리에서 레이아웃을 강제로 합니다. 읽고 쓰기를 반복문 안에서 번갈아 하면 레이아웃을 반복 횟수만큼 하게 되는데, 이것을 [[레이아웃 스래싱]]이라고 합니다. 읽기를 먼저 다 모아서 하고 쓰기를 나중에 몰아서 하면 한 번으로 줄어듭니다.

```js
// 나쁨: 읽기(offsetWidth)와 쓰기(style.width)가 번갈아 → 강제 레이아웃 n번
for (const el of items) el.style.width = `${box.offsetWidth / 2}px`;

// 좋음: 한 번 읽고, 쓰기만 몰아서 → 레이아웃은 프레임 끝에 한 번
const half = box.offsetWidth / 2;
for (const el of items) el.style.width = `${half}px`;
```

:::quiz frame-budget 주사율 120Hz 화면에서 브라우저가 한 프레임에 쓸 수 있는 시간은 약 몇 ms일까요?
= 8.3 | 8.33 | 8 | 8.3ms

1000 ÷ 120 ≈ **8.3ms**입니다. 60Hz의 절반이니, 120Hz 화면에서 매끄럽게 보이려면 JS와 레이아웃과 페인트가 그 안에 끝나야 합니다. 맞추지 못하면 브라우저는 그 프레임을 건너뜁니다.
:::

:::quiz thrash 반복문에서 요소 100개마다 `box.offsetWidth`를 읽고 그 요소의 `style.width`를 바꿉니다. 브라우저가 레이아웃을 하는 횟수는 대략?
- [ ] 프레임 끝에 한 번
- [ ] 두 번
- [x] 100번 가까이
- [ ] 레이아웃은 하지 않는다

100번 가까이입니다. 앞에서 바꾼 스타일 때문에 `offsetWidth`가 맞는 값을 주려면 그 자리에서 레이아웃을 다시 해야 하니, 읽을 때마다 강제 레이아웃이 일어납니다. 읽기를 반복문 밖으로 빼면 한 번으로 줄어듭니다.
:::

## 클릭 하나, 마지막으로

이 장을 다 읽고 맨 아래 "다 읽었어요"를 누르면 이 책의 마지막 일이 일어납니다.

1. 마우스 스위치가 인터럽트를 걸고, 커널과 창 관리자를 지나 브라우저 프로세스가 클릭을 받습니다(4장).
2. 브라우저 프로세스는 클릭 좌표가 어느 탭, 어느 프레임 위인지 보고 이 페이지의 렌더러에 IPC로 넘깁니다(6장).
3. 렌더러의 메인 스레드는 이벤트 루프에서 이 클릭을 꺼내, `app.js`가 붙여 둔 리스너를 V8로 실행합니다(5·6장). 진행 기록 객체는 렌더러의 힙에 있습니다(7장).
4. 리스너는 `localStorage.setItem`으로 `{"journey:read":1, …}`를 JSON 문자열로 넘깁니다. 브라우저는 이걸 받아 모아 두었다가 프로필 폴더의 파일에 `write`하고, 커널은 페이지 캐시에 적었다가 SSD에 내려보냅니다(8장).
5. 그사이 체크 상자의 모양이 바뀌었으니 스타일, 페인트, 합성을 거쳐 다음 프레임에 체크 표시가 그려집니다. 이 장에서 본 그대로입니다.

:::quiz setitem-where `localStorage.setItem`이 돌아온 바로 그 순간, 진행 기록은 어디까지 갔을까요?

- [x] 브라우저가 받아 두었고, 프로필 폴더의 파일과 SSD에는 조금 뒤에 쓰인다
- [ ] 서버의 데이터베이스로 전송되었다
- [ ] 쿠키에 담겨 다음 요청 때 서버로 간다

브라우저가 받아 두었을 뿐입니다. 페이지 쪽 코드는 바로 다음 줄에서 새 값을 읽을 수 있지만, 파일에 쓰는 일은 모아서 나중에 하고, 그 `write`조차 페이지 캐시에 적고 돌아옵니다(8장). 이 기록은 서버로는 아예 가지 않습니다.
:::

## 다시 장면으로: 이 책의 마지막 장면

맨 앞 그림을 한 번에 읽으면 이렇습니다. 키 하나가 인터럽트가 되어 브라우저에 닿았습니다. 이름은 리졸버와 네임서버들을 거쳐 IP가 되었습니다. 연결은 핸드셰이크로 맺어지고 암호로 감싸였습니다. 요청은 패킷으로 쪼개져 공유기와 라우터들을 지나 서버에 닿았습니다. 커널과 Caddy와 nginx를 거쳐 페이지 캐시의 바이트가 돌아왔고, 렌더러가 그 바이트를 글자로, 나무로, 상자로, 픽셀로 바꿨습니다. 그리고 마지막 클릭은 다시 바이트가 되어 SSD에 남았습니다. 1장의 0과 1에서 시작한 이 책은, 이 페이지 하나가 지나는 길을 26장에 걸쳐 따라왔습니다.

이 책의 장면들은 모두 이 페이지와 이 서버였지만, 같은 길은 어느 웹 페이지에나 있습니다. 다음에 느린 페이지를 만나면 이 그림의 어느 칸이 느린지부터 물어보세요. DNS인지, 연결인지, 서버인지, 큰 스크립트인지, 레이아웃인지. 그 질문에 답할 수 있다면 이 책이 할 일을 다 한 것입니다.

## 곁가지: 면접에서 이 질문에 2분 안에 답하기

"주소창에 URL을 치면 무슨 일이 일어나나요?"는 정답이 하나인 질문이 아니라, 지원자가 어느 층까지 아는지 보는 질문입니다. 큰 줄기를 먼저 말하고, 면접관이 파고드는 칸에서 이 책의 그 장으로 내려가면 됩니다.

1. 브라우저가 입력이 URL인지 검색어인지 판단하고, HSTS 목록을 보고 스킴을 정합니다.
2. DNS로 도메인을 IP로 바꿉니다. 브라우저, OS, 리졸버 캐시를 거치고, 없으면 루트부터 차례로 묻습니다.
3. 그 IP의 443번 포트와 TCP 3-way 핸드셰이크로 연결합니다.
4. TLS 핸드셰이크로 인증서를 확인하고 대칭키를 정합니다.
5. HTTP 요청을 보냅니다. 패킷은 IP 라우팅으로 서버까지 가고, 구간마다 MAC 주소가 바뀝니다.
6. 서버에서는 로드 밸런서나 리버스 프록시가 받아 앱 서버로 넘기고, 응답을 돌려줍니다.
7. 브라우저는 HTML을 파싱해 DOM을, CSS로 CSSOM을 만들고, 렌더 트리, 레이아웃, 페인트, 합성을 거쳐 그립니다.
8. 그 사이 만나는 CSS, JS, 이미지를 추가로 요청하고, JS가 실행되며 페이지가 살아납니다.

## 프론트엔드와 이어지는 곳

웹 성능 지표는 이 장의 그림에 그대로 대응합니다.

| 지표 | 무엇을 재나 | 이 장의 어느 칸 |
| --- | --- | --- |
| [[TTFB]] | 요청부터 응답 첫 바이트까지 | DNS, TCP, TLS, 서버 처리 (9~17장) |
| FCP | 첫 글자나 이미지가 그려진 때 | 렌더 차단 리소스, 첫 렌더링 |
| LCP | 화면에서 가장 큰 요소가 그려진 때 | 큰 이미지와 글꼴, 렌더링 |
| CLS | 그리는 도중 요소가 얼마나 밀렸나 | 늦게 온 이미지와 광고가 일으킨 리플로우 |
| INP | 클릭이나 입력 뒤 다음 프레임이 그려지기까지 | 롱 태스크, 레이아웃 스래싱 |

- 이미지에 `width`와 `height`를 적어 두면 브라우저가 자리를 미리 잡아 CLS가 줄어듭니다.
- 첫 화면에 필요한 CSS는 작게(12장의 14KB), 나머지 스크립트는 `defer`로.
- 움직임은 `transform`과 `opacity`로, 위치를 읽는 코드와 쓰는 코드는 묶어서.
- DevTools의 Performance 패널은 이 장의 그림을 실제 시간 막대로 보여 줍니다.

## 용어 정리

:::terms
- 중요 렌더링 경로 (critical rendering path) — 브라우저가 HTML, CSS, JS를 받아 첫 화면의 픽셀을 그리기까지 거치는 단계들. 파싱, 스타일, 레이아웃, 페인트, 합성입니다.
- CSSOM (CSS Object Model) — 브라우저가 CSS를 파싱해 만든 규칙들의 나무. DOM과 합쳐 각 요소의 최종 스타일을 정합니다.
- 렌더 트리 (render tree) — DOM과 CSSOM을 합쳐 화면에 실제로 그릴 것만 남긴 나무. `display: none`인 요소는 빠집니다.
- 렌더 차단 리소스 (render-blocking resource) — 다 받을 때까지 브라우저가 첫 화면을 그리지 않고 기다리는 자원. `<head>`의 CSS가 대표적입니다.
- 리플로우 (reflow) — 요소의 위치나 크기에 영향을 주는 변경 때문에 레이아웃을 다시 계산하는 것. 레이아웃이라고도 부릅니다.
- 리페인트 (repaint) — 위치와 크기는 그대로이고 색, 그림자처럼 보이는 모습만 바뀌어 페인트부터 다시 하는 것입니다.
- 레이어 (layer) — 브라우저가 페이지를 나눠 따로 그려 두는 판. 합성 단계에서 GPU가 겹쳐 한 화면을 만들고, `transform`, `opacity` 변경은 레이어만 옮겨 처리합니다.
- 합성 (compositing) — 따로 그려 둔 레이어들을 GPU로 겹쳐 최종 화면을 만드는 단계. 메인 스레드가 아닌 합성 스레드가 합니다.
- 롱 태스크 (long task) — 메인 스레드를 50ms 넘게 붙잡는 작업 하나. 그동안 입력 처리와 화면 갱신이 밀립니다.
- 레이아웃 스래싱 (layout thrashing) — 스타일 쓰기와 위치 읽기를 번갈아 해서 브라우저가 레이아웃을 강제로 여러 번 하게 되는 것입니다.
- TTFB (Time To First Byte) — 요청을 보낸 뒤 응답의 첫 바이트가 도착하기까지의 시간. DNS, 연결, TLS, 서버 처리 시간이 모두 들어갑니다.
:::

## 직접 해보기

:::practice timing 이 페이지가 오기까지 걸린 시간을 구간별로 재기
`curl`은 DNS, 연결, TLS, 첫 바이트, 끝까지 걸린 시각을 따로 알려 줍니다. 두 번 연달아 재서 DNS 캐시가 생긴 뒤 무엇이 줄어드는지 봅니다.

```sh macOS · Linux
curl -o /dev/null -s --compressed -w 'dns %{time_namelookup}  tcp %{time_connect}  tls %{time_appconnect}  ttfb %{time_starttransfer}  total %{time_total}\n' https://cs.mlnl.cloud/
```

```powershell Windows (PowerShell)
curl.exe -o NUL -s --compressed -w "dns %{time_namelookup}  tcp %{time_connect}  tls %{time_appconnect}  ttfb %{time_starttransfer}  total %{time_total}\n" https://cs.mlnl.cloud/
```

숫자는 시작부터 그 단계가 끝날 때까지 쌓인 초입니다. 이 글을 쓰며 잰 한 번은 DNS 0.042초, TCP 0.049초, TLS 0.063초, 첫 바이트 0.078초였습니다. 이웃한 숫자의 차이가 9장 맨 앞 그림의 왕복 하나하나입니다.
:::

:::practice performance DevTools로 이 페이지의 한 프레임 들여다보기
Chrome에서 이 페이지를 열고 DevTools의 Performance 패널에서 새로고침 녹화 버튼을 누릅니다. 녹화가 끝나면 Network 줄에서 HTML, CSS, JS가 온 때를, Main 줄에서 Parse HTML, Recalculate Style, Layout, Paint를, Frames 줄에서 그려진 프레임을 찾습니다. 그다음 문제 하나를 풀어 클릭 한 번의 Event: click부터 다음 Paint까지를 찾아봅니다.
:::

:::practice thrash 레이아웃 스래싱을 눈으로 보기
아무 페이지의 콘솔에 아래를 붙여 넣고 두 방식의 시간을 비교합니다. Performance 패널로 녹화하면 나쁜 쪽에 보라색 Layout 막대가 수백 개 찍힌 것이 보입니다.

```js 콘솔
const box = document.body;
const els = Array.from({ length: 500 }, () => document.body.appendChild(document.createElement("div")));
let t = performance.now();
for (const el of els) el.style.width = `${box.offsetWidth / 2}px`;    // 읽기와 쓰기를 번갈아
console.log("번갈아", performance.now() - t, "ms");
t = performance.now();
const half = box.offsetWidth / 2;
for (const el of els) el.style.width = `${half}px`;                   // 한 번 읽고 몰아 쓰기
console.log("몰아서", performance.now() - t, "ms");
els.forEach((el) => el.remove());
```
:::

## 장 전체 문제

:::quiz first-paint-order 처음 방문할 때 엔터에서 첫 화면까지의 순서로 맞는 것은?
- [ ] TCP 연결 → DNS → TLS → HTML 파싱 → 레이아웃 → 페인트 → 합성
- [ ] DNS → TCP 연결 → TLS → HTML 파싱 → 페인트 → 레이아웃 → 합성
- [ ] DNS → TLS → TCP 연결 → HTML 파싱 → 레이아웃 → 페인트 → 합성
- [x] DNS → TCP 연결 → TLS → HTML 파싱 → 레이아웃 → 페인트 → 합성

DNS로 IP를 얻어야 연결하고, TLS는 TCP 위에서 하고, 받은 HTML을 파싱해야 그릴 것이 생깁니다. 그리고 위치와 크기를 정해야(레이아웃) 그릴 수 있고(페인트), 그린 레이어들을 겹쳐야(합성) 화면이 됩니다.
:::

:::quiz ttfb-calc 처음 방문해 DNS 캐시가 없고, 리졸버까지 RTT가 10ms, 서버까지 RTT가 20ms, 서버 처리가 5ms라면 TTFB는 최소 몇 ms일까요? (리졸버는 한 번에 답을 준다고 합니다)
= 75 | 75ms

10 + 20 × 3 + 5 = **75ms**입니다. DNS 왕복 하나, TCP, TLS, HTTP 왕복 셋, 그리고 서버 처리입니다. 같은 서버에 두 번째로 오면 DNS와 연결이 이미 있으니 20 + 5 = 25ms로 줄어듭니다.
:::

## 스스로 점검

:::qa CSS가 렌더 차단 리소스인 이유와, 스크립트가 파싱을 막는 이유는 각각 무엇인가요?
CSS가 오기 전에 그리면 꾸밈 없는 화면이 번쩍였다가 다시 그려지니, 브라우저는 `<head>`의 CSS를 다 받을 때까지 첫 화면을 미룹니다. 스크립트는 `document.write` 등으로 문서 자체를 바꿀 수 있어서, 표시 없는 스크립트를 만나면 파서가 실행이 끝날 때까지 멈춥니다. `defer`와 `async`가 이 멈춤을 없앱니다.
:::

:::qa 리플로우와 리페인트의 차이를 말하고, 각각 일으키는 속성을 예로 드세요.
리플로우는 위치나 크기가 바뀌어 레이아웃부터 다시 하는 것이고(`width`, `top`, 글자 추가, `display`), 리페인트는 위치는 그대로 두고 모습만 바뀌어 페인트부터 다시 하는 것입니다(`color`, `background`, `visibility`). `transform`과 `opacity`는 레이어에 있으면 둘 다 건너뛰고 합성만 합니다.
:::

:::qa JS가 바쁠 때 `top`으로 만든 애니메이션은 끊기고 `transform`으로 만든 애니메이션은 부드러운 이유는?
`top`은 레이아웃과 페인트를 다시 해야 하는데 그 일은 메인 스레드에서 하니, JS가 메인 스레드를 붙잡으면 함께 밀립니다. `transform`은 레이어의 위치만 바꾸면 되고 그 일은 합성 스레드와 GPU가 하니, 메인 스레드가 바빠도 프레임을 낼 수 있습니다.
:::

:::qa 같은 페이지를 두 번째로 열 때 첫 번째보다 빨라지는 곳을 이 장의 그림에서 세 군데 이상 꼽아 보세요.
DNS 답이 브라우저와 OS 캐시에 남아 있어 DNS 왕복이 없습니다. 같은 탭에서는 연결이 열려 있으면 TCP와 TLS 핸드셰이크가 없고, 최근에 접속했다면 TLS를 짧게 재개합니다. 해시가 붙은 CSS와 JS는 1년 캐시라 요청조차 하지 않고, HTML은 304로 본문 없이 끝날 수 있습니다(14장). 렌더러도 V8의 코드 캐시로 `app.js`를 더 빨리 실행합니다.
:::
