7장은 메모리 바깥으로 나가며 끝났습니다. "학습 완료"를 누르면 렌더러의 힙에 있던 진행 기록이 SSD에 내려가야 내일도 남습니다. 그 기록은 실제로 이런 길을 지나갑니다.

![진행 기록 한 줄이 SSD의 블록이 되기까지. 브라우저는 프로필 폴더의 파일에 쓰는 시스템 콜만 부르고, 그 아래는 커널이 페이지 캐시, 파일 시스템, 드라이버를 거쳐 처리합니다. SSD는 블록 번호만 압니다](io-write-path.svg)

프로그램이 바깥세상과 주고받는 모든 것을 입출력(I/O)이라고 합니다. 파일을 읽고 쓰는 것, 키보드 입력을 받는 것, 화면에 출력하는 것, 그리고 이 페이지가 네트워크에서 들어오는 것까지 모두 입출력입니다. 이 장은 위 그림을 아래에서 위로 올라가며 파일을 중심으로 운영체제가 입출력을 다루는 방법을 보고, 마지막에 그 방법이 네트워크에서 어떻게 쓰이는지로 넘어갑니다. 3부 네트워크로 가는 다리입니다.

## 디스크는 블록의 나열일 뿐입니다

SSD나 HDD는 "몇 번 블록을 읽어라, 몇 번 블록에 이걸 써라"만 알아듣습니다. 블록은 보통 512바이트나 4KB이고, 번호가 0부터 수억까지 매겨져 있습니다. 디스크 입장에서는 파일도 폴더도 없습니다.

위 그림의 맨 아래 칸들이 그것입니다. SSD는 진행 기록이 무엇인지 모르고, "81,512번 블록에 이 바이트들을 써라"만 압니다.

디스크를 몇 구역으로 나눈 것을 [[파티션]]이라고 합니다. 3장의 EFI 시스템 파티션, Windows의 C: 드라이브, Mac의 Macintosh HD가 각각 파티션(또는 볼륨)입니다. 각 파티션 위에 파일 시스템을 올려야 파일과 폴더가 생깁니다. 이 작업이 "포맷"입니다.

## 파일 시스템이 하는 일

[[파일 시스템]]은 블록의 나열 위에 이름 있는 파일과 폴더의 나무를 만드는 규칙입니다. 하는 일은 이렇습니다.

- 파일 이름에서 그 내용이 든 블록들을 찾아 줍니다.
- 폴더(디렉터리) 나무를 관리합니다.
- 크기, 만든 때, 고친 때, 주인, 권한 같은 메타데이터를 기록합니다.
- 어느 블록이 비어 있는지 관리합니다.
- 쓰는 도중 전원이 나가도 파일 시스템 전체가 깨지지 않게 합니다.

유닉스 계열 파일 시스템은 파일 이름과 파일 본체를 나눠 둡니다. 파일 본체(메타데이터와 데이터 블록 위치)는 [[inode]]라는 기록에 있고 번호가 붙어 있습니다. 디렉터리는 "이름 → inode 번호" 목록을 담은 특별한 파일일 뿐입니다. 그래서 파일 이름 바꾸기(같은 파티션 안의 `mv`)는 파일 크기와 상관없이 순식간에 끝납니다. 데이터는 그대로 두고 목록의 한 줄만 고치기 때문입니다. NTFS는 MFT라는 표의 기록이 비슷한 역할을 합니다.

![이름에서 블록까지. 디렉터리는 이름과 inode 번호의 목록이고, inode가 크기·권한·블록 위치를 들고 있습니다. 다른 디렉터리의 이름이 같은 inode를 가리키면 하드 링크입니다](io-inode.svg)

:::quiz mv-fast 2GB 동영상을 같은 디스크의 다른 폴더로 `mv`하면 순식간인데, USB 디스크로 옮기면 몇 분이 걸립니다. 이유는?
- [ ] USB 디스크의 파일 시스템이 저널링을 하지 않아서
- [ ] 같은 디스크 안에서는 운영체제가 파일을 압축해서 옮겨서
- [x] 같은 파일 시스템 안에서는 디렉터리의 이름 줄만 고치면 되지만, 다른 디스크로는 데이터 블록을 모두 복사해야 해서
- [ ] 같은 디스크 안에서는 페이지 캐시에 이미 올라와 있어서

같은 파일 시스템 안의 `mv`는 이름 목록의 한 줄만 바꿉니다. inode와 2GB의 블록은 그대로입니다. 다른 디스크는 다른 파일 시스템이라 그쪽에 새 inode와 블록을 만들어 2GB를 다 복사한 뒤 원본을 지워야 합니다.
:::

쓰는 도중 전원이 나가면 "데이터는 썼는데 목록은 못 고친" 어중간한 상태가 됩니다. 요즘 파일 시스템은 바꿀 내용을 먼저 일지에 적고 나서 실제로 바꿉니다. 이게 [[저널링]]입니다. 다시 켜면 일지를 보고 끝내지 못한 일을 마무리하거나 되돌립니다. 옛날처럼 부팅할 때 디스크 전체를 검사하는 일이 거의 없어진 이유입니다. APFS와 Btrfs는 아예 덮어쓰지 않고 새 자리에 쓴 뒤 가리키는 곳을 바꾸는 copy-on-write 방식으로 같은 문제를 풉니다.

## 세 운영체제의 파일 시스템

| | [[NTFS]] | [[APFS]] | [[ext4]] | [[exFAT]] |
| --- | --- | --- | --- | --- |
| 주로 쓰는 곳 | Windows | macOS, iOS (2017년부터) | Linux | USB, SD 카드 |
| 대소문자 | 구분 안 함 | 기본은 구분 안 함 | 구분함 | 구분 안 함 |
| 권한 | ACL | POSIX 권한 + ACL | POSIX 권한 | 없음 |
| 특징 | 저널링, 압축, 암호화, 대체 데이터 스트림 | copy-on-write, 스냅숏(Time Machine), 순식간 복제, 암호화 | 저널링. 오래되고 안정적 | 단순. 거의 모든 기기가 읽고 씀 |
| 다른 OS에서 | macOS는 읽기만, Linux는 읽고 씀 | Windows, Linux는 기본으로 못 읽음 | Windows, macOS는 기본으로 못 읽음 | 모두 읽고 씀 |

USB 하나로 Windows와 Mac 사이에 파일을 옮기려면 exFAT으로 포맷하는 이유가 이 표에 있습니다. 옛 FAT32도 어디서나 읽히지만 파일 하나가 4GB를 넘을 수 없습니다.

:::quiz case-ci `import Button from "./button"`이 Mac에서는 잘 되는데, 파일 이름이 `Button.tsx`라서 Linux CI에서만 "모듈을 찾을 수 없음"이 납니다. 원인은?
- [ ] Linux의 Node가 TypeScript를 못 읽어서
- [ ] CI의 Git이 파일 이름을 소문자로 바꿔서
- [ ] Mac의 번들러가 캐시를 써서
- [x] APFS는 기본으로 대소문자를 구분하지 않고, ext4는 구분해서

파일 시스템의 대소문자 규칙이 다르기 때문입니다. Mac에서는 `button`과 `Button`이 같은 파일이라 찾아지지만, Linux의 ext4에서는 다른 이름입니다. import 경로를 파일 이름과 정확히 맞추고, 대소문자만 바꾼 이름 변경은 `git mv`로 합니다.
:::

5장에서 Windows가 인터넷에서 받은 파일에 붙이는 `Zone.Identifier`는 NTFS의 대체 데이터 스트림에, macOS의 격리 표시는 APFS의 확장 속성에 들어 있습니다. 파일 내용과 별도로 파일에 붙는 메타데이터입니다.

## 디렉터리 구조

운영체제마다 정해진 자리가 있습니다. 설정 파일은 어디에, 로그는 어디에, 프로그램은 어디에 두는지 알면 서버에서 길을 잃지 않습니다.

| 무엇 | Windows | macOS | Linux |
| --- | --- | --- | --- |
| 최상위 | 드라이브마다 `C:\`, `D:\` | `/` 하나 | `/` 하나 |
| 내 폴더 | `C:\Users\me` | `/Users/me` | `/home/me` |
| 설치된 프로그램 | `C:\Program Files` | `/Applications`, Homebrew는 `/opt/homebrew` | `/usr/bin`, `/usr/local/bin`, `/opt` |
| 앱 설정과 데이터 | `%APPDATA%` (`AppData\Roaming`), `AppData\Local` | `~/Library/Application Support`, `~/Library/Preferences` | `~/.config`, `~/.local/share` |
| 브라우저 프로필 (Chrome) | `AppData\Local\Google\Chrome\User Data` | `~/Library/Application Support/Google/Chrome` | `~/.config/google-chrome` |
| 시스템 설정 | 레지스트리 | `/Library/Preferences`, `/etc` | `/etc` |
| 로그 | 이벤트 뷰어 | 콘솔 앱, `log show` | `/var/log`, `journalctl` |
| 임시 파일 | `%TEMP%` | `$TMPDIR` (`/var/folders/…`) | `/tmp` |
| 외장 디스크 | 새 드라이브 문자 `E:\` | `/Volumes/이름` | `/media/me/이름`, `/mnt` |

이 페이지의 진행 기록도 이 표의 "브라우저 프로필" 칸 아래 `Default/Local Storage/` 폴더의 파일에 들어갑니다. 맨 앞 그림의 오른쪽 위 칸입니다.

유닉스 계열은 모든 것이 `/` 하나 아래에 있습니다. 새 디스크를 꽂으면 그 디스크의 파일 시스템을 나무의 한 가지에 붙이는데, 이걸 [[마운트]]라고 합니다. Linux 서버의 주요 디렉터리는 표준(FHS)으로 정해져 있습니다.

| Linux 디렉터리 | 들어 있는 것 |
| --- | --- |
| `/etc` | 설정 파일 (`/etc/hosts`, `/etc/nginx/`, `/etc/systemd/`) |
| `/var` | 자주 바뀌는 데이터: 로그 `/var/log`, Docker 데이터 `/var/lib/docker` |
| `/srv` | 이 서버가 내보내는 서비스의 데이터. 이 사이트의 서버도 `/srv/archiev`에 설정을 둡니다 |
| `/home` | 사용자 폴더 |
| `/usr` | 설치된 프로그램과 라이브러리 |
| `/tmp` | 임시 파일. 재부팅하면 지워지기도 함 |
| `/proc`, `/sys` | 디스크에 없는 가짜 파일들. 커널 정보를 파일처럼 보여 줌 (7장의 `/proc/self/maps`) |
| `/dev` | 장치를 나타내는 파일 (`/dev/null`, `/dev/sda`) |

## 곁가지: 경로, 절대 경로, 상대 경로, 현재 디렉터리

[[절대 경로]]는 나무의 뿌리부터 적은 경로입니다(`/Users/me/app/src/index.ts`, `C:\Users\me\app`). [[상대 경로]]는 지금 위치에서부터 적은 경로입니다(`src/index.ts`, `../config.json`). `.`은 지금 디렉터리, `..`는 한 단계 위, `~`는 내 폴더(셸이 바꿔 주는 것)입니다.

"지금 위치"는 프로세스마다 하나씩 있는 [[현재 작업 디렉터리]]입니다. 셸에서 `cd`로 바꾸고, 자식 프로세스는 부모의 것을 물려받습니다. Node에서 상대 경로로 파일을 열면 스크립트 파일 위치가 아니라 이 현재 작업 디렉터리를 기준으로 찾습니다.

```js
// 프로젝트 루트에서 `node scripts/build.js`로 실행하면
process.cwd();                             // /Users/me/app (어디서 실행했나)
import.meta.dirname;                       // /Users/me/app/scripts (스크립트가 어디 있나)
fs.readFileSync("data.json");              // /Users/me/app/data.json을 찾음
fs.readFileSync(path.join(import.meta.dirname, "data.json")); // 스크립트 옆의 파일
```

다른 폴더에서 실행하면 깨지는 스크립트의 원인은 대부분 이것입니다.

## 곁가지: 링크, 바로가기, 심볼릭 링크, 하드 링크

- **[[심볼릭 링크]]**: "진짜 파일은 저 경로에 있음"이라고 적힌 작은 파일입니다. 원본을 지우면 끊어집니다. `ln -s 원본 링크`로 만듭니다.
- **[[하드 링크]]**: 같은 inode를 가리키는 이름을 하나 더 만드는 것입니다. 두 이름은 완전히 동등하고, 모든 이름을 지워야 데이터가 사라집니다. `ln 원본 링크`.
- **Windows 바로 가기(`.lnk`)**: 파일 시스템 기능이 아니라 탐색기가 읽는 보통 파일입니다. 프로그램이 열면 그냥 `.lnk` 파일이 열립니다. Windows에도 진짜 심볼릭 링크(`mklink`)가 있지만 만들려면 개발자 모드나 관리자 권한이 필요합니다.

pnpm이 두 가지를 모두 씁니다. 패키지 파일은 컴퓨터 전체에 한 벌만 저장해 두고 프로젝트마다 하드 링크로 연결해 디스크를 아끼고, `node_modules` 안의 의존성 구조는 심볼릭 링크로 만듭니다. `ls -l node_modules`를 쳐 보면 화살표(`->`)가 보입니다.

## 권한

파일 시스템은 이름과 블록 말고도 "누가 이 파일을 읽고 쓸 수 있나"를 기록합니다. 브라우저 프로필 폴더는 내 계정만 읽고 쓰게 되어 있어서, 같은 컴퓨터의 다른 사용자가 내 진행 기록이나 쿠키를 열어 볼 수 없습니다.

유닉스 계열에서 파일마다 세 무리(주인, 그룹, 나머지)에게 세 가지 권한(읽기 r, 쓰기 w, 실행 x)을 줍니다. `ls -l`의 맨 앞이 그것입니다.

![`ls -l`의 `-rwxr-xr--` 읽는 법. 맨 앞은 종류이고, 세 칸씩 주인, 그룹, 나머지의 권한입니다. 무리마다 숫자로 더하면 754입니다](io-permissions.svg)

각 무리의 권한을 r=4, w=2, x=1로 더해 숫자 세 자리로도 씁니다. `755`(rwxr-xr-x)는 실행 파일과 디렉터리, `644`(rw-r--r--)는 보통 파일, `600`(rw-------)은 나만 읽어야 하는 파일입니다. 디렉터리의 x는 "그 안으로 들어갈 수 있다"는 뜻입니다.

| | Windows | macOS | Linux |
| --- | --- | --- | --- |
| 모델 | [[ACL]]: 사용자와 그룹마다 세밀한 허용/거부 목록. 상위 폴더에서 물려받음 | POSIX rwx + 필요하면 ACL | POSIX rwx (+ ACL 선택) |
| 바꾸는 법 | 속성 → 보안 탭, `icacls` | `chmod`, `chown`, `chmod +a` | `chmod`, `chown`, `setfacl` |
| 실행 가능 여부 | 확장자 | 실행 권한 비트 | 실행 권한 비트 |

권한 때문에 실제로 자주 막히는 곳들입니다.

- SSH 개인 키 파일이 다른 사람도 읽을 수 있게 되어 있으면 ssh가 `UNPROTECTED PRIVATE KEY FILE!`이라며 쓰기를 거부합니다. `chmod 600 key.pem`으로 고칩니다. 서버 접속을 처음 해 볼 때 단골로 만나는 오류입니다.
- 셸 스크립트를 실행하려는데 `Permission denied`가 나면 실행 권한이 없는 것입니다. `chmod +x deploy.sh`.
- `npm install -g`에서 `EACCES`가 나는 건 전역 설치 폴더가 root 소유라서입니다. `sudo`로 밀어붙이기보다 nvm 같은 도구로 내 폴더에 Node를 설치합니다.

**640**입니다. 주인 rw- = 4 + 2 = 6, 그룹 r-- = 4, 나머지 --- = 0입니다. SSH 개인 키처럼 나만 읽어야 하는 파일은 그룹까지 막은 600을 씁니다.
:::

이름과 권한을 확인했으면 이제 파일을 실제로 엽니다. 맨 앞 그림의 `write(fd, …)`에서 `fd`는 무엇일까요?

## 파일 디스크립터와 핸들

프로그램이 파일을 열면(`open` 시스템 콜), 커널은 작은 정수 하나를 돌려줍니다. 이게 [[파일 디스크립터]](fd)입니다. 이후 읽기, 쓰기, 닫기는 모두 이 번호로 합니다. 커널은 프로세스마다 "fd 번호 → 열린 파일" 표를 두고, 열린 파일 쪽에는 지금 읽는 위치 같은 정보를 둡니다. Windows에서는 같은 개념을 [[핸들]]이라고 부릅니다.

모든 프로세스는 처음부터 세 개가 열린 채로 시작합니다.

| fd | 이름 | 기본 연결 | JS |
| --- | --- | --- | --- |
| 0 | 표준 입력 (stdin) | 키보드 | `process.stdin` |
| 1 | 표준 출력 (stdout) | 터미널 화면 | `console.log`, `process.stdout` |
| 2 | 표준 오류 (stderr) | 터미널 화면 | `console.error`, `process.stderr` |

이 셋을 묶어 [[표준 입출력]]이라고 합니다. 셸의 [[리다이렉션]]은 이 번호들의 연결을 바꾸는 것입니다. `> out.txt`는 1번을 파일로, `2> err.txt`는 2번을 파일로, `2>&1`은 2번을 1번과 같은 곳으로 보냅니다. 파이프 `|`는 앞 프로세스의 1번과 뒤 프로세스의 0번을 잇습니다. 오류 메시지가 `| grep`에 안 걸리고 화면에 그대로 나오는 이유는 오류가 2번으로 나가기 때문입니다.

![프로세스의 fd 표. 번호 0, 1, 2는 처음부터 터미널을 가리키고, 새로 연 파일과 소켓은 다음 번호를 받습니다. 프로세스는 대상이 무엇이든 번호로만 다룹니다](io-fd-table.svg)

:::quiz grep-stderr `npm run build | grep error`로 오류만 거르려 했는데, 오류 메시지가 걸러지지 않고 화면에 그대로 다 나옵니다. 왜일까요?
- [ ] `grep`이 색이 들어간 글자를 읽지 못해서
- [x] 오류 메시지는 fd 2(stderr)로 나가는데 파이프는 fd 1(stdout)만 `grep`에 이어서
- [ ] npm이 파이프로 연결되면 출력을 멈춰서
- [ ] 파이프는 한 줄씩만 보낼 수 있어서

파이프가 1번만 잇기 때문입니다. 오류는 2번으로 나가 파이프를 거치지 않고 터미널로 바로 갑니다. `2>&1`로 2번을 1번과 같은 곳에 붙인 뒤 파이프에 넘기면 함께 걸러집니다.
:::

유닉스 계열은 "모든 것은 파일"이라는 생각을 따릅니다. 일반 파일뿐 아니라 파이프, 장치(`/dev/null`, `/dev/urandom`), 그리고 네트워크 [[소켓]]도 fd 하나로 다룹니다. 그래서 파일을 읽는 `read`로 소켓도 읽을 수 있습니다. 이 사실이 아래 I/O 다중화의 바탕이 됩니다.

fd는 프로세스마다 열 수 있는 수가 정해져 있습니다(`ulimit -n`). 파일 감시 도구나 연결이 많은 서버가 이 한도에 닿으면 Node에서 `EMFILE: too many open files`가 납니다.

## 스트림

이 페이지도 스트림으로 왔습니다. 브라우저는 4만 바이트를 다 받을 때까지 기다리지 않고, 앞부분이 도착하는 대로 읽고 그리기 시작합니다. 파일이나 네트워크 데이터를 한 번에 다 메모리에 올리지 않고, 앞에서부터 조각조각 흘려 처리하는 방식을 [[스트림]]이라고 합니다. 2GB 영상을 업로드하는 서버가 영상을 통째로 메모리에 올리면 금방 OOM으로 죽지만, 스트림으로 받으면서 바로 디스크나 저장소로 흘려보내면 메모리는 몇 MB만 씁니다. Node의 `fs.createReadStream`, `req.pipe(res)`, 브라우저의 `ReadableStream`과 `fetch`의 `response.body`가 스트림입니다. 받는 쪽이 느리면 보내는 쪽을 늦추는 장치(backpressure)가 함께 있습니다.

## 버퍼와 페이지 캐시

4장에서 시스템 콜은 비싸다고 했습니다. 1바이트씩 `write`를 백만 번 부르면 아주 느립니다. 그래서 프로그램은 데이터를 메모리에 모았다가 한 번에 씁니다. 이 모아 두는 메모리를 [[버퍼]]라고 합니다. C의 `printf`, Node의 스트림이 안에 버퍼를 두고 있습니다.

커널도 버퍼를 둡니다. 파일을 읽으면 커널은 디스크에서 읽은 내용을 RAM에 남겨 두고, 다음에 같은 부분을 읽으면 디스크에 가지 않고 RAM에서 바로 줍니다. 이 RAM을 [[페이지 캐시]]라고 합니다. 7장의 `free`에서 본 `buff/cache`가 이것입니다. 빌드나 `git status`를 두 번째 돌리면 훨씬 빠른 이유 중 하나가 페이지 캐시입니다.

쓰기도 마찬가지입니다. `write`는 보통 데이터를 페이지 캐시에 적기만 하고 바로 돌아옵니다. 실제로 디스크에 쓰는 건 커널이 나중에 모아서 합니다. 맨 앞 그림의 점선 화살표입니다. 덕분에 "학습 완료"를 눌러도 화면이 바로 반응하지만, 그 사이에 전원이 나가면 "저장했다"고 생각한 데이터가 사라질 수 있습니다. 정말 디스크에 닿을 때까지 기다리게 하는 시스템 콜이 [[fsync]]입니다. 데이터베이스가 트랜잭션을 확정할 때마다 fsync를 부르는 이유이고, 그래서 DB의 쓰기 속도는 디스크가 fsync를 얼마나 빨리 끝내는지에 묶입니다. USB를 "안전하게 제거"하라는 것도 캐시에 남은 쓰기를 디스크로 내보내라는 뜻입니다.

:::quiz write-power 앱이 파일에 `write`를 했고 성공이 돌아왔습니다. 그런데 1초 뒤 전원이 나가자 그 내용이 사라졌습니다. 가장 정확한 설명은?
- [x] `write`의 성공은 커널이 받았다는 뜻일 뿐, 아직 페이지 캐시에만 있었다
- [ ] SSD가 쓰기를 1초 늦게 처리하도록 정해져 있다
- [ ] 저널링이 방금 쓴 내용을 되돌렸다
- [ ] 파일 디스크립터를 닫지 않아서 무효가 되었다

`write`의 성공은 "페이지 캐시에 적었다"는 뜻입니다. 커널은 나중에 모아서 디스크에 쓰니, 그 전에 전원이 나가면 RAM과 함께 사라집니다. 확실히 남겨야 하면 `fsync`로 디스크에 닿을 때까지 기다립니다. 저널링은 파일 시스템이 깨지지 않게 지킬 뿐, 아직 쓰지 않은 내용을 살려 주지는 않습니다.
:::

## 장치와 메모리 사이: DMA

디스크나 네트워크 카드에서 RAM으로 데이터를 옮길 때 CPU가 바이트를 하나하나 나르면 CPU가 그 일만 하게 됩니다. 그래서 장치가 CPU를 거치지 않고 RAM에 직접 쓰게 합니다. 이게 [[DMA]](직접 메모리 접근)입니다.

1. 커널이 장치에 "이 RAM 주소에 이만큼 넣어 줘"라고 부탁합니다.
2. 장치가 데이터를 RAM에 직접 씁니다. 그동안 CPU는 다른 일을 합니다.
3. 다 쓰면 장치가 인터럽트로 알립니다.

여기서 장면이 방향을 바꿉니다. 지금까지는 진행 기록이 SSD로 나가는 길이었고, 이제부터는 이 페이지가 들어온 길입니다. 네트워크 카드는 DMA를 쉬지 않고 돌립니다. 커널이 RAM에 빈 칸들을 고리 모양으로 마련해 두면, 패킷이 도착할 때마다 카드가 다음 빈 칸에 DMA로 써 넣고 인터럽트를 겁니다. 이 페이지의 4만 바이트가 내 컴퓨터 메모리에 "들어온" 실제 순간이 이것이고, 26장에서 다시 만납니다.

![이 페이지의 패킷이 RAM으로 들어오는 순간. 네트워크 카드가 고리 모양의 빈 칸에 DMA로 써 넣고, 인터럽트로 커널을 깨우면, 커널은 헤더를 벗겨 브라우저 소켓의 버퍼로 넘깁니다](io-dma-ring.svg)

그림의 오른쪽 끝, 브라우저의 소켓 fd에 "읽을 게 있다"는 소식은 어떻게 전해질까요? 브라우저는 그 소켓 하나만 쳐다보며 기다리고 있었을까요?

## 기다리는 방법: 블로킹과 논블로킹, 동기와 비동기

디스크와 네트워크는 CPU에 비해 엄청나게 느립니다. 그래서 입출력의 핵심 질문은 "기다리는 동안 무엇을 하느냐"입니다.

- **[[블로킹 I/O]]**: `read`를 부르면 데이터가 올 때까지 스레드가 잠듭니다(6장의 대기 상태). 코드는 단순하지만, 그 스레드는 기다리는 동안 다른 일을 못 합니다.
- **[[논블로킹 I/O]]**: `read`를 부르면 데이터가 없을 때 기다리지 않고 "지금은 없음"(`EAGAIN`)을 바로 돌려줍니다. 스레드는 다른 일을 하다가 나중에 다시 물어봅니다.

이와 별개로 동기와 비동기라는 말도 씁니다. 학교와 면접에서 자주 묻는 구분입니다.

- **동기**: 결과를 내가 직접 확인하고 가져옵니다. 일을 부탁한 쪽이 완료를 챙깁니다.
- **비동기**: 결과가 준비되면 상대가 알려 줍니다(콜백, 이벤트, Promise). 완료를 챙기는 책임이 넘어갑니다.

| | 동기 | 비동기 |
| --- | --- | --- |
| 블로킹 | `fs.readFileSync`: 끝날 때까지 멈춰서 결과를 받음 | 드묾. 비동기로 시작해 놓고 바로 결과를 기다리며 멈추는 경우 |
| 논블로킹 | 준비됐는지 계속 물어봄(폴링). epoll로 "준비됐다"는 소식을 받고 내가 읽기 | `fs.readFile(cb)`, `fetch().then`: 시작만 하고 끝나면 알림을 받음 |

## 한 스레드로 여러 연결 기다리기: I/O 다중화

서버는 동시에 연결 수천, 수만 개를 받습니다. 가장 단순한 방법은 연결마다 스레드를 하나씩 두고 블로킹으로 기다리는 것입니다. 하지만 스레드마다 스택 메모리가 들고, 수만 개면 컨텍스트 스위칭만으로 CPU가 바빠집니다. 1999년에 "연결 1만 개를 어떻게 받나"라는 [[C10K 문제]]로 정리된 고민입니다.

답은 스레드 하나가 많은 fd를 한꺼번에 지켜보다가 "준비된 것만" 처리하는 것입니다. 이를 [[I/O 다중화]]라고 합니다.

1. 지켜볼 fd들을 커널에 등록합니다. "이 소켓 1만 개 중 읽을 게 생기면 알려 줘."
2. 한 번의 시스템 콜로 잠듭니다.
3. 커널이 "3번, 17번, 902번 소켓에 데이터가 왔다"며 깨웁니다.
4. 그 소켓들만 논블로킹으로 읽어 처리하고, 2로 돌아갑니다.

옛 방법인 `select`와 `poll`은 매번 fd 목록 전체를 커널에 넘기고 전체를 훑어서 연결이 많으면 느렸습니다. 그래서 운영체제마다 더 나은 방법을 만들었고, 그 이름이 다 다릅니다.

| | Windows | macOS | Linux |
| --- | --- | --- | --- |
| 방법 | [[IOCP]] (I/O 완료 포트) | [[kqueue]] | [[epoll]], 그리고 새로운 io_uring |
| 알려 주는 것 | "부탁한 읽기가 끝났다" (완료 기반) | "지금 읽을 수 있다" (준비 기반) | epoll은 준비 기반, io_uring은 완료 기반 |
| 쓰는 곳 | IIS, .NET, Windows의 Node | macOS와 BSD의 nginx, Node | 거의 모든 Linux 서버 (nginx, Node, Redis) |

![연결 1만 개를 받는 두 방법. 왼쪽은 연결마다 스레드를 두고 모두 잠들어 기다리고, 오른쪽은 스레드 하나가 epoll에 전부 맡겨 두었다가 준비된 연결만 처리합니다](io-multiplex.svg)

nginx, Redis, Node가 적은 스레드로 많은 연결을 받는 비결이 이것입니다. 브라우저의 네트워크 서비스도 수많은 탭의 연결을 이렇게 한꺼번에 지켜봅니다. 이 페이지를 보내 준 서버의 웹 서버(17장의 nginx, Caddy)도 마찬가지입니다.

:::quiz c10k Node 서버 하나가 동시 연결 1만 개를 받고 있는데 CPU는 한가합니다. 가능한 이유로 맞는 것은?
- [x] 연결 대부분이 기다리는 중이고, 스레드 하나가 epoll로 데이터가 온 연결만 깨어나 처리해서
- [ ] Node가 연결마다 스레드를 1만 개 만들어 코어에 고르게 나눠서
- [ ] 커널이 연결 1만 개의 데이터를 미리 JS 객체로 바꿔 두어서
- [ ] 연결이 많으면 운영체제가 자동으로 연결을 끊어서

epoll 덕분입니다. 1만 개 연결 중 대부분은 상대가 무언가를 보내기를 기다리는 중이라 할 일이 없습니다. 스레드 하나가 epoll에 전부 등록해 두고 잠들었다가, 커널이 알려 주는 몇 개만 처리하니 스레드도 CPU도 거의 들지 않습니다.
:::

## libuv와 Node의 이벤트 루프 다시 보기

5장에서 Node 안에 [[libuv]]가 있다고 했습니다. libuv는 위 표의 차이를 감싸서, 어느 운영체제에서든 Node가 같은 이벤트 루프로 돌게 합니다.

- **네트워크**: Linux에서는 epoll, macOS에서는 kqueue, Windows에서는 IOCP를 씁니다. 이벤트 루프의 poll 단계에서 "준비된(또는 끝난) 소켓"을 받아 JS 콜백을 부릅니다.
- **파일**: 일반 파일은 epoll에 등록해도 늘 "준비됨"으로 나와서 다중화가 소용없습니다. 그래서 libuv는 파일 입출력을 [[스레드 풀]](기본 4개)에 맡기고, 끝나면 이벤트 루프에 알립니다.
- **스레드 풀을 쓰는 다른 것들**: `dns.lookup`(운영체제의 이름 조회 함수가 블로킹이라서), `crypto.pbkdf2`, `zlib` 압축.

여기서 실무 함정이 하나 나옵니다. 스레드 풀이 4개뿐이라, 느린 `dns.lookup`이나 무거운 암호화가 4개를 다 잡으면 파일 읽기까지 줄을 서서 기다립니다. `UV_THREADPOOL_SIZE` 환경 변수로 늘릴 수 있습니다. 직접 해보기에서 확인합니다.

## 다시 장면으로: 2부를 마치며

맨 앞 그림은 이제 이렇게 읽힙니다. "학습 완료"를 누르면 `app.js`가 `localStorage`에 쓰고, 브라우저는 프로필 폴더 안 파일의 fd에 `write` 시스템 콜을 부릅니다. 커널은 권한을 확인하고, 내용을 페이지 캐시에 적고 바로 돌아옵니다. 조금 뒤 파일 시스템이 파일의 그 부분이 몇 번 블록인지 정하고, 드라이버가 DMA로 SSD에 내려보냅니다. 거꾸로 이 페이지는 네트워크 카드가 DMA로 RAM에 써 넣었고, 커널이 헤더를 벗겨 소켓 버퍼로 넘겼고, 브라우저는 epoll로 그 소식을 받았습니다.

2부가 여기서 끝납니다. 4장부터 8장까지 운영체제가 하드웨어를 감싸고, 프로그램을 띄우고, CPU와 메모리와 디스크를 나눠 주는 것을 봤습니다. 이 페이지가 화면에 뜨고 클릭에 반응하기까지 내 컴퓨터 안에서 일어나는 일은 거의 다 본 셈입니다.

남은 것은 바깥입니다. 소켓 fd 너머, 네트워크 카드 너머에서 이 페이지의 패킷은 어떤 길을 건너왔을까요? 집의 공유기, 통신사, 바다 밑 케이블, 그리고 데이터센터의 서버까지, 3부는 그 길을 따라갑니다.

## 프론트엔드와 이어지는 곳

- Vite와 webpack의 HMR은 운영체제의 파일 감시 기능(FSEvents, inotify, ReadDirectoryChangesW)으로 저장을 알아챕니다. Linux에서 `ENOSPC: System limit for number of file watchers reached`가 나면 inotify 감시 한도(`fs.inotify.max_user_watches`)를 늘립니다. Docker로 띄운 개발 서버가 Mac의 파일 변경을 못 알아채면 폴링 옵션을 켭니다.
- 빌드 스크립트에서 `readFileSync`는 괜찮지만, 서버의 요청 처리 안에서 동기 파일 함수를 쓰면 그동안 모든 요청이 멈춥니다.
- 큰 파일 업로드와 다운로드는 스트림으로 처리합니다.
- `node_modules`의 화살표는 pnpm의 심볼릭 링크입니다. Windows에서 심볼릭 링크 권한 문제로 설치가 실패하면 개발자 모드를 켭니다.

## 용어 정리

:::terms
- 파티션 (partition) — 디스크를 나눈 구역. 각 파티션에 따로 파일 시스템을 올립니다.
- 파일 시스템 (file system) — 디스크의 블록 위에 파일, 디렉터리, 메타데이터를 만들고 관리하는 규칙입니다.
- inode — 유닉스 계열 파일 시스템에서 파일의 메타데이터와 데이터 블록 위치를 담은 기록. 파일 이름은 디렉터리가 따로 가집니다.
- 저널링 (journaling) — 파일 시스템이 바꿀 내용을 먼저 일지에 적어, 도중에 전원이 나가도 일관성을 되찾게 하는 방법입니다.
- NTFS — Windows의 기본 파일 시스템. 저널링, ACL 권한, 대체 데이터 스트림을 지원합니다.
- APFS (Apple File System) — 2017년부터 macOS와 iOS의 기본 파일 시스템. copy-on-write, 스냅숏, 순식간 복제를 지원합니다.
- ext4 — 대부분의 Linux가 쓰는 저널링 파일 시스템입니다.
- exFAT — Windows, macOS, Linux가 모두 읽고 쓰는 단순한 파일 시스템. USB와 SD 카드에 씁니다.
- 마운트 (mount) — 파일 시스템을 디렉터리 나무의 한 위치에 붙여 그 안의 파일을 쓸 수 있게 하는 것입니다.
- 절대 경로 (absolute path) — 루트(`/` 또는 `C:\`)부터 적은 경로입니다.
- 상대 경로 (relative path) — 현재 작업 디렉터리를 기준으로 적은 경로입니다.
- 현재 작업 디렉터리 (current working directory) — 프로세스마다 하나씩 있는 "지금 위치". 상대 경로의 기준이고 자식 프로세스가 물려받습니다.
- 심볼릭 링크 (symbolic link) — 다른 경로를 가리키는 작은 파일. 원본을 지우면 끊어집니다.
- 하드 링크 (hard link) — 같은 inode를 가리키는 또 하나의 이름. 모든 이름을 지워야 데이터가 사라집니다.
- 파일 권한 (file permission) — 유닉스 계열에서 주인, 그룹, 나머지에게 읽기, 쓰기, 실행을 허락하는 표시. `755`, `644` 같은 숫자로도 씁니다.
- ACL (Access Control List) — 사용자와 그룹마다 허용하거나 거부할 일을 적은 목록. Windows의 기본 권한 모델입니다.
- 파일 디스크립터 (file descriptor) — 프로세스가 연 파일, 소켓, 파이프를 가리키는 작은 정수. 0, 1, 2는 표준 입출력입니다.
- 핸들 (handle) — Windows에서 열린 파일이나 객체를 가리키는 값. 파일 디스크립터와 같은 개념입니다.
- 표준 입출력 (standard streams) — 모든 프로세스가 처음부터 가진 표준 입력(0), 표준 출력(1), 표준 오류(2)입니다.
- 리다이렉션 (redirection) — 셸에서 `>`, `<`, `2>&1`로 표준 입출력을 파일이나 다른 곳으로 돌리는 것입니다.
- 스트림 (stream) — 데이터를 한 번에 다 올리지 않고 조각조각 흘려 처리하는 방식입니다.
- 버퍼 (buffer) — 데이터를 모아 두었다가 한 번에 처리하려고 쓰는 메모리. 시스템 콜 횟수를 줄입니다.
- 페이지 캐시 (page cache) — 커널이 디스크에서 읽거나 쓸 파일 내용을 RAM에 남겨 두는 캐시입니다.
- fsync — 페이지 캐시에 있는 파일의 변경 내용을 디스크에 실제로 쓸 때까지 기다리는 시스템 콜입니다.
- DMA (Direct Memory Access) — 장치가 CPU를 거치지 않고 RAM에 직접 데이터를 읽고 쓰는 기능. 끝나면 인터럽트로 알립니다.
- 블로킹 I/O (blocking I/O) — 입출력이 끝날 때까지 호출한 스레드가 잠들어 기다리는 방식입니다.
- 논블로킹 I/O (non-blocking I/O) — 데이터가 없으면 기다리지 않고 즉시 돌아오는 방식입니다.
- C10K 문제 (C10K problem) — 서버 한 대가 동시 연결 1만 개를 어떻게 처리할지에 관한 문제. 연결마다 스레드를 두는 방식의 한계를 드러냈습니다.
- I/O 다중화 (I/O multiplexing) — 스레드 하나가 여러 fd를 한꺼번에 지켜보다가 준비된 것만 처리하는 방식입니다.
- epoll — Linux의 I/O 다중화 기능. 지켜볼 fd를 등록해 두고 준비된 것만 돌려받습니다.
- kqueue — macOS와 BSD의 I/O 다중화 기능입니다.
- IOCP (I/O Completion Port) — Windows의 완료 기반 비동기 입출력 기능. 입출력을 시작해 두면 끝났을 때 알려 줍니다.
- 스레드 풀 (thread pool) — 미리 만들어 둔 스레드 몇 개에 일을 나눠 맡기는 구조. libuv는 파일 입출력, DNS 조회, 암호화에 씁니다.
:::

Node로 간단한 서버를 띄우고, 그 프로세스가 연 fd 목록에서 표준 입출력, 열린 파일, 듣고 있는 소켓을 찾아봅니다.

kill %1
```

```

:::practice links inode와 링크 실험하기

cd /tmp && echo "hello" > a.txt

```

:::practice threadpool libuv 스레드 풀 크기 체감하기
무거운 암호화 작업 8개를 동시에 시작하면, 스레드 풀이 4개라서 4개씩 두 번에 나눠 끝나는 게 보입니다. 풀 크기를 8로 늘리면 거의 동시에 끝납니다.

  crypto.pbkdf2("pw", "salt", 300000, 64, "sha512", () => console.log(i, Date.now() - start, "ms"));
```

```

```

## 장 전체 문제

:::quiz write-order "학습 완료" 기록이 SSD에 닿기까지 지나는 순서로 맞는 것은?
- [ ] 파일 시스템 → write 시스템 콜 → 페이지 캐시 → SSD 드라이버
- [ ] write 시스템 콜 → SSD 드라이버 → 파일 시스템 → 페이지 캐시
- [ ] 페이지 캐시 → write 시스템 콜 → SSD 드라이버 → 파일 시스템
- [x] write 시스템 콜 → 페이지 캐시 → 파일 시스템 → SSD 드라이버

write → 페이지 캐시 → 파일 시스템 → 드라이버입니다. 프로그램은 시스템 콜로 커널에 부탁하고, 커널은 먼저 페이지 캐시에 적고 돌아옵니다. 실제로 내려보낼 때 파일 시스템이 블록 위치를 정하고 드라이버가 장치 명령으로 바꿉니다.
:::

:::quiz threadpool-why Node에서 소켓은 epoll로 기다리는데, 파일 읽기는 libuv의 스레드 풀에 맡깁니다. 이유는?
- [ ] 파일 읽기는 네트워크보다 언제나 느려서
- [ ] 파일은 소켓과 달리 fd가 없어서
- [x] 일반 파일은 epoll에 등록해도 늘 "준비됨"이라고 나와 기다림을 맡길 수 없어서
- [ ] 스레드 풀이 페이지 캐시를 건너뛰어 더 빨라서

epoll이 일반 파일에는 쓸모가 없기 때문입니다. 디스크 파일은 늘 "읽을 수 있음"으로 보이지만 실제 읽기는 디스크를 기다리며 막힐 수 있습니다. 그래서 libuv는 그 막히는 읽기를 별도 스레드에 맡기고, 끝나면 이벤트 루프에 알립니다. 파일에도 fd는 있습니다.
:::

## 스스로 점검

:::qa 1GB 파일을 같은 디스크 안에서 다른 폴더로 `mv`하면 순식간에 끝나는데, 다른 디스크로 옮기면 오래 걸리는 이유는?
같은 파일 시스템 안의 이동은 디렉터리의 "이름 → inode" 목록만 고치면 되고 데이터 블록은 그대로입니다. 다른 디스크는 다른 파일 시스템이라 데이터를 전부 복사한 뒤 원본을 지워야 합니다.
:::

:::qa `node scripts/build.js`는 잘 되는데 `cd scripts && node build.js`는 파일을 못 찾는다고 합니다. 왜인가요?
코드가 상대 경로로 파일을 열고 있어서, 그 경로가 스크립트 위치가 아니라 현재 작업 디렉터리를 기준으로 해석되기 때문입니다. `import.meta.dirname`(또는 `__dirname`)과 `path.join`으로 스크립트 기준의 경로를 만듭니다.
:::

:::qa `write`가 성공했는데 직후에 전원이 나가 데이터가 사라질 수 있는 이유는? 어떻게 막나요?
`write`는 보통 커널의 페이지 캐시에 적고 바로 돌아오고, 디스크에는 나중에 씁니다. 디스크에 닿기 전에 전원이 나가면 사라집니다. 반드시 남아야 하는 데이터는 `fsync`로 디스크 기록을 기다립니다.
:::

:::qa 연결마다 스레드를 두는 서버와 epoll을 쓰는 서버의 차이를, 동시 연결 1만 개 상황으로 설명해 보세요.
스레드 방식은 1만 개 스레드의 스택 메모리와 잦은 컨텍스트 스위칭 비용을 치르는데, 대부분은 기다리기만 합니다. epoll 방식은 스레드 하나가 1만 개 소켓을 등록해 두고 데이터가 온 소켓만 받아 처리하니 메모리와 전환 비용이 훨씬 적습니다.
:::

:::qa Node에서 네트워크는 epoll로 처리하는데 파일 읽기는 왜 스레드 풀로 처리하나요?
일반 파일은 epoll에 등록해도 항상 읽을 수 있다고 나와서, 실제로 디스크를 기다려야 하는지 알 수 없습니다. 그래서 libuv는 블로킹 파일 읽기를 별도 스레드에 맡기고, 끝나면 이벤트 루프에 알립니다.
:::

:::qa `cmd 2>&1 | grep error`에서 `2>&1`이 없으면 왜 오류 메시지를 거를 수 없나요?
파이프는 앞 프로세스의 표준 출력(1번)만 뒤 프로세스의 입력에 잇습니다. 오류 메시지는 표준 오류(2번)로 나가니 grep을 거치지 않고 화면에 바로 나옵니다. `2>&1`이 2번을 1번과 같은 곳으로 보내 줍니다.
:::
