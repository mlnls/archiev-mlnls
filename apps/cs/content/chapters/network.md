## 컴퓨터 두 대를 잇는다는 것

컴퓨터 두 대를 전선 하나로 이었다고 해 봅니다. 데이터를 보내려면 정할 게 아주 많습니다.

- 전압이 몇 볼트면 1이고, 1초에 몇 비트를 보낼까?
- 비트가 줄줄이 오는데, 메시지가 어디서 시작하고 어디서 끝날까?
- 전선 하나에 컴퓨터가 셋 이상 붙으면, 이 메시지는 누구에게 가는 걸까?
- 받는 쪽이 같은 건물이 아니라 다른 나라에 있으면 어느 길로 보낼까?
- 도중에 잡음으로 비트가 뒤집히거나 메시지가 사라지면?
- 받는 쪽 컴퓨터에서 이 데이터는 브라우저 것일까, 메신저 것일까?
- 데이터의 내용은 어떤 형식으로 읽어야 할까?

이 질문 하나하나에 대한 약속이 [[프로토콜]]입니다. 사람끼리 편지를 주고받을 때 봉투에 받는 사람 주소를 어디에 어떤 순서로 쓰는지, 우표는 어디에 붙이는지 정해 둔 것과 같습니다. 인터넷 프로토콜의 약속은 [[RFC]]라는 공개 문서로 적혀 있고, IETF라는 단체가 관리합니다. TCP는 RFC 9293, HTTP는 RFC 9110처럼 번호가 붙어 있습니다.

## 회선 교환과 패킷 교환

전화망은 통화를 시작할 때 두 전화기 사이에 길 하나를 잡아 두고, 통화가 끝날 때까지 그 길을 독차지합니다. 이걸 [[회선 교환]]이라고 합니다. 말이 없는 동안에도 길은 비어 있는 채로 묶여 있습니다.

인터넷은 다르게 합니다. 보낼 데이터를 작은 조각으로 자르고, 조각마다 받는 사람의 주소를 붙여 각자 보냅니다. 이 조각이 [[패킷]]이고, 이 방식이 [[패킷 교환]]입니다. 길은 누구의 것도 아니고, 수많은 사람의 패킷이 섞여서 같은 선을 나눠 씁니다. 택배 상자들이 같은 트럭에 섞여 실려 가는 것과 비슷합니다.

![회선 교환은 길 하나를 잡아 두고 독차지하고, 패킷 교환은 조각마다 따로 보내며 길을 모두가 나눠 씁니다](network-switching.svg)

| | 회선 교환 | 패킷 교환 |
| --- | --- | --- |
| 길 | 처음에 잡아 두고 독차지 | 잡지 않음. 모두가 나눠 씀 |
| 효율 | 말이 없어도 길이 묶임 | 쉬는 동안 다른 사람이 씀 |
| 고장에 대한 강함 | 길이 끊기면 통화가 끊김 | 다른 길로 돌아가면 됨 |
| 대가 | 지연이 일정함 | 패킷마다 지연이 다르고, 사라지거나 순서가 바뀔 수 있음 |

패킷 교환은 1960년대 미국의 ARPANET에서 시작했습니다. 핵전쟁으로 일부가 파괴되어도 살아남는 통신망을 만들려는 연구였습니다. "사라지거나 순서가 바뀔 수 있는" 대가를 누가 치르느냐가 12장의 TCP 이야기입니다.

:::quiz trade-off 인터넷이 회선 교환 대신 패킷 교환을 쓰면서 치르는 대가는 무엇일까요?
- [ ] 통화처럼 길을 미리 잡아 두느라 처음 연결이 느리다
- [ ] 한 번에 한 사람만 선을 쓸 수 있다
- [ ] 길 하나가 끊기면 통신 전체가 끊긴다
- [x] 패킷마다 지연이 다르고, 사라지거나 순서가 바뀔 수 있다

패킷마다 지연이 다르고 사라지거나 뒤바뀔 수 있다는 것이 대가입니다. 길을 잡아 두지 않고 모두가 나눠 쓰니 효율적이고 고장에도 강하지만, 패킷이 섞여 가다 보니 이런 일이 생깁니다. 이 뒤처리를 12장의 TCP가 맡습니다. 나머지 보기는 모두 회선 교환의 특징입니다.
:::

## 계층으로 나누기

위의 질문들을 프로그램 하나가 다 풀면 너무 복잡하고, Wi-Fi에서 유선으로 바꿀 때마다 브라우저를 다시 짜야 합니다. 그래서 네트워크는 일을 층으로 나눕니다. 각 층은 한 가지 문제만 풀고, 아래층이 해 주는 일을 믿고 쓰며, 위층에 서비스를 줍니다. 아래층을 Wi-Fi에서 유선 이더넷으로 바꿔도 위층의 HTTP는 그대로입니다.

층을 나누는 대표적인 지도가 둘 있습니다. 하나는 교과서와 면접에서 쓰는 [[OSI 7계층]]이고, 하나는 실제 인터넷이 따르는 [[TCP/IP 모델]]입니다.

| OSI 계층 | 푸는 문제 | 프로토콜 예 | 데이터 단위 | 장비 | TCP/IP 모델 |
| --- | --- | --- | --- | --- | --- |
| 7 응용 | 이 데이터는 무슨 뜻인가 | HTTP, DNS, SSH, SMTP | 메시지 | 로드 밸런서(L7), 프록시 | 응용 |
| 6 표현 | 어떤 형식과 암호로 적었나 | TLS, 문자 인코딩, 압축 | | | 응용 |
| 5 세션 | 대화를 어떻게 이어 가나 | (TLS 세션 등) | | | 응용 |
| 4 전송 | 어느 프로그램에게, 빠짐없이 순서대로 | TCP, UDP, QUIC | 세그먼트, 데이터그램 | 로드 밸런서(L4), 방화벽 | 전송 |
| 3 네트워크 | 다른 네트워크의 어느 컴퓨터에게, 어느 길로 | IP, ICMP | 패킷 | [[라우터]] | 인터넷 |
| 2 데이터 링크 | 같은 네트워크 안의 어느 기기에게 | 이더넷, Wi-Fi | 프레임 | 스위치, 액세스 포인트 | 네트워크 접근 |
| 1 물리 | 비트를 어떤 신호로 | 전기, 빛, 전파 | 비트 | 케이블, 허브, 리피터 | 네트워크 접근 |

실제 인터넷에서 5, 6층은 따로 존재하기보다 응용 프로그램과 TLS 안에 녹아 있습니다. 그래서 개발자들은 대개 TCP/IP 모델로 생각하고, OSI는 "L4 로드 밸런서", "L7 방화벽"처럼 층을 가리키는 번호로 씁니다.

이 책의 다음 장들이 이 표를 아래에서 위로 올라갑니다. 10장은 1~2층(같은 네트워크 안), 11장은 3층(IP와 라우팅), 12장은 4층(TCP, UDP), 13장과 14장은 7층(DNS, HTTP)입니다.

:::quiz osi-tls OSI 7계층으로 설명할 때 TLS 암호화, 문자 인코딩, 압축은 보통 몇 층의 일로 분류할까요?
- [ ] 2층 데이터 링크
- [ ] 3층 네트워크
- [ ] 4층 전송
- [x] 6층 표현

6층 표현 계층입니다. "데이터를 어떤 형식과 암호로 적었나"를 다루는 층입니다. 다만 실제 인터넷에서는 5, 6층이 따로 있지 않고 응용 프로그램과 TLS 라이브러리 안에 녹아 있어서, 개발자는 대개 TCP/IP 모델의 응용 계층으로 묶어서 생각합니다.
:::

## 캡슐화: 봉투 안에 봉투

층마다 자기가 필요한 정보를 데이터 앞에 붙입니다. 이 정보 묶음을 [[헤더]], 헤더 뒤에 실린 원래 데이터를 [[페이로드]]라고 합니다. 위층의 헤더와 데이터 전체가 아래층의 페이로드가 되고, 아래층은 그 앞에 자기 헤더를 또 붙입니다. 이렇게 봉투를 봉투에 넣는 것을 [[캡슐화]]라고 합니다.

![브라우저가 `GET /`를 보낼 때 층마다 앞에 헤더가 하나씩 붙는 모습. 진한 칸이 그 층이 새로 붙인 헤더이고, 위층 전체가 아래층의 페이로드가 됩니다](network-encapsulation.svg)

받는 쪽은 거꾸로 봉투를 하나씩 엽니다(역캡슐화). 네트워크 카드는 이더넷 헤더를 보고 "내 것이 맞네" 하고 벗기고, 커널의 IP 계층은 IP 헤더를 보고 "내 주소가 맞네" 하고 벗기고, TCP 계층은 포트 번호를 보고 "3000번 포트를 듣는 Node 프로세스의 것"이라며 그 소켓으로 넘깁니다.

길 위의 장비들은 자기 층의 봉투까지만 열어 봅니다. 스위치는 이더넷 헤더(MAC 주소)만, 라우터는 IP 헤더까지만 봅니다. 라우터는 패킷 안이 HTTP인지 게임 데이터인지 모르고 관심도 없습니다. 이 단순함 덕분에 인터넷의 장비들은 엄청난 양의 패킷을 빠르게 넘길 수 있습니다.

![스위치는 2층, 라우터는 3층까지만 열어 보고 넘깁니다. 네 층을 모두 다루는 것은 양 끝의 두 컴퓨터뿐입니다](network-devices-layers.svg)

:::quiz header-order 브라우저의 HTTP 요청이 이더넷 선에 실릴 때, 맨 앞(바깥)부터 차례대로 맞게 적은 것은?
- [x] 이더넷 헤더 → IP 헤더 → TCP 헤더 → HTTP 요청
- [ ] HTTP 요청 → TCP 헤더 → IP 헤더 → 이더넷 헤더
- [ ] IP 헤더 → 이더넷 헤더 → TCP 헤더 → HTTP 요청
- [ ] TCP 헤더 → IP 헤더 → 이더넷 헤더 → HTTP 요청

이더넷 → IP → TCP → HTTP 순서입니다. 보낼 때는 위층부터 헤더를 붙여 내려가니, 가장 나중에 붙인 이더넷 헤더가 맨 바깥에 옵니다. 받는 쪽은 바깥부터 하나씩 벗깁니다.
:::

:::quiz mss MTU가 1500바이트이고 IP 헤더와 TCP 헤더가 각각 20바이트일 때, 패킷 하나에 실을 수 있는 HTTP 데이터는 최대 몇 바이트일까요?
= 1460 | 1460바이트 | 1460B

1500 − 20 − 20 = **1460바이트**입니다. MTU는 IP 패킷 전체의 최대 크기라서 IP 헤더와 TCP 헤더가 그 안에서 자리를 먼저 차지합니다. 이더넷 헤더(14바이트)와 FCS(4바이트)는 MTU 바깥이라 빼지 않습니다. 이 1460을 TCP에서는 MSS라고 부릅니다(12장).
:::

:::quiz router-reads 라우터가 패킷을 어느 쪽으로 넘길지 정할 때 보는 것은?
- [ ] HTTP 요청의 URL
- [ ] TCP 헤더의 포트 번호
- [x] IP 헤더의 목적지 IP 주소
- [ ] 이더넷 프레임 끝의 FCS

목적지 IP 주소를 봅니다. 라우터는 3층 장비라 IP 헤더까지만 열어 보고 목적지 주소로 갈 길을 정합니다. 안에 실린 것이 HTTP인지 게임 데이터인지는 모르고, 그래서 새 응용 프로토콜이 나와도 길 위의 장비를 바꿀 필요가 없습니다.
:::

## 속도를 말하는 단어들

네트워크 성능을 말할 때 "인터넷이 빠르다"는 말에는 서로 다른 것들이 섞여 있습니다.

- **[[대역폭]]**(bandwidth): 1초에 보낼 수 있는 최대 비트 수. 수도관의 굵기입니다. "1기가 인터넷"이 이것입니다.
- **[[지연 시간]]**(latency): 데이터 한 조각이 출발해서 도착하기까지 걸리는 시간. 수도꼭지를 틀고 물이 나오기까지의 시간입니다.
- **[[RTT]]**(Round-Trip Time, 왕복 시간): 보내고 답이 돌아오기까지 걸리는 시간. 지연 시간의 왕복입니다. `ping`이 재는 값입니다.
- **[[처리량]]**(throughput): 실제로 1초에 전달된 데이터 양. 대역폭보다 작습니다.
- **[[패킷 손실]]**(packet loss): 도중에 사라진 패킷의 비율. 1%만 되어도 TCP는 눈에 띄게 느려집니다.
- **[[지터]]**(jitter): 지연 시간이 얼마나 들쭉날쭉한지. 화상 통화와 게임에서 중요합니다.

지연 시간은 크게 네 가지로 이루어집니다.

| 구성 | 뜻 | 줄이는 법 |
| --- | --- | --- |
| 전파 지연 | 신호가 거리를 가는 시간. 광섬유 속 빛은 1ms에 약 200km | 서버를 가까이 (CDN) |
| 전송 지연 | 패킷의 모든 비트를 선에 올리는 시간 | 대역폭을 늘리기 |
| 큐 지연 | 장비 안에서 앞 패킷들을 기다리는 시간 | 혼잡을 피하기 |
| 처리 지연 | 장비가 헤더를 읽고 갈 길을 정하는 시간 | 대개 아주 작음 |

빛의 속도는 바꿀 수 없습니다. 서울에서 미국 서부까지 케이블 길이를 생각하면 편도만 60ms 안팎이 들고, 왕복은 130ms가 넘습니다. 대략적인 RTT를 알아 두면 성능 문제를 볼 때 감이 생깁니다.

| 구간 | RTT (대략) |
| --- | --- |
| 같은 컴퓨터 (localhost) | 0.05ms 이하 |
| 같은 집의 유선 LAN | 1ms 미만 |
| 집 Wi-Fi에서 공유기까지 | 2~5ms |
| 서울 ↔ 부산 | 10ms 안팎 |
| 서울 ↔ 도쿄 | 30ms 안팎 |
| 서울 ↔ 미국 서부 | 130ms 안팎 |
| 서울 ↔ 유럽 | 250ms 안팎 |

맨 앞 그림처럼 이 페이지 하나를 여는 데도 DNS 조회, 연결 맺기, TLS, 요청과 응답까지 왕복이 네 번 듭니다. 서버까지 RTT가 30ms라면 그 셋만으로 90ms입니다. 그래서 대역폭을 10배로 늘려도 페이지가 10배 빨라지지 않습니다. 작은 파일 여러 개를 받는 웹은 대개 대역폭이 아니라 RTT에 묶여 있습니다. 2장의 숫자표를 떠올리면, 네트워크 왕복 한 번은 컴퓨터 안의 거의 모든 일보다 비쌉니다.

:::quiz light-rtt 서울에서 미국 서부까지 케이블 길이를 10,000km라고 하면, 빛의 속도만으로 드는 왕복 시간(RTT)은 최소 몇 ms일까요? 광섬유 속 빛은 1ms에 200km를 갑니다.
= 100 | 100ms

편도 10,000 ÷ 200 = 50ms, 왕복은 **100ms**입니다. 실제로는 케이블이 직선이 아니고 중간 장비의 처리와 큐 지연이 더해져 130ms 안팎이 나옵니다. 대역폭을 아무리 늘려도 이 100ms는 줄지 않고, 줄이려면 서버를 가까이(CDN) 두는 수밖에 없습니다.
:::

:::quiz bandwidth 인터넷을 100Mbps에서 1Gbps로 바꿨더니 큰 파일은 빨리 받아지는데 웹 페이지 여는 속도는 거의 그대로입니다. 가장 큰 이유는?
- [ ] 브라우저가 1Gbps를 지원하지 않아서
- [ ] 대역폭이 늘면 패킷 손실도 함께 늘어서
- [x] 웹 페이지는 작은 요청이 여러 번 오가서 왕복 시간(RTT)에 묶여 있어서
- [ ] 공유기가 HTTP를 해석하느라 느려져서

RTT에 묶여 있기 때문입니다. 웹 페이지는 DNS, 연결, TLS, 요청과 응답까지 왕복을 여러 번 하는데, 왕복 한 번의 시간은 거리로 정해져 대역폭과 상관이 없습니다. 굵은 수도관은 많은 물을 보내는 데 도움이 되지만 물이 도착하는 시간을 줄이지는 못합니다.
:::

## 인터넷은 어떻게 생겼나

인터넷은 커다란 네트워크 하나가 아니라, 수만 개의 네트워크를 이어 붙인 네트워크의 네트워크입니다. 이름도 inter-network에서 나왔습니다. 내 노트북에서 해외 서버까지 가는 길을 따라가 봅니다.

1. **집 안의 네트워크**: 노트북은 Wi-Fi로 [[공유기]]에 붙습니다. 집 안의 이 작은 네트워크를 [[LAN]](근거리 네트워크)이라고 합니다.
2. **통신사의 접속망**: 공유기는 벽의 광케이블 단자에 붙은 [[ONT]](광 신호를 전기 신호로 바꾸는 장비)를 거쳐 통신사로 이어집니다. 이 통신사가 [[ISP]](인터넷 서비스 제공자)입니다. 한국에서는 KT, SK브로드밴드, LG유플러스 등입니다.
3. **통신사의 기간망**: 동네의 통신사 국사에서 데이터는 더 굵은 선으로 모여 통신사의 큰 망(백본)으로 들어갑니다.
4. **다른 네트워크와의 연결**: 통신사끼리, 통신사와 클라우드 회사끼리는 서로 선을 잇습니다. 여러 네트워크가 한곳에 모여 서로 잇는 장소를 [[IX]](인터넷 교환 지점)라고 합니다. 서로 공짜로 트래픽을 주고받는 계약을 피어링, 돈을 내고 더 큰 망에 실어 보내는 계약을 트랜짓이라고 합니다.
5. **바다 건너기**: 다른 나라로 가는 데이터의 대부분은 위성이 아니라 바다 밑에 깔린 [[해저 케이블]]을 탑니다. 한국은 부산, 거제 같은 곳에 해저 케이블이 육지로 올라오는 기지가 있습니다.
6. **데이터센터**: 목적지 서버는 [[데이터센터]]의 선반(랙)에 꽂혀 있습니다. 데이터센터 안에도 스위치와 라우터로 된 자기만의 네트워크가 있습니다. AWS 서울 리전 같은 클라우드의 "리전"은 이런 데이터센터 묶음입니다.

![노트북에서 바다 건너 데이터센터의 서버까지. 왕복 시간 대부분은 장비가 아니라 거리에서, 특히 바다를 건너는 데서 듭니다](network-internet-map.svg)

휴대폰은 1~2단계가 다릅니다. 휴대폰은 전파로 동네 기지국에 붙고, 기지국은 통신사의 이동통신 핵심망을 거쳐 인터넷으로 나갑니다.

이 거대한 망에는 중앙 관리자가 없습니다. 각 네트워크가 "나는 이 주소들로 가는 길을 안다"고 옆 네트워크에 알리고, 그 정보가 퍼져 나가 길이 정해집니다. 11장의 BGP가 그 이야기입니다.

## 길 위의 장비들

| 장비 | 계층 | 하는 일 |
| --- | --- | --- |
| [[네트워크 인터페이스 카드]] (NIC) | 1~2 | 컴퓨터를 네트워크에 붙이는 부품. 랜 포트, Wi-Fi 칩. 고유한 MAC 주소를 가짐 |
| [[모뎀]], ONT | 1 | 통신사 회선의 신호(전화선, 동축, 광)를 이더넷 신호로 바꿈 |
| 허브 | 1 | 들어온 신호를 모든 포트로 그대로 복사. 지금은 거의 안 씀 |
| [[스위치]] | 2 | 같은 네트워크 안에서 프레임을 받는 기기의 포트로만 보냄 |
| [[액세스 포인트]] (AP) | 2 | Wi-Fi 기기들을 유선 네트워크에 잇는 무선 기지 |
| [[라우터]] | 3 | 서로 다른 네트워크 사이에서 패킷을 목적지 쪽으로 넘김 |
| [[방화벽]] | 3~7 | 규칙에 따라 패킷을 통과시키거나 막음 |
| [[로드 밸런서]] | 4 또는 7 | 들어온 요청을 여러 서버에 나눠 줌 (17장) |

집의 [[공유기]]는 사실 이 장비 여러 개를 상자 하나에 넣은 것입니다.

- 통신사 쪽과 집 안쪽을 잇는 **라우터**
- 뒷면의 랜 포트 4개를 잇는 **스위치**
- **Wi-Fi 액세스 포인트**
- 집 안 기기에 IP 주소를 나눠 주는 **DHCP 서버** (11장)
- 공인 IP 하나를 여러 기기가 나눠 쓰게 하는 **NAT** (11장)
- 바깥에서 먼저 들어오는 연결을 막는 **방화벽**
- DNS 질문을 통신사로 전달하는 **DNS 중계기** (13장)

이 책에서 공유기라는 단어가 나올 때마다 이 중 어떤 역할을 말하는지 떠올리면 헷갈리지 않습니다.

## 내 컴퓨터 안의 네트워크 스택

계층 모델은 컴퓨터 안에도 그대로 있습니다. 1~4층은 운영체제 커널이, 7층은 프로그램이 맡습니다.

```text
사용자 공간   브라우저, Node 서버      HTTP를 만들고 읽음, TLS 암호화
            ───────── 소켓 API (socket, connect, send, recv 시스템 콜) ─────────
커널         TCP / UDP               포트, 연결, 재전송, 순서
             IP                      주소, 라우팅 테이블
             이더넷 / Wi-Fi 드라이버    프레임
하드웨어      네트워크 카드              신호, DMA, 인터럽트
```

이 커널 안의 네트워크 처리 코드 전체를 [[네트워크 스택]]이라고 합니다. 프로그램은 4장의 시스템 콜로 [[소켓]]을 만들어 이 스택에 부탁할 뿐, TCP 재전송이나 IP 라우팅을 직접 하지 않습니다. 브라우저가 하는 네트워크 일은 HTTP와 TLS, 그리고 DNS 조회 정도입니다. 예외로 HTTP/3의 QUIC은 TCP 대신 사용자 공간에서 직접 구현하는데, 12장에서 이유를 봅니다.

## 다시 장면으로: 화살표 하나가 지나는 길

맨 앞 그림의 화살표 하나, `GET /`를 따라가 봅니다. 브라우저가 소켓에 쓰면 커널의 네트워크 스택이 TCP 헤더, IP 헤더, Wi-Fi 헤더를 차례로 붙여 프레임을 만듭니다. 프레임은 전파를 타고 공유기에 닿고, 공유기는 2층 봉투를 벗긴 뒤 IP 헤더만 보고 통신사 쪽으로 넘깁니다. 통신사와 IX, 데이터센터의 라우터들도 IP 헤더만 보고 다음 장비로 넘깁니다. 서버의 커널이 봉투를 거꾸로 벗겨 443번 포트를 듣는 프로그램(Caddy)에게 건네면, 그제야 누군가 HTTP를 읽습니다. 그 사이의 장비 수십 대는 이 페이지가 무슨 내용인지 모릅니다.

이제 첫 구간부터 자세히 봅니다. 노트북에서 공유기까지는 전파입니다. 전파는 방 안의 휴대폰과 TV, 옆집 노트북에도 똑같이 닿습니다. 그 속에서 공유기는 이 프레임이 자기에게 온 것임을 어떻게 알고, 답은 어떻게 이 노트북에게만 돌아올까요? 10장의 이야기입니다.

## 세 운영체제에서 네트워크 들여다보기

이 장부터 네트워크 명령을 자주 씁니다. 같은 일을 하는 명령을 한데 모아 둡니다.

| 하는 일 | Windows | macOS | Linux |
| --- | --- | --- | --- |
| 네트워크 장치와 IP 보기 | `ipconfig /all` | `ifconfig`, `ipconfig getifaddr en0` | `ip addr` |
| 기본 게이트웨이 | `ipconfig`, `route print` | `netstat -rn`, `route -n get default` | `ip route` |
| 쓰고 있는 DNS 서버 | `ipconfig /all`, `Get-DnsClientServerAddress` | `scutil --dns` | `resolvectl status`, `/etc/resolv.conf` |
| 연결 확인 | `ping` | `ping` | `ping` |
| 거쳐 가는 길 | `tracert` | `traceroute` | `traceroute`, `tracepath`, `mtr` |
| 열린 연결과 포트 | `netstat -ano`, `Get-NetTCPConnection` | `netstat -an`, `lsof -i` | `ss -tunap` |
| 패킷 잡아 보기 | Wireshark, `pktmon` | Wireshark, `tcpdump` | Wireshark, `tcpdump` |

[[Wireshark]]는 선 위를 지나가는 패킷을 잡아서 층별로 열어 보여 주는 프로그램입니다. 이 장의 캡슐화 그림을 실제 패킷으로 확인할 수 있어서, 3부를 공부하는 동안 가장 좋은 도구입니다.

## 프론트엔드와 이어지는 곳

- DevTools Network 탭의 요청 하나를 누르고 Timing을 보면 이 장의 층이 그대로 나옵니다. Queueing, Stalled(브라우저 안 대기), DNS Lookup(13장), Initial connection(12장), SSL(14장), Request sent, Waiting for server response(서버 처리 + RTT), Content Download(대역폭).
- DevTools의 네트워크 속도 제한(throttling)은 대역폭과 RTT를 함께 낮춥니다. 느린 회선에서 페이지가 느려지는 주 원인이 RTT라는 걸 체감할 수 있습니다.
- 요청 수를 줄이고, 연결을 재사용하고, `preconnect`로 미리 연결하고, CDN으로 서버를 사용자 가까이 두는 최적화는 모두 RTT를 줄이려는 것입니다.

## 용어 정리

:::terms
- 프로토콜 (protocol) — 통신하는 쪽들이 메시지의 형식, 순서, 의미, 오류 처리를 맞추기 위해 정한 약속입니다.
- RFC (Request for Comments) — 인터넷 프로토콜을 정의하는 공개 문서. IETF가 관리하며 번호가 붙습니다.
- 회선 교환 (circuit switching) — 통신을 시작할 때 두 끝 사이에 길을 잡아 두고 끝날 때까지 독차지하는 방식. 옛 전화망.
- 패킷 (packet) — 네트워크로 보내려고 잘라 낸 데이터 조각과 그 앞에 붙은 주소 정보. 좁게는 IP 계층의 데이터 단위를 말합니다.
- 패킷 교환 (packet switching) — 데이터를 패킷으로 잘라 각자 보내고, 여러 통신이 같은 선을 나눠 쓰는 방식. 인터넷의 바탕입니다.
- OSI 7계층 (OSI model) — 네트워크 기능을 물리, 데이터 링크, 네트워크, 전송, 세션, 표현, 응용의 7층으로 나눈 참조 모델입니다.
- TCP/IP 모델 (TCP/IP model) — 실제 인터넷이 따르는 계층 구조. 네트워크 접근, 인터넷, 전송, 응용의 4층입니다.
- 캡슐화 (encapsulation) — 위층의 데이터를 페이로드로 삼고 그 앞에 아래층의 헤더를 붙여 나가는 것. 받는 쪽은 거꾸로 하나씩 벗깁니다.
- 헤더 (header) — 데이터 앞에 붙는 제어 정보. 주소, 포트, 길이, 순서 번호 같은 것이 들어 있습니다.
- 페이로드 (payload) — 헤더 뒤에 실린 실제 전달할 데이터입니다.
- 대역폭 (bandwidth) — 1초에 보낼 수 있는 최대 데이터 양. bps(초당 비트)로 셉니다.
- 지연 시간 (latency) — 데이터가 출발해서 도착하기까지 걸리는 시간입니다.
- RTT (Round-Trip Time) — 보낸 데이터에 대한 답이 돌아오기까지 걸리는 왕복 시간. `ping`이 잽니다.
- 처리량 (throughput) — 실제로 단위 시간에 전달된 데이터 양입니다.
- 패킷 손실 (packet loss) — 전송 도중 사라진 패킷. 혼잡이나 무선 잡음이 원인입니다.
- 지터 (jitter) — 패킷마다 지연 시간이 들쭉날쭉한 정도입니다.
- LAN (Local Area Network) — 집, 사무실처럼 가까운 범위의 네트워크입니다.
- ISP (Internet Service Provider) — 집과 회사를 인터넷에 이어 주는 통신사입니다.
- IX (Internet Exchange) — 여러 통신사와 네트워크가 한곳에 모여 서로 트래픽을 주고받는 지점입니다.
- 해저 케이블 (submarine cable) — 바다 밑에 깔린 광케이블. 나라 사이 인터넷 트래픽의 대부분을 나릅니다.
- 데이터센터 (data center) — 서버, 스토리지, 네트워크 장비를 모아 전기와 냉방을 갖춰 운영하는 시설입니다.
- 네트워크 인터페이스 카드 (NIC) — 컴퓨터를 네트워크에 연결하는 장치. 랜 포트, Wi-Fi 칩이 여기 속하고 MAC 주소를 가집니다.
- 모뎀 (modem) — 통신사 회선의 신호와 컴퓨터가 쓰는 디지털 신호를 서로 바꾸는 장비입니다.
- ONT (Optical Network Terminal) — 집까지 들어온 광케이블의 빛 신호를 이더넷 신호로 바꾸는 장비입니다.
- 라우터 (router) — 서로 다른 네트워크 사이에서 IP 주소를 보고 패킷을 다음 장비로 넘기는 장비입니다.
- 공유기 (home router) — 라우터, 스위치, Wi-Fi AP, DHCP 서버, NAT, 방화벽을 상자 하나에 넣은 가정용 장비입니다.
- 네트워크 스택 (network stack) — 운영체제 커널 안에서 이더넷, IP, TCP, UDP를 처리하는 코드 전체입니다.
- Wireshark — 네트워크 패킷을 잡아 층별로 풀어서 보여 주는 프로그램입니다.
:::

## 직접 해보기

:::practice my-network 우리 집 네트워크 지도 그리기
내 컴퓨터의 IP 주소, 기본 게이트웨이(공유기), DNS 서버를 찾아 종이에 그림으로 그립니다. 공유기 주소를 브라우저에 쳐서 관리 화면이 뜨는지도 봅니다.

```sh macOS
ipconfig getifaddr en0              # 내 IP (Wi-Fi가 en0이 아닐 수도 있음)
route -n get default | grep gateway # 공유기
scutil --dns | grep nameserver | head -3
```

```powershell Windows (PowerShell)
ipconfig /all
# "IPv4 주소", "기본 게이트웨이", "DNS 서버" 줄을 찾습니다
```

```sh Linux
ip addr show
ip route | grep default
resolvectl status | grep "DNS Servers"
```
:::

:::practice rtt 거리와 RTT 재 보기
공유기, 국내 사이트, 해외 사이트에 `ping`을 보내 RTT를 표로 적습니다. 거리와 RTT가 어떻게 비례하는지 봅니다.

```sh macOS · Linux
ping -c 5 192.168.0.1        # 공유기 주소로 바꿉니다
ping -c 5 naver.com
ping -c 5 www.google.co.jp
ping -c 5 www.bbc.co.uk
```

```powershell Windows
ping -n 5 192.168.0.1
ping -n 5 naver.com
```
:::

:::practice wireshark Wireshark로 캡슐화 눈으로 보기
Wireshark를 설치하고 Wi-Fi(또는 이더넷) 장치에서 잡기를 시작한 뒤, 터미널에서 `curl http://example.com`을 실행합니다. 필터 칸에 `http`를 넣고 GET 요청 패킷 하나를 골라, 아래 창에서 Ethernet II → Internet Protocol → Transmission Control Protocol → Hypertext Transfer Protocol 순으로 봉투가 겹쳐 있는 걸 확인합니다. 각 헤더에서 MAC 주소, IP 주소, 포트 번호를 찾아 적습니다.
:::

:::practice devtools-timing 요청 하나의 시간 쪼개 보기
아무 사이트를 새로 열고 DevTools Network 탭에서 첫 HTML 요청의 Timing 탭을 봅니다. DNS Lookup, Initial connection, SSL, Waiting(TTFB), Content Download가 각각 몇 ms인지 적고, 같은 페이지를 새로고침했을 때 어느 칸이 사라지는지 비교합니다. 사라진 칸이 왜 사라졌는지는 12~14장에서 확인합니다.
:::

## 장 전체 문제

:::quiz scene-ms 맨 앞 그림에서 DNS 리졸버까지 RTT가 10ms, 서버까지 RTT가 30ms라면, HTML이 오기 시작하기까지 네트워크에서만 최소 몇 ms가 들까요?
= 100 | 100ms

10 + 30 × 3 = **100ms**입니다. DNS 왕복 한 번은 가까운 리졸버와, TCP, TLS, HTTP 왕복 세 번은 서버와 합니다. 서버가 아무리 빨리 답해도 이 시간은 줄지 않습니다. 그래서 브라우저는 DNS 답을 캐시하고 연결을 재사용하며, TLS 1.3과 HTTP/3은 왕복 수 자체를 줄입니다.
:::

:::quiz who-reads 이 페이지의 `GET /` 요청이 지나는 것 가운데 HTTP 내용(경로와 헤더)까지 열어 보는 것은?
- [ ] 집 공유기 안의 스위치
- [x] 서버에서 443번 포트를 듣는 Caddy
- [ ] 통신사의 라우터
- [ ] 해저 케이블 양 끝의 장비

Caddy입니다. 스위치는 2층, 라우터는 3층까지만 열고, 케이블 장비는 신호만 다룹니다. HTTP는 7층이라 양 끝만 읽습니다. 게다가 이 페이지는 HTTPS라서 중간 장비가 열어 보려 해도 암호문만 보입니다(14장). 서버에서 TLS를 풀고 HTTP를 읽어 알맞은 프로그램에 넘기는 Caddy는 17장에서 봅니다.
:::

## 스스로 점검

:::qa 패킷 교환이 회선 교환보다 효율적인 이유와, 그 대가는?
길을 독차지하지 않고 모두가 나눠 쓰니 쉬는 동안의 회선을 낭비하지 않고, 길 하나가 끊겨도 다른 길로 돌아갈 수 있습니다. 대가로 패킷마다 지연이 다르고, 패킷이 사라지거나 순서가 바뀔 수 있어 이를 위층(TCP)이 처리해야 합니다.
:::

:::qa 브라우저가 보낸 HTTP 요청이 선에 실릴 때, 어떤 헤더가 어떤 순서로 붙나요? 각 헤더의 핵심 정보는?
바깥부터 이더넷 헤더(받는 쪽과 보내는 쪽 MAC 주소), IP 헤더(IP 주소), TCP 헤더(포트 번호, 순서 번호), 그리고 HTTP 요청입니다. 이더넷 프레임 끝에는 오류 검사값(FCS)이 붙습니다.
:::

:::qa 라우터는 패킷의 어디까지 열어 보나요? 그게 왜 중요한가요?
IP 헤더까지만 봅니다. 위층이 HTTP인지 무엇인지 몰라도 목적지 주소만 보고 넘기면 되니, 장비가 단순하고 빨라지며 새 응용 프로토콜이 생겨도 길 위의 장비를 바꿀 필요가 없습니다.
:::

:::qa 인터넷 속도를 100Mbps에서 1Gbps로 올렸는데 웹 페이지 여는 속도는 별로 안 빨라졌습니다. 왜일까요?
작은 파일 여러 개로 된 웹 페이지는 DNS, 연결, TLS, 요청마다 왕복이 필요해 RTT에 묶여 있습니다. 대역폭은 큰 파일을 내려받을 때 효과가 크고, RTT는 빛의 속도와 거리, 장비 수로 정해져 대역폭으로 줄지 않습니다.
:::

:::qa 집 공유기가 하는 일을 다섯 가지 이상 대 보세요.
라우터(집 안과 통신사망 사이의 패킷 전달), 스위치(유선 포트 연결), Wi-Fi 액세스 포인트, DHCP 서버(IP 나눠 주기), NAT(공인 IP 하나를 나눠 쓰기), 방화벽(밖에서 먼저 오는 연결 막기), DNS 중계를 합니다.
:::
