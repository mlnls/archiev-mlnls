4장은 두 질문을 남겼습니다. 브라우저 아이콘을 눌렀을 때 SSD에 있던 브라우저 "파일"은 어떻게 실행 중인 프로그램이 될까요? 그리고 이 페이지의 JS는 2장에서 본 기계어도 아닌데, 어떻게 CPU에서 돌까요?

두 질문은 사실 한 장면의 두 갈래입니다.

![이 페이지가 화면에서 움직이는 데 필요한 두 재료. ① 아이콘을 누르면 로더가 SSD의 브라우저 실행 파일을 RAM에 올리고, ② 이 페이지와 함께 온 app.js는 그 안의 V8이 읽어 실행합니다. CPU에 닿는 것은 둘 다 결국 기계어입니다](program-scene.svg)

①의 브라우저는 누군가 C++로 쓴 코드를 미리 기계어로 바꿔 둔 것입니다. ②의 `app.js`는 글자 그대로 도착해서, 실행되는 그 자리에서 바뀝니다. 이 장은 ①부터 봅니다. C++ 코드가 어떻게 SSD의 실행 파일이 되고, 아이콘을 누르면 그 파일이 어떻게 프로세스가 되는지 따라간 뒤, ②의 V8로 넘어갑니다. 프론트엔드 개발자가 매일 쓰는 TypeScript 컴파일러, 번들러, 소스 맵이 왜 그런 모양인지도 여기서 이해됩니다.

## 소스 코드에서 기계어까지

브라우저는 수천만 줄짜리 C++ 프로그램이라 따라가기엔 너무 큽니다. 원리는 같으니 C로 쓴 아주 작은 프로그램이 실행 파일이 되기까지를 따라가 봅니다.

```c hello.c
#include <stdio.h>

int main(void) {
  printf("hello\n");
  return 0;
}
```

`cc hello.c -o hello` 한 줄이면 실행 파일이 생기지만, 그 안에서는 네 단계가 차례로 돕니다.

| 단계 | 하는 일 | 결과 |
| --- | --- | --- |
| 전처리 | `#include`를 그 파일 내용으로 바꾸고 매크로를 펼침 | 펼쳐진 C 코드 |
| [[컴파일]] | C 코드를 그 CPU의 [[어셈블리어]]로 번역 | `hello.s` |
| 어셈블 | 어셈블리어를 기계어 바이트로 바꿈 | [[오브젝트 파일]] `hello.o` |
| [[링크]] | 오브젝트 파일들과 라이브러리를 이어 붙임 | [[실행 파일]] `hello` |

![`hello.c`가 실행 파일 `hello`가 되기까지 네 단계. 마지막 링크 단계에서 표준 C 라이브러리의 `printf`가 이어 붙습니다](program-pipeline.svg)

각 단계를 따로 멈춰서 볼 수도 있습니다. `cc -S hello.c`는 어셈블리어를, `cc -c hello.c`는 오브젝트 파일을 만들고 거기서 멈춥니다. 직접 해보기에서 확인합니다. 네 단계 중 가장 많은 일을 하는 것은 두 번째, 컴파일입니다.

## 컴파일러가 하는 일

[[컴파일러]]는 한 언어로 쓴 코드를 다른 언어로 바꾸는 프로그램입니다. 안에서는 대략 이런 일을 합니다.

1. **어휘 분석**: 글자 덩어리를 `int`, `main`, `(`, `)` 같은 낱말(토큰)로 자릅니다.
2. **구문 분석**: 토큰을 문법에 맞춰 나무 구조로 엮습니다. 이 나무가 [[추상 구문 트리]](AST)입니다.
3. **의미 분석**: 타입이 맞는지, 선언하지 않은 변수를 쓰지 않았는지 확인합니다.
4. **최적화**: 결과가 같으면서 더 빠른 코드로 바꿉니다. `x * 2`를 비트 시프트로, 쓰이지 않는 코드를 지우기 등.
5. **코드 생성**: 목표 CPU의 명령어로 적습니다. x86-64용과 ARM64용은 여기서 갈립니다.

![`y = x * 2;` 한 줄이 토큰이 되고 AST가 되는 모습. 같은 AST를 두고 ESLint는 검사만, Prettier와 Babel은 다시 JS로 출력, C 컴파일러는 기계어로 내보냅니다](program-compiler.svg)

앞의 1~3단계는 프론트엔드 개발자에게 익숙합니다. TypeScript 컴파일러, Babel, ESLint, Prettier가 모두 코드를 AST로 바꾼 뒤 일합니다. ESLint는 AST를 검사하고, Prettier는 AST를 다시 예쁘게 출력하고, Babel은 AST를 고쳐서 옛 문법의 JS로 출력합니다. 기계어가 아니라 다른 소스 코드를 내놓는 컴파일러를 [[트랜스파일러]]라고 부르기도 합니다.

컴파일러는 기본적으로 지금 컴퓨터의 CPU와 운영체제용 기계어를 만듭니다. 다른 조합용으로 만드는 것을 크로스 컴파일이라고 합니다. Mac에서 Linux x86-64 서버용 Go 프로그램을 `GOOS=linux GOARCH=amd64 go build`로 만드는 것이 그 예입니다. 브라우저 회사가 같은 소스로 Windows용, macOS용, Linux용 설치 파일을 따로 내놓는 것도 이 때문입니다.

그런데 컴파일러가 만든 `hello.o`만으로는 아직 실행할 수 없습니다. 빈칸이 남아 있기 때문입니다.

## 링커: 조각을 하나로 잇기

`hello.o` 안에는 `main`의 기계어는 있지만 `printf`의 기계어는 없습니다. `printf`는 표준 C 라이브러리에 있기 때문입니다. 오브젝트 파일은 "여기서 `printf`라는 이름의 함수를 부르는데 주소는 아직 모름"이라는 빈칸을 남겨 둡니다. 함수나 변수의 이런 이름을 [[심볼]]이라고 합니다.

[[링커]]는 여러 오브젝트 파일과 라이브러리를 모아 이 빈칸을 채웁니다. 큰 프로그램은 파일 수천 개로 나뉘어 따로 컴파일되고, 링커가 마지막에 하나로 잇습니다. 링커가 빈칸을 채우는 방법은 두 가지입니다.

- **[[정적 링크]]**: 라이브러리의 기계어를 실행 파일 안에 복사해 넣습니다. 실행 파일 하나만 있으면 어디서든 돌지만, 파일이 커지고 라이브러리에 보안 패치가 나와도 다시 빌드해야 반영됩니다. Go와 Rust는 기본적으로 정적 링크를 많이 씁니다.
- **[[동적 링크]]**: 실행 파일에는 "이 라이브러리의 이 함수가 필요함"이라고만 적어 두고, 실행할 때 운영체제가 [[동적 라이브러리]]를 찾아 연결합니다. 여러 프로그램이 같은 라이브러리를 메모리 하나로 나눠 쓰고, 라이브러리만 업데이트하면 모두에 반영됩니다.

![같은 빈칸을 채우는 두 방법. 정적 링크는 printf의 기계어를 실행 파일 안에 복사하고, 동적 링크는 실행할 때 메모리에 있는 라이브러리 한 벌에 연결해 여러 프로그램이 나눠 씁니다](program-linking.svg)

| | Windows | macOS | Linux |
| --- | --- | --- | --- |
| 동적 라이브러리 확장자 | `.dll` | `.dylib`, `.framework` | `.so` (shared object) |
| 실행 때 연결해 주는 것 | Windows 로더 (`ntdll.dll`) | `dyld` | `ld-linux.so` |
| 의존 라이브러리 보기 | `dumpbin /dependents` | `otool -L` | `ldd` |
| 흔한 오류 | "VCRUNTIME140.dll이 없어 실행할 수 없습니다" | "Library not loaded: …dylib" | "error while loading shared libraries: libssl.so.3" |

동적 링크의 대가는 "실행할 컴퓨터에 그 라이브러리의 그 버전이 있어야 한다"는 것입니다. 게임을 설치할 때 Visual C++ 재배포 패키지를 함께 설치하라는 이유, Docker 이미지를 Alpine(musl)으로 바꾸면 glibc용으로 빌드된 프로그램이 안 도는 이유가 이것입니다.

:::quiz alpine-glibc Debian 기반 Docker 이미지에서 잘 돌던 프로그램을 Alpine 이미지로 옮겼더니 "not found" 비슷한 오류로 실행조차 되지 않습니다. 소스는 그대로입니다. 가장 그럴듯한 원인은?
- [ ] Alpine은 x86-64 CPU를 지원하지 않아서
- [x] glibc에 동적 링크된 실행 파일인데 Alpine에는 musl만 있어서
- [ ] Alpine의 커널이 Linux가 아니어서
- [ ] Docker 이미지가 정적 링크를 막아서

동적 라이브러리가 없어서입니다. 실행 파일은 "glibc의 이 함수들이 필요하다"고만 적고 있는데 Alpine에는 다른 C 라이브러리(musl)가 들어 있어 동적 링커가 연결할 대상을 찾지 못합니다. 커널과 CPU는 같습니다. 정적 링크로 빌드했다면 이 문제가 없습니다.
:::

링크가 끝나면 SSD에 실행 파일 하나가 놓입니다. 브라우저를 설치했다는 것은 이런 파일이 디스크에 생겼다는 뜻입니다. 이 파일은 어떻게 생겼을까요?

## 실행 파일의 생김새

[[실행 파일]]은 기계어만 덩그러니 든 파일이 아닙니다. 운영체제가 읽는 머리말과 여러 구역으로 나뉜 정해진 형식이 있습니다. 운영체제마다 형식이 다릅니다.

| | Windows | macOS | Linux |
| --- | --- | --- | --- |
| 형식 | [[PE]] (Portable Executable) | [[Mach-O]] | [[ELF]] |
| 맨 앞 바이트 (매직 넘버) | `4D 5A` ("MZ") | `CF FA ED FE` (64비트), 유니버설은 `CA FE BA BE` | `7F 45 4C 46` ("\x7FELF") |
| 실행 파일 확장자 | `.exe` 필수 | 없음 (앱은 `.app` 폴더 안에) | 없음 |

형식은 달라도 안에 담는 것은 비슷합니다.

- **머리말**: 어떤 CPU용인지, 어디부터 실행할지([[엔트리 포인트]]), 어떤 동적 라이브러리가 필요한지.
- **코드 구역** (`.text`): 기계어 명령어들. 읽기와 실행만 되고 쓰기는 막힙니다.
- **데이터 구역** (`.data`, `.rodata`, `.bss`): 초기값이 있는 전역 변수, 문자열 상수, 0으로 시작하는 전역 변수.
- **심볼 표**: 함수와 변수 이름. 디버거와 오류 스택에 이름이 보이는 이유입니다. 배포할 때는 지우기도 합니다.

![ELF 실행 파일 안의 구역들. 머리말이 "어떤 CPU용이고 어디서부터 실행하라"를 알려 주고, 기계어는 쓰기가 막힌 코드 구역에 들어 있습니다](program-exe-layout.svg)

같은 C 코드라도 Windows용 PE와 Linux용 ELF는 형식부터 다르고, 부르는 시스템 콜도 다르니 서로 실행되지 않습니다. CPU가 같은 x86-64여도 그렇습니다. "Mac에서 `.exe`를 못 돌리는 이유"는 형식, 시스템 콜, 라이브러리가 모두 다르기 때문입니다.

:::quiz magic-elf 어떤 파일의 맨 앞 네 바이트가 `7F 45 4C 46`입니다. 이 파일을 그대로 실행할 수 있는 곳은?
- [ ] Windows
- [ ] macOS
- [x] Linux
- [ ] 세 운영체제 모두

Linux입니다. `7F 45 4C 46`은 "\x7FELF", 곧 ELF 실행 파일의 매직 넘버입니다. Windows는 PE("MZ"), macOS는 Mach-O를 읽으니 이 파일을 실행 파일로 알아보지 못합니다. 1장에서 본 매직 넘버가 여기서도 쓰입니다.
:::

이제 SSD에 놓인 브라우저 파일의 모양을 압니다. 아이콘을 누르면 이 파일에 무슨 일이 일어날까요?

## 실행하면 무슨 일이 일어나나: 로더

셸에서 `./hello`를 치거나 아이콘을 더블클릭하면, 결국 운영체제의 프로그램 실행 시스템 콜(`execve` 또는 `CreateProcess`)이 불립니다. 커널과 [[로더]]가 이어서 일합니다.

1. 커널이 파일의 머리말을 읽어 형식과 CPU가 맞는지 확인합니다. 안 맞으면 `exec format error`입니다.
2. 새 [[주소 공간]]을 만듭니다(7장). 이 프로그램만의 빈 메모리 지도입니다.
3. 실행 파일의 코드 구역과 데이터 구역을 주소 공간에 연결합니다. 이때 전부 읽어 오지 않고 "필요하면 이 파일의 이 부분을 읽어 오라"고만 적어 둡니다. 실제로 읽는 건 그 코드가 처음 실행될 때입니다(페이지 폴트, 7장).
4. 스택을 만들고 그 위에 명령줄 인자(`argv`)와 환경 변수를 올려 둡니다. `process.argv`와 `process.env`의 출처입니다.
5. 동적 링크된 프로그램이면 동적 링커(`ld-linux.so`, `dyld`)를 먼저 실행해, 필요한 라이브러리를 찾아 주소 공간에 붙이고 빈칸을 채웁니다.
6. 엔트리 포인트로 건너뜁니다. C 프로그램이면 런타임 초기화 코드(`_start`)가 돌고 나서 `main`이 불립니다.

![실행 파일 하나가 프로세스가 되는 여섯 단계. 디스크의 파일은 주소 공간에 "연결"만 되고, 실제로 읽히는 것은 그 부분을 처음 쓸 때입니다](program-loader.svg)

요즘 운영체제는 매번 코드와 라이브러리를 다른 주소에 올립니다. 이걸 [[ASLR]]이라고 합니다. 공격자가 메모리 주소를 미리 알고 공격하지 못하게 하려는 것입니다.

브라우저 아이콘을 누른 순간도 똑같습니다. macOS라면 Finder가 `Google Chrome.app` 안의 Mach-O 파일로 이 과정을 시작하고, 몇백 밀리초 뒤 브라우저의 `main`이 돌기 시작합니다. 수백 MB짜리 브라우저가 그렇게 빨리 뜨는 이유가 3번입니다. 전부 읽지 않고, 당장 필요한 부분만 읽기 때문입니다.

:::quiz lazy-load 수백 MB짜리 실행 파일인데 아이콘을 누르고 1초도 안 되어 창이 뜹니다. 로더의 어떤 동작 덕분일까요?
- [ ] 실행 파일을 미리 압축 해제해 RAM에 상주시켜 둬서
- [x] 실행 파일을 주소 공간에 연결만 해 두고, 실제로 읽는 건 그 부분을 처음 쓸 때 해서
- [ ] 엔트리 포인트를 건너뛰고 바로 `main`을 실행해서
- [ ] ASLR이 실행 파일을 작게 만들어서

연결만 해 두고 필요할 때 읽기 때문입니다. 로더는 파일 전체를 RAM에 복사하지 않고 "이 주소는 파일의 이 부분"이라고 적어 둡니다. 실제 읽기는 그 코드가 처음 실행될 때 페이지 단위로 일어납니다(7장의 페이지 폴트). 쓰지 않는 기능의 코드는 끝까지 디스크에 남아 있습니다.
:::

브라우저는 이제 실행 중입니다. 실행 중인 프로그램은 함수를 부르고, 그 함수가 또 함수를 부르며 돌아갑니다. 어디까지 들어갔다가 어디로 돌아올지는 어디에 적어 둘까요?

## 함수 호출과 콜 스택

프로그램이 실행되는 동안 "지금 어느 함수 안에 있고, 끝나면 어디로 돌아갈지"를 기억하는 곳이 [[콜 스택]]입니다. 함수를 부를 때마다 스택 위에 칸 하나, [[스택 프레임]]이 쌓입니다. 프레임에는 돌아갈 주소, 인자, 지역 변수가 들어 있습니다. 함수가 끝나면 그 프레임을 걷어 내고 돌아갈 주소로 갑니다.

![`main` → `render` → `format` 순서로 불렀을 때의 콜 스택과, 같은 순간에 오류가 나면 보이는 JS 오류 스택. 오류 스택은 프레임을 위에서부터 읽은 것입니다](program-callstack.svg)

JS의 오류 스택(`at format (app.js:12)`, `at render (app.js:30)`)은 바로 이 프레임들을 위에서부터 읽은 것입니다. 재귀가 끝나지 않으면 프레임이 계속 쌓여 스택에 정해진 크기를 넘고, [[스택 오버플로]]가 납니다. JS에서는 `RangeError: Maximum call stack size exceeded`로 보입니다.

여기까지가 ①, 브라우저라는 실행 파일의 이야기입니다. 이제 ②로 넘어갑니다. 이 페이지와 함께 온 `app.js`는 기계어가 아니라 글자입니다. CPU는 글자를 실행하지 못하는데, 어떻게 체크박스가 움직일까요?

## 컴파일하지 않는 언어: 인터프리터와 바이트코드

모든 언어가 미리 기계어로 컴파일되지는 않습니다. [[인터프리터]]는 코드를 한 줄씩 읽으면서 그 자리에서 실행하는 프로그램입니다. 인터프리터 자체는 기계어로 된 실행 파일이고, 우리 코드는 그 인터프리터가 읽는 데이터입니다. `python app.py`, `node app.js`에서 실행 파일은 `python`과 `node`이고 `app.py`, `app.js`는 입력입니다.

브라우저에서도 마찬가지입니다. 실행 파일은 브라우저이고, 이 페이지의 `app.js`는 그 브라우저 안의 JS 엔진이 읽는 데이터입니다.

소스 코드를 매번 처음부터 해석하면 느리니, 대부분의 인터프리터는 먼저 [[바이트코드]]라는 단순한 중간 명령어로 바꾼 뒤 그걸 실행합니다. Python의 `.pyc`, Java의 `.class`가 바이트코드입니다. 바이트코드는 특정 CPU가 아니라 가상의 기계를 위한 명령어라서 어느 운영체제, 어느 CPU에서든 그 언어의 인터프리터만 있으면 실행됩니다.

| | 미리 컴파일 (AOT) | 인터프리터 | JIT |
| --- | --- | --- | --- |
| 언제 기계어가 되나 | 배포 전에 | 기계어가 되지 않음 (인터프리터가 대신 실행) | 실행하면서 자주 쓰는 부분만 |
| 시작 속도 | 빠름 | 빠름 | 빠름 (처음엔 인터프리터로) |
| 최고 속도 | 빠름 | 느림 | 빠름 (데워지고 나면) |
| 예 | C, C++, Rust, Go, Swift | 초기 Python, Ruby, 셸 스크립트 | JS (V8), Java (HotSpot), C# |

## JIT: 실행하면서 컴파일하기

JS 엔진은 [[JIT 컴파일]]을 씁니다. 처음에는 인터프리터로 빨리 시작하고, 실행해 보면서 자주 도는 함수를 골라 그때 기계어로 컴파일합니다. Chrome과 Node의 엔진인 [[V8]]은 이렇게 단계를 올립니다.

1. **파싱**: JS 코드를 AST로 만듭니다. 당장 안 부르는 함수는 대충만 훑고 넘어갑니다(지연 파싱).
2. **Ignition**: AST를 바이트코드로 바꾸고 인터프리터로 실행합니다. 실행하면서 "이 `+`에는 늘 정수가 왔다", "이 객체는 늘 `{x, y}` 모양이었다" 같은 타입 정보를 모읍니다.
3. **Sparkplug, Maglev**: 자주 불리는 함수를 빠르게 기계어로 바꿉니다.
4. **TurboFan**: 아주 뜨거운 함수는 모은 타입 정보를 믿고 강하게 최적화한 기계어로 바꿉니다. "늘 정수였으니 정수 덧셈 명령어 하나로" 같은 식입니다.
5. **디옵티마이제이션**: 믿었던 가정이 깨지면(갑자기 문자열이 들어오면) 최적화된 기계어를 버리고 바이트코드로 돌아갑니다.

![V8이 JS를 실행하는 단계. 처음엔 모두 바이트코드로 시작하고, 자주 불릴수록 오른쪽의 더 강한 컴파일러가 기계어로 바꿉니다. 가정이 깨지면 바이트코드로 되돌아갑니다](program-v8.svg)

이 페이지의 `app.js`는 대부분 왼쪽에서 끝납니다. 진행 막대를 그리는 함수는 체크할 때 한 번씩 불릴 뿐이라 바이트코드로 충분합니다. 반대로 스크롤마다 수천 번 도는 코드나 게임의 계산 루프는 금세 오른쪽 끝까지 갑니다.

V8은 객체의 "모양"(어떤 속성이 어떤 순서로 있는지)을 [[히든 클래스]]로 기억하고, 같은 모양의 객체가 계속 오면 속성 위치를 미리 알고 빠르게 읽습니다. 그래서 JS 성능 조언에 이런 것들이 나옵니다.

- 객체의 속성은 생성자나 리터럴에서 한 번에, 같은 순서로 만듭니다. 나중에 `obj.newProp = …`를 붙이거나 `delete`하면 모양이 바뀝니다.
- 한 함수에 여러 모양의 객체나 여러 타입을 번갈아 넘기지 않습니다.
- 배열에 숫자와 문자열을 섞지 않습니다.

대부분의 앱에서는 이런 미세 조정보다 알고리즘과 네트워크가 훨씬 중요하지만, "JS가 왜 처음엔 느리다가 빨라지는지", "벤치마크는 왜 여러 번 돌려 데운 뒤 재는지"는 JIT로 설명됩니다.

:::quiz deopt 숫자만 더하던 함수가 충분히 빨라진 뒤, 한 번 문자열이 섞여 들어왔더니 한동안 느려졌습니다. V8 안에서 일어난 일은?
- [ ] 가비지 컬렉션이 함수의 기계어를 지워서
- [ ] 문자열 덧셈은 운영체제의 시스템 콜이 필요해서
- [ ] 함수의 AST를 처음부터 다시 파싱해서
- [x] "늘 숫자"라는 가정으로 만든 기계어를 버리고 바이트코드로 돌아가서

디옵티마이제이션입니다. TurboFan은 Ignition이 모은 "늘 숫자였다"는 정보를 믿고 숫자 덧셈 명령어로 기계어를 만들었는데, 가정이 깨지면 그 기계어는 틀린 답을 낼 수 있으니 버리고 바이트코드로 돌아갑니다. 다시 데워지면 새 정보로 다시 최적화합니다.
:::

## Node.js는 무엇으로 되어 있나

이 페이지의 `app.js`를 돌린 V8은 브라우저 안에 있었습니다. 같은 V8을 브라우저 밖으로 꺼낸 것이 Node입니다.

[[Node.js]]는 브라우저 밖에서 JS를 실행하는 프로그램입니다. `node`라는 실행 파일 하나 안에 이런 것들이 들어 있습니다.

- **V8**: JS를 실행합니다. 브라우저의 V8과 같은 엔진입니다.
- **[[libuv]]**: 파일, 네트워크, 타이머, 자식 프로세스를 다루는 C 라이브러리. 운영체제마다 다른 방식(epoll, kqueue, IOCP)을 같은 모양으로 감싸 줍니다. 이벤트 루프가 여기 있습니다(8장).
- **C++ 바인딩**: `fs`, `net`, `crypto` 같은 JS 모듈이 libuv와 OpenSSL을 부를 수 있게 이어 주는 코드.
- **JS로 쓴 표준 라이브러리**: `fs`, `http`, `path` 모듈의 JS 부분.

`node`는 운영체제와 CPU마다 따로 빌드된 기계어 실행 파일입니다. 그래서 Node를 설치할 때 "macOS ARM64", "Windows x64" 같은 걸 고릅니다. 다른 JS 실행 환경도 구성은 비슷합니다. Deno는 V8 + Rust, Bun은 Safari의 JavaScriptCore + Zig로 만들었습니다.

브라우저도 마찬가지로 JS 엔진(V8, Firefox의 SpiderMonkey, Safari의 JavaScriptCore)에 DOM과 렌더링 엔진, 네트워크 스택을 붙인 큰 프로그램입니다.

## 곁가지: WebAssembly

[[WebAssembly]](Wasm)는 브라우저가 실행하는 바이트코드 형식입니다. C, C++, Rust 같은 언어를 Wasm으로 컴파일하면, 브라우저가 이를 받아 그 컴퓨터의 기계어로 빠르게 컴파일해 실행합니다. JS보다 시작과 실행이 예측 가능하게 빠르고, 브라우저의 보안 울타리 안에서 돕니다. Figma, Photoshop 웹판, 브라우저의 동영상 편집기가 무거운 계산을 Wasm으로 합니다. Wasm은 브라우저 밖(서버, 엣지)에서도 쓰입니다.

## 곁가지: 이 실행 파일을 믿어도 되나, 코드 서명

인터넷에서 받은 실행 파일은 누가 만들었는지, 도중에 바뀌지 않았는지 알 수 없습니다. 그래서 운영체제는 [[코드 서명]]을 확인합니다. 개발자가 인증 기관에서 받은 인증서로 실행 파일에 [[디지털 서명]]을 하고, 운영체제가 실행 전에 그 서명을 검사합니다.

| | Windows | macOS | Linux |
| --- | --- | --- | --- |
| 서명 방식 | Authenticode | Apple 개발자 인증서 + [[공증]](Apple이 악성 여부를 검사하고 도장) | 대개 앱 단위 서명 없음. 패키지 저장소가 GPG로 서명 |
| 인터넷에서 받은 파일 표시 | Mark of the Web (`Zone.Identifier` 정보) | 격리 속성 (`com.apple.quarantine`) | 없음 |
| 경고 창 | [[SmartScreen]]: "Windows의 PC 보호" | [[Gatekeeper]]: "확인되지 않은 개발자", "손상되었기 때문에 열 수 없습니다" | 없음 |
| 실행 권한 | `.exe` 확장자면 실행 대상 | 실행 권한 비트 + 서명 | 실행 권한 비트 (`chmod +x`) |

## 곁가지: 스크립트는 어떻게 실행되나

`.sh`나 `.js` 같은 스크립트는 기계어가 아니니 운영체제가 바로 실행할 수 없습니다. 그래서 "이 파일은 무엇으로 실행하라"는 표시가 필요합니다.

- **macOS, Linux**: 파일 첫 줄에 `#!/usr/bin/env node` 같은 [[셔뱅]]을 적고 실행 권한을 주면, 커널이 첫 줄을 보고 그 인터프리터에 파일을 넘깁니다.
- **Windows**: 셔뱅을 모릅니다. 확장자에 연결된 프로그램으로 엽니다. 그래서 `.js` 파일을 더블클릭하면 Node가 아니라 Windows에 내장된 옛 스크립트 엔진(Windows Script Host)이 실행해 엉뚱한 오류를 냅니다.

npm은 이 차이를 숨기려고 `node_modules/.bin`에 실행 파일을 만들 때, macOS와 Linux에서는 셔뱅이 있는 파일로 가는 링크를, Windows에서는 `node`를 불러 주는 `.cmd`와 `.ps1` 파일을 따로 만듭니다. `npx vite`가 세 운영체제에서 모두 되는 이유입니다.

## 다시 장면으로: 아이콘을 누르고 체크박스가 움직이기까지

맨 앞 그림을 이제 말로 풀 수 있습니다. 브라우저 회사는 C++ 소스를 컴파일하고 링크해 Mach-O, PE, ELF 실행 파일을 따로 만들어 배포했습니다(①). 아이콘을 누르자 커널과 로더가 그 파일의 머리말을 확인하고, 새 주소 공간에 코드를 연결하고, 동적 라이브러리를 붙이고, 엔트리 포인트로 건너뛰었습니다. 그렇게 뜬 브라우저 안의 V8이 이 페이지와 함께 온 `app.js`를 AST로, 바이트코드로 바꿔 실행하고 있습니다(②). 체크박스를 누를 때 도는 코드는 바이트코드 인터프리터를 거쳐, 결국 CPU의 기계어 명령어로 실행됩니다.

그런데 작업 관리자나 활동 모니터를 열어 보면 이상한 게 보입니다. 브라우저 아이콘은 한 번 눌렀는데 Chrome이라는 이름의 프로그램이 수십 개 떠 있습니다. 게다가 CPU 코어는 8개뿐인데 실행 중인 프로그램은 수백 개입니다. 하나의 실행 파일이 여러 개로 돌고, 적은 코어를 많은 프로그램이 나눠 쓰는 일, 6장의 프로세스 이야기입니다.

## 프론트엔드와 이어지는 곳

- TypeScript, Babel, SWC, esbuild는 컴파일러입니다. 소스를 AST로 바꾸고, 고치고, 다시 소스로 출력합니다.
- [[번들러]](Vite, webpack, Rollup)는 링커와 닮았습니다. import로 이어진 모듈들을 찾아 하나로 잇고, 쓰이지 않는 코드를 버리고(tree shaking, 링커의 죽은 코드 제거), 필요할 때 불러올 조각으로 나눕니다(code splitting, 동적 링크와 비슷).
- [[소스 맵]]은 실행 파일의 디버그 심볼처럼, 압축되고 변환된 코드의 위치를 원래 소스 위치로 되돌려 줍니다. 오류 추적 도구가 원본 줄 번호를 보여 주는 이유입니다.
- 함수가 처음 불릴 때 느리고 나중에 빨라지는 것, 벤치마크 결과가 들쭉날쭉한 것은 JIT 때문입니다.

## 용어 정리

:::terms
- 컴파일 (compile) — 한 언어로 쓴 코드를 다른 언어(주로 기계어)로 번역하는 일입니다.
- 컴파일러 (compiler) — 컴파일을 하는 프로그램. 어휘 분석, 구문 분석, 의미 분석, 최적화, 코드 생성 단계를 거칩니다.
- 추상 구문 트리 (AST, Abstract Syntax Tree) — 코드를 문법 구조에 따라 나무 모양으로 나타낸 것. 컴파일러, Babel, ESLint, Prettier가 모두 AST로 일합니다.
- 트랜스파일러 (transpiler) — 기계어가 아니라 다른 소스 코드를 내놓는 컴파일러. TypeScript → JS, 최신 JS → 옛 JS.
- 어셈블리어 (assembly language) — 기계어 명령어를 사람이 읽을 수 있는 글자(`mov`, `add`)로 적은 언어. 어셈블러가 기계어로 바꿉니다.
- 오브젝트 파일 (object file) — 소스 파일 하나를 컴파일한 기계어 조각. 다른 파일의 함수 주소는 빈칸으로 남아 있습니다.
- 심볼 (symbol) — 함수나 전역 변수의 이름. 링커가 이름으로 빈칸을 채우고, 디버거가 이름을 보여 줍니다.
- 링크 (link) — 오브젝트 파일과 라이브러리를 이어 하나의 실행 파일로 만드는 일입니다.
- 링커 (linker) — 링크를 하는 프로그램. 심볼의 빈칸을 실제 주소로 채웁니다.
- 정적 링크 (static linking) — 라이브러리 코드를 실행 파일 안에 복사해 넣는 방식. 파일 하나로 어디서든 돕니다.
- 동적 링크 (dynamic linking) — 실행할 때 운영체제가 동적 라이브러리를 찾아 연결하는 방식. 여러 프로그램이 라이브러리를 나눠 씁니다.
- 동적 라이브러리 (dynamic library) — 실행 중에 연결되는 공유 코드 파일. Windows `.dll`, macOS `.dylib`, Linux `.so`.
- 실행 파일 (executable) — 운영체제가 읽을 머리말, 기계어 코드, 데이터를 정해진 형식으로 담은 파일입니다.
- PE (Portable Executable) — Windows의 실행 파일 형식. `.exe`, `.dll`이 이 형식이고 "MZ"로 시작합니다.
- Mach-O — macOS와 iOS의 실행 파일 형식입니다.
- ELF (Executable and Linkable Format) — Linux와 대부분의 유닉스 계열의 실행 파일 형식. `7F 45 4C 46`으로 시작합니다.
- 엔트리 포인트 (entry point) — 실행 파일에서 맨 처음 실행할 명령어의 위치입니다.
- 로더 (loader) — 실행 파일을 읽어 메모리에 배치하고, 동적 라이브러리를 연결하고, 엔트리 포인트로 넘겨 주는 운영체제의 부분입니다.
- ASLR (Address Space Layout Randomization) — 실행할 때마다 코드, 라이브러리, 스택을 다른 주소에 올려 공격을 어렵게 하는 기법입니다.
- 콜 스택 (call stack) — 실행 중인 함수 호출을 쌓아 두는 메모리 영역. 함수가 끝나면 어디로 돌아갈지를 기억합니다.
- 스택 프레임 (stack frame) — 함수 호출 하나가 콜 스택에 차지하는 칸. 돌아갈 주소, 인자, 지역 변수가 들어 있습니다.
- 스택 오버플로 (stack overflow) — 콜 스택이 정해진 크기를 넘는 것. 끝나지 않는 재귀가 흔한 원인입니다.
- 인터프리터 (interpreter) — 코드를 미리 기계어로 바꾸지 않고 읽으면서 바로 실행하는 프로그램입니다.
- 바이트코드 (bytecode) — 가상의 기계를 위한 단순한 중간 명령어. 인터프리터나 JIT가 실행합니다.
- JIT 컴파일 (Just-In-Time compilation) — 실행하는 도중에 자주 쓰는 코드를 기계어로 컴파일하는 방식. JS 엔진이 씁니다.
- V8 — Chrome과 Node.js의 JS 엔진. 바이트코드 인터프리터(Ignition)와 여러 단계의 JIT 컴파일러(Sparkplug, Maglev, TurboFan)로 되어 있습니다.
- 히든 클래스 (hidden class) — JS 엔진이 객체의 속성 구성과 순서를 기억하는 내부 구조. 같은 모양이 반복되면 속성 접근이 빨라집니다.
- 디옵티마이제이션 (deoptimization) — JIT가 믿었던 타입 가정이 깨졌을 때 최적화된 기계어를 버리고 느린 단계로 돌아가는 것입니다.
- Node.js — V8, libuv, 표준 라이브러리를 묶어 브라우저 밖에서 JS를 실행하는 프로그램입니다.
- libuv — 파일, 네트워크, 타이머를 운영체제와 상관없이 같은 방식으로 다루게 해 주는 C 라이브러리. Node의 이벤트 루프가 여기 있습니다.
- WebAssembly — 브라우저(와 그 밖)에서 실행하는 이식 가능한 바이트코드 형식. C, Rust 등을 컴파일해 거의 기계어 속도로 돌립니다.
- 코드 서명 (code signing) — 실행 파일에 개발자의 디지털 서명을 붙여 누가 만들었고 바뀌지 않았음을 증명하는 것입니다.
- 공증 (notarization) — Apple이 개발자가 제출한 앱을 자동 검사하고 통과 표시를 붙여 주는 과정. Gatekeeper가 이 표시를 확인합니다.
- Gatekeeper — macOS가 인터넷에서 받은 앱의 서명과 공증을 확인해 실행을 허락하거나 막는 기능입니다.
- SmartScreen — Windows가 인터넷에서 받은 파일의 평판과 서명을 확인해 경고하는 기능입니다.
- 셔뱅 (shebang) — 스크립트 첫 줄의 `#!` 표시. macOS와 Linux 커널이 이걸 보고 어떤 인터프리터로 실행할지 정합니다.
- 번들러 (bundler) — 모듈들을 import를 따라 모아 브라우저가 받을 파일 몇 개로 묶는 도구. Vite, webpack, Rollup, esbuild.
- 소스 맵 (source map) — 변환·압축된 코드의 위치를 원래 소스 코드의 위치로 되돌리는 정보를 담은 파일입니다.
:::

## 직접 해보기

:::practice compile C 프로그램을 단계별로 멈춰 보기
macOS(Xcode 명령줄 도구: `xcode-select --install`)나 Linux(`gcc`), Windows라면 WSL에서 합니다. 각 단계의 결과를 열어 보고, 내 CPU(x86-64, ARM64)의 어셈블리어가 어떻게 생겼는지 봅니다.

```sh macOS · Linux
cat > hello.c <<'EOF'
#include <stdio.h>
int main(void) { printf("hello\n"); return 0; }
EOF
cc -S -O1 hello.c && cat hello.s   # 어셈블리어
cc -c hello.c && nm hello.o         # 오브젝트 파일의 심볼. printf는 U(정의 안 됨)
cc hello.c -o hello && ./hello
file hello                          # Mach-O 64-bit arm64 또는 ELF 64-bit x86-64
xxd -l 4 hello                      # 매직 넘버
```
:::

:::practice deps 실행 파일이 기대는 동적 라이브러리 보기
`node` 실행 파일이 어떤 형식이고 어떤 동적 라이브러리를 쓰는지 봅니다.

```sh macOS
file "$(which node)"
otool -L "$(which node)"
```

```sh Linux
file "$(which node)"
ldd "$(which node)"
```

```powershell Windows (PowerShell)
Get-Item (Get-Command node).Source | Select-Object FullName, Length
# Visual Studio의 개발자 명령 프롬프트가 있다면: dumpbin /dependents "C:\Program Files\nodejs\node.exe"
```
:::

:::practice bytecode V8의 바이트코드 엿보기
작은 함수를 V8이 어떤 바이트코드로 바꾸는지, 그리고 여러 번 부르면 최적화되는지 봅니다.

```sh 터미널
node --print-bytecode --print-bytecode-filter=add -e "function add(a, b) { return a + b } add(1, 2)"

node --trace-opt --trace-deopt -e "
function add(a, b) { return a + b }
for (let i = 0; i < 1e6; i++) add(i, 1)
add('a', 'b')  // 타입이 바뀌면 deopt 기록이 남는지 봅니다
" | grep -E "add|deoptimiz" | head
```
:::

:::practice quarantine 인터넷에서 받은 파일의 표시 확인하기
브라우저로 아무 파일이나 하나 받은 뒤, 운영체제가 붙여 둔 "인터넷에서 왔음" 표시를 찾아봅니다.

```sh macOS
xattr -l ~/Downloads/받은파일
# com.apple.quarantine 항목이 보입니다
```

```powershell Windows (PowerShell)
Get-Content -Path "$HOME\Downloads\받은파일" -Stream Zone.Identifier
# ZoneId=3 은 인터넷 영역이라는 뜻입니다
```
:::

:::practice shims npm이 만든 실행 파일 보기
아무 프로젝트의 `node_modules/.bin`을 열어 `vite`나 `tsc`가 어떤 파일인지 봅니다. macOS·Linux에서는 링크와 셔뱅을, Windows에서는 `.cmd` 파일 내용을 확인합니다.

```sh macOS · Linux
ls -l node_modules/.bin | head
head -1 "$(readlink -f node_modules/.bin/tsc)"
```

```powershell Windows (PowerShell)
Get-ChildItem node_modules\.bin | Select-Object -First 10
Get-Content node_modules\.bin\tsc.cmd
```
:::

## 장 전체 문제

:::quiz browser-vs-js 브라우저 실행 파일과 이 페이지의 `app.js`를 비교한 설명으로 맞는 것은?
- [ ] 둘 다 배포 전에 기계어로 컴파일되어 있다
- [ ] 브라우저는 V8이 실행하고, `app.js`는 로더가 실행한다
- [x] 브라우저는 미리 기계어로 컴파일된 실행 파일이고, `app.js`는 브라우저 안의 V8이 실행하면서 바꾼다
- [ ] `app.js`는 Mach-O나 PE 형식으로 바뀌어 디스크에 저장된 뒤 실행된다

브라우저는 미리 컴파일된 실행 파일이고, `app.js`는 실행되는 자리에서 V8이 바꿉니다. 로더가 다루는 것은 브라우저 실행 파일이고, `app.js`는 그 브라우저가 읽는 데이터입니다. 그래서 같은 `app.js`가 어느 운영체제, 어느 CPU의 브라우저에서든 그대로 돕니다.
:::

:::quiz node-binary 같은 `server.js`는 macOS ARM64와 Windows x64에서 모두 도는데, `node` 설치 파일은 운영체제와 CPU마다 따로 받아야 합니다. 이유는?
- [x] `node`는 V8과 libuv를 컴파일한 기계어 실행 파일이고, `server.js`는 그 위에서 해석되는 글자라서
- [ ] `server.js`가 설치할 때 각 운영체제용으로 컴파일되어서
- [ ] Windows는 JS를 다른 문법으로 읽어서
- [ ] `node`는 바이트코드라서 CPU마다 다시 받아야 해서

`node`는 기계어 실행 파일이고 `server.js`는 데이터이기 때문입니다. 기계어는 ISA와 실행 파일 형식에 묶여 있지만, JS 소스는 어느 `node`든 똑같이 읽습니다. 이 장의 ①과 ②의 관계와 같습니다.
:::

## 스스로 점검

:::qa 같은 x86-64 CPU인데 Windows용 `.exe`를 Linux에서 그냥 실행할 수 없는 이유를 세 가지 대 보세요.
실행 파일 형식이 다르고(PE와 ELF), 부르는 시스템 콜과 그 방식이 다르고(Win32/NT API와 Linux 시스템 콜), 기대는 동적 라이브러리가 다릅니다(`.dll`과 `.so`). Wine 같은 호환 계층은 이 차이를 번역해 줍니다.
:::

:::qa 정적 링크와 동적 링크의 장단점은? Go로 만든 서버를 Docker의 아주 작은 이미지(scratch)에 넣을 수 있는 이유는?
정적 링크는 파일 하나로 어디서든 돌지만 크고, 라이브러리 패치를 반영하려면 다시 빌드해야 합니다. 동적 링크는 작고 라이브러리를 나눠 쓰지만 실행할 곳에 맞는 라이브러리가 있어야 합니다. Go는 기본으로 정적 링크해 실행 파일이 다른 라이브러리를 필요로 하지 않으니, 아무것도 없는 이미지에서도 돕니다.
:::

:::qa `RangeError: Maximum call stack size exceeded`가 무엇이고 왜 생기나요?
함수 호출마다 콜 스택에 스택 프레임이 쌓이는데, 끝나지 않는 재귀 등으로 프레임이 정해진 스택 크기를 넘은 것입니다. 스택 오버플로입니다.
:::

:::qa V8에서 같은 함수에 늘 `{x, y}` 객체를 넘기다가 가끔 `{y, x}`나 `{x, y, z}`를 넘기면 왜 느려질 수 있나요?
V8은 객체 모양(히든 클래스)을 보고 속성 위치를 가정한 최적화 코드를 만듭니다. 모양이 여러 가지면 가정을 여러 개 확인해야 하거나, 가정이 깨져 디옵티마이제이션이 일어나 느린 경로로 돌아갑니다.
:::

:::qa 번들러가 하는 일을 링커와 비교해 설명해 보세요.
링커가 오브젝트 파일들의 심볼 빈칸을 채워 실행 파일 하나로 잇듯, 번들러는 import/export로 이어진 모듈들을 따라가 브라우저가 받을 파일로 잇습니다. 쓰지 않는 코드를 버리는 tree shaking은 링커의 죽은 코드 제거와, 나중에 불러올 조각으로 나누는 code splitting은 동적 링크와 닮았습니다.
:::

:::qa Windows에서 `.js` 파일을 더블클릭하면 이상한 오류 창이 뜨는 이유는?
Windows는 셔뱅을 모르고 확장자로 실행 프로그램을 정하는데, `.js`의 기본 연결이 Node가 아니라 Windows Script Host(옛 JScript 엔진)라서 Node용 코드를 이해하지 못하기 때문입니다.
:::
