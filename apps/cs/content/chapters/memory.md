6장은 세 질문을 남겼습니다. 렌더러 수십 개가 각자 메모리를 쓰는데, 서로의 메모리는 어떻게 못 보게 막을까요? 이 페이지의 4만 바이트와 `app.js`가 만든 JS 객체는 RAM의 어디에 있을까요? 탭을 많이 열면 컴퓨터는 왜 느려질까요?

세 질문의 답은 모두 [[가상 메모리]]에서 나옵니다. 이상한 사실 두 개로 시작해 봅니다. 이 페이지의 렌더러와 다른 탭의 렌더러가 같은 메모리 주소에 서로 다른 값을 저장하고 있는데도 아무 문제가 없습니다. 그리고 16GB RAM 컴퓨터에서 프로그램들이 쓰겠다고 잡아 둔 메모리를 다 더하면 수백 GB가 넘기도 합니다. 이 장은 운영체제가 RAM을 프로세스들에게 나눠 주는 방법, 그리고 그 위에서 JS 같은 언어가 메모리를 관리하는 방법을 봅니다. 브라우저 탭이 "메모리가 부족해" 다시 로드되거나, 서버 컨테이너가 `OOMKilled`로 죽는 이유도 여기서 풀립니다.

## 주소는 다 가짜입니다

프로그램이 "주소 `0x1000`에서 값을 읽어라"라고 할 때, 그 주소는 RAM 칩의 실제 위치가 아닙니다. 프로세스마다 0부터 아주 큰 수까지 자기만의 주소 범위가 있고, 이걸 [[주소 공간]]이라고 합니다. 프로그램이 쓰는 주소는 이 공간 안의 [[가상 주소]]이고, CPU가 메모리에 접근할 때마다 이 가상 주소를 RAM의 실제 위치, [[물리 주소]]로 번역합니다.

![이 페이지의 렌더러(A)와 다른 탭의 렌더러(B)가 둘 다 주소 `0x1000`을 쓰지만, 각자의 페이지 테이블이 서로 다른 RAM 위치로 번역합니다. A의 표에는 B의 프레임이 아예 없습니다](memory-translation.svg)

번역을 맡는 하드웨어가 CPU 안의 [[MMU]](메모리 관리 장치)이고, 번역표는 커널이 프로세스마다 만들어 둡니다. 이렇게 한 단계를 끼워 넣어서 얻는 것이 많습니다.

- **격리**: 프로세스 A의 번역표에는 B의 메모리가 아예 없습니다. A는 B를 가리킬 주소조차 만들 수 없습니다. 4장에서 말한 보호의 실체가 이것입니다.
- **단순함**: 모든 프로세스가 0번지부터 시작하는 넓고 깨끗한 공간을 받습니다. RAM이 조각조각 흩어져 있어도 프로그램은 연속된 메모리처럼 씁니다.
- **RAM보다 크게**: 당장 안 쓰는 부분은 디스크에 내려놓을 수 있습니다.
- **나눠 쓰기**: 여러 프로세스의 가상 주소를 같은 물리 메모리에 연결하면, 같은 라이브러리 코드를 RAM 하나로 나눠 씁니다.

64비트 CPU라도 실제로는 주소의 48비트 정도만 씁니다. 그래도 256TB입니다. 프로세스 하나가 상상할 수 있는 주소 공간은 RAM보다 훨씬 크고, 대부분은 비어 있습니다.

:::quiz isolation 악성 사이트의 렌더러가 이 페이지 렌더러의 메모리를 읽으려고 주소를 하나씩 바꿔 가며 읽어도 실패합니다. 근본적인 이유는?
- [ ] 브라우저가 메모리 주소를 암호화해 두어서
- [x] 그 렌더러의 페이지 테이블에는 다른 프로세스의 프레임이 아예 없어서, 어떤 주소를 만들어도 거기에 닿지 않아서
- [ ] 같은 주소를 두 프로세스가 동시에 읽을 수 없어서
- [ ] 커널이 읽기 시스템 콜마다 출처를 검사해서

번역표에 길이 없기 때문입니다. 프로그램이 쓰는 주소는 모두 자기 페이지 테이블을 거쳐 번역되고, 그 표에는 자기 프레임만 적혀 있습니다. 6장의 사이트 격리가 프로세스를 보안 경계로 쓸 수 있는 이유가 이것입니다.
:::

그런데 번역표를 바이트마다 둔다면 표가 메모리보다 커질 것입니다. 실제로는 어떻게 할까요?

## 페이지와 페이지 테이블

바이트 하나하나마다 번역표를 두면 표가 메모리보다 커집니다. 그래서 메모리를 일정한 크기의 덩어리로 잘라 덩어리 단위로 번역합니다. 가상 메모리 쪽 덩어리를 [[페이지]], RAM 쪽 덩어리를 [[페이지 프레임]]이라고 합니다. 크기는 보통 4KB이고, Apple Silicon 맥은 16KB입니다.

[[페이지 테이블]]은 "이 프로세스의 가상 페이지 몇 번은 RAM의 프레임 몇 번"을 적은 표입니다. 표의 한 줄에는 위치 말고도 중요한 표시들이 붙어 있습니다.

| 표시 | 뜻 | 쓰임 |
| --- | --- | --- |
| 있음(present) | 이 페이지가 지금 RAM에 있는가 | 없으면 페이지 폴트 (아래 절) |
| 쓰기 가능 | 이 페이지에 쓸 수 있는가 | 코드 영역은 쓰기 금지. copy-on-write에도 씀 |
| 실행 가능 | 이 페이지의 내용을 명령어로 실행할 수 있는가 | 데이터 영역은 실행 금지. 공격자가 넣은 데이터를 코드로 실행하지 못하게 |
| 사용자 접근 | 사용자 모드에서 접근할 수 있는가 | 커널 메모리는 사용자 모드에서 못 봄 |
| 접근함, 수정함 | 최근에 읽었는가, 썼는가 | 어떤 페이지를 디스크로 내릴지 고를 때 |

주소 공간이 크니 표를 한 장으로 두지 않고 여러 단계(x86-64는 4~5단계)의 나무로 둡니다. 쓰지 않는 넓은 구간은 표를 아예 만들지 않아 공간을 아낍니다.

## TLB: 번역 결과의 캐시

메모리를 한 번 읽을 때마다 여러 단계의 페이지 테이블을 먼저 읽어야 한다면, 메모리 접근이 몇 배로 느려집니다. 그래서 MMU는 최근 번역 결과를 기억해 둡니다. 이 작은 캐시가 [[TLB]]입니다. 지역성 덕분에 대부분의 번역은 TLB에서 끝납니다.

![가상 주소 하나가 번역되는 길. 아래 12비트(페이지 안의 위치)는 그대로 두고 위쪽 비트(페이지 번호)만 바꿉니다. TLB에 있으면 바로, 없으면 페이지 테이블을 읽어 번역하고 TLB에 기억합니다](memory-paging.svg)

:::quiz page-number 페이지 크기가 4KB(`0x1000`)일 때, 가상 주소 `0x3008`은 몇 번 페이지에 있을까요? (0번부터 셉니다)
= 3 | 3번

**3번** 페이지입니다. 4KB 페이지에서는 아래 12비트(16진수 세 자리)가 페이지 안의 위치이고 그 위가 페이지 번호이니, `0x3008`은 3번 페이지의 8번째 바이트입니다. 번역할 때 `3`만 프레임 번호로 바꾸고 `008`은 그대로 둡니다.
:::

컨텍스트 스위칭으로 프로세스가 바뀌면 번역표도 바뀌니 TLB의 내용도 쓸모가 없어집니다. 프로세스 전환이 스레드 전환보다 비싼 이유 중 하나입니다. 데이터베이스처럼 메모리를 아주 많이 쓰는 프로그램은 TLB를 아끼려고 2MB짜리 큰 페이지(huge page)를 쓰기도 합니다.

## 페이지 폴트

프로그램이 접근한 페이지가 페이지 테이블에 "있음"으로 표시되어 있지 않으면, MMU는 번역을 멈추고 CPU에 예외를 일으킵니다. 이것이 [[페이지 폴트]]입니다. 이름은 "잘못"이지만 대부분은 정상적인 일이고, 커널이 원인을 보고 처리합니다.

| 원인 | 커널이 하는 일 | 비용 |
| --- | --- | --- |
| 처음 만지는 새 메모리 | 빈 프레임을 0으로 채워 연결 | 작음 (minor) |
| 실행 파일이나 매핑된 파일의 일부 | 디스크에서 그 부분을 읽어 와 연결 | 큼 (major, 디스크 읽기) |
| 디스크로 내려 둔(스왑된) 페이지 | 디스크에서 다시 읽어 와 연결 | 큼 (major) |
| copy-on-write 페이지에 쓰기 | 페이지를 복사해 이 프로세스 전용으로 연결 | 작음 |
| 허락되지 않은 주소 | 프로세스에 오류를 알리고 보통 종료 | 프로그램이 죽음 |

![페이지 폴트 한 번의 흐름. 번역에 실패하면 CPU가 커널을 부르고, 커널이 프레임을 채워 연결한 뒤 같은 명령을 다시 실행시킵니다. 프로그램은 잠깐 멈췄다는 것도 모릅니다](memory-page-fault.svg)

마지막 경우가 그 유명한 [[세그멘테이션 폴트]]입니다. Linux와 macOS에서는 `Segmentation fault (core dumped)`, Windows에서는 "액세스 위반 0xC0000005"로 보입니다. C 프로그램이 이미 해제한 메모리나 NULL 포인터를 건드릴 때 납니다. JS는 엔진이 메모리를 대신 관리해서 이런 일이 거의 없지만, Node의 네이티브 모듈이나 브라우저 자체의 버그로는 일어날 수 있습니다.

첫째 줄이 중요한 사실을 알려 줍니다. 프로그램이 메모리 1GB를 달라고 해도, 운영체제는 주소 공간에 "여기 1GB 쓸 거임"이라고 적어만 두고 RAM은 주지 않습니다. 실제로 그 페이지에 처음 쓸 때 한 페이지씩 줍니다. 이걸 지연 할당이라고 합니다. 직접 해보기에서 Node로 확인합니다. 프로그램들이 잡아 둔 메모리의 합이 RAM보다 훨씬 커도 괜찮은 이유가 이것입니다. 5장에서 수백 MB짜리 브라우저가 1초도 안 되어 뜬 것도 같은 원리입니다. 실행 파일의 코드 페이지도 처음 실행될 때 페이지 폴트로 한 장씩 읽혀 옵니다.

:::quiz lazy-alloc `new Uint8Array(1e9)`를 만들었는데 활동 모니터의 메모리 숫자가 거의 그대로입니다. 언제 크게 늘어날까요?
- [ ] 다음 GC가 돌 때
- [ ] 1초 뒤 운영체제가 몰아서 채울 때
- [ ] 배열의 `length`를 읽을 때
- [x] 배열의 칸들에 실제로 값을 써서 각 페이지를 처음 만질 때

처음 만질 때 늘어납니다. 운영체제는 주소 공간에 자리만 적어 두고, 각 페이지에 처음 쓰는 순간의 페이지 폴트에서 프레임을 한 장씩 줍니다. `fill(1)`처럼 전체를 쓰면 그때 1GB가 실제로 RAM을 차지합니다.
:::

그럼 프로세스들이 실제로 만진 페이지를 다 더한 것이 RAM보다 커지면 어떻게 될까요? 탭을 수십 개 열었을 때 일어나는 일입니다.

## RAM이 모자라면: 스왑, 페이지 파일, 메모리 압축

프로세스들이 실제로 만진 메모리가 RAM보다 커지면, 운영체제는 한동안 안 쓴 페이지를 골라 디스크에 내려놓고 그 프레임을 다른 데 씁니다. 이걸 [[스왑]]이라고 합니다. 내려놓은 페이지를 다시 만지면 페이지 폴트가 나고 디스크에서 읽어 옵니다.

2장의 표를 떠올리면 RAM 읽기는 100ns, SSD 읽기는 수십 µs입니다. 수백 배 느립니다. 한참 안 본 탭으로 돌아갔을 때 잠깐 버벅이는 것은 그 탭의 페이지들이 디스크나 압축 영역에서 돌아오는 시간입니다. 스왑이 조금 일어나는 건 괜찮지만, 필요한 페이지를 읽어 오려고 다른 필요한 페이지를 내리고, 그걸 또 읽어 오는 일이 반복되면 컴퓨터가 거의 멈춥니다. 이 상태를 [[스래싱]]이라고 합니다. "메모리가 모자라면 컴퓨터가 버벅인다"의 정체입니다.

운영체제마다 이 상황을 버티는 방법이 다릅니다.

| | Windows | macOS | Linux |
| --- | --- | --- | --- |
| 디스크로 내리는 곳 | [[페이지 파일]] `C:\pagefile.sys` | 필요할 때 만드는 스왑 파일 (`/private/var/vm/`) | 스왑 파티션이나 스왑 파일. 서버는 없는 경우도 많음 |
| 내리기 전에 | 메모리 압축 (작업 관리자의 "압축됨") | [[메모리 압축]]을 적극적으로 씀 | 기본은 없음. zswap, zram을 켤 수 있음 |
| 상태 보기 | 작업 관리자 → 성능 → 메모리 | 활성 상태 보기 → 메모리 → "메모리 압력" 그래프 | `free -h`, `vmstat 1` |
| 끝까지 모자라면 | "메모리가 부족합니다" 경고. 페이지 파일을 늘림 | "응용 프로그램 메모리가 부족합니다" 창에서 앱 강제 종료를 권함 | [[OOM 킬러]]가 점수가 가장 높은(대개 가장 많이 쓰는) 프로세스를 SIGKILL |

메모리 압축은 잘 안 쓰는 페이지를 디스크로 내리는 대신 RAM 안에서 압축해 둡니다. 압축하고 푸는 데 CPU를 쓰지만 디스크보다는 훨씬 빠릅니다. macOS 활성 상태 보기의 "압축됨" 숫자가 이것입니다.

서버에서는 OOM 킬러를 자주 만납니다. Docker 컨테이너에 메모리 한도를 걸면, 그 컨테이너가 한도를 넘는 순간 커널이 컨테이너 안의 프로세스를 SIGKILL로 죽입니다. 이 사이트의 `docker-compose.yml`도 정적 사이트 컨테이너에 `mem_limit: 48m`을 걸어 두었습니다. 죽은 컨테이너의 종료 코드는 137입니다. 128 + 9(SIGKILL)라는 뜻이고, `docker inspect`에서 `OOMKilled: true`로 보입니다.

RAM이 꽉 찼을 때 어느 페이지를 내릴지 고르는 규칙을 [[페이지 교체 알고리즘]]이라고 합니다.

| 알고리즘 | 내리는 페이지 | 특징 |
| --- | --- | --- |
| FIFO | 가장 먼저 들어온 것 | 단순하지만 자주 쓰는 페이지도 오래됐다는 이유로 내림 |
| OPT | 앞으로 가장 오래 안 쓸 것 | 가장 좋지만 미래를 알아야 해서 비교 기준으로만 씀 |
| LRU | 가장 오래 안 쓴 것 | 최근에 쓴 것은 곧 또 쓴다는 지역성에 기댐(18장의 LRU 캐시) |
| LFU | 가장 적게 쓴 것 | 예전에 많이 쓴 페이지가 오래 남는 약점 |
| Clock | 참조 비트가 꺼진 것을 시계처럼 돌며 찾음 | LRU를 싸게 흉내 낸 것. 실제 운영체제가 쓰는 방식에 가까움 |

내려도 내려도 곧 다시 필요한 페이지들뿐이면, 컴퓨터는 디스크와 RAM 사이에서 페이지를 옮기느라 실제 일을 거의 못 합니다. 이 상태가 [[스래싱]]입니다. 프로그램을 몇 개 닫으면 갑자기 멀쩡해지는 이유입니다.

:::quiz oom-code 6장의 시그널 표를 떠올려 봅니다. 컨테이너 안의 프로세스가 SIGTERM(15)으로 끝나면 종료 코드는 얼마로 보일까요?
= 143

128 + 15 = **143**입니다. 시그널로 끝난 프로세스의 종료 코드는 128에 시그널 번호를 더해 보여 주는 관례가 있습니다. 137(128 + 9)이면 SIGKILL, 대개 OOM이나 강제 종료이고, 143이면 SIGTERM으로 정중하게 멈춘 것입니다.
:::

휴대폰은 더 엄격합니다. iOS와 Android는 스왑을 거의 쓰지 않고, 메모리가 모자라면 뒤에 있는 앱과 브라우저 탭을 바로 정리합니다. 모바일 Safari에서 다른 탭에 갔다 오면 페이지가 다시 로드되는 이유입니다.

:::quiz lru-page 페이지를 담는 칸이 3개이고, 페이지 1, 2, 3, 1 순서로 썼습니다. 이제 페이지 4가 필요할 때 LRU는 어느 페이지를 내릴까요?
= 2 | 2번

**2번**입니다. 1은 방금 다시 썼으니 가장 최근이고, 남은 2와 3 중 2가 가장 오래 쓰이지 않았습니다. FIFO였다면 가장 먼저 들어온 1을 내렸을 것입니다.
:::

## 프로세스의 주소 공간 지도

이제 두 번째 질문으로 갑니다. 이 페이지의 바이트와 JS 객체는 렌더러의 주소 공간 어디에 있을까요? 프로세스 하나의 주소 공간은 대략 이렇게 나뉩니다. 5장의 로더가 이 지도를 만듭니다.

![프로세스 하나의 주소 공간 지도. 아래쪽은 실행 파일에서 온 코드와 데이터이고, 힙은 위로, 스택은 아래로 자랍니다. 이 페이지를 띄운 렌더러라면 브라우저의 기계어는 `.text`에, 이 페이지의 HTML과 DOM, `app.js`의 객체는 힙에 있습니다](memory-address-space.svg)

이 지도를 직접 볼 수 있습니다. macOS는 `vmmap`, Linux는 `/proc/PID/maps`, Windows는 Sysinternals의 VMMap입니다.

## 스택과 힙

프로그램이 쓰는 메모리는 크게 두 가지 방식으로 관리됩니다.

- **스택**: 5장의 [[콜 스택]]입니다. 함수가 불릴 때 지역 변수 자리가 생기고 함수가 끝나면 저절로 사라집니다. 할당과 해제가 포인터 하나를 옮기는 것으로 끝나 아주 빠릅니다. 대신 크기가 작고(Linux와 macOS 메인 스레드 기본 8MB, Windows 1MB), 함수가 끝난 뒤에도 살아 있어야 하는 데이터는 둘 수 없습니다.
- **[[힙|힙 영역]]**: 크기와 수명을 미리 알 수 없는 데이터를 위한 넓은 공간입니다. C에서는 `malloc`으로 받고 `free`로 돌려줍니다. 돌려주는 걸 잊으면 새고, 돌려준 뒤에 또 쓰면 프로그램이 망가집니다. 오래 쓰다 보면 빈자리가 조각조각 흩어져서, 합치면 충분한데 연속된 큰 자리가 없는 단편화가 생깁니다.

JS에서는 이 구분을 직접 하지 않습니다. 객체, 배열, 클로저, 문자열은 엔진이 힙에 만들고, 다 쓴 것은 엔진이 알아서 치웁니다. 이 페이지에서 `app.js`가 만든 진행 기록 객체도, 브라우저가 이 HTML로 만든 DOM 노드 수천 개도 힙에 있습니다. 그 "알아서 치우는 것"이 다음 절의 가비지 컬렉션입니다.

## 가비지 컬렉션

[[가비지 컬렉션]](GC)은 프로그램이 더 이상 쓸 수 없는 메모리를 찾아 자동으로 돌려주는 기능입니다. 기준은 **도달 가능성**입니다. 전역 변수, 지금 실행 중인 함수들의 지역 변수(콜 스택) 같은 뿌리에서 참조를 따라가 닿을 수 있는 객체는 살아 있고, 닿을 수 없는 객체는 쓰레기입니다.

```js
let user = { name: "a", avatar: new ArrayBuffer(1e6) };
user = null; // 이제 { name, avatar }에 닿을 길이 없으니 다음 GC 때 치워집니다
```

![이 페이지의 힙에서 GC가 보는 것. `app.js`의 진행 기록 객체는 document에 붙은 리스너가 클로저로 붙잡고 있어 뿌리에서 닿으니 살아남고, 버린 객체는 서로 참조하고 있어도 닿지 않으니 치워집니다](memory-gc.svg)

가장 기본적인 방법은 표시하고 쓸기(mark-and-sweep)입니다. 뿌리에서 닿는 객체에 모두 표시하고, 표시가 없는 객체를 치웁니다. 그런데 큰 힙 전체를 훑으려면 오래 걸리고, 그동안 JS 실행을 멈춰야 합니다. 화면이 순간 끊기는 GC 멈춤입니다.

V8은 "대부분의 객체는 금방 죽는다"는 관찰을 이용한 [[세대별 GC]]를 씁니다.

- **새 세대(young generation)**: 새로 만든 객체가 여기 들어갑니다. 작고 자주 치웁니다. 살아남은 객체만 다른 칸으로 복사하고 나머지는 통째로 버리니 빠릅니다. 렌더링 함수 안에서 만든 임시 객체는 대부분 여기서 바로 사라집니다.
- **옛 세대(old generation)**: 두 번 살아남은 객체가 옮겨 갑니다. 크고 가끔 치웁니다. 멈춤을 줄이려고 일을 잘게 나눠 JS 실행 사이사이에 하거나(점진적), 다른 스레드에서 함께 합니다(동시).

모든 언어가 이 방식은 아닙니다. Swift와 Objective-C는 참조하는 곳의 수를 세다가 0이 되면 바로 치우는 참조 계수(ARC)를 쓰고, Rust는 컴파일러가 수명을 따져 GC 없이 해제 시점을 정합니다.

:::quiz reachable 이 페이지의 `app.js`는 진행 기록을 담은 `done` 객체를 전역 변수에 두지 않았는데도 GC가 치우지 않습니다. 이유는?
- [ ] 한 번 만든 객체는 페이지를 닫을 때까지 GC가 건드리지 않아서
- [ ] `localStorage`에 저장된 값은 힙에 고정되어서
- [x] document에 등록된 이벤트 리스너가 클로저로 `done`을 참조해 뿌리에서 닿기 때문에
- [ ] 객체가 작아서 GC가 무시해서

리스너를 거쳐 닿기 때문입니다. `document`는 뿌리이고, 거기 붙은 리스너 함수는 자기가 만들어진 스코프의 `done`을 클로저로 붙잡고 있습니다. 필요해서 붙잡은 것이니 정상이고, 같은 구조로 필요 없어진 것을 붙잡으면 다음 절의 누수가 됩니다.
:::

## 메모리 누수: GC가 있어도 새는 이유

GC는 "닿을 수 없는" 것만 치웁니다. 더는 안 쓰지만 어딘가에서 여전히 참조하고 있으면 치우지 못합니다. 이게 JS의 [[메모리 누수]]입니다. 자주 나오는 모양은 정해져 있습니다.

- **지우지 않은 이벤트 리스너와 타이머**: 컴포넌트가 사라져도 `window.addEventListener`나 `setInterval`의 콜백이 그 컴포넌트의 상태를 클로저로 붙잡고 있습니다. React `useEffect`의 정리 함수(cleanup)를 빠뜨리면 생깁니다.
- **끝없이 자라는 캐시**: 전역 `Map`이나 객체에 계속 넣기만 하고 빼지 않습니다. 서버에서 요청마다 무언가를 쌓으면 며칠 뒤 컨테이너가 OOM으로 죽습니다.
- **떨어져 나간 DOM**: 화면에서 지운 DOM 요소를 JS 변수나 배열이 아직 참조하고 있습니다. DevTools 힙 스냅샷에서 "Detached"로 보입니다.
- **큰 객체를 붙잡은 클로저**: 작은 함수 하나가 큰 배열이 있는 스코프를 참조해서 배열 전체가 살아남습니다.

키가 되는 객체가 사라지면 항목도 같이 사라져도 되는 캐시라면 `WeakMap`을 씁니다. `WeakMap`은 키를 [[약한 참조]]로 들고 있어서, 다른 곳에서 그 키 객체를 참조하지 않으면 GC가 치울 수 있습니다.

:::quiz leak-effect React 컴포넌트가 `useEffect`에서 `window.addEventListener("resize", onResize)`만 하고 정리 함수가 없습니다. 이 컴포넌트를 열고 닫기를 반복하면?
- [ ] 컴포넌트가 사라지면 리스너도 GC가 함께 치운다
- [x] 닫힌 컴포넌트의 `onResize`와 그 클로저가 window에 붙은 채 남아 계속 쌓인다
- [ ] React가 경고를 띄우고 리스너를 자동으로 지운다
- [ ] 같은 이름의 리스너라 하나로 덮어써진다

계속 쌓입니다. `window`는 뿌리라서 거기 붙은 리스너는 언제나 닿을 수 있고, 리스너가 클로저로 붙잡은 컴포넌트의 상태도 함께 살아남습니다. 열 때마다 새 함수가 만들어지니 덮어써지지도 않습니다. 정리 함수에서 `removeEventListener`를 불러야 합니다.
:::

## 메모리를 나눠 쓰는 방법

가상 메모리 덕분에 여러 프로세스가 같은 물리 메모리를 안전하게 나눠 쓸 수 있습니다.

- **공유 라이브러리**: 프로세스 100개가 같은 libc를 쓰면, 그 코드 페이지는 RAM에 한 벌만 있고 100개의 페이지 테이블이 같은 프레임을 가리킵니다. 코드는 읽기 전용이니 안전합니다. 렌더러가 수십 개여도 브라우저의 기계어가 RAM에 수십 벌 올라가지 않는 이유입니다.
- **[[copy-on-write]]**: 6장의 `fork`는 자식에게 부모 메모리를 복사해 주는 척만 하고, 둘의 페이지 테이블이 같은 프레임을 "읽기 전용"으로 가리키게 합니다. 누군가 쓰려는 순간 페이지 폴트가 나고, 그때 그 페이지만 복사합니다. 쓰지 않는 페이지는 끝까지 복사하지 않습니다.
- **[[메모리 맵 파일]]**(`mmap`): 파일을 주소 공간에 연결해, 파일을 읽고 쓰는 대신 메모리를 읽고 쓰듯 다룹니다. 실제 디스크 읽기는 페이지 폴트가 날 때 합니다. 5장의 로더가 실행 파일을 이렇게 올리고, SQLite 같은 데이터베이스도 이렇게 파일을 다룹니다.

메모리를 나누다 보면 쓰지 못하는 틈이 생깁니다. 이걸 단편화라고 하고 두 가지입니다. 페이지처럼 고정 크기로 나눠 주면 마지막 페이지의 남는 부분이 버려지는데, 이걸 [[내부 단편화]]라고 합니다. 크기가 제각각인 덩어리로 나눠 주고 돌려받기를 반복하면, 빈 공간의 합은 충분한데 한 덩어리로 이어진 곳이 없어 큰 요청을 못 받는데, 이걸 [[외부 단편화]]라고 합니다. 페이징은 외부 단편화를 없애는 대신 약간의 내부 단편화를 받아들인 방식이고, 크기가 다른 덩어리로 나누는 세그멘테이션은 반대입니다.

## "메모리 사용량"은 무엇을 세는가

작업 관리자와 활성 상태 보기가 보여 주는 메모리 숫자는 생각보다 여러 가지입니다.

| 숫자 | 뜻 | 주의 |
| --- | --- | --- |
| 가상 크기 (VSZ) | 주소 공간에 잡아 둔 전체 크기 | 아주 큼. 실제 RAM 사용과 거의 상관없음 |
| [[RSS]] (상주 크기) | 지금 RAM에 올라와 있는 페이지 | 공유 라이브러리를 프로세스마다 중복으로 셈 |
| 사설 메모리 (private) | 이 프로세스만 쓰는 RAM | "이 프로세스를 끄면 돌아올 메모리"에 가장 가까움 |
| 메모리 풋프린트 | macOS가 보여 주는 값. 사설 메모리 + 압축된 것 + 스왑된 것 | 활성 상태 보기의 "메모리" 칸 |
| 작업 집합 (working set) | Windows의 RSS. 작업 관리자 "메모리" 칸은 사설 작업 집합 | |

Linux 서버에서 `free -h`를 치면 `used`보다 `buff/cache`가 훨씬 커서 메모리가 꽉 찬 것처럼 보이곤 합니다. 이건 8장의 [[페이지 캐시]]입니다. 디스크에서 읽은 파일 내용을 빈 RAM에 남겨 두었다가 필요하면 바로 내주는 것이라 걱정할 일이 아닙니다. 봐야 할 숫자는 `available`입니다. "빈 RAM은 낭비된 RAM"이라는 말이 운영체제의 기본 태도입니다.

## 다시 장면으로: 이 페이지는 메모리 어디에

6장 끝의 세 질문에 답할 수 있습니다. 렌더러끼리 서로의 메모리를 못 보는 이유는 각자의 페이지 테이블에 남의 프레임이 없기 때문입니다. 이 페이지의 바이트와 DOM, `app.js`의 객체는 이 페이지 렌더러의 주소 공간 중 힙에 있고, 실제로는 그 페이지들이 연결된 RAM 프레임 어딘가에 흩어져 있습니다. 리스너가 붙잡고 있는 진행 기록은 GC가 치우지 않습니다. 탭을 많이 열면 실제로 만진 페이지의 합이 RAM을 넘어 압축과 스왑이 시작되고, 심하면 스래싱으로 버벅이거나 오래된 탭이 정리됩니다.

이제 메모리 바깥으로 나갈 차례입니다. "학습 완료"를 누르면 이 힙에 있던 진행 기록이 SSD에 쓰여야 내일도 남습니다. 거꾸로 이 페이지의 4만 바이트는 네트워크 카드에서 이 메모리로 들어왔습니다. 메모리와 바깥 장치 사이를 오가는 일, 8장의 입출력입니다.

| 프로세스 메모리 보기 | 작업 관리자 세부 정보 | 활성 상태 보기, `footprint PID` | `ps -o rss`, `smem`, `/proc/PID/status` |

## 프론트엔드와 이어지는 곳

- DevTools의 Memory 패널에서 힙 스냅샷을 두 번 찍어 비교하면, 그 사이에 늘어나고 치워지지 않은 객체가 누수 후보입니다. "Detached"로 검색하면 떨어져 나간 DOM이 나옵니다.
- `useEffect`에서 등록한 리스너, 구독, 타이머는 정리 함수에서 꼭 해제합니다.
- 큰 이미지는 압축 파일 크기가 아니라 펼친 크기(가로 × 세로 × 4바이트)만큼 메모리를 씁니다. 모바일에서 탭이 다시 로드되는 이유가 되곤 합니다.
- Node 서버는 V8 힙 한도를 `--max-old-space-size`로 정할 수 있습니다. 컨테이너 메모리 한도보다 조금 작게 잡아야 커널의 OOM 킬러보다 V8이 먼저 GC를 열심히 합니다.
- 서버 컨테이너가 종료 코드 137로 죽었다면 OOM을 먼저 의심합니다.

## 용어 정리

:::terms
- 가상 메모리 (virtual memory) — 프로세스마다 독립된 넓은 주소 공간을 주고, 이를 RAM의 실제 위치로 번역하는 구조. 격리, RAM보다 큰 사용, 공유를 가능하게 합니다.
- 주소 공간 (address space) — 한 프로세스가 쓸 수 있는 가상 주소의 범위와 그 안의 배치입니다.
- 가상 주소 (virtual address) — 프로그램이 쓰는 주소. 실제 RAM 위치가 아니라 번역을 거칩니다.
- 물리 주소 (physical address) — RAM 칩 안의 실제 위치입니다.
- MMU (Memory Management Unit) — 메모리에 접근할 때마다 가상 주소를 물리 주소로 번역하는 CPU 안의 하드웨어입니다.
- 페이지 (page) — 가상 메모리를 나누는 고정 크기의 덩어리. 보통 4KB, Apple Silicon은 16KB입니다.
- 페이지 프레임 (page frame) — 페이지가 들어가는 RAM 쪽의 같은 크기 칸입니다.
- 페이지 테이블 (page table) — 가상 페이지가 어느 프레임에 있는지와 읽기, 쓰기, 실행 권한을 적은 프로세스별 표입니다.
- TLB (Translation Lookaside Buffer) — 최근의 가상-물리 주소 번역 결과를 담아 두는 MMU 안의 작은 캐시입니다.
- 페이지 폴트 (page fault) — 접근한 페이지가 RAM에 연결되어 있지 않아 CPU가 커널을 부르는 예외. 대부분 커널이 페이지를 채워 정상 처리합니다.
- 세그멘테이션 폴트 (segmentation fault) — 허락되지 않은 메모리에 접근해 운영체제가 프로세스를 멈추는 오류. Windows에서는 액세스 위반입니다.
- 스왑 (swap) — RAM이 모자랄 때 잘 안 쓰는 페이지를 디스크에 내려놓고 필요할 때 다시 읽어 오는 것입니다.
- 페이지 파일 (page file) — Windows가 스왑에 쓰는 디스크 파일 `pagefile.sys`입니다.
- 메모리 압축 (memory compression) — 잘 안 쓰는 페이지를 디스크로 내리는 대신 RAM 안에서 압축해 두는 기법. macOS와 Windows가 씁니다.
- 스래싱 (thrashing) — 페이지를 내리고 다시 읽는 일이 끝없이 반복되어 실제 일은 거의 못 하는 상태입니다.
- OOM 킬러 (OOM killer) — Linux에서 메모리가 바닥나면 프로세스 하나를 골라 SIGKILL로 죽여 메모리를 되찾는 커널 기능입니다. 컨테이너 메모리 한도를 넘었을 때도 동작합니다.
- 힙 영역 (heap) — 크기와 수명이 정해지지 않은 데이터를 동적으로 할당하는 메모리 영역. JS 객체가 여기 만들어집니다.
- 가비지 컬렉션 (garbage collection) — 프로그램이 더는 닿을 수 없는 메모리를 찾아 자동으로 해제하는 기능입니다.
- 세대별 GC (generational GC) — 객체를 새 세대와 옛 세대로 나눠, 금방 죽는 새 객체는 자주 빠르게, 오래 산 객체는 가끔 치우는 GC 방식. V8이 씁니다.
- 메모리 누수 (memory leak) — 더는 쓰지 않는 메모리가 해제되지 않고 쌓이는 것. GC 언어에서는 쓰지 않는데도 참조가 남아 있어서 생깁니다.
- 약한 참조 (weak reference) — GC가 객체를 치우는 것을 막지 않는 참조. JS의 `WeakMap`, `WeakRef`가 씁니다.
- copy-on-write — 복사를 미뤄 두고 같은 메모리를 공유하다가, 누군가 쓰려고 할 때 그 부분만 복사하는 기법. `fork`가 씁니다.
- 메모리 맵 파일 (memory-mapped file) — 파일을 주소 공간에 연결해 메모리처럼 읽고 쓰게 하는 것. `mmap` 시스템 콜로 만듭니다.
- RSS (Resident Set Size) — 프로세스의 페이지 중 지금 RAM에 올라와 있는 양. 공유 메모리도 포함합니다.
- 페이지 교체 알고리즘 (page replacement algorithm) — RAM이 꽉 찼을 때 어느 페이지를 디스크로 내릴지 고르는 규칙. FIFO, LRU, LFU, Clock 등이 있습니다.
- 내부 단편화 (internal fragmentation) — 고정 크기로 나눠 준 칸 안에서 쓰지 않고 남는 공간입니다.
- 외부 단편화 (external fragmentation) — 빈 공간의 합은 충분하지만 여기저기 흩어져 있어 큰 덩어리를 줄 수 없는 상태입니다.
:::

## 직접 해보기

:::practice lazy 할당과 실제 사용의 차이 보기
Node로 1GB를 할당한 직후와, 모든 페이지에 한 바이트씩 쓴 뒤의 RSS를 비교합니다. 할당만으로는 RSS가 거의 늘지 않아야 합니다.

```js lazy.js
const mb = () => Math.round(process.memoryUsage().rss / 1e6) + "MB";
console.log("시작", mb());
const buf = new Uint8Array(1e9);                          // 1GB를 잡기만 함
console.log("할당 직후", mb());
for (let i = 0; i < buf.length; i += 4096) buf[i] = 1;   // 4KB마다 한 바이트씩 만짐
console.log("모든 페이지를 만진 뒤", mb());
```

```sh macOS
/usr/bin/time -l node lazy.js 2>&1 | grep -E "MB|page"   # page reclaims(minor), page faults(major)
```

```sh Linux
/usr/bin/time -v node lazy.js 2>&1 | grep -E "MB|page faults"
```
:::

:::practice map 주소 공간 지도 열어 보기
실행 중인 프로세스의 주소 공간에서 코드, 힙, 스택, 동적 라이브러리 영역을 찾아봅니다.

```sh macOS
vmmap $$ | head -60        # 지금 셸 프로세스
vmmap --summary $$
```

```sh Linux

```

```text Windows
Sysinternals의 VMMap을 받아 실행하고 아무 프로세스를 골라 Image, Heap, Stack, Private Data 영역을 봅니다.
```
:::

:::practice pressure 내 컴퓨터의 메모리 압력 읽기
지금 메모리가 얼마나 여유 있는지, 압축이나 스왑이 일어나고 있는지 봅니다. 브라우저 탭을 많이 연 뒤 다시 봅니다.


```powershell Windows (PowerShell)

# 작업 관리자 → 성능 → 메모리에서 "압축됨"과 "커밋됨"을 봅니다
```

:::practice heap DevTools로 메모리 누수 잡기
아무 페이지의 콘솔에서 떨어져 나간 DOM을 일부러 만들고, Memory 패널의 힙 스냅샷에서 찾아봅니다.

```js 브라우저 콘솔
window.leak = [];
for (let i = 0; i < 1000; i++) {
  const div = document.createElement("div");
  div.textContent = "x".repeat(1000);
  document.body.append(div);
  div.remove();          // 화면에서는 지웠지만
  window.leak.push(div); // 배열이 아직 잡고 있음
}
// Memory 패널 → Heap snapshot → 필터에 "Detached" 입력
// window.leak = null 후 다시 스냅샷을 찍어 사라지는지 봅니다
```
:::

:::practice oom 컨테이너를 OOM으로 죽여 보기
Docker가 있다면 메모리 64MB 한도의 컨테이너에서 메모리를 계속 잡아 OOM 킬러를 만나 봅니다. 종료 코드 137과 `OOMKilled`를 확인합니다.

```sh 터미널 (Docker)
docker run --name oomtest -m 64m node:24-alpine \
  node -e "const a = []; setInterval(() => { a.push(Buffer.alloc(8e6, 1)); console.log(a.length * 8, 'MB') }, 100)"
echo "종료 코드: $?"
docker inspect oomtest --format '{{.State.OOMKilled}} {{.State.ExitCode}}'
docker rm oomtest
```
:::

## 장 전체 문제

:::quiz tab-reload 휴대폰 Safari에서 다른 앱을 쓰다 돌아왔더니 보던 탭이 처음부터 다시 로드됩니다. 가장 가까운 설명은?
- [x] 메모리가 모자라 운영체제가 뒤에 있던 탭의 메모리를 정리했고, 브라우저가 다시 받아 그렸다
- [ ] 탭의 페이지가 스왑에서 돌아오는 중이라 로딩 표시가 보인다
- [ ] 서버가 세션을 끊어 브라우저가 새로 요청했다
- [ ] GC가 페이지 전체를 쓰레기로 판단해 지웠다

메모리를 되찾으려고 탭을 정리했기 때문입니다. 휴대폰 운영체제는 스왑을 거의 쓰지 않고, 모자라면 뒤에 있는 앱과 탭을 바로 정리합니다. GC는 닿을 수 없는 객체만 치우지 페이지 전체를 지우지 않습니다.
:::

:::quiz rss-shared 렌더러 20개의 RSS를 모두 더했더니 실제 RAM 크기보다 큽니다. 어떻게 된 걸까요?
- [ ] 운영체제가 숫자를 잘못 셌다
- [ ] 렌더러들이 이미 스왑을 써서 RAM보다 커졌다
- [ ] RSS는 주소 공간에 잡아만 둔 크기까지 센다
- [x] 여러 렌더러가 함께 쓰는 공유 라이브러리와 브라우저 코드 페이지를 각자의 RSS에 중복으로 세어서

중복으로 세어서입니다. RSS는 "지금 이 프로세스에 연결된 RAM 페이지"를 세는데, 공유된 코드 페이지는 RAM에 한 벌뿐이어도 그 페이지를 쓰는 모든 프로세스의 RSS에 들어갑니다. "끄면 돌아올 메모리"를 보려면 사설 메모리를 봅니다.
:::

## 스스로 점검

:::qa 두 프로세스가 같은 가상 주소에 다른 값을 가질 수 있는 이유는?
프로세스마다 페이지 테이블이 따로 있어서, 같은 가상 주소라도 각자의 표에 따라 서로 다른 물리 프레임으로 번역되기 때문입니다.
:::

:::qa `new Uint8Array(1e9)`를 했는데 메모리 사용량이 1GB 늘지 않습니다. 왜인가요? 언제 늘어나나요?
운영체제는 주소 공간에 영역만 잡아 두고 실제 RAM은 주지 않습니다(지연 할당). 각 페이지에 처음 접근할 때 페이지 폴트가 나고 그때 0으로 채운 프레임을 하나씩 연결하므로, 만진 만큼만 RSS가 늘어납니다.
:::

:::qa 페이지 폴트가 났다고 항상 문제는 아닌 이유는? 문제가 되는 경우는?
대부분은 처음 쓰는 메모리 채우기, 실행 파일을 필요할 때 읽기, copy-on-write처럼 정상적인 처리입니다. 디스크에서 읽어야 하는 major 폴트가 잦거나(스왑, 스래싱), 허락되지 않은 주소 접근(세그멘테이션 폴트)이면 문제입니다.
:::

:::qa 서버 컨테이너가 종료 코드 137로 자꾸 재시작됩니다. 무엇을 의심하고 어떻게 확인하나요?
137은 128 + 9, 즉 SIGKILL로 죽었다는 뜻이고 메모리 한도를 넘어 OOM 킬러에 죽은 경우가 가장 흔합니다. `docker inspect`의 `OOMKilled`, `dmesg`의 OOM 기록을 보고, 메모리 누수인지 한도가 너무 작은지 따집니다.
:::

:::qa GC가 있는 JS에서 메모리 누수가 생기는 대표적인 경우 세 가지는?
정리하지 않은 이벤트 리스너나 타이머가 클로저로 상태를 붙잡는 경우, 계속 커지기만 하는 전역 캐시(Map), 화면에서 지웠지만 변수가 참조하고 있는 DOM 노드가 있습니다. 모두 "안 쓰지만 닿을 수 있어서" GC가 치우지 못합니다.
:::

:::qa Linux 서버에서 `free`를 보니 `used`는 작은데 `buff/cache`가 메모리 대부분을 차지합니다. 문제인가요?
아닙니다. 디스크에서 읽은 파일 내용을 빈 RAM에 페이지 캐시로 남겨 둔 것이고, 프로세스가 메모리를 필요로 하면 즉시 내줍니다. 여유는 `available`로 판단합니다.
:::
