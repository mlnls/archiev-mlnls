9장은 전파 속에서 공유기가 자기에게 온 프레임을 어떻게 알아보느냐는 질문으로 끝났습니다. 노트북이 `GET /`를 담은 프레임을 내보내면 전파는 방 안의 모든 기기에 닿습니다. 그다음은 이렇게 됩니다.

![노트북이 보낸 프레임은 공중에서 모두에게 닿지만, 프레임 맨 앞의 받는 쪽 MAC 주소를 보고 공유기만 받습니다. 나머지는 버리고, 다른 네트워크의 기기는 암호를 몰라 읽지도 못합니다](link-scene.svg)

이 장은 9장 계층 표의 맨 아래 두 층, 물리 계층과 데이터 링크 계층을 봅니다. 두 층의 일은 "같은 네트워크 안의 바로 옆 기기에게 프레임 하나를 확실히 건네는 것"입니다. 지구 반대편까지 가는 길은 11장의 IP가 맡지만, 그 긴 여행도 결국 "바로 옆 기기에게 건네기"를 수십 번 반복하는 것입니다. 노트북에서 공유기까지가 그 첫 번째입니다.

## 물리 계층: 비트를 신호로

[[물리 계층]]은 0과 1을 실제 신호로 바꿔 매체에 싣습니다. 매체마다 방법이 다릅니다.

| 매체 | 신호 | 쓰는 곳 | 특징 |
| --- | --- | --- | --- |
| 구리선 (UTP 랜선) | 전압의 변화 | 집과 사무실의 유선 랜 | 100m까지. Cat5e는 1Gbps, Cat6A는 10Gbps |
| 광섬유 | 빛의 깜빡임 | 통신사망, 데이터센터, 해저 케이블, 집까지 들어오는 인터넷 | 수십 km를 가도 약해지지 않음. 전기 잡음에 강함 |
| 전파 | 전파의 세기, 위상 변화 | Wi-Fi, LTE, 5G, 블루투스 | 선이 필요 없지만 잡음, 간섭, 거리 영향을 많이 받음 |

랜선 안에는 꼬인 구리선이 네 쌍 들어 있습니다. 두 선을 꼬아 두면 바깥 전기 잡음이 두 선에 똑같이 들어와 서로 상쇄됩니다. 랜선의 등급(Cat5e, Cat6)은 이 꼬임과 차폐를 얼마나 잘했는지, 그래서 얼마나 빠른 신호를 버티는지를 뜻합니다. "기가 인터넷인데 속도가 100Mbps에서 멈춘다"면 오래된 랜선이나 한 쌍이 끊어진 선을 의심합니다.

## 데이터 링크 계층이 푸는 문제

물리 계층은 비트를 흘려보낼 뿐입니다. [[데이터 링크 계층]]은 그 위에서 이런 문제를 풉니다.

- **틀 짓기**: 비트의 흐름에서 한 덩어리의 시작과 끝을 정합니다. 이 덩어리가 [[프레임]]입니다.
- **주소**: 같은 네트워크의 여러 기기 중 누구에게 가는지 적습니다. [[MAC 주소]]입니다.
- **오류 찾기**: 도중에 비트가 뒤집혔는지 확인합니다.
- **말할 차례**: 여러 기기가 같은 매체를 쓸 때 동시에 말하지 않게 합니다.

유선에서는 [[이더넷]], 무선에서는 [[Wi-Fi]]가 이 층의 대표 프로토콜입니다.

## 이더넷과 프레임

이더넷 프레임은 이렇게 생겼습니다.

| 칸 | 크기 | 내용 |
| --- | --- | --- |
| 받는 쪽 MAC | 6바이트 | 이 프레임을 받을 기기 |
| 보내는 쪽 MAC | 6바이트 | 이 프레임을 보낸 기기 |
| 타입 | 2바이트 | 페이로드가 무엇인지. `0x0800` IPv4, `0x86DD` IPv6, `0x0806` ARP |
| 페이로드 | 46~1500바이트 | 대개 IP 패킷 |
| FCS | 4바이트 | 오류 검사값 (CRC) |

페이로드의 최대 크기 1500바이트를 [[MTU]](최대 전송 단위)라고 합니다. IP 패킷은 이보다 클 수 없고, 더 큰 데이터는 여러 패킷으로 나뉩니다. 9장의 그림에서 HTTP 데이터가 한 번에 약 1460바이트씩 실리는 이유입니다(1500 − IP 헤더 20 − TCP 헤더 20).

받는 쪽 네트워크 카드는 프레임 전체로 CRC를 다시 계산해 FCS와 비교합니다. 다르면 비트가 망가진 것이니 그 프레임을 조용히 버립니다. 유선 이더넷은 버린 프레임을 다시 보내 달라고 하지 않습니다. 사라진 데이터를 다시 받아 오는 건 12장의 TCP가 할 일입니다. 층마다 맡은 일이 나뉘어 있다는 게 이런 뜻입니다.

![이더넷 프레임의 칸. 앞 14바이트가 헤더이고, MTU 1500바이트는 페이로드 칸의 최대 크기입니다. 끝의 FCS로 망가진 프레임을 걸러 냅니다](link-frame.svg)

:::quiz frame-overhead 이더넷 프레임에서 페이로드를 뺀 나머지 칸(MAC 주소 둘, 타입, FCS)은 모두 몇 바이트일까요?
= 18 | 18바이트 | 18B

6 + 6 + 2 + 4 = **18바이트**입니다. 그래서 페이로드를 MTU만큼 1500바이트 채운 프레임은 1518바이트가 됩니다. MTU는 이 18바이트를 뺀 페이로드 칸만 가리킵니다.
:::

## MAC 주소

[[MAC 주소]]는 네트워크 카드마다 공장에서 붙여 나오는 48비트 주소입니다. `3c:22:fb:a1:b2:c3`처럼 16진수 여섯 바이트로 적습니다. 앞 세 바이트는 제조사 번호(OUI)라서, MAC 주소만 보고 "Apple 기기", "Samsung 기기"를 알아낼 수 있습니다.

MAC 주소에 관해 꼭 알아 둘 것들입니다.

- **같은 네트워크 안에서만 쓰입니다.** 라우터를 넘어가지 않습니다. 해외 서버는 내 MAC 주소를 모릅니다. 서버가 보는 건 IP 주소입니다.
- **특별한 주소** `ff:ff:ff:ff:ff:ff`는 [[브로드캐스트]]입니다. 이 주소로 보낸 프레임은 같은 네트워크의 모든 기기가 받습니다.
- **바꿀 수 있습니다.** 공장 값이 있지만 운영체제가 다른 값으로 바꿔 쓸 수 있습니다.

요즘 운영체제와 휴대폰은 Wi-Fi에 붙을 때 네트워크마다 다른 가짜 MAC 주소를 씁니다. 카페와 쇼핑몰의 Wi-Fi가 MAC 주소로 사람의 동선을 추적하지 못하게 하려는 것입니다. 이걸 [[MAC 주소 무작위화]]라고 합니다. iPhone의 "비공개 Wi-Fi 주소", Windows의 "임의 하드웨어 주소", macOS의 "비공개 Wi-Fi 주소"가 이것입니다. 공유기에서 "MAC 주소로 기기 고정"을 했는데 휴대폰이 자꾸 다른 기기로 잡힌다면 이 기능 때문입니다.

## 허브에서 스위치로

옛날 [[허브]]는 한 포트로 들어온 신호를 나머지 모든 포트로 복사했습니다. 모두가 모든 프레임을 받고, 자기 MAC 주소가 아니면 버렸습니다. 두 기기가 동시에 보내면 신호가 섞여 충돌이 나서 둘 다 잠시 기다렸다 다시 보냈습니다. 기기가 많아질수록 느려졌습니다.

![A가 C에게 보낸 프레임을 허브는 모든 포트로 복사하고, 스위치는 C의 포트로만 보냅니다](link-hub-switch.svg)

[[스위치]]는 더 똑똑합니다. 각 포트에 어떤 MAC 주소가 붙어 있는지 배워서 표로 기억하고, 프레임을 받는 기기의 포트로만 보냅니다. 이 표를 [[MAC 주소 테이블]]이라고 합니다. 배우는 방법은 단순합니다.

1. 프레임이 들어오면 **보내는 쪽** MAC 주소를 보고 "이 주소는 이 포트에 있구나"라고 표에 적습니다.
2. **받는 쪽** MAC 주소를 표에서 찾습니다. 있으면 그 포트로만 보냅니다.
3. 표에 없거나 브로드캐스트면 들어온 포트를 뺀 모든 포트로 보냅니다(플러딩). 답이 돌아오면 1번 규칙으로 그 주소도 배웁니다.

![스위치가 표를 채워 가는 순서. 프레임이 들어올 때마다 **보내는 쪽** MAC과 들어온 포트를 적고, 받는 쪽이 표에 없을 때만 모든 포트로 보냅니다](link-switch-learning.svg)

요즘 스위치는 포트마다 보내기와 받기를 따로 하는 전이중 방식이라 충돌 자체가 없습니다. 집 공유기 뒤의 랜 포트 네 개가 바로 작은 스위치입니다.

:::quiz switch-learn 스위치가 MAC 주소 테이블에 "이 주소는 이 포트에 있다"고 적을 때 쓰는 정보는?
- [ ] 들어온 프레임의 받는 쪽 MAC 주소와 내보낼 포트
- [ ] 프레임 안 IP 헤더의 보내는 IP 주소와 들어온 포트
- [x] 들어온 프레임의 보내는 쪽 MAC 주소와 들어온 포트
- [ ] 공유기가 DHCP로 나눠 준 주소 목록

보내는 쪽 MAC 주소와 그 프레임이 들어온 포트를 짝지어 적습니다. 그 주소의 기기가 그 포트 너머에 있다는 확실한 증거이기 때문입니다. 받는 쪽 MAC은 표에서 **찾는** 데 쓰고, 스위치는 2층 장비라 IP 헤더를 보지 않습니다.
:::

## 브로드캐스트와 브로드캐스트 도메인

브로드캐스트 프레임은 스위치를 지나 같은 네트워크의 모든 기기에 닿습니다. 하지만 라우터는 브로드캐스트를 넘기지 않습니다. 그래서 브로드캐스트가 닿는 범위가 곧 "같은 네트워크"의 경계가 되고, 이 범위를 [[브로드캐스트 도메인]]이라고 부릅니다. 아래에서 볼 ARP와 11장의 DHCP가 브로드캐스트로 동작하니, 이 둘은 같은 네트워크 안에서만 쓰입니다.

![브로드캐스트 프레임은 스위치를 지나 같은 도메인의 모든 기기에 닿지만, 라우터에서 멈춥니다](link-broadcast-domain.svg)

기기가 수천 대인 하나의 큰 네트워크를 만들면 브로드캐스트가 모든 기기를 계속 깨워 느려집니다. 그래서 회사와 데이터센터는 네트워크를 작게 나눕니다.

## Wi-Fi

[[Wi-Fi]]는 전파로 프레임을 주고받는 데이터 링크 계층입니다. 기기들은 [[액세스 포인트]](AP)에 붙고, AP가 유선 네트워크로 이어 줍니다. AP가 알리는 네트워크 이름이 [[SSID]]입니다.

| 이름 | 표준 | 주파수 | 특징 |
| --- | --- | --- | --- |
| Wi-Fi 4 | 802.11n | 2.4GHz, 5GHz | 오래된 기기 |
| Wi-Fi 5 | 802.11ac | 5GHz | 아직 흔함 |
| Wi-Fi 6 / 6E | 802.11ax | 2.4, 5GHz / 6E는 6GHz 추가 | 기기가 많은 곳에서 효율이 좋음 |
| Wi-Fi 7 | 802.11be | 2.4, 5, 6GHz | 여러 대역을 동시에 씀 |

주파수 대역마다 성격이 다릅니다. 2.4GHz는 벽을 잘 통과해 멀리 가지만, 겹치지 않는 채널이 셋(1, 6, 11번)뿐이고 전자레인지와 블루투스와도 겹쳐 붐빕니다. 5GHz와 6GHz는 빠르고 채널이 많지만 벽에 약합니다. 공유기 Wi-Fi 이름이 `집-2G`, `집-5G` 두 개로 보이는 이유입니다.

![2.4GHz 대역의 채널은 5MHz 간격인데 폭이 약 20MHz라서 서로 겹칩니다. 겹치지 않게 고를 수 있는 것은 1, 6, 11번뿐입니다](link-wifi-channels.svg)

Wi-Fi는 유선과 근본적으로 다른 점이 있습니다.

- **매체를 모두가 나눠 씁니다.** 같은 채널의 기기들은 한 번에 하나만 말할 수 있습니다. 그래서 말하기 전에 조용한지 듣고, 조금 기다렸다 보냅니다(CSMA/CA). 기기가 많고 이웃집 AP가 같은 채널을 쓰면 서로 기다리느라 느려집니다.
- **프레임마다 받았다는 답(ACK)을 받습니다.** 전파는 잘 망가지니, 유선과 달리 데이터 링크 계층에서 바로 다시 보냅니다. 이 재전송 때문에 Wi-Fi의 지연 시간은 들쭉날쭉합니다(지터).
- **공중으로 퍼집니다.** 누구나 전파를 받을 수 있으니 WPA2, WPA3로 기기와 AP 사이의 구간을 암호화합니다. 이 암호화는 AP까지만입니다. AP 너머의 인터넷 구간을 보호하는 건 14장의 HTTPS입니다.

화상 회의나 게임에서 유선이 Wi-Fi보다 안정적인 이유가 이 세 가지입니다.

:::quiz wifi-retry 카페 Wi-Fi에서 전파 잡음으로 프레임 하나가 망가졌습니다. 이 프레임을 가장 먼저 다시 보내는 쪽은?
- [ ] 받는 쪽 TCP. Wi-Fi는 망가진 프레임을 버리기만 한다
- [x] 보내는 쪽 Wi-Fi. 프레임마다 ACK를 받으니 못 받으면 바로 다시 보낸다
- [ ] 브라우저. 요청이 실패하면 HTTP 요청을 처음부터 다시 보낸다
- [ ] AP. 망가진 비트를 FCS로 고쳐서 넘긴다

보내는 쪽 Wi-Fi가 데이터 링크 계층에서 바로 다시 보냅니다. 전파는 잘 망가지니 Wi-Fi는 유선 이더넷과 달리 프레임마다 ACK를 받고, 오지 않으면 재전송합니다. 이 재전송 때문에 Wi-Fi의 지연이 들쭉날쭉해집니다. FCS는 망가졌는지 알아낼 뿐 고치지는 못합니다.
:::

:::quiz wifi-channel 아파트에서 이웃 AP들이 2.4GHz의 1번과 6번 채널을 쓰고 있습니다. 내 공유기의 2.4GHz 채널로 가장 나은 것은?
- [ ] 3번
- [ ] 4번
- [ ] 8번
- [x] 11번

11번입니다. 2.4GHz 채널은 5MHz 간격인데 한 채널의 폭이 약 20MHz라서, 서로 겹치지 않는 것은 1, 6, 11번뿐입니다. 3번과 4번은 1번과 6번 모두와, 8번은 6번과 겹쳐 서로 기다리고 간섭합니다.
:::

## ARP: IP 주소로 MAC 주소 찾기

이제 중요한 문제 하나가 남았습니다. 프로그램은 IP 주소로 보내라고 합니다. 그런데 프레임을 만들려면 받는 쪽 MAC 주소가 필요합니다. IP 주소를 MAC 주소로 바꿔 주는 프로토콜이 [[ARP]]입니다.

![노트북(192.168.0.23)이 공유기(192.168.0.1)의 MAC 주소를 모를 때. 질문은 브로드캐스트로 모두에게, 답은 노트북에게만 갑니다](link-arp.svg)

답은 [[ARP 캐시]]에 몇 분 동안 남아 있어서, 프레임을 보낼 때마다 묻지 않아도 됩니다.

여기서 꼭 이해해야 할 점이 있습니다. **다른 네트워크에 있는 서버로 보낼 때, ARP로 찾는 건 서버의 MAC 주소가 아니라 공유기(기본 게이트웨이)의 MAC 주소입니다.** 컴퓨터는 목적지 IP가 같은 네트워크 안인지 먼저 따집니다(11장의 서브넷). 같은 네트워크면 그 기기의 MAC을 찾고, 다른 네트워크면 "일단 공유기에게 건넨다"며 공유기의 MAC을 찾습니다. 해외 서버의 MAC 주소는 알 필요도, 알 방법도 없습니다.

ARP에는 인증이 없습니다. 누가 "내가 192.168.0.1이야"라고 거짓 답을 보내도 그대로 믿습니다. 공용 Wi-Fi에서 나쁜 사람이 이렇게 해서 다른 사람의 트래픽이 자기를 거쳐 가게 만드는 공격을 [[ARP 스푸핑]]이라고 합니다. 이렇게 중간에 끼어든 사람도 HTTPS로 암호화된 내용은 읽지 못합니다. 모든 사이트가 HTTPS를 써야 하는 이유 중 하나입니다.

IPv6에서는 ARP 대신 NDP라는 프로토콜이 같은 일을 합니다.

:::quiz arp-local 노트북(192.168.0.23/24)이 같은 공유기에 붙은 프린터(192.168.0.50)로 인쇄할 때, ARP로 알아내는 MAC 주소는 누구의 것일까요?
- [x] 프린터의 MAC 주소
- [ ] 공유기의 MAC 주소
- [ ] 노트북 자신의 MAC 주소
- [ ] 통신사 라우터의 MAC 주소

프린터의 MAC 주소입니다. 목적지가 같은 네트워크에 있으니 공유기를 거칠 필요 없이 프린터에게 바로 프레임을 건넵니다. 공유기(기본 게이트웨이)의 MAC을 찾는 것은 목적지가 다른 네트워크에 있을 때뿐입니다.
:::

## 프레임은 홉마다 새로 만들어집니다

패킷이 라우터를 하나 지날 때마다(이걸 한 [[홉]]이라고 합니다) 이더넷 봉투는 버려지고 새로 만들어집니다. IP 봉투는 그대로입니다. 노트북에서 해외 서버로 가는 패킷을 보면 이렇습니다.

| 구간 | 보내는 MAC | 받는 MAC | 보내는 IP | 받는 IP |
| --- | --- | --- | --- | --- |
| 노트북 → 공유기 | 노트북 | 공유기 | 192.168.0.23 | 서버 IP |
| 공유기 → 통신사 라우터 | 공유기 바깥쪽 | 통신사 라우터 | 공유기의 공인 IP (NAT) | 서버 IP |
| 통신사 라우터 → 다음 라우터 | 통신사 라우터 | 다음 라우터 | 공유기의 공인 IP | 서버 IP |
| … | … | … | 그대로 | 그대로 |
| 마지막 라우터 → 서버 | 마지막 라우터 | 서버 | 공유기의 공인 IP | 서버 IP |

MAC 주소는 "이번 한 걸음의 출발지와 도착지", IP 주소는 "여행 전체의 출발지와 도착지"입니다. 택배로 치면 MAC 주소는 트럭이 이번에 가는 다음 물류 센터이고, IP 주소는 상자에 붙은 최종 배송지입니다. 공유기 구간에서 보내는 IP가 바뀌는 건 11장의 NAT 때문이고, 그것 말고는 IP 주소가 바뀌지 않습니다.

![같은 패킷이 홉을 지날 때. 이더넷 헤더의 MAC 주소는 구간마다 새로 적히고, IP 헤더는 NAT 구간을 빼면 끝까지 그대로입니다](link-hops.svg)

:::quiz last-hop 노트북이 보낸 패킷이 라우터 여러 개를 지나 해외 서버에 닿았습니다. 서버가 받은 이더넷 프레임의 보내는 쪽 MAC 주소는 누구의 것일까요?
- [ ] 노트북의 MAC 주소
- [ ] 우리 집 공유기의 MAC 주소
- [ ] 통신사 첫 라우터의 MAC 주소
- [x] 서버 바로 앞 마지막 라우터의 MAC 주소

서버 바로 앞 마지막 라우터의 MAC 주소입니다. 이더넷 헤더는 홉마다 새로 만들어지고, MAC 주소는 "이번 한 걸음"의 출발지와 도착지만 담습니다. 노트북의 MAC은 첫 구간에서 이미 사라졌고, 서버가 알 수 있는 건 IP 주소뿐입니다.
:::

## 곁가지: VLAN

회사에서는 같은 스위치에 붙은 기기들이라도 부서별로 네트워크를 나누고 싶을 때가 있습니다. 스위치에 설정만 해서 하나의 물리 네트워크를 여러 논리 네트워크로 쪼개는 기술이 [[VLAN]]입니다. 프레임에 4바이트 표시(VLAN 번호)를 끼워 구분합니다. 서로 다른 VLAN은 다른 브로드캐스트 도메인이라 라우터를 거쳐야만 통신합니다. 클라우드의 VPC(가상 사설 네트워크)도 비슷한 생각을 소프트웨어로 크게 키운 것입니다.

:::quiz vlan 같은 스위치에 붙어 있지만 VLAN 10에 속한 PC와 VLAN 20에 속한 PC가 통신하려면 어떻게 될까요?
- [x] 서로 다른 브로드캐스트 도메인이라 라우터를 거쳐야 한다
- [ ] 같은 스위치이니 상대 MAC만 알면 바로 프레임을 주고받는다
- [ ] ARP 브로드캐스트가 VLAN을 넘어가서 상대 MAC을 찾아 준다
- [ ] 스위치가 VLAN 표시를 떼고 상대 포트로 그냥 넘겨 준다

라우터를 거쳐야 합니다. VLAN은 물리 스위치 하나를 논리 네트워크 여럿으로 나눈 것이라, 서로 다른 VLAN은 다른 브로드캐스트 도메인입니다. 브로드캐스트인 ARP도 VLAN을 넘지 못하니 상대 MAC을 직접 알아낼 수도 없습니다.
:::

## 가상 네트워크 장치

내 컴퓨터의 네트워크 장치 목록을 보면 실제 랜 포트와 Wi-Fi 말고도 여러 장치가 나옵니다. 운영체제가 소프트웨어로 만든 [[가상 네트워크 인터페이스]]입니다.

- **루프백** (`lo`, `lo0`): 컴퓨터 자신에게 보내는 가짜 장치. `localhost`, `127.0.0.1`이 여기 붙어 있습니다(11장).
- **VPN** (`utun`, `tun`, Windows의 VPN 어댑터): VPN 프로그램이 만든 장치. 여기로 보낸 패킷은 암호화되어 VPN 서버로 갑니다.
- **Docker** (`docker0`, `veth…`, `br-…`): Docker가 만든 가상 스위치(브리지)와, 컨테이너마다 하나씩 이어 붙인 가상 랜선. 컨테이너는 이 가상 네트워크에서 자기 IP와 MAC 주소를 받습니다.
- **WSL, 가상 머신** (`vEthernet (WSL)`, `bridge100`): 가상 머신과 호스트를 잇는 가상 네트워크.

이 사이트의 서버에서도 가상 네트워크가 쓰입니다. Caddy 컨테이너와 이 사이트를 내보내는 nginx 컨테이너는 같은 Docker 네트워크(`docker-compose.yml`의 `edge`)에 붙어 있어서, Caddy가 `mlnl-cs:80`이라는 이름으로 nginx를 찾아갑니다. 둘 사이의 패킷은 실제 랜선이 아니라 커널 안의 가상 스위치를 지납니다.

## 다시 장면으로: 공유기가 받은 다음

맨 앞 그림의 프레임은 이제 이렇게 읽힙니다. 노트북은 `GET /`를 담은 IP 패킷의 받는 쪽이 54.116.117.190이라 다른 네트워크라고 판단했고, ARP로 공유기의 MAC을 찾아 프레임의 받는 쪽에 적었습니다. 공중에 퍼진 프레임을 휴대폰과 TV는 받는 쪽 MAC을 보고 버렸고, 공유기는 FCS를 확인한 뒤 Wi-Fi ACK를 돌려보냈습니다. 공유기는 이제 Wi-Fi 봉투를 벗기고 안의 IP 패킷을 꺼냅니다. 그다음 구간에서는 새 봉투에 담겨 통신사 라우터로 갑니다.

여기서부터는 MAC 주소로 할 수 있는 일이 없습니다. 공유기는 54.116.117.190이 어느 쪽에 있는지 알아야 하고, 노트북의 192.168.0.23이라는 주소는 집 밖에서는 쓸 수 없습니다. 숫자 네 개짜리 주소는 어떻게 생겼길래 수만 개의 네트워크를 지나 서버 한 대를 찾아가고, 집 안의 주소는 공유기에서 무엇으로 바뀔까요? 11장의 이야기입니다.

## 프론트엔드와 이어지는 곳

- 휴대폰으로 내 개발 서버를 보려면, 둘이 같은 Wi-Fi(같은 네트워크)에 있고 휴대폰 브라우저에 내 컴퓨터의 LAN IP를 쳐야 합니다. Vite의 `--host` 옵션이 하는 일은 16장에서 봅니다.
- 호텔이나 카페 Wi-Fi에 붙으면 로그인 화면이 먼저 뜨는 것을 [[캡티브 포털]]이라고 합니다. 공유기가 HTTP 요청을 가로채 로그인 페이지로 돌리는 것이라, 그동안 `navigator.onLine`은 `true`인데 실제 API 요청은 실패합니다. 온라인 여부는 실제 요청이 성공하는지로 판단합니다.
- Wi-Fi는 지연이 들쭉날쭉하니, 실시간 기능(채팅, 협업 편집, 게임)은 패킷이 늦게, 몰아서 도착하는 상황을 견디도록 만듭니다.

## 용어 정리

:::terms
- 물리 계층 (physical layer) — 비트를 전기, 빛, 전파 같은 실제 신호로 바꿔 매체에 싣는 계층입니다.
- 데이터 링크 계층 (data link layer) — 같은 네트워크 안의 바로 옆 기기에게 프레임을 전달하는 계층. 틀 짓기, MAC 주소, 오류 검사를 맡습니다.
- 프레임 (frame) — 데이터 링크 계층의 데이터 단위. 이더넷 프레임은 MAC 주소, 타입, 페이로드, FCS로 되어 있습니다.
- 이더넷 (Ethernet) — 유선 LAN에서 쓰는 데이터 링크 계층 프로토콜이자 물리 규격입니다.
- MAC 주소 (MAC address) — 네트워크 카드마다 붙는 48비트 주소. 같은 네트워크 안에서 프레임의 받는 쪽과 보내는 쪽을 가리킵니다.
- MAC 주소 무작위화 (MAC address randomization) — 추적을 막으려고 Wi-Fi 네트워크마다 다른 가짜 MAC 주소를 쓰는 기능입니다.
- MTU (Maximum Transmission Unit) — 한 프레임에 실을 수 있는 페이로드의 최대 크기. 이더넷은 1500바이트입니다.
- 브로드캐스트 (broadcast) — 같은 네트워크의 모든 기기에 보내는 것. 이더넷에서는 `ff:ff:ff:ff:ff:ff`로 보냅니다.
- 브로드캐스트 도메인 (broadcast domain) — 브로드캐스트가 닿는 범위. 라우터가 경계가 되며, 곧 "같은 네트워크"의 범위입니다.
- 허브 (hub) — 들어온 신호를 모든 포트로 복사하는 옛 장비. 충돌이 잦아 지금은 거의 쓰지 않습니다.
- 스위치 (switch) — MAC 주소를 배워 프레임을 받는 기기의 포트로만 보내는 데이터 링크 계층 장비입니다.
- MAC 주소 테이블 (MAC address table) — 스위치가 포트마다 어떤 MAC 주소가 붙어 있는지 배워 적어 두는 표입니다.
- Wi-Fi — IEEE 802.11 표준을 따르는 무선 LAN. 액세스 포인트와 기기들이 전파로 프레임을 주고받습니다.
- 액세스 포인트 (access point) — Wi-Fi 기기들을 유선 네트워크에 잇는 무선 기지입니다.
- SSID (Service Set Identifier) — Wi-Fi 네트워크의 이름입니다.
- ARP (Address Resolution Protocol) — 같은 네트워크에서 IP 주소에 해당하는 MAC 주소를 브로드캐스트로 물어 알아내는 프로토콜입니다.
- ARP 캐시 (ARP cache) — ARP로 알아낸 IP-MAC 짝을 잠시 기억해 두는 표입니다.
- ARP 스푸핑 (ARP spoofing) — 거짓 ARP 답으로 남의 트래픽이 자기를 거쳐 가게 만드는 공격입니다.
- 홉 (hop) — 패킷이 라우터 하나를 지나는 한 구간. 홉마다 데이터 링크 계층 봉투가 새로 만들어집니다.
- VLAN (Virtual LAN) — 하나의 물리 스위치를 설정으로 여러 논리 네트워크로 나누는 기술입니다.
- 가상 네트워크 인터페이스 (virtual network interface) — 실제 하드웨어 없이 운영체제가 소프트웨어로 만든 네트워크 장치. 루프백, VPN, Docker 브리지가 있습니다.
- 캡티브 포털 (captive portal) — 공용 Wi-Fi에서 인터넷을 쓰기 전에 로그인이나 동의 페이지로 먼저 보내는 장치입니다.
:::

## 직접 해보기

:::practice arp ARP 캐시 들여다보기
지금 내 컴퓨터의 ARP 캐시에 무엇이 있는지 보고, 공유기의 IP와 MAC 주소를 찾습니다. MAC 주소 앞 세 바이트로 제조사를 검색해 봅니다. 해외 사이트에 `ping`을 해도 그 서버의 MAC 주소는 캐시에 생기지 않는다는 것도 확인합니다.

```sh macOS · Linux
arp -a                 # Linux는 ip neigh 도 됩니다
ping -c 1 google.com
arp -a                 # google의 MAC은 없고, 공유기 항목만 있습니다
```

```powershell Windows
arp -a
ping -n 1 google.com
arp -a
```
:::

:::practice interfaces 내 컴퓨터의 네트워크 장치 목록 읽기
네트워크 장치를 모두 나열하고 각각이 실제 장치인지 가상 장치인지(루프백, VPN, Docker, WSL) 구분해 봅니다. 각 장치의 MAC 주소와 MTU도 찾습니다.

```sh macOS
ifconfig | grep -E "^[a-z]|ether|mtu"
networksetup -listallhardwareports
```

```sh Linux
ip -br link
ip -br addr
```


:::practice wireshark-arp Wireshark로 ARP 주고받기 잡기
Wireshark에서 필터에 `arp`를 넣고 잡기를 시작한 뒤, ARP 캐시를 비우고 공유기에 ping을 보냅니다. 브로드캐스트로 나간 질문(Who has …?)과 나에게만 온 답(… is at …)을 찾고, 각 프레임의 받는 쪽 MAC 주소가 무엇인지 확인합니다.

```sh macOS
sudo arp -d -a && ping -c 1 192.168.0.1
```

```powershell Windows (관리자)
arp -d * ; ping -n 1 192.168.0.1
```

```sh Linux
sudo ip neigh flush all && ping -c 1 192.168.0.1
```
:::

## 장 전체 문제

:::quiz gateway-arp 노트북(192.168.0.23/24)의 ARP 캐시가 비어 있을 때 이 페이지(서버 54.116.117.190)를 열면, 노트북이 ARP로 MAC 주소를 묻는 IP 주소는 무엇일까요? 공유기는 192.168.0.1입니다.
= 192.168.0.1

**192.168.0.1**, 공유기입니다. 54.116.117.190은 192.168.0.x가 아니니 다른 네트워크이고, 다른 네트워크로 가는 프레임은 언제나 기본 게이트웨이에게 건넵니다. 서버의 MAC 주소는 알 필요도, 알 방법도 없습니다. ARP 브로드캐스트는 공유기를 넘어가지 않기 때문입니다.
:::

:::quiz spoof 카페 Wi-Fi에서 ARP 스푸핑을 당해, 이 페이지를 여는 동안 패킷이 공격자의 노트북을 거쳐 갑니다. 공격자가 알 수 있는 것은?
- [ ] 이 페이지의 HTML 본문
- [x] 내가 54.116.117.190과 주고받았다는 사실과 데이터의 양
- [ ] "다 읽었어요" 진행 기록
- [ ] 브라우저가 보낸 쿠키 값

IP 헤더와 데이터의 양입니다. 라우터가 길을 찾으려면 IP 헤더를 읽어야 하니 IP 헤더는 암호화되지 않습니다. 그 안의 HTTP는 HTTPS로 암호화되어 있어서 본문과 쿠키는 보이지 않습니다(14장). 진행 기록은 내 브라우저의 `localStorage`에만 있어 애초에 네트워크로 나가지 않습니다.
:::

## 스스로 점검

:::qa 해외 서버로 패킷을 보낼 때, 내 컴퓨터가 ARP로 알아내는 MAC 주소는 누구의 것인가요? 왜인가요?
기본 게이트웨이(공유기)의 MAC 주소입니다. 목적지가 다른 네트워크에 있으면 바로 건넬 수 없으니 일단 같은 네트워크의 게이트웨이에게 건네고, 거기서부터는 라우터들이 이어서 넘깁니다. MAC 주소는 같은 네트워크 안에서만 쓰입니다.
:::

:::qa 패킷이 라우터 다섯 개를 지나는 동안 MAC 주소와 IP 주소는 각각 어떻게 되나요?
MAC 주소는 홉마다 바뀝니다. 각 라우터가 프레임을 벗기고 자기 MAC을 보내는 쪽으로, 다음 장비의 MAC을 받는 쪽으로 해서 새 프레임을 만듭니다. IP 주소는 NAT를 지나는 경우를 빼면 처음부터 끝까지 그대로입니다.
:::

:::qa 스위치는 처음 보는 MAC 주소로 가는 프레임을 어떻게 처리하고, 어떻게 길을 배우나요?
MAC 주소 테이블에 없으면 들어온 포트를 뺀 모든 포트로 보냅니다(플러딩). 프레임이 들어올 때마다 보내는 쪽 MAC 주소와 들어온 포트를 표에 적어 배우므로, 답이 돌아오면 그 주소의 포트도 알게 됩니다.
:::

:::qa 유선 이더넷에서 FCS 검사에 실패한 프레임은 어떻게 되나요? 그 데이터는 영영 사라지나요?
조용히 버려집니다. 이더넷은 다시 보내 달라고 하지 않습니다. 사라진 데이터는 받는 쪽 TCP가 빠진 것을 알아채고 보내는 쪽에 재전송을 요청해 되찾습니다. 층마다 맡은 일이 나뉘어 있습니다.
:::

:::qa 카페 Wi-Fi가 WPA2로 암호화되어 있으면 HTTPS가 없어도 안전한가요?
아닙니다. WPA2는 기기와 AP 사이의 전파 구간만 암호화합니다. 같은 Wi-Fi에 붙은 사람이 ARP 스푸핑으로 트래픽을 자기에게 돌리거나, AP 너머의 구간에서는 내용이 그대로 보일 수 있습니다. 끝에서 끝까지 보호하려면 HTTPS가 필요합니다.
:::
