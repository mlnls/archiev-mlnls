13장은 연결 위로 무엇을 주고받는지, 그리고 그 말을 길 위의 누구도 읽거나 고치지 못하게 하려면 어떻게 하는지를 물으며 끝났습니다. 9장 맨 앞 그림의 왕복 3과 4입니다. 이 페이지를 열 때 실제로 오간 요청과 응답은 이렇게 생겼습니다.

드디어 맨 위층입니다. 브라우저와 서버가 주고받는 저 말이 [[HTTP]]입니다. 그리고 그 말을 길 위의 누구도 엿듣거나 바꾸지 못하게 감싸는 것이 TLS이고, TLS로 감싼 HTTP가 [[HTTPS]]입니다. 프론트엔드 개발자가 매일 다루는 `fetch`, 쿠키, 캐시, CORS 오류가 모두 이 장의 내용입니다.

## HTTP는 요청과 응답

HTTP는 단순합니다. 클라이언트가 [[요청]]을 보내면 서버가 [[응답]]을 하나 돌려줍니다. 서버가 먼저 말을 거는 일은 없습니다(그게 필요하면 WebSocket이나 SSE를 씁니다). 그리고 HTTP는 [[무상태]]입니다. 서버는 앞의 요청을 기억하지 않고, 요청 하나하나를 처음 보는 요청처럼 처리합니다. 로그인 상태 같은 걸 이어 가려면 아래의 쿠키 같은 장치가 따로 필요합니다.

요청할 대상은 [[URL]]로 가리킵니다.

```text
https://blog.example.com:443/posts/hello?ref=home#comments
└─┬─┘   └──────┬───────┘└┬┘└────┬─────┘└──┬───┘└───┬───┘
스킴         호스트       포트   경로        쿼리     프래그먼트
```

- 스킴은 어떤 프로토콜인지, 호스트는 DNS로 찾을 이름, 포트는 12장의 포트(생략하면 https는 443, http는 80)입니다.
- 경로와 쿼리는 서버에 그대로 전달됩니다.
- `#` 뒤의 프래그먼트는 **서버로 보내지 않습니다.** 브라우저 안에서만 씁니다. 해시 라우팅 SPA가 서버 설정 없이 동작하는 이유이고, 서버 로그에 `#` 뒷부분이 남지 않는 이유입니다.

:::quiz fragment 이 페이지에서 `https://cs.mlnl.…sslip.io/http/#tls`로 이동할 때, 서버가 받는 요청의 경로는?
= /http/

**`/http/`**입니다. `#` 뒤의 프래그먼트는 서버로 보내지 않고 브라우저가 페이지 안에서 그 위치로 스크롤하는 데만 씁니다. 이 책의 목차 링크가 페이지를 다시 받지 않고 움직이는 이유입니다.
:::

## 요청과 응답 메시지

HTTP/1.1 메시지는 사람이 읽을 수 있는 글자입니다. 브라우저가 실제로 보내는 요청은 이렇게 생겼습니다.

```text 요청
GET /posts/hello?ref=home HTTP/1.1          ← 요청 줄: 메서드, 경로, 버전
Host: blog.example.com                      ← 헤더들 (이름: 값)
User-Agent: Mozilla/5.0 (Macintosh; …)
Accept: text/html
Accept-Encoding: gzip, br, zstd
Cookie: session=abc123
                                            ← 빈 줄: 헤더 끝
(GET은 보통 본문이 없음)
```

```text 응답
HTTP/1.1 200 OK                             ← 상태 줄: 버전, 상태 코드, 문구
Content-Type: text/html; charset=utf-8
Content-Length: 5120
Content-Encoding: br
Cache-Control: no-cache
Set-Cookie: theme=dark; Path=/; Max-Age=31536000
                                            ← 빈 줄
<!doctype html><html>…                      ← 본문 (Content-Length 바이트)
```

12장에서 TCP는 경계 없는 바이트 스트림이라고 했습니다. HTTP는 "빈 줄까지가 헤더, 그 뒤 `Content-Length` 바이트가 본문"이라는 규칙으로 메시지의 끝을 압니다. 길이를 미리 모를 때는 조각마다 길이를 적어 보내는 방식(chunked)을 씁니다.

## 메서드

[[HTTP 메서드]]는 요청이 무엇을 하려는지 나타냅니다.

| 메서드 | 뜻 | 안전한가 | [[멱등성]] | 본문 |
| --- | --- | --- | --- | --- |
| GET | 가져오기 | 예 | 예 | 없음 |
| HEAD | GET과 같되 헤더만 | 예 | 예 | 없음 |
| POST | 새로 만들기, 그 밖의 처리 | 아니요 | 아니요 | 있음 |
| PUT | 통째로 바꾸기 (없으면 만들기) | 아니요 | 예 | 있음 |
| PATCH | 일부만 바꾸기 | 아니요 | 보통 아니요 | 있음 |
| DELETE | 지우기 | 아니요 | 예 | 보통 없음 |
| OPTIONS | 무엇이 허용되는지 묻기 (CORS 사전 요청) | 예 | 예 | 없음 |

**안전하다**는 서버의 상태를 바꾸지 않는다는 뜻입니다. 그래서 브라우저, 검색 엔진, 프리페치가 GET 링크를 마음대로 미리 눌러 봐도 됩니다. 로그아웃이나 삭제를 GET 링크로 만들면 안 되는 이유입니다.

**멱등하다**는 같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같다는 뜻입니다. 네트워크가 끊겨 응답을 못 받았을 때 멱등한 요청은 안심하고 다시 보낼 수 있지만, POST는 다시 보내면 주문이 두 번 들어갈 수 있습니다. 결제 API들이 요청마다 고유한 키(Idempotency-Key)를 받게 하는 이유입니다.

GET과 POST의 차이를 묻는 면접 질문의 답은 "GET은 데이터를 URL에, POST는 본문에"보다 위의 두 성질이 핵심입니다. URL은 브라우저 기록, 서버 로그, Referer에 남으니 비밀번호 같은 값은 GET 쿼리에 넣지 않는 것도 함께 기억합니다.

:::quiz idempotent 응답을 받기 전에 네트워크가 끊겼습니다. 같은 요청을 그대로 다시 보내도 결과가 한 번 보낸 것과 같은 것은?
- [ ] `POST /orders` (주문 만들기)
- [ ] `POST /comments` (댓글 달기)
- [x] `PUT /posts/42` (글 42를 이 본문으로 통째로 바꾸기)
- [ ] `PATCH /counter` (값을 1 늘리기)

PUT입니다. "이 본문으로 바꿔라"는 몇 번 보내도 결과가 같습니다. POST는 보낼 때마다 새로 만들고, "1 늘려라" 같은 PATCH는 보낼 때마다 값이 바뀝니다. 그래서 결제 API는 POST에 Idempotency-Key를 붙여 중복을 막습니다.
:::

## 상태 코드

[[상태 코드]]는 응답의 결과를 세 자리 숫자로 알립니다. 첫 자리가 종류입니다.

| 코드 | 뜻 | 자주 만나는 상황 |
| --- | --- | --- |
| 200 OK | 성공 | |
| 201 Created | 만들었음 | POST로 새 글 작성 |
| 204 No Content | 성공, 본문 없음 | DELETE, 저장 |
| 206 Partial Content | 일부만 보냄 | 동영상 이어 보기 (Range 요청) |
| 301 / 308 | 영구 이동 | `http` → `https`, `www` → 맨 도메인. 이 사이트의 Caddy도 `www.`를 `permanent`로 돌림 |
| 302 / 307 | 임시 이동 | 로그인 후 원래 페이지로 |
| 304 Not Modified | 캐시한 그대로 써라 | 아래 캐시 절 |
| 400 Bad Request | 요청 형식이 잘못됨 | 깨진 JSON |
| 401 Unauthorized | 누구인지 모름 (인증 필요) | 로그인 안 함 |
| 403 Forbidden | 누구인지는 알지만 권한 없음 | 남의 글 수정 |
| 404 Not Found | 없음 | |
| 405 Method Not Allowed | 그 메서드는 안 됨 | GET만 되는 곳에 POST |
| 409 Conflict | 지금 상태와 충돌 | 동시에 같은 글 수정 |
| 413 Content Too Large | 본문이 너무 큼 | 업로드 크기 제한. 이 사이트의 블로그 API는 6MB를 넘으면 Caddy가 413을 돌려줌 |
| 429 Too Many Requests | 너무 자주 요청함 | 요청 수 제한 |
| 500 Internal Server Error | 서버 코드 오류 | 처리하지 못한 예외 |
| 502 Bad Gateway | 프록시가 뒤의 서버에서 이상한 답을 받거나 연결을 못 함 | 리버스 프록시 뒤의 앱이 죽었음 |
| 503 Service Unavailable | 잠시 처리할 수 없음 | 과부하, 점검 중 |
| 504 Gateway Timeout | 프록시가 뒤의 서버를 기다리다 시간 초과 | 앱이 너무 느림 |

4xx는 "요청한 쪽 문제", 5xx는 "서버 쪽 문제"입니다. 502와 504는 17장의 리버스 프록시를 알면 바로 이해됩니다. 앞에 선 프록시(이 사이트에서는 Caddy)는 살아 있는데, 그 뒤의 앱(컨테이너)이 죽었거나(502) 너무 느린(504) 것입니다.

:::quiz bad-gateway 이 사이트 앞의 Caddy는 살아 있는데, 뒤의 nginx 컨테이너가 죽었습니다. 브라우저가 받는 상태 코드는?
= 502

**502 Bad Gateway**입니다. Caddy가 `mlnl-cs:80`에 연결하지 못하니 "뒤의 서버에서 제대로 된 답을 못 받았다"고 알립니다. nginx가 살아 있지만 너무 느리면 504가 됩니다. 둘 다 프론트엔드 코드의 문제가 아닙니다.
:::

## 헤더

[[HTTP 헤더]]는 요청과 응답에 붙는 부가 정보입니다. 꼭 알아 둘 것들입니다.

| 헤더 | 방향 | 하는 일 |
| --- | --- | --- |
| `Host` | 요청 | 어느 사이트에 대한 요청인지. HTTP/1.1부터 필수 |
| `Content-Type` | 양쪽 | 본문의 형식 ([[MIME 타입]]) |
| `Content-Length` | 양쪽 | 본문의 바이트 수 |
| `Content-Encoding` | 응답 | 본문을 어떻게 압축했는지 (gzip, br, zstd) |
| `Accept`, `Accept-Encoding`, `Accept-Language` | 요청 | 받을 수 있는 형식, 압축, 언어 |
| `Authorization` | 요청 | 인증 정보 (`Bearer 토큰`) |
| `Cookie`, `Set-Cookie` | 요청, 응답 | 쿠키 |
| `Cache-Control`, `ETag`, `If-None-Match` | 양쪽 | 캐시 |
| `Location` | 응답 | 3xx에서 이동할 곳, 201에서 만든 것의 주소 |
| `Origin`, `Access-Control-*` | 양쪽 | CORS |
| `Strict-Transport-Security` | 응답 | 이 사이트는 HTTPS로만 접속하라 (HSTS) |

`Host` 헤더가 특히 중요합니다. 서버 하나(IP 하나)가 여러 사이트를 받을 수 있는 건, 요청마다 `Host`에 어느 사이트를 원하는지 적혀 있기 때문입니다. 이걸 [[가상 호스팅]]이라고 합니다. 이 사이트의 서버도 IP 하나로 들어온 요청을 Caddy가 `Host`를 보고 `blog.…`이면 블로그 컨테이너로, `cs.…`면 이 사이트의 컨테이너로 나눠 보냅니다(`deploy/Caddyfile.mlnl`).

`Content-Encoding`은 본문 압축입니다. 브라우저가 `Accept-Encoding: gzip, br, zstd`로 풀 수 있는 방식을 알리면, 서버가 그중 하나로 압축해 보냅니다. HTML, CSS, JS 같은 텍스트는 보통 70~90% 줄어듭니다. 이 사이트의 Caddy 설정의 `encode zstd gzip`이 이 일을 합니다.

:::quiz host-routing 이 서버는 IP 하나로 블로그와 이 사이트를 함께 받습니다. TLS를 푼 Caddy가 요청을 어느 컨테이너로 보낼지 정할 때 보는 것은?
- [ ] 패킷의 받는 IP 주소
- [x] `Host` 헤더
- [ ] 브라우저의 임시 포트 번호
- [ ] `User-Agent` 헤더

`Host` 헤더입니다. 받는 IP와 포트(443)는 블로그든 이 사이트든 같으니 구분이 안 됩니다. `Host`에 적힌 이름이 `cs.`로 시작하면 이 사이트의 nginx로 보냅니다. 이것이 가상 호스팅이고, TLS 단계에서는 SNI가 같은 일을 합니다.
:::

## MIME 타입

[[MIME 타입]]은 본문이 어떤 종류인지 `종류/세부` 형식으로 알리는 이름표입니다. `text/html`, `text/css`, `application/javascript`, `application/json`, `image/png`, `image/webp`, `font/woff2`처럼 씁니다. 1장에서 본 것처럼 파일 안에는 "나는 무엇이다"라는 표시가 없으니, 서버가 이 헤더로 알려 줘야 합니다.

브라우저는 예전에 MIME 타입이 이상하면 내용을 보고 추측하곤 했는데(MIME 스니핑), 이게 보안 구멍이 되었습니다. 사용자가 올린 이미지 파일 안에 스크립트를 숨겨 실행시키는 식입니다. 그래서 서버는 `X-Content-Type-Options: nosniff` 헤더로 "추측하지 말고 내가 적은 타입만 믿어라"라고 알립니다. 이 사이트의 nginx 설정에도 이 헤더가 들어 있습니다. 대신 서버가 MIME 타입을 틀리게 보내면 그대로 실패합니다. CSS가 적용되지 않는데 콘솔에 "MIME type ('text/plain') is not a supported stylesheet MIME type"이 보이면 이 경우입니다.

## 쿠키와 세션

HTTP는 무상태라, 로그인한 사용자의 다음 요청을 서버가 알아보려면 브라우저가 요청마다 "나 누구"라는 표시를 들고 와야 합니다. 그 표시를 자동으로 들고 다니게 하는 장치가 [[쿠키]]입니다.

1. 로그인에 성공하면 서버가 응답에 `Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Lax`를 붙입니다.
2. 브라우저는 이 쿠키를 저장해 두고, 같은 사이트로 가는 요청마다 `Cookie: session=abc123`을 자동으로 붙입니다.
3. 서버는 `abc123`으로 자기 저장소에서 "이건 사용자 42의 로그인"이라는 기록을 찾습니다. 이 서버 쪽 기록이 [[세션]]입니다.

쿠키 속성이 보안에 중요합니다.

| 속성 | 뜻 |
| --- | --- |
| `Domain`, `Path` | 어느 호스트와 경로에 보낼지. `Domain=.example.com`이면 모든 서브도메인에 보냄 |
| `Expires`, `Max-Age` | 언제까지 유지할지. 없으면 브라우저를 닫을 때 사라짐 |
| `Secure` | HTTPS 요청에만 보냄 |
| `HttpOnly` | JS의 `document.cookie`로 읽을 수 없음. XSS로 세션을 훔쳐 가지 못하게 |
| `SameSite` | 다른 사이트에서 시작된 요청에 보낼지. `Lax`(기본)는 링크 이동 같은 경우만, `Strict`는 절대 안 보냄, `None`은 늘 보냄(`Secure` 필수). CSRF 방어 |

세션 대신 로그인 정보를 서명된 토큰(JWT 등)에 담아 클라이언트가 들고 다니게 하는 방식도 있습니다. 서버가 저장소를 볼 필요가 없지만, 토큰을 중간에 무효화하기 어렵습니다. 이 사이트의 블로그 API는 서버에 세션 저장소를 두지 않고, 만료 시각에 서버만 아는 비밀 키로 HMAC 서명을 붙인 값을 `HttpOnly` 쿠키로 줍니다(`apps/api/src/security.ts`). 쿠키의 `Domain`을 상위 도메인으로 두어 블로그와 다른 서브도메인이 함께 씁니다.

- [x] 페이지에 몰래 들어간 JS가 `document.cookie`로 세션 값을 읽어 가는 것
- [ ] 암호화되지 않은 `http://` 요청에 쿠키가 실리는 것
- [ ] 다른 사이트에서 시작된 요청에 쿠키가 붙는 것
- [ ] 쿠키가 기간이 지나 사라지는 것

JS가 쿠키를 읽는 것입니다. XSS로 스크립트가 들어와도 세션 값을 꺼내 가지 못합니다. `http://`로 실리는 걸 막는 건 `Secure`, 다른 사이트의 요청에 붙는 걸 막는 건 `SameSite`입니다.
:::

## HTTP 캐시

같은 파일을 매번 다시 받지 않도록 브라우저와 중간 서버(CDN)는 응답을 저장해 둡니다. 2장에서 본 "가까운 곳에 복사본"의 HTTP 판입니다. 이 [[HTTP 캐시]]를 어떻게 쓸지는 서버가 응답 헤더로 정합니다.

| `Cache-Control` 값 | 뜻 |
| --- | --- |
| `max-age=3600` | 3600초 동안은 서버에 묻지 않고 그냥 씀 |
| `no-cache` | 저장은 하되, 쓰기 전에 매번 서버에 "아직 그대로야?"라고 물어봄 |
| `no-store` | 아예 저장하지 않음 (민감한 정보) |
| `public`, `private` | CDN 같은 공유 캐시에 저장해도 되는지, 이 사용자의 브라우저에만인지 |
| `immutable` | 기간 안에는 절대 바뀌지 않으니 새로고침해도 묻지 마라 |

"아직 그대로야?"라고 묻는 방법이 조건부 요청입니다. 서버는 처음 응답에 내용의 지문인 [[ETag]]를 붙여 보냅니다. 브라우저는 다음에 `If-None-Match: "그 지문"`을 붙여 묻고, 내용이 그대로면 서버는 본문 없이 `304 Not Modified`만 보냅니다. 왕복은 들지만 본문을 다시 받지 않습니다.

실무에서 가장 많이 쓰는 조합은 이렇습니다. 이 사이트의 nginx 설정이 바로 이 방식입니다.

- **파일 이름에 내용 해시를 넣은 정적 자원** (`/assets/style.3f9a1c2b7e.css`): `Cache-Control: public, max-age=31536000, immutable`. 1년 동안 묻지도 않습니다. 내용이 바뀌면 이름(해시)이 바뀌어 새 파일이 되니 옛 캐시가 문제 되지 않습니다. 이걸 캐시 무효화(cache busting)라고 합니다.
- **HTML**: `Cache-Control: no-cache`. 매번 서버에 확인합니다. HTML이 새 해시 이름의 CSS, JS를 가리키니, HTML만 새로 받으면 나머지는 저절로 새것을 씁니다.

Vite, Next.js 같은 빌드 도구가 파일 이름 뒤에 해시를 붙이는 이유가 이것입니다. 이 사이트도 빌드할 때 `style.css`와 `app.js`의 이름에 해시를 넣어 `/assets/`에 둡니다.

![이 사이트의 캐시 전략. HTML은 매번 확인하되 그대로면 304로 짧게 끝나고, 해시가 붙은 CSS와 JS는 이름이 바뀌기 전까지 묻지도 않습니다](http-cache.svg)

:::quiz after-deploy 이 사이트가 CSS를 고쳐 다시 배포했습니다. 어제 방문한 사람이 오늘 이 페이지를 다시 열면?
- [ ] CSS가 `immutable`이라 1년 동안 옛 CSS가 보인다
- [ ] 강력 새로고침을 해야만 새 CSS를 받는다
- [ ] 서버가 브라우저에게 옛 CSS를 지우라고 알린다
- [x] HTML을 서버에 확인하고, 새 HTML이 가리키는 새 이름의 CSS를 받는다

HTML은 `no-cache`라 매번 확인하고, 바뀌었으니 200으로 새 HTML이 옵니다. 새 HTML은 새 해시가 붙은 CSS 이름을 가리키는데 캐시에 없으니 새로 받습니다. 옛 CSS는 캐시에 남아 있지만 아무도 가리키지 않습니다.
:::

## 출처와 CORS

브라우저는 한 사이트의 JS가 다른 사이트의 데이터를 마음대로 읽지 못하게 막습니다. 내가 로그인해 둔 은행 사이트를, 지금 열어 둔 수상한 사이트의 JS가 `fetch`로 읽어 가면 안 되니까요. 이 규칙이 [[동일 출처 정책]]입니다. 여기서 [[출처]](origin)는 스킴, 호스트, 포트 세 가지가 모두 같은 범위를 말합니다. `https://example.com`과 `https://api.example.com`, `http://localhost:3000`과 `http://localhost:5173`은 모두 다른 출처입니다.

그래도 다른 출처의 API를 불러야 할 때가 많습니다. 서버가 "이 출처의 JS는 내 응답을 읽어도 된다"고 허락하는 방법이 [[CORS]]입니다.

1. `https://app.example.com`의 JS가 `https://api.example.com`에 `fetch`를 보내면, 브라우저가 요청에 `Origin: https://app.example.com`을 붙입니다.
2. 서버가 응답에 `Access-Control-Allow-Origin: https://app.example.com`을 붙이면 브라우저가 JS에 응답을 넘깁니다. 없으면 응답은 왔는데도 JS에 주지 않고 CORS 오류를 냅니다.
3. JSON을 POST하거나 `Authorization` 헤더를 붙이는 등 단순하지 않은 요청이면, 브라우저가 먼저 `OPTIONS` 메서드로 "이런 요청 보내도 돼?"라고 묻는 [[프리플라이트]] 요청을 보냅니다. 서버가 허락하면 진짜 요청을 보냅니다.
4. 쿠키를 함께 보내려면 `fetch(url, { credentials: "include" })`와 서버의 `Access-Control-Allow-Credentials: true`가 함께 필요하고, 이때는 `*`를 쓸 수 없습니다.

CORS는 **브라우저가** 지키는 규칙이고, 허락은 **서버가** 합니다. 같은 요청이 `curl`이나 Postman에서는 되는데 브라우저에서만 막히는 이유입니다. CORS 오류는 프론트엔드 코드로는 고칠 수 없고, 서버의 응답 헤더를 고치거나 같은 출처의 프록시를 거쳐야 합니다. 이 사이트의 API는 `ALLOWED_ORIGINS` 환경 변수에 적힌 출처만 허락합니다.

:::quiz cors-fix 같은 API 요청이 `curl`에서는 되는데 브라우저의 `fetch`에서만 CORS 오류가 납니다. 고쳐야 할 곳은?
- [ ] `fetch`에 `mode: "no-cors"`를 붙인다
- [ ] 요청에서 `Origin` 헤더를 지운다
- [x] 서버 응답의 `Access-Control-Allow-Origin`에 이 출처를 허락한다
- [ ] 브라우저 확장으로 CORS 검사를 끈다

서버가 허락해야 합니다. CORS는 브라우저가 지키는 규칙이라 `curl`은 상관하지 않습니다. `no-cors`로 보내면 오류는 사라져도 응답을 JS에서 읽을 수 없고, `Origin`은 브라우저가 붙이는 헤더라 JS로 지울 수 없습니다.
:::

## HTTP의 변화: 1.1, 2, 3

| | HTTP/1.1 (1997) | [[HTTP/2]] (2015) | [[HTTP/3]] (2022) |
| --- | --- | --- | --- |
| 메시지 형식 | 사람이 읽는 글자 | 바이너리 프레임 | 바이너리 프레임 |
| 연결 하나에 동시 요청 | 하나씩 차례로 | 여러 개를 섞어서 ([[멀티플렉싱]]) | 여러 개, 서로 독립 |
| 전송 계층 | TCP | TCP | QUIC (UDP) |
| 헤더 압축 | 없음 | HPACK | QPACK |
| 패킷 하나가 사라지면 | 그 연결의 요청이 멈춤 | 모든 요청이 함께 멈춤 (TCP 헤드 오브 라인 블로킹) | 그 스트림만 멈춤 |
| 연결 맺기 | TCP 1 RTT + TLS 1 RTT | 같음 | QUIC + TLS 합쳐 1 RTT, 재접속은 0 RTT |

HTTP/1.1에서는 연결 하나로 요청을 하나씩만 처리할 수 있어서, 브라우저는 호스트마다 연결을 6개쯤 열어 병렬로 받았습니다. 그래도 모자라 개발자들은 이미지를 한 장으로 합치고(스프라이트), JS를 하나로 묶고(번들), 도메인을 여러 개로 나눴습니다(도메인 샤딩). HTTP/2는 연결 하나에 요청 여러 개를 잘게 쪼개 섞어 보내서 이 문제를 풀었습니다. 그래서 HTTP/2 이후로는 도메인 샤딩이 오히려 손해이고, 아주 작은 파일 수백 개를 묶을 필요도 줄었습니다. HTTP/3는 남아 있던 TCP의 헤드 오브 라인 블로킹까지 QUIC으로 없앴습니다.

어느 버전을 쓸지는 연결할 때 정합니다. HTTP/2는 TLS 핸드셰이크 안에서 ALPN이라는 확장으로 "h2 할 수 있어?"를 묻고, HTTP/3는 서버가 HTTP/2 응답에 `Alt-Svc: h3=":443"` 헤더로 "QUIC으로도 와도 돼"라고 알린 뒤 다음부터 씁니다. DevTools Network 탭의 Protocol 칸(`http/1.1`, `h2`, `h3`)에서 확인할 수 있습니다.

:::quiz h2-loss HTTP/2로 CSS, JS, 이미지 요청 10개를 연결 하나에 섞어 받는 중에 TCP 패킷 하나가 사라졌습니다. 어떻게 될까요?
- [ ] 그 패킷이 속한 요청 하나만 멈춘다
- [ ] 연결이 끊겨 10개를 처음부터 다시 받는다
- [x] 빈칸이 채워질 때까지 같은 연결의 요청 10개가 모두 멈춘다
- [ ] 멀티플렉싱 덕분에 아무 영향이 없다

모두 멈춥니다. HTTP/2는 요청을 섞어 보내지만 그 아래 TCP는 바이트를 순서대로만 넘기므로, 빈칸 하나가 모든 스트림을 막습니다(12장의 헤드 오브 라인 블로킹). HTTP/3는 QUIC이 스트림마다 따로 순서를 챙겨 그 요청만 멈춥니다.
:::

## 암호의 기초

HTTPS가 하는 일을 이해하려면 암호 도구 네 가지를 알아야 합니다. HTTPS가 지키려는 것은 세 가지입니다. 남이 내용을 못 보게(기밀성), 도중에 바뀌지 않게(무결성), 상대가 진짜 그 사이트인지(인증).

- **[[대칭키 암호]]**: 같은 키로 잠그고 엽니다. AES, ChaCha20. 아주 빠릅니다. 문제는 그 키를 상대에게 어떻게 안전하게 건네느냐입니다. 키를 인터넷으로 보내면 엿듣는 사람도 키를 얻습니다.
- **[[공개키 암호]]**: 키가 짝으로 있습니다. 공개키로 잠근 것은 짝인 개인키로만 열리고, 개인키로 서명한 것은 공개키로 누구나 확인할 수 있습니다. RSA, 타원 곡선(ECDSA, X25519). 공개키는 마음껏 퍼뜨려도 됩니다. 대신 대칭키보다 수천 배 느립니다.
- **[[키 교환]]**: 엿듣는 사람이 있는 길 위에서도, 두 사람이 각자 비밀 값을 섞어 주고받는 것만으로 둘만 아는 같은 값을 만들어 내는 방법입니다(디피-헬먼). 엿듣는 사람은 섞인 값만 보고는 결과를 계산할 수 없습니다. 이렇게 만든 값으로 대칭키를 만듭니다.
- **[[해시 함수]]**: 아무 길이의 데이터를 고정 길이(SHA-256은 32바이트)의 지문으로 바꿉니다. 같은 입력은 늘 같은 지문, 한 비트만 달라도 완전히 다른 지문이 나오고, 지문에서 원래 데이터를 되돌릴 수 없습니다. Git 커밋 해시, 파일 무결성 확인, 비밀번호 저장(bcrypt, argon2처럼 일부러 느린 해시)에 씁니다.
- **[[디지털 서명]]**: 데이터의 해시를 개인키로 서명하면, 누구나 공개키로 "이 데이터는 그 개인키 주인이 서명했고 그 뒤로 바뀌지 않았다"를 확인할 수 있습니다. 5장의 코드 서명, 3장의 Secure Boot, 아래의 인증서가 모두 이것입니다.

HTTPS는 이 도구들을 이렇게 조합합니다. 공개키 암호와 서명으로 상대가 진짜인지 확인하고, 키 교환으로 둘만의 대칭키를 만든 뒤, 실제 데이터는 빠른 대칭키 암호로 주고받습니다.

## 인증서와 인증 기관

키 교환으로 비밀 통로를 만들어도, 그 상대가 진짜 `naver.com`이 아니라 중간에 끼어든 공격자라면 소용이 없습니다. 공격자도 자기 공개키를 내밀며 "내가 naver.com"이라고 할 수 있으니까요. 그래서 "이 공개키는 정말 naver.com의 것"이라고 믿을 만한 제3자가 보증해 줘야 합니다.

그 보증서가 [[인증서]]입니다. 인증서에는 도메인 이름, 그 도메인의 공개키, 유효 기간, 발급자가 적혀 있고, 발급자가 디지털 서명을 해 두었습니다. 발급자가 [[인증 기관]](CA)입니다. Let's Encrypt, DigiCert, Sectigo, Google Trust Services 등이 있습니다.

그럼 인증 기관은 누가 보증할까요? 사슬로 올라갑니다.

```text 인증서 체인
naver.com 인증서        ← 중간 CA가 서명
  └ 중간 CA 인증서       ← 루트 CA가 서명
      └ 루트 CA 인증서    ← 자기가 자기를 서명. 운영체제와 브라우저에 미리 들어 있음
```

[[인증서 체인]]의 꼭대기인 루트 인증서는 운영체제와 브라우저가 미리 들고 있는 "믿는 목록"에 들어 있습니다. 브라우저는 서버가 보낸 인증서에서 시작해 서명을 하나씩 확인하며 올라가, 믿는 루트에 닿으면 통과시킵니다. 도메인 이름이 다르거나, 기간이 지났거나, 믿는 루트에 닿지 못하면 "연결이 비공개로 설정되어 있지 않습니다" 경고가 뜹니다.

인증 기관은 인증서를 내주기 전에 신청자가 정말 그 도메인의 주인인지 확인합니다. 그 도메인의 웹 서버에 정해진 파일을 올리게 하거나, DNS에 정해진 TXT 레코드를 넣게 하는 식입니다(13장). [[Let's Encrypt]]는 이 확인과 발급을 자동으로, 무료로 해 줍니다. 16장에서 서버에 HTTPS를 붙일 때 다시 봅니다.

## TLS 핸드셰이크

[[TLS]]는 TCP 연결 위에서 위의 일을 하는 프로토콜입니다. 예전 이름인 SSL로도 많이 부릅니다. 연결 직후 [[TLS 핸드셰이크]]로 상대를 확인하고 키를 정합니다. 요즘 쓰는 TLS 1.3의 흐름입니다.

![이 페이지를 열 때의 TLS 1.3 핸드셰이크. 왕복 한 번으로 상대를 확인하고 대칭키를 정한 뒤, 브라우저의 마지막 메시지와 함께 첫 HTTP 요청이 갑니다](http-tls.svg)

- **1 RTT**: 핸드셰이크가 한 번의 왕복으로 끝납니다. TLS 1.2는 두 번이었습니다. 그래서 새 HTTPS 연결은 TCP 1 RTT + TLS 1 RTT, 데이터 요청까지 최소 3 RTT가 듭니다(26장).
- **0-RTT 재접속**: 최근에 접속했던 서버라면 저장해 둔 키로 첫 메시지에 바로 데이터를 실어 보낼 수 있습니다. 대신 공격자가 그 메시지를 다시 보내는 재전송 공격이 가능해서 GET처럼 안전한 요청에만 씁니다.
- **[[전방 비밀성]]**: 매 연결마다 새 키 교환 값을 쓰고 버립니다. 나중에 서버의 개인키가 털려도 지난 대화를 풀 수 없습니다.
- **[[SNI]]**: ClientHello에 접속하려는 도메인 이름을 적습니다. IP 하나에 사이트가 여럿이니 서버가 어느 인증서를 내밀지 알아야 하기 때문입니다. 가상 호스팅의 TLS 판입니다. 이 이름은 암호화되기 전에 보내져서 길 위에서 보입니다. 한국에서도 2019년부터 불법 사이트 차단에 SNI를 보는 방식을 써 왔습니다. 이를 암호화하는 ECH라는 확장이 퍼지고 있습니다.
- **ALPN**: 위에서 본 HTTP 버전 고르기입니다.

:::quiz tls-rtts DNS 답은 이미 캐시에 있습니다. 새 HTTPS 연결(TCP 위의 TLS 1.3)로 HTML을 요청해 응답이 오기 시작하기까지 최소 몇 번 왕복할까요?
= 3 | 3번 | 세번

**3번**입니다. TCP 핸드셰이크 1번, TLS 핸드셰이크 1번, 그리고 HTTP 요청과 응답 1번입니다. HTTP/3(QUIC)는 앞의 둘을 합쳐 2번, 최근에 접속한 서버라면 0-RTT로 1번에 끝냅니다.
:::

## HTTPS가 지켜 주는 것과 못 지키는 것

| 지켜 줌 (암호화됨) | 지키지 못함 (길 위에서 보임) |
| --- | --- |
| 요청 경로와 쿼리, 헤더, 쿠키 | 접속하는 서버의 IP 주소 |
| 요청과 응답 본문 | SNI의 도메인 이름 (ECH가 없으면) |
| 내용이 도중에 바뀌지 않았다는 것 | DNS 조회 (DoH가 없으면) |
| 상대가 진짜 그 도메인이라는 것 | 주고받은 시각과 데이터 크기 |

처음 접속을 `http://`로 하면 그 첫 요청은 암호화되지 않아 중간에서 가로챌 수 있습니다. 그래서 서버는 응답에 [[HSTS]] 헤더(`Strict-Transport-Security: max-age=31536000`)를 붙여 "앞으로 1년 동안은 처음부터 HTTPS로 와라"라고 알리고, 브라우저는 그 뒤로 `http://`를 쳐도 스스로 `https://`로 바꿔 보냅니다. 이 사이트의 Caddy 설정에도 이 헤더가 있습니다. 브라우저에 미리 들어 있는 HSTS 목록(preload)에 올라간 도메인은 첫 접속부터 HTTPS입니다.

HTTPS 페이지가 `http://`로 이미지나 스크립트를 불러오는 것을 [[혼합 콘텐츠]]라고 하고, 브라우저가 막거나 자동으로 `https://`로 바꿉니다.

## 다시 장면으로: 3부를 마치며

9장 맨 앞 그림의 화살표 여덟 개를 모두 풀었습니다. 왕복 1에서 브라우저는 캐시를 거쳐 통신사의 리졸버에게 이름을 물었습니다(13장). 왕복 2에서 임시 포트로 SYN을 보내 연결을 맺었습니다(12장). 왕복 3에서 ClientHello에 이름을 적어 Caddy의 인증서를 받고 대칭키를 만들었고, 왕복 4에서 `GET /http/`를 보내 HTML을 받았습니다(이 장). 그 모든 메시지는 IP 패킷이 되어 공유기의 NAT와 수십 개의 라우터를 지났고(11장), 구간마다 새 프레임에 실렸습니다(10장).

3부는 여기서 끝납니다. 노트북을 떠나 서버의 443번 포트까지 왔습니다. 그런데 그 너머는 아직 상자 몇 개로만 그렸습니다. Caddy는 왜 앞에 서서 TLS를 풀고 `Host`로 요청을 나눌까요? 서버 컴퓨터는 어디에 있고, 무엇이 그 컴퓨터를 서버로 만들까요? 내 노트북에서도 서버를 열 수 있을까요? 4부는 선의 반대편, 서버로 건너갑니다.

## 세 운영체제의 인증서 저장소

| | Windows | macOS | Linux |
| --- | --- | --- | --- |
| 믿는 루트 목록 | 인증서 저장소 (`certmgr.msc`) | 키체인 접근 앱의 시스템 루트 | `/etc/ssl/certs`, `ca-certificates` 패키지 |
| 사내 인증서 추가 | 인증서 가져오기 마법사, 그룹 정책 | 키체인에 추가 후 "항상 신뢰" | `/usr/local/share/ca-certificates/`에 넣고 `update-ca-certificates` |
| 누가 이 목록을 쓰나 | Edge, Chrome, 대부분의 앱 | Safari, Chrome, 대부분의 앱 | curl, 대부분의 프로그램 |

Firefox와 Node는 운영체제 목록 대신 자기만의 루트 목록을 들고 다닙니다. 회사 보안 프록시가 모든 HTTPS를 자기 인증서로 다시 감싸는 환경에서 브라우저는 되는데 `npm install`이 `UNABLE_TO_GET_ISSUER_CERT_LOCALLY`로 실패하는 이유입니다. `NODE_EXTRA_CA_CERTS` 환경 변수로 회사 인증서를 추가하거나, 최근 Node의 `--use-system-ca` 옵션으로 운영체제 목록을 쓰게 합니다.

## 프론트엔드와 이어지는 곳

- 빌드 결과의 해시 붙은 파일은 1년 `immutable`, HTML은 `no-cache`가 기본 캐시 전략입니다. 배포했는데 사용자에게 옛 화면이 보이면 HTML의 캐시 설정부터 봅니다.
- CORS 오류는 서버가 허락하지 않은 것입니다. 개발 중에는 Vite의 `server.proxy`로 같은 출처를 흉내 내 피하고, 운영에서는 서버의 허락 목록을 고칩니다.
- 서비스 워커, 클립보드, 위치 정보, 카메라 같은 API는 HTTPS(보안 컨텍스트)에서만 됩니다. `localhost`는 예외로 보안 컨텍스트로 쳐 줍니다. 휴대폰에서 LAN IP로 개발 서버를 열면 이 API들이 안 되는 이유입니다. 로컬에서 진짜 HTTPS가 필요하면 `mkcert`로 내 컴퓨터만 믿는 인증서를 만듭니다.
- `fetch`가 502, 504를 받으면 프론트가 아니라 서버나 프록시 쪽 문제입니다. 413이면 업로드 크기 제한입니다.
- 로그인 쿠키에는 `HttpOnly`, `Secure`, `SameSite`를 꼭 붙입니다.

## 용어 정리

:::terms
- HTTP (HyperText Transfer Protocol) — 클라이언트의 요청과 서버의 응답으로 이루어진 웹의 응용 계층 프로토콜. 기본적으로 무상태입니다.
- HTTPS — TLS로 암호화하고 서버를 인증한 연결 위의 HTTP. 기본 포트는 443입니다.
- 요청 (request) — 클라이언트가 서버에 보내는 HTTP 메시지. 메서드, 경로, 헤더, 본문으로 되어 있습니다.
- 응답 (response) — 서버가 요청에 대해 돌려주는 HTTP 메시지. 상태 코드, 헤더, 본문으로 되어 있습니다.
- 무상태 (stateless) — 서버가 앞의 요청을 기억하지 않고 요청마다 독립적으로 처리하는 성질입니다.
- URL (Uniform Resource Locator) — 스킴, 호스트, 포트, 경로, 쿼리, 프래그먼트로 자원의 위치를 나타내는 주소. 프래그먼트(`#` 뒤)는 서버로 보내지 않습니다.
- HTTP 메서드 (HTTP method) — 요청의 의도를 나타내는 이름. GET, POST, PUT, PATCH, DELETE 등.
- 멱등성 (idempotency) — 같은 요청을 여러 번 보내도 한 번 보낸 것과 결과가 같은 성질. GET, PUT, DELETE는 멱등하고 POST는 아닙니다.
- 상태 코드 (status code) — 응답의 결과를 나타내는 세 자리 숫자. 2xx 성공, 3xx 이동, 4xx 요청 쪽 오류, 5xx 서버 쪽 오류.
- HTTP 헤더 (HTTP header) — 요청과 응답에 붙는 "이름: 값" 형태의 부가 정보입니다.
- 가상 호스팅 (virtual hosting) — IP 하나의 서버가 `Host` 헤더(TLS에서는 SNI)를 보고 여러 사이트를 나눠 처리하는 것입니다.
- MIME 타입 (MIME type) — `text/html`, `image/png`처럼 데이터의 종류를 알리는 이름. HTTP의 `Content-Type` 헤더에 씁니다.
- 쿠키 (cookie) — 서버가 `Set-Cookie`로 저장시키고 브라우저가 이후 요청마다 `Cookie`로 자동으로 보내는 작은 데이터입니다.
- 세션 (session) — 서버가 쿠키의 세션 ID로 찾아보는, 사용자별 상태(로그인 등)의 서버 쪽 기록입니다.
- HTTP 캐시 (HTTP cache) — 브라우저와 CDN이 응답을 저장해 두고 다시 쓰는 것. `Cache-Control`, `ETag` 헤더로 조절합니다.
- ETag — 응답 내용의 지문. 다음 요청의 `If-None-Match`와 비교해 바뀌지 않았으면 서버가 304로 답합니다.
- 출처 (origin) — 스킴, 호스트, 포트의 조합. 셋이 모두 같아야 같은 출처입니다.
- 동일 출처 정책 (same-origin policy) — 한 출처의 스크립트가 다른 출처의 응답을 마음대로 읽지 못하게 하는 브라우저의 보안 규칙입니다.
- CORS (Cross-Origin Resource Sharing) — 서버가 응답 헤더로 특정 출처의 스크립트에게 자기 응답을 읽도록 허락하는 방법입니다.
- 프리플라이트 (preflight) — 단순하지 않은 교차 출처 요청 전에 브라우저가 OPTIONS로 허락을 먼저 묻는 요청입니다.
- HTTP/2 — 바이너리 프레임과 멀티플렉싱으로 TCP 연결 하나에 요청 여러 개를 동시에 보내는 HTTP 버전입니다.
- HTTP/3 — QUIC 위에서 동작해 TCP의 헤드 오브 라인 블로킹을 없앤 HTTP 버전입니다.
- 멀티플렉싱 (multiplexing) — 연결 하나에 여러 요청과 응답을 잘게 쪼개 섞어 동시에 보내는 것입니다.
- 대칭키 암호 (symmetric encryption) — 같은 키로 암호화하고 복호화하는 방식. AES, ChaCha20. 빠르지만 키를 나누는 문제가 있습니다.
- 공개키 암호 (public-key cryptography) — 공개키와 개인키 짝을 쓰는 방식. 공개키는 퍼뜨리고 개인키는 숨깁니다. RSA, 타원 곡선 암호.
- 키 교환 (key exchange) — 엿듣는 사람이 있는 통로에서도 두 쪽이 같은 비밀 값을 만들어 내는 방법. 디피-헬먼(ECDHE)이 대표적입니다.
- 해시 함수 (hash function) — 데이터를 고정 길이의 지문으로 바꾸는 함수. 되돌릴 수 없고, 입력이 조금만 달라도 결과가 완전히 달라집니다. SHA-256 등.
- 디지털 서명 (digital signature) — 데이터의 해시를 개인키로 서명해, 공개키로 누가 서명했고 바뀌지 않았음을 확인하게 하는 것입니다.
- 인증서 (certificate) — 도메인 이름과 공개키, 유효 기간을 담고 인증 기관이 서명한 문서. 이 공개키가 그 도메인의 것임을 보증합니다.
- 인증 기관 (CA, Certificate Authority) — 도메인 소유를 확인하고 인증서에 서명해 주는 기관. Let's Encrypt, DigiCert 등.
- 인증서 체인 (certificate chain) — 사이트 인증서에서 중간 CA를 거쳐 운영체제나 브라우저가 믿는 루트 인증서까지 서명으로 이어진 사슬입니다.
- TLS (Transport Layer Security) — 연결을 암호화하고 상대를 인증하는 프로토콜. 예전 이름은 SSL입니다.
- TLS 핸드셰이크 (TLS handshake) — TLS 연결 시작 때 암호 방식을 정하고, 인증서로 서버를 확인하고, 키 교환으로 대칭키를 만드는 과정. TLS 1.3은 1 RTT입니다.
- 전방 비밀성 (forward secrecy) — 연결마다 새 키 교환 값을 쓰고 버려, 나중에 개인키가 유출돼도 지난 통신을 풀 수 없게 하는 성질입니다.
- SNI (Server Name Indication) — TLS 핸드셰이크 첫 메시지에 접속하려는 도메인 이름을 적는 확장. 서버가 맞는 인증서를 고르게 합니다.
- HSTS (HTTP Strict Transport Security) — 서버가 브라우저에게 정해진 기간 동안 HTTPS로만 접속하라고 알리는 헤더입니다.
- 혼합 콘텐츠 (mixed content) — HTTPS 페이지가 HTTP로 불러오는 자원. 브라우저가 막거나 HTTPS로 바꿉니다.
:::

## 직접 해보기

:::practice curl-v curl로 HTTP 대화 그대로 보기
`curl -v`로 요청과 응답의 헤더를 모두 보고, TLS 핸드셰이크 정보(버전, 인증서 발급자, ALPN으로 고른 HTTP 버전)를 찾습니다. 같은 요청을 HTTP/1.1로 강제했을 때와 비교합니다. Windows에서는 `curl.exe`로 씁니다.

```sh 터미널
curl -v https://example.com -o /dev/null 2>&1 | grep -E "^[<>*]" | head -40
curl -sI https://www.google.com            # 응답 헤더만
curl -sI --http1.1 https://www.google.com | head -1
curl -sI -H "Accept-Encoding: br" https://www.google.com | grep -i content-encoding
```
:::

:::practice raw-http 손으로 HTTP 요청 보내기
TCP 연결만 열어 HTTP 요청을 직접 타이핑해 봅니다. HTTP가 정말 글자로 된 대화라는 걸 확인합니다. 마지막에 빈 줄(엔터 두 번)을 쳐야 서버가 답합니다.

```sh macOS · Linux
nc example.com 80
GET / HTTP/1.1
Host: example.com

```

```sh 터미널 (HTTPS, 어디서나)
openssl s_client -connect example.com:443 -servername example.com -quiet
GET / HTTP/1.1
Host: example.com
Connection: close

```
:::

:::practice cert 인증서 체인 직접 확인하기
브라우저 주소창의 자물쇠를 눌러 인증서를 열고, 사이트 인증서 → 중간 CA → 루트 CA 순서와 각각의 유효 기간을 적습니다. 터미널에서도 같은 걸 봅니다. 그리고 내 운영체제의 루트 목록에서 그 루트 CA를 찾아봅니다.

```sh 터미널
openssl s_client -connect www.naver.com:443 -servername www.naver.com -showcerts </dev/null 2>/dev/null | grep -E "^ *[0-9] s:|i:"
echo | openssl s_client -connect www.naver.com:443 -servername www.naver.com 2>/dev/null | openssl x509 -noout -dates -issuer -subject
```
:::

:::practice cache-headers 캐시와 304 관찰하기
아무 사이트에서 DevTools Network 탭을 열고 새로고침을 두 번 합니다. 해시가 붙은 JS, CSS 파일과 HTML의 `Cache-Control` 응답 헤더를 비교하고, 두 번째에 "(memory cache)", "(disk cache)", "304"가 각각 어느 파일에 나오는지 봅니다. `curl`로 ETag를 받아 조건부 요청도 직접 해 봅니다.

```sh 터미널
ETAG=$(curl -sI https://example.com | grep -i '^etag' | cut -d' ' -f2 | tr -d '\r')
curl -sI -H "If-None-Match: $ETAG" https://example.com | head -1   # 304가 나오면 성공
```
:::

:::practice cors CORS 오류 만들고 고치기
두 포트에 서버를 띄워 다른 출처를 만들고, 브라우저에서 CORS 오류를 직접 본 뒤 헤더 한 줄로 고칩니다. 같은 요청을 `curl`로 보내면 막히지 않는다는 것도 확인합니다.

```js cors.mjs
import http from "node:http";
http.createServer((req, res) => {
  // 아래 줄을 지웠다 살렸다 하며 비교합니다
  res.setHeader("Access-Control-Allow-Origin", "http://localhost:5000");
  res.setHeader("Content-Type", "application/json");
  res.end(JSON.stringify({ ok: true }));
}).listen(4000);
http.createServer((req, res) => {
  res.setHeader("Content-Type", "text/html; charset=utf-8");
  res.end(`<script>fetch("http://localhost:4000").then(r => r.json()).then(d => document.body.textContent = JSON.stringify(d), e => document.body.textContent = e)</script>`);
}).listen(5000);
console.log("http://localhost:5000 을 열어 보세요");
```

## 장 전체 문제

:::quiz first-visit 이 페이지를 처음 열 때 일어나는 일을 순서대로 맞게 적은 것은?
- [ ] TCP 핸드셰이크 → DNS 조회 → TLS 핸드셰이크 → `GET /http/`
- [x] DNS 조회 → TCP 핸드셰이크 → TLS 핸드셰이크 → `GET /http/`
- [ ] DNS 조회 → TLS 핸드셰이크 → TCP 핸드셰이크 → `GET /http/`
- [ ] TLS 핸드셰이크 → DNS 조회 → TCP 핸드셰이크 → `GET /http/`

DNS → TCP → TLS → HTTP입니다. 연결하려면 IP가 있어야 하고(DNS), TLS는 TCP 연결 위에서 하고, HTTP 요청은 TLS로 감싼 통로 안으로 보냅니다. 9장 맨 앞 그림의 왕복 1~4가 이 순서입니다.
:::

:::quiz same-conn HTML을 받은 뒤 브라우저가 같은 사이트의 `/assets/style.….css`를 요청합니다. 이번에는 무엇을 다시 하지 않아도 될까요?
- [ ] 셋 다 다시 한다: 파일마다 새 연결이 필요하다
- [ ] DNS 조회만 건너뛰고 TCP와 TLS는 다시 한다
- [ ] TLS만 다시 한다
- [x] DNS, TCP, TLS 모두 건너뛰고 열린 연결로 바로 요청한다

같은 출처이니 이미 열린 연결을 재사용합니다. DNS 답은 캐시에 있고, TCP와 TLS는 맺어 둔 그대로입니다. HTTP/2라면 CSS와 JS 요청을 그 연결 하나에 섞어 동시에 보냅니다. 남는 건 요청과 응답 왕복 하나뿐입니다.
:::

## 스스로 점검

:::qa URL의 `#` 뒷부분은 서버로 전달되나요? 이 사실이 SPA 라우팅과 어떤 관계가 있나요?
전달되지 않습니다. 브라우저 안에서만 씁니다. 그래서 해시 라우팅(`/#/posts/1`)은 서버가 늘 같은 HTML만 주면 되고, 경로 라우팅(`/posts/1`)은 서버가 모든 경로에 같은 HTML을 주도록 설정(SPA fallback)해야 새로고침해도 404가 나지 않습니다.
:::

:::qa POST 요청의 응답을 못 받고 연결이 끊겼습니다. 그냥 다시 보내도 될까요? PUT이라면?
POST는 멱등하지 않아 이미 처리됐다면 다시 보낼 때 주문 같은 일이 두 번 일어날 수 있습니다. 멱등성 키 같은 장치가 없으면 함부로 다시 보내지 않습니다. PUT은 같은 내용으로 통째로 바꾸는 것이라 여러 번 보내도 결과가 같으니 다시 보내도 됩니다.
:::

:::qa 같은 API 요청이 curl에서는 되는데 브라우저 `fetch`에서만 CORS 오류가 납니다. 왜이고, 어디를 고쳐야 하나요?
CORS는 브라우저가 다른 출처의 응답을 JS에 넘겨도 되는지 확인하는 규칙이라 curl은 신경 쓰지 않습니다. 서버가 `Access-Control-Allow-Origin` 등으로 그 출처를 허락해야 하므로, 서버의 응답 헤더를 고치거나 같은 출처의 프록시를 둡니다. 프론트 코드로는 고칠 수 없습니다.
:::

:::qa 빌드한 JS 파일에는 1년 캐시를, HTML에는 `no-cache`를 거는 이유는?
JS와 CSS는 파일 이름에 내용 해시가 들어 있어서 내용이 바뀌면 이름도 바뀌니 같은 이름은 영원히 같은 내용입니다. HTML은 이름이 늘 같으니 매번 서버에 확인하고, 새 HTML이 새 해시 이름의 파일을 가리키게 해서 배포가 바로 반영되게 합니다.
:::

:::qa HTTPS에서 공개키 암호와 대칭키 암호를 둘 다 쓰는 이유는?
공개키 암호는 키를 미리 나누지 않아도 서명으로 상대를 확인하고 키 교환으로 비밀 값을 만들 수 있지만 느립니다. 대칭키 암호는 빠르지만 키를 나누는 문제가 있습니다. 그래서 핸드셰이크에서만 공개키 쪽 기술로 인증과 키 합의를 하고, 실제 데이터는 그 키로 대칭 암호화합니다.
:::

:::qa 브라우저가 `naver.com`의 인증서를 믿어도 된다고 판단하는 과정은?
서버가 보낸 인증서의 도메인 이름이 접속한 이름과 맞는지, 유효 기간 안인지 보고, 중간 CA 인증서의 공개키로 서명을 확인하고, 다시 루트 CA의 공개키로 중간 CA의 서명을 확인합니다. 그 루트가 운영체제나 브라우저의 믿는 목록에 있으면 통과입니다. 그다음 핸드셰이크의 서명으로 서버가 그 인증서의 개인키를 가졌는지 확인합니다.
:::

:::qa 리버스 프록시 뒤에 있는 서비스에서 502와 504는 각각 무엇을 뜻하나요?
502 Bad Gateway는 프록시가 뒤의 서버에 연결하지 못했거나 이상한 답을 받은 것으로, 대개 앱이 죽었거나 떠 있지 않습니다. 504 Gateway Timeout은 연결은 됐지만 앱이 정해진 시간 안에 답하지 않은 것으로, 앱이 너무 느리거나 멈춘 경우입니다.
:::
