21장은 데이터를 담고 찾는 법이었습니다. 이 장은 데이터베이스가 정말 어려운 일을 하는 부분입니다. 계좌 이체 도중에 서버가 꺼지면? 두 사람이 마지막 남은 좌석을 동시에 예매하면? 이 문제들은 6장의 경쟁 조건과 8장의 fsync를 데이터베이스 규모로 키운 것입니다. 데이터베이스가 이걸 대신 풀어 주는 덕분에, 앱 개발자는 대부분의 경우 코드 몇 줄로 안전한 서비스를 만들 수 있습니다.

## 트랜잭션: 전부 되거나, 전부 안 되거나

민수가 지은에게 1만 원을 보낸다면 두 가지 일이 함께 일어나야 합니다.

```sql
UPDATE accounts SET balance = balance - 10000 WHERE id = 'minsu';
UPDATE accounts SET balance = balance + 10000 WHERE id = 'jieun';
```

첫 줄만 실행되고 서버가 죽으면 1만 원이 사라집니다. 둘 사이에 누군가 두 계좌의 합을 읽으면 1만 원이 모자란 이상한 순간을 봅니다. 그래서 여러 작업을 하나로 묶어 "전부 성공하거나 전부 없던 일이 되게" 합니다. 이 묶음이 [[트랜잭션]]입니다.

```sql
BEGIN;
UPDATE accounts SET balance = balance - 10000 WHERE id = 'minsu';
UPDATE accounts SET balance = balance + 10000 WHERE id = 'jieun';
COMMIT;      -- 확정. 문제가 있으면 ROLLBACK으로 둘 다 취소
```

## ACID

데이터베이스가 트랜잭션에 약속하는 네 가지를 머리글자로 [[ACID]]라고 합니다.

| 성질 | 약속 | 지키는 장치 |
| --- | --- | --- |
| [[원자성]] (Atomicity) | 트랜잭션은 전부 되거나 전부 안 된다 | 로그와 되돌리기 |
| [[일관성]] (Consistency) | 트랜잭션 전후에 정한 규칙(키, 제약)이 늘 지켜진다 | 제약 조건 검사 |
| [[격리성]] (Isolation) | 동시에 도는 트랜잭션들이 서로의 중간 상태를 보지 않는다 | 잠금, MVCC |
| [[지속성]] (Durability) | `COMMIT`이 성공했으면 서버가 꺼져도 사라지지 않는다 | WAL과 fsync |

## 죽어도 잃지 않는 법: 선행 기록 로그

8장에서 `write`는 페이지 캐시에 적기만 하고, 디스크에 닿는 건 나중이라고 했습니다. 데이터베이스가 바꾼 페이지를 `COMMIT`마다 디스크 여기저기에 바로 쓰면 너무 느리고, 쓰는 도중 꺼지면 반쯤 바뀐 페이지가 남습니다.

그래서 데이터베이스는 [[WAL]](선행 기록 로그)을 씁니다.

1. 바꿀 내용을 먼저 로그 파일 끝에 순서대로 덧붙여 적습니다. 끝에 덧붙이기는 디스크에서 가장 빠른 쓰기입니다.
2. `COMMIT`할 때 로그만 `fsync`로 디스크에 확실히 씁니다. 이게 끝나야 "성공"을 돌려줍니다.
3. 실제 데이터 페이지는 버퍼 풀(21장)에서 바꿔 두고, 나중에 모아서 디스크에 씁니다(체크포인트).
4. 서버가 죽었다 살아나면 로그를 처음부터 다시 따라가며, 커밋된 일은 다시 하고 커밋 안 된 일은 버립니다.

8장의 파일 시스템 저널링과 같은 생각입니다. 데이터베이스의 쓰기 속도가 결국 "로그를 얼마나 빨리 fsync하느냐"에 묶이는 이유이고, 여러 트랜잭션의 커밋을 모아 fsync 한 번에 처리하는(그룹 커밋) 최적화가 있는 이유입니다. PostgreSQL의 WAL, MySQL InnoDB의 redo 로그, SQLite의 WAL 모드가 모두 이것입니다. 이 장 뒤에서 볼 복제도 이 로그를 다른 서버에 보내는 방식으로 합니다.

## 동시에 쓰면 생기는 일들

트랜잭션들을 정말로 한 번에 하나씩만 돌리면 격리는 완벽하지만 느립니다. 그래서 데이터베이스는 동시에 돌리면서 "어느 정도까지 서로를 볼 수 있게 할지"를 [[격리 수준]]으로 고르게 합니다. 격리를 낮출수록 빠르지만 다음 이상한 일들이 생길 수 있습니다.

| 이상 현상 | 무슨 일 | 예 |
| --- | --- | --- |
| [[더티 리드]] | 아직 커밋 안 된 다른 트랜잭션의 값을 읽음 | 취소될 송금액을 잔액으로 보여 줌 |
| [[반복 불가능한 읽기]] | 같은 행을 두 번 읽었는데 그사이 남이 커밋해 값이 다름 | 보고서 앞뒤 숫자가 안 맞음 |
| [[팬텀 리드]] | 같은 조건으로 두 번 조회했는데 그사이 남이 행을 추가해 개수가 다름 | 합계를 내는 도중 새 주문이 끼어듦 |
| [[갱신 손실]] | 둘이 같은 값을 읽고 각자 고쳐 써서 한쪽 변경이 사라짐 | 좋아요 수가 동시에 눌린 만큼 안 늘어남 |
| 쓰기 왜곡 | 둘이 각자 조건을 확인하고 서로 다른 행을 바꿔, 합치면 규칙이 깨짐 | 당직 의사 둘이 동시에 "다른 사람이 있으니" 빠져서 아무도 없음 |

SQL 표준이 정한 격리 수준과 막아 주는 것입니다.

| 격리 수준 | 더티 리드 | 반복 불가능한 읽기 | 팬텀 | 기본값으로 쓰는 곳 |
| --- | --- | --- | --- | --- |
| Read Uncommitted | 생김 | 생김 | 생김 | 거의 안 씀 |
| Read Committed | 막음 | 생김 | 생김 | PostgreSQL, Oracle |
| Repeatable Read | 막음 | 막음 | 표준상 생김 (실제 구현은 대부분 막음) | MySQL InnoDB |
| Serializable | 막음 | 막음 | 막음 | SQLite (쓰기가 한 번에 하나라서) |

Serializable은 "동시에 돌렸지만 결과는 어떤 순서로 하나씩 돌린 것과 같다"를 보장합니다. 가장 안전하지만 충돌이 나면 트랜잭션 하나가 실패하니, 앱이 다시 시도할 준비를 해야 합니다. 대부분의 서비스는 기본값을 쓰다가 돈, 재고, 예약처럼 꼭 맞아야 하는 곳에서만 아래의 잠금이나 더 높은 격리를 씁니다.

## 잠금과 MVCC

격리를 지키는 방법은 크게 둘입니다.

**잠금**: 6장의 뮤텍스처럼 행에 자물쇠를 겁니다. 읽는 사람끼리는 함께 잡을 수 있는 공유 잠금, 쓰는 사람은 혼자만 잡는 배타 잠금을 씁니다. 쓰는 동안 다른 사람은 기다립니다. 확실하지만 기다림이 생기고, 6장의 [[데드락]]도 생깁니다. 데이터베이스는 데드락을 스스로 찾아내 한쪽 트랜잭션을 실패시키고, 앱은 그 트랜잭션을 다시 시도합니다.

**[[MVCC]]**(다중 버전 동시성 제어): 행을 고칠 때 덮어쓰지 않고 새 버전을 만듭니다. 각 트랜잭션은 자기가 시작한 시점의 스냅숏을 봅니다. 그래서 **읽기는 쓰기를 기다리지 않고, 쓰기도 읽기를 기다리지 않습니다.** PostgreSQL, MySQL InnoDB, Oracle이 모두 MVCC를 씁니다. 대가로 아무도 안 보는 옛 버전이 쌓이니 치우는 작업이 필요합니다. PostgreSQL의 VACUUM이 그 일입니다(7장의 가비지 컬렉션과 같은 생각).

## 갱신 손실을 막는 실전 방법

"재고가 1개 남은 상품을 두 사람이 동시에 산다"는 문제를 앱에서 푸는 방법들입니다.

**한 문장으로 확인과 변경을 함께**: 가장 간단하고 강력합니다. 데이터베이스가 행 하나를 바꾸는 동안은 그 행을 잠그니 둘이 동시에 성공할 수 없습니다.

```sql
UPDATE products SET stock = stock - 1 WHERE id = 7 AND stock >= 1;
-- 바뀐 행이 0개면 품절
```

**[[비관적 잠금]]**: "충돌이 날 것"이라고 보고 읽을 때부터 잠급니다.

```sql
BEGIN;
SELECT stock FROM products WHERE id = 7 FOR UPDATE;   -- 이 행을 잠금. 다른 트랜잭션은 기다림
-- 앱에서 확인하고 계산
UPDATE products SET stock = 6 WHERE id = 7;
COMMIT;
```

**[[낙관적 잠금]]**: "충돌은 드물 것"이라고 보고 잠그지 않되, 행에 버전 번호를 두고 쓸 때 확인합니다.

```sql
SELECT stock, version FROM products WHERE id = 7;      -- stock 7, version 3
UPDATE products SET stock = 6, version = 4 WHERE id = 7 AND version = 3;
-- 바뀐 행이 0개면 그사이 누가 먼저 고친 것. 다시 읽고 다시 시도
```

협업 문서나 게시글 편집처럼 사람이 오래 들고 있다가 저장하는 경우에 맞습니다. 웹에서는 14장의 `ETag`와 `If-Match` 헤더로 같은 일을 합니다. "다른 사람이 먼저 수정했습니다"라는 409 응답이 이것입니다.

## 복제: 데이터베이스를 여러 대로

데이터베이스 서버 한 대가 죽으면 서비스가 멈춥니다. 읽기 요청이 너무 많으면 한 대로 버티기 어렵습니다. 그래서 같은 데이터를 여러 서버에 복사해 둡니다. 이게 [[복제]]입니다.

가장 흔한 모양은 주 서버 하나와 [[읽기 복제본]] 여러 대입니다. 쓰기는 주 서버만 받고, 주 서버는 WAL을 복제본들에게 흘려보내고, 복제본들은 그 로그를 따라 같은 변경을 합니다. 읽기는 복제본들에 나눠 보냅니다. 주 서버가 죽으면 복제본 하나를 새 주 서버로 올립니다(장애 조치).

| | 동기 복제 | 비동기 복제 |
| --- | --- | --- |
| 커밋 성공을 언제 알리나 | 복제본도 받았다고 답한 뒤 | 주 서버에만 쓰고 바로 |
| 장점 | 주 서버가 죽어도 커밋한 데이터를 잃지 않음 | 빠름 |
| 단점 | 느리고, 복제본이 멈추면 쓰기도 멈춤 | 주 서버가 죽으면 마지막 몇 개를 잃을 수 있음 |

비동기 복제에서는 복제본이 주 서버보다 조금 늦습니다. 이 차이를 [[복제 지연]]이라고 합니다. 사용자가 글을 쓰고(주 서버) 바로 목록을 새로고침했는데(복제본) 방금 쓴 글이 없는 이상한 일이 생깁니다. 그래서 "자기가 방금 쓴 것은 주 서버에서 읽기" 같은 규칙을 둡니다. 24장의 일관성 이야기로 이어집니다.

## 샤딩: 데이터를 나눠 담기

복제는 같은 데이터를 여러 벌 두는 것이라 쓰기 양이나 데이터 크기는 줄지 않습니다. 데이터가 서버 한 대에 다 안 들어가거나 쓰기가 너무 많으면, 데이터를 쪼개 서로 다른 서버에 나눠 담습니다. 이걸 [[샤딩]]이라고 합니다.

- **키 범위로**: 사용자 ID 1~100만은 1번 서버, 그다음은 2번 서버. 범위 조회가 쉽지만 한쪽에 몰릴 수 있습니다.
- **해시로**: 사용자 ID의 해시를 서버 수로 나눈 나머지(18장의 해시 테이블과 같은 생각). 고르게 퍼지지만 서버를 늘리면 데이터를 다시 옮겨야 합니다(일관된 해싱으로 옮길 양을 줄입니다).

샤딩하면 여러 샤드에 걸친 조인과 트랜잭션이 아주 어려워집니다. 그래서 할 수 있는 한 미루고, 정말 필요할 때 "한 사용자의 데이터는 한 샤드에"처럼 함께 쓰는 데이터가 같은 샤드에 가도록 키를 고릅니다.

## 백업

복제는 백업이 아닙니다. 실수로 `DELETE FROM users`를 하면 복제본에서도 곧바로 지워집니다. 정기적으로 전체를 떠 두고, WAL을 계속 보관해 두면 "어제 오후 3시 12분 상태로" 되돌릴 수 있습니다(시점 복구). 백업은 실제로 복구해 보기 전까지는 있는 게 아니라는 말이 있습니다. 17장의 볼륨에 데이터를 둔 이 사이트의 API도 볼륨을 따로 백업해야 합니다.

## 관계형이 아닌 데이터베이스: NoSQL

관계형 데이터베이스는 대부분의 서비스에 맞지만, 모든 문제에 맞지는 않습니다. 정해진 스키마, 조인, 강한 일관성을 조금 내려놓는 대신 다른 장점을 얻는 데이터베이스들을 묶어 [[NoSQL]]이라고 부릅니다.

| 종류 | 데이터 모양 | 잘하는 것 | 예 |
| --- | --- | --- | --- |
| [[키-값 저장소]] | 키 → 값 | 아주 빠른 단순 조회, 캐시, 세션 | Redis(17장), DynamoDB, etcd |
| [[문서 데이터베이스]] | JSON 비슷한 문서 | 모양이 자주 바뀌거나 중첩된 데이터를 통째로 읽고 쓰기 | MongoDB, Firestore, CouchDB |
| 와이드 컬럼 | 행마다 다른 열, 거대한 표 | 엄청난 양의 쓰기, 시계열, 여러 데이터센터 | Cassandra, ScyllaDB, HBase |
| [[그래프 데이터베이스]] | 정점과 간선 (19장) | 관계를 여러 단계 따라가기 (친구의 친구, 추천) | Neo4j |
| 검색 엔진 | 문서 + [[역색인]] | 전문 검색, 관련도 순위, 오타 허용 | Elasticsearch, OpenSearch, Meilisearch |
| 시계열 | 시각 + 값 | 지표, 센서 데이터 | InfluxDB, TimescaleDB |
| 벡터 데이터베이스 | 숫자 벡터 | 의미가 비슷한 것 찾기 (AI 검색) | pgvector, Pinecone |

검색 엔진의 [[역색인]]은 책 뒤의 찾아보기를 단어마다 만든 것입니다. "단어 → 그 단어가 나오는 문서 목록"을 미리 만들어 두면, 21장에서 인덱스를 쓸 수 없던 `LIKE '%검색어%'` 같은 문제를 빠르게 풉니다. 한국어는 띄어쓰기만으로 단어가 나뉘지 않아 형태소 분석기나 글자 n개씩 자르기(n-gram)를 함께 씁니다.

많은 NoSQL은 여러 서버에 데이터를 나눠 두는 것을 처음부터 염두에 두고 만들었고, 그 대가로 24장의 [[CAP 정리]]에서 일관성 대신 가용성을 고르는 경우가 많습니다. 즉, 잠시 서로 다른 값이 보이더라도 결국 같아지는 [[최종적 일관성]]을 받아들입니다.

어느 쪽을 고를까요? 처음에는 PostgreSQL 같은 관계형 데이터베이스 하나로 시작하는 것이 거의 늘 맞습니다. PostgreSQL은 JSON 열, 전문 검색, 벡터 확장까지 지원해서 상당히 멀리까지 갑니다. 그러다 특정한 필요(캐시, 대량 검색, 초당 수십만 쓰기)가 분명해지면 그 일에 맞는 저장소를 옆에 더합니다.

## 프론트엔드와 이어지는 곳

- "저장했는데 새로고침하면 옛 값이 보여요"는 캐시(14장, 17장)나 복제 지연일 수 있습니다. 쓰고 나서 바로 읽는 화면은 서버가 방금 쓴 결과를 응답으로 돌려주게 하거나, 낙관적 업데이트로 화면을 먼저 바꿉니다.
- TanStack Query의 낙관적 업데이트는 이름처럼 "실패는 드물다"고 보고 화면을 먼저 바꾼 뒤, 실패하면 되돌립니다. 낙관적 잠금과 같은 사고방식입니다.
- 결제 버튼을 두 번 누르는 문제는 앱에서 버튼을 막는 것만으로는 부족하고, 서버가 멱등성 키(14장)나 유일 제약으로 같은 주문이 두 번 생기지 않게 막아야 합니다.
- Firebase Firestore 같은 서비스를 쓴다면, 그것이 문서 데이터베이스라 조인이 없고 데이터를 화면 모양에 맞게 중복해 두는 설계를 한다는 점을 알고 시작합니다.

## 용어 정리

:::terms
- 트랜잭션 (transaction) — 여러 데이터베이스 작업을 묶어 전부 확정(COMMIT)하거나 전부 취소(ROLLBACK)하게 하는 단위입니다.
- ACID — 트랜잭션이 지키는 원자성, 일관성, 격리성, 지속성의 머리글자입니다.
- 원자성 (atomicity) — 트랜잭션의 작업이 전부 되거나 전부 안 되는 성질입니다.
- 일관성 (consistency) — 트랜잭션 전후에 데이터베이스가 정한 규칙(키, 제약 조건)이 늘 지켜지는 성질입니다.
- 격리성 (isolation) — 동시에 실행되는 트랜잭션들이 서로의 중간 상태에 영향받지 않는 성질입니다.
- 지속성 (durability) — 커밋된 트랜잭션은 서버가 꺼져도 사라지지 않는 성질입니다.
- WAL (Write-Ahead Log) — 데이터를 바꾸기 전에 변경 내용을 로그에 먼저 순서대로 기록하는 방식. 장애 복구와 복제에 씁니다.
- 격리 수준 (isolation level) — 동시에 도는 트랜잭션끼리 어디까지 서로의 변경을 볼 수 있게 할지 정한 단계입니다.
- 더티 리드 (dirty read) — 아직 커밋되지 않은 다른 트랜잭션의 변경을 읽는 현상입니다.
- 반복 불가능한 읽기 (non-repeatable read) — 한 트랜잭션 안에서 같은 행을 두 번 읽었는데 그사이 다른 커밋으로 값이 달라지는 현상입니다.
- 팬텀 리드 (phantom read) — 같은 조건으로 두 번 조회했는데 그사이 다른 트랜잭션이 행을 추가하거나 지워 결과 행이 달라지는 현상입니다.
- 갱신 손실 (lost update) — 두 트랜잭션이 같은 값을 읽고 각자 고쳐 써서 한쪽의 변경이 사라지는 현상입니다.
- MVCC (Multi-Version Concurrency Control) — 행을 고칠 때 새 버전을 만들어 각 트랜잭션이 자기 시점의 스냅숏을 읽게 하는 방식. 읽기와 쓰기가 서로 기다리지 않습니다.
- 비관적 잠금 (pessimistic locking) — 충돌을 예상하고 읽을 때부터 행을 잠가 다른 트랜잭션을 기다리게 하는 방식입니다.
- 낙관적 잠금 (optimistic locking) — 잠그지 않고 버전 번호로 쓸 때 충돌을 확인해, 충돌하면 다시 시도하는 방식입니다.
- 복제 (replication) — 같은 데이터를 여러 데이터베이스 서버에 복사해 두는 것. 장애 대비와 읽기 분산에 씁니다.
- 읽기 복제본 (read replica) — 주 서버의 변경을 따라 받아 읽기 요청만 처리하는 복제 서버입니다.
- 복제 지연 (replication lag) — 비동기 복제에서 복제본이 주 서버의 최신 상태보다 늦은 정도입니다.
- 샤딩 (sharding) — 데이터를 키에 따라 쪼개 여러 데이터베이스 서버에 나눠 담는 것입니다.
- NoSQL — 관계형 모델 대신 키-값, 문서, 와이드 컬럼, 그래프 같은 모델을 쓰는 데이터베이스들을 묶어 부르는 말입니다.
- 키-값 저장소 (key-value store) — 키로 값을 넣고 꺼내는 가장 단순한 데이터베이스. Redis, DynamoDB.
- 문서 데이터베이스 (document database) — JSON 같은 문서를 통째로 저장하고 문서 안의 필드로 조회하는 데이터베이스. MongoDB, Firestore.
- 그래프 데이터베이스 (graph database) — 정점과 간선으로 데이터를 저장해 관계를 여러 단계 따라가는 질의에 강한 데이터베이스입니다.
- 역색인 (inverted index) — 단어마다 그 단어가 들어 있는 문서 목록을 저장한 색인. 검색 엔진의 핵심 구조입니다.
:::

## 직접 해보기

:::practice lost-update 갱신 손실을 만들고 막기
SQLite에 좋아요 수 행을 하나 만들고, Node로 "읽고 → 1 더해서 → 쓰기"를 동시에 100번 실행해 최종 값이 100보다 작게 나오는 걸 봅니다(비동기 사이사이에 끼어들도록 읽기와 쓰기 사이에 `await`를 둡니다). 그다음 `UPDATE likes SET n = n + 1`처럼 한 문장으로 바꿔 정확히 100이 나오는지 확인합니다.

```js likes.mjs
import { DatabaseSync } from "node:sqlite";   // Node 22.13 이상 (그 아래는 --experimental-sqlite)
const db = new DatabaseSync(":memory:");
db.exec("CREATE TABLE likes (id INTEGER PRIMARY KEY, n INTEGER); INSERT INTO likes VALUES (1, 0);");
const tick = () => new Promise((r) => setTimeout(r, Math.random() * 5));

async function readModifyWrite() {
  const { n } = db.prepare("SELECT n FROM likes WHERE id = 1").get();
  await tick();                                       // 그사이 다른 요청이 끼어듦
  db.prepare("UPDATE likes SET n = ? WHERE id = 1").run(n + 1);
}
await Promise.all(Array.from({ length: 100 }, readModifyWrite));
console.log("읽고 쓰기:", db.prepare("SELECT n FROM likes").get().n);

db.exec("UPDATE likes SET n = 0");
await Promise.all(Array.from({ length: 100 }, async () => { await tick(); db.exec("UPDATE likes SET n = n + 1 WHERE id = 1"); }));
console.log("한 문장:", db.prepare("SELECT n FROM likes").get().n);
```
:::

:::practice rollback 트랜잭션 되돌리기
SQLite 셸에서 송금 트랜잭션을 `BEGIN`으로 시작해 첫 `UPDATE`만 하고 `ROLLBACK`한 뒤 잔액이 그대로인지 확인합니다. 그다음 `CHECK (balance >= 0)` 제약을 건 테이블에서 잔액보다 큰 금액을 보내면 트랜잭션 전체가 실패하는지 봅니다(일관성).

```sql
CREATE TABLE accounts (id TEXT PRIMARY KEY, balance INTEGER CHECK (balance >= 0));
INSERT INTO accounts VALUES ('minsu', 30000), ('jieun', 0);
BEGIN;
UPDATE accounts SET balance = balance - 10000 WHERE id = 'minsu';
SELECT * FROM accounts;
ROLLBACK;
SELECT * FROM accounts;
UPDATE accounts SET balance = balance - 50000 WHERE id = 'minsu';   -- CHECK 제약 위반
```
:::

:::practice two-sessions 두 세션으로 격리 보기
PostgreSQL이 있다면(Docker: `docker run --rm -e POSTGRES_PASSWORD=pw -p 127.0.0.1:5432:5432 postgres`) `psql` 창 두 개를 열고, 한쪽에서 `BEGIN; UPDATE …`만 한 상태로 다른 쪽에서 같은 행을 `SELECT`(커밋 전 값이 안 보이는지)와 `UPDATE`(기다리는지) 해 봅니다. 한쪽을 `COMMIT`하면 기다리던 쪽이 어떻게 되는지 확인하고, `SELECT … FOR UPDATE`도 같은 방식으로 시험합니다.
:::

:::practice inverted-index 작은 역색인 만들기
문서 몇 개(이 책의 장 요약 문장들)를 공백으로 나눠 "단어 → 문서 번호 집합" `Map`을 만들고, 두 단어가 모두 들어간 문서를 집합의 교집합으로 찾는 작은 검색을 만듭니다. 한글에서 "서버를"과 "서버"가 다른 단어로 나뉘는 문제를 보고, 두 글자씩 자르기(바이그램)로 바꾸면 어떻게 되는지도 봅니다.
:::

## 스스로 점검

:::qa 송금 도중 서버가 꺼져도 돈이 사라지지 않는 이유를 트랜잭션과 WAL로 설명해 보세요.
두 UPDATE를 한 트랜잭션으로 묶으면, 데이터베이스는 변경을 먼저 WAL에 적고 COMMIT 때 로그를 fsync합니다. 커밋 전에 꺼지면 다시 켤 때 로그에 커밋 기록이 없으니 둘 다 버리고, 커밋 뒤에 꺼지면 로그를 따라 둘 다 다시 적용합니다. 어느 쪽이든 반만 된 상태는 남지 않습니다.
:::

:::qa 좋아요 수를 "읽고, 1 더하고, 쓰는" 코드가 동시 요청에서 틀리는 이유와 고치는 방법 두 가지는?
두 요청이 같은 값을 읽고 각자 1을 더해 쓰면 한쪽 변경이 사라지는 갱신 손실이 생깁니다. `UPDATE … SET n = n + 1`처럼 한 문장으로 바꾸거나, `SELECT … FOR UPDATE`로 행을 잠그거나, 버전 번호로 낙관적 잠금을 겁니다.
:::

:::qa MVCC를 쓰면 왜 읽기가 쓰기를 기다리지 않나요? 대가는?
행을 고칠 때 덮어쓰지 않고 새 버전을 만들고, 읽는 트랜잭션은 자기가 시작한 시점의 옛 버전을 보면 되기 때문입니다. 대가로 옛 버전들이 쌓여 공간을 차지하니 주기적으로 치워야 합니다(PostgreSQL의 VACUUM).
:::

:::qa 글을 쓰고 바로 새로고침했더니 방금 쓴 글이 목록에 없습니다. 데이터베이스 쪽에서 의심할 것은?
쓰기는 주 서버에, 목록 읽기는 비동기 읽기 복제본에 가는데 복제 지연 때문에 아직 반영이 안 된 경우입니다. 방금 쓴 사용자의 읽기는 잠시 주 서버로 보내는 식으로 "자기가 쓴 것은 읽히게" 합니다.
:::

:::qa 복제와 샤딩은 각각 무엇을 해결하나요?
복제는 같은 데이터를 여러 벌 두어 서버가 죽어도 버티게 하고 읽기를 나눠 처리합니다. 샤딩은 데이터를 나눠 서로 다른 서버에 두어, 한 대에 다 들어가지 않는 데이터 크기와 한 대로 감당 못 하는 쓰기 양을 해결합니다.
:::

:::qa 새 서비스를 시작할 때 MongoDB와 PostgreSQL 중 무엇으로 시작하는 게 보통 맞나요? 이유는?
대부분은 PostgreSQL 같은 관계형으로 시작하는 게 맞습니다. 데이터 사이의 관계, 트랜잭션, 제약 조건이 대부분의 서비스에 필요하고, PostgreSQL은 JSON과 전문 검색까지 지원합니다. 문서 데이터베이스는 데이터가 정말 문서 단위로 통째로 읽히고 모양이 자주 바뀌는 경우에 맞습니다.
:::
