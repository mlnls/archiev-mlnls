3장은 로그인하고 브라우저 아이콘을 누르는 데서 끝났습니다. 그 브라우저가 이 페이지를 띄웠고, 이제 맨 아래의 "다 읽었어요"를 누른다고 해 봅니다. 클릭 한 번이 브라우저에 전해지고, 기록이 SSD에 남기까지 이런 길을 지나갑니다.

![클릭 한 번이 SSD에 기록되기까지. 마우스는 인터럽트로 커널을 부르고, 브라우저는 시스템 콜로 커널을 부릅니다. 브라우저는 마우스도 SSD도 직접 만지지 않습니다](os-click-path.svg)

눈여겨볼 것은 브라우저가 하드웨어를 한 번도 직접 만지지 않는다는 점입니다. 마우스가 눌렸다는 사실도, SSD에 쓰는 일도 모두 가운데의 커널을 거칩니다. 부팅이 끝난 뒤로 브라우저든 VS Code든 Node 서버든, 모든 프로그램은 운영체제에 부탁해서만 일을 합니다. 이 장은 이 그림의 아래쪽 절반, 그 "부탁하는 구조"를 봅니다. 다음 네 장(프로그램, 프로세스, 메모리, 입출력)은 이 구조 위에서 운영체제가 각각의 자원을 어떻게 나눠 주는지 하나씩 자세히 봅니다.

## 운영체제가 없다면

운영체제 없이 프로그램을 돌린다고 생각해 봅니다.

- 파일 하나를 읽으려면 프로그램이 SSD 컨트롤러의 명령 형식을 알고, 몇 번 블록에 무엇이 있는지 직접 계산해야 합니다. SSD를 바꾸면 프로그램을 다시 짜야 합니다.
- 브라우저와 음악 앱이 같은 메모리 주소에 쓰면 서로의 데이터를 망가뜨립니다.
- 한 프로그램이 무한 루프에 빠지면 CPU를 돌려받을 방법이 없어 컴퓨터 전체가 멈춥니다.

[[운영체제]]는 이 세 문제를 풉니다.

1. **추상화**: 하드웨어의 복잡한 세부를 감추고 쓰기 쉬운 개념을 줍니다. 디스크 블록 대신 [[파일]], 네트워크 카드 레지스터 대신 [[소켓]], CPU 코어 대신 [[프로세스]]와 [[스레드]]를 줍니다.
2. **자원 나누기**: CPU 시간, 메모리, 디스크, 네트워크를 여러 프로그램에 공평하게 나눕니다.
3. **보호**: 프로그램끼리, 그리고 프로그램과 운영체제 사이에 벽을 세워 하나가 망가져도 나머지가 살아 있게 합니다. 사용자마다 권한도 나눕니다.

위 그림의 가운데 줄이 이 세 가지를 하는 곳입니다. 그 줄은 다른 줄과 무엇이 다를까요?

## 커널과 사용자 공간

운영체제라고 하면 바탕화면, 파일 탐색기, 설정 앱까지 떠올리지만, 진짜 핵심은 [[커널]]입니다. 커널은 부팅 때 메모리에 올라와 꺼질 때까지 머무르며 하드웨어를 직접 다루는 유일한 프로그램입니다. 나머지 모든 프로그램이 도는 곳을 [[사용자 공간]]이라고 부릅니다. Finder와 작업 표시줄도 사용자 공간의 평범한 프로그램입니다.

이 벽은 소프트웨어 약속이 아니라 CPU가 지킵니다. CPU에는 실행 모드가 있습니다.

| | [[커널 모드]] | [[사용자 모드]] |
| --- | --- | --- |
| x86 이름 | 링 0 | 링 3 |
| ARM 이름 | EL1 | EL0 |
| 할 수 있는 것 | 모든 명령어, 모든 메모리, 장치 직접 접근 | 일반 계산과 자기 메모리 접근만 |
| 여기서 도는 것 | 커널, 드라이버 | 브라우저, 에디터, Node, 모든 앱 |
| 잘못되면 | 컴퓨터 전체가 멈춤 | 그 프로그램만 죽음 |

![앱은 모두 위쪽 사용자 공간에 있고, 아래로 내려가는 길은 시스템 콜 하나뿐입니다. 장치를 직접 만지려 하면 CPU가 그 자리에서 막습니다](os-kernel-user.svg)

사용자 모드에서 장치를 직접 건드리는 명령어를 실행하거나 남의 메모리를 읽으려 하면, CPU가 그 자리에서 멈추고 커널을 부릅니다. 커널은 보통 그 프로그램을 죽입니다. 앱이 "예기치 않게 종료되었습니다"로 끝나도 컴퓨터는 멀쩡한 이유입니다.

반대로 커널 모드의 코드가 잘못되면 막아 줄 사람이 없습니다. 그래서 커널이나 드라이버가 죽으면 Windows는 파란 화면(BSOD), macOS와 Linux는 [[커널 패닉]]을 띄우고 재시작합니다.

## 시스템 콜: 커널에 부탁하는 창구

사용자 프로그램이 파일을 읽거나, 네트워크로 보내거나, 새 프로그램을 실행하려면 커널에 부탁해야 합니다. 이 부탁이 [[시스템 콜]]입니다.

1. 프로그램이 "몇 번 부탁(시스템 콜 번호)", "어떤 파일, 몇 바이트" 같은 인자를 레지스터에 넣습니다.
2. `syscall`(x86-64)이나 `svc`(ARM) 명령어를 실행합니다. CPU가 커널 모드로 바뀌고, 커널이 미리 정해 둔 입구로 건너뜁니다.
3. 커널이 인자를 검사하고(이 프로그램이 이 파일을 읽을 권한이 있나?) 일을 합니다.
4. 결과를 레지스터에 넣고 사용자 모드로 돌아갑니다.

![시스템 콜 한 번의 왕복. 진한 화살표에서 CPU가 커널 모드로 바뀌고, 돌아오는 화살표에서 다시 사용자 모드가 됩니다](os-syscall.svg)

자주 쓰는 시스템 콜은 몇십 개 안 됩니다. `open`, `read`, `write`, `close`(파일), `socket`, `connect`, `accept`, `send`, `recv`(네트워크), `fork`, `exec`, `exit`, `wait`(프로세스), `mmap`(메모리). 이 책에서 계속 나옵니다.

JS 코드도 결국 시스템 콜로 끝납니다. Node에서 `fs.readFile("a.txt")`를 부르면 이렇게 내려갑니다.

![`fs.readFile` 한 줄이 SSD까지 내려가는 길. libuv 아래에서 운영체제마다 갈라지고, 점선을 넘는 진한 화살표가 시스템 콜입니다](os-readfile.svg)

운영체제마다 시스템 콜을 노출하는 방식이 다릅니다.

| | Windows | macOS | Linux |
| --- | --- | --- | --- |
| 프로그램이 부르는 것 | Win32 API (`kernel32.dll`의 `CreateFileW` 등) | libSystem의 POSIX 함수 (`open` 등) | glibc나 musl의 POSIX 함수, 또는 시스템 콜 직접 |
| 실제 시스템 콜 | `ntdll.dll`의 Native API (`NtCreateFile`). 번호가 버전마다 바뀌어 직접 부르지 않음 | BSD 시스템 콜 + Mach 트랩. 직접 부르는 건 지원하지 않음 | 번호와 형식이 안정적으로 유지됨. Go처럼 직접 부르는 언어도 있음 |
| 시스템 콜 엿보기 | Process Monitor (Sysinternals) | `sudo fs_usage`, Instruments | `strace` |

시스템 콜은 공짜가 아닙니다. 모드를 바꾸고 인자를 검사하는 데 함수 호출보다 수십~수백 배 시간이 듭니다. 그래서 파일을 1바이트씩 `read`하면 느리고, 크게 한 번에 읽는 편이 빠릅니다. 이걸 줄이려는 장치가 8장의 [[버퍼]]입니다.

:::quiz read-cost 1MB 파일을 1바이트씩 `read`를 백만 번 불러 읽으면, 한 번에 크게 읽을 때보다 훨씬 느립니다. 주된 이유는?
- [ ] SSD가 1바이트 단위로는 읽지 못해 매번 실패하고 다시 읽어서
- [ ] JS 엔진이 1바이트마다 가비지 컬렉션을 돌려서
- [x] `read`마다 커널 모드로 넘어가고 인자를 검사하는 비용이 붙어서
- [ ] 커널이 한 프로그램의 시스템 콜을 1초에 몇 번까지만 받아 줘서

[[시스템 콜]]마다 커널 모드로 바꾸고 인자를 검사하는 고정 비용이 붙기 때문입니다. 이 비용은 함수 호출의 수십~수백 배라서, 백만 번 부르면 실제로 옮기는 데이터보다 드나드는 비용이 훨씬 커집니다. 그래서 크게 한 번에 읽거나 [[버퍼]]를 둡니다.
:::

시스템 콜은 프로그램이 커널을 부르는 문입니다. 그럼 반대로, 마우스나 네트워크 카드 같은 하드웨어가 커널에게 "일이 생겼다"고 알릴 때는 어떻게 할까요? 맨 앞 그림의 왼쪽 위, 클릭이 들어오는 길입니다.

## 인터럽트: 하드웨어가 커널을 부르는 방법

프로그램이 커널을 부르는 게 시스템 콜이라면, 하드웨어가 커널을 부르는 것은 [[인터럽트]]입니다.

키보드를 눌렀는지 알려면 CPU가 1초에 수천 번씩 "눌렸어?" 하고 물어볼 수도 있습니다(폴링). 하지만 그러면 CPU가 다른 일을 못 합니다. 대신 키보드가 눌렸을 때 CPU에 전기 신호를 보내게 합니다. CPU는 지금 하던 명령어를 마치고, 상태를 저장하고, 커널의 [[인터럽트 핸들러]]로 건너뜁니다. 핸들러가 일을 마치면 하던 일로 돌아갑니다.

인터럽트를 보내는 것들은 많습니다.

- 키보드, 마우스: 입력이 왔습니다.
- [[네트워크 인터페이스 카드]]: 패킷이 도착했습니다. 이 책 뒷부분에서 데이터가 내 컴퓨터에 "들어오는" 순간이 바로 이것입니다.
- 디스크: 부탁한 읽기가 끝났습니다.
- **타이머**: 정해진 시간(보통 수 밀리초)이 지났습니다.

타이머 인터럽트가 특히 중요합니다. 프로그램이 무한 루프를 돌아도 타이머 인터럽트가 오면 CPU는 강제로 커널로 넘어갑니다. 커널은 "이 프로그램은 충분히 썼으니 다른 프로그램 차례"라고 판단하고 바꿔 줍니다. 이게 6장의 [[선점형 스케줄링]]이고, 무한 루프 하나가 컴퓨터 전체를 멈추지 못하는 이유입니다.

![A가 무한 루프를 돌아도 타이머 인터럽트가 올 때마다 커널(진한 칸)이 끼어들어 B에게 차례를 넘깁니다](os-timer.svg)

CPU 스스로 커널을 부르는 경우도 있습니다. 0으로 나누기, 없는 메모리 접근, 7장의 [[페이지 폴트]] 같은 [[예외]]입니다. 시스템 콜, 인터럽트, 예외는 모두 "CPU가 사용자 모드에서 커널 모드로 넘어가는 문"이고, 커널은 이 세 문으로만 일을 시작합니다.

![커널로 들어가는 세 문. 누가 일으키는지만 다르고, 모두 점선을 넘어 커널 모드로 들어갑니다](os-three-doors.svg)

:::quiz nic-door 네트워크 카드에 패킷이 도착했을 때, 커널이 이를 알게 되는 문은 시스템 콜, 인터럽트, 예외 가운데 무엇일까요?
= 인터럽트 | interrupt | 하드웨어 인터럽트

**인터럽트**입니다. 프로그램이 부탁한 것도 아니고 명령어가 잘못된 것도 아니라, 하드웨어 장치가 "일이 생겼다"고 CPU에 신호를 보낸 것입니다. CPU는 하던 명령어를 마치고 커널의 [[인터럽트 핸들러]]로 건너가 패킷을 받아 갑니다.
:::

커널은 인터럽트를 받으면 "어느 장치가 무엇을 원하는지" 알아야 합니다. 그런데 마우스, Wi-Fi 칩, SSD는 회사마다 말하는 방식이 다릅니다.

## 디바이스 드라이버

그래픽카드, Wi-Fi 칩, 프린터는 회사마다 명령 형식이 다릅니다. 커널이 이걸 다 알 수는 없으니, 장치별 지식을 따로 떼어 [[디바이스 드라이버]]에 담습니다. 드라이버는 커널 안에서 돌며, 커널이 정한 공통 형식("이 데이터를 보내라")을 그 장치만의 명령으로 바꿔 줍니다.

| | Windows | macOS | Linux |
| --- | --- | --- | --- |
| 드라이버를 누가 만드나 | 장치 회사가 만들어 배포. Windows Update로도 받음 | Apple이 하드웨어를 정하니 대부분 기본 포함 | 대부분 커널 소스에 함께 들어 있음 |
| 설치 | 장치마다 설치 프로그램이나 자동 설치 | 거의 필요 없음. 외부 장치는 DriverKit으로 사용자 공간에서 | 대개 필요 없음. 일부(NVIDIA 등)는 따로 설치 |
| 드라이버 버그가 나면 | 파란 화면의 흔한 원인 | 사용자 공간 드라이버는 그 드라이버만 죽음 | 커널 패닉이나 장치 오작동 |

:::quiz driver-crash 앱이 죽으면 그 앱만 꺼지는데, 커널 안에서 도는 드라이버에 버그가 나면 컴퓨터 전체가 멈출 수 있는 이유는?
- [x] 드라이버가 커널 모드에서 돌아 잘못을 막아 줄 쪽이 없어서
- [ ] 드라이버는 사용자 모드에서 돌지만 앱보다 우선순위가 높아서
- [ ] 앱은 시스템 콜을 쓰지 않아 커널까지 닿지 않아서
- [ ] 드라이버는 CPU가 아니라 장치 안의 칩에서 돌아서

드라이버가 커널 모드에서 돌기 때문입니다. 사용자 모드 앱이 금지된 일을 하면 CPU가 커널을 불러 그 앱만 끝내지만, 커널 모드 코드는 모든 메모리와 장치를 만질 수 있어 위에서 막아 줄 쪽이 없습니다. 그래서 파란 화면이나 [[커널 패닉]]으로 이어집니다.
:::

여기까지가 맨 앞 그림의 커널 줄에서 일어나는 일입니다. 이제 이 페이지가 어느 운영체제 위에서 돌고 있든 같은 구조라는 것을 알았습니다. 그런데 세 운영체제는 커널을 짜는 방식이 조금씩 다릅니다.

## 곁가지: 커널의 구조, 모놀리식, 마이크로, 하이브리드

커널 안에 무엇까지 넣을지에 따라 설계가 나뉩니다.

- **[[모놀리식 커널]]**: 파일 시스템, 네트워크, 드라이버를 모두 커널 안에 넣습니다. 서로 함수 호출로 부르니 빠르지만, 드라이버 하나의 버그가 전체를 멈출 수 있습니다. Linux가 대표적입니다. 드라이버를 필요할 때 끼웠다 뺄 수 있는 [[커널 모듈]] 기능으로 유연함을 더했습니다.
- **[[마이크로커널]]**: 커널에는 프로세스, 메모리, 메시지 전달만 남기고 파일 시스템과 드라이버는 사용자 공간 프로그램으로 뺍니다. 하나가 죽어도 다시 띄우면 되니 튼튼하지만, 메시지를 주고받는 비용 때문에 느려지기 쉽습니다. Mach, MINIX, 자동차에 많이 쓰는 QNX가 있습니다.
- **[[하이브리드 커널]]**: 마이크로커널 구조를 바탕으로 하되 성능을 위해 많은 것을 다시 커널 안에 넣은 형태입니다. Windows NT와 macOS의 XNU가 여기 속합니다. XNU는 Mach 마이크로커널, BSD 유닉스 계층, IOKit 드라이버 틀을 한 커널에 합쳤습니다.

![같은 부품을 점선(사용자 모드와 커널 모드의 경계) 위아래 어디에 두느냐의 차이입니다. 마이크로커널은 파일 시스템과 드라이버까지 위로 올립니다](os-kernel-structures.svg)

:::quiz micro-driver Linux에서는 드라이버 버그가 커널 패닉으로 이어질 수 있지만, 마이크로커널에서는 드라이버만 다시 띄우면 되는 경우가 많습니다. 이 차이를 만드는 것은?
- [ ] 마이크로커널의 드라이버는 메모리 안전한 언어로만 짜서
- [ ] 마이크로커널은 드라이버 없이 커널이 장치를 직접 다뤄서
- [ ] Linux의 커널 모듈은 사용자 공간에서 돌아서
- [x] 마이크로커널은 드라이버를 사용자 공간 프로그램으로 돌려서

[[마이크로커널]]은 드라이버를 사용자 공간의 평범한 프로그램으로 돌립니다. 그래서 드라이버가 죽어도 그 프로세스만 끝나고 커널은 멀쩡합니다. Linux의 [[커널 모듈]]은 끼웠다 뺄 수 있을 뿐 커널 안에서 돌기 때문에, 모듈 버그는 커널 전체에 영향을 줍니다.
:::

## 세 운영체제는 어디서 왔나

세 운영체제의 성격 차이는 대부분 출신에서 나옵니다.

![세 운영체제의 계보. macOS는 유닉스의 직계 후손이고, Linux는 유닉스를 흉내 낸 새 구현(점선)이며, Windows는 따로 자랐습니다](os-lineage.svg)

- **macOS**는 유닉스의 직계 후손이고 공식 UNIX 인증도 받았습니다. 그래서 터미널을 열면 Linux와 거의 같은 명령이 됩니다.
- **Linux**는 코드상으로는 유닉스의 후손이 아니지만 유닉스와 똑같이 동작하도록 만든 "유닉스 같은" 운영체제입니다. Linux는 엄밀히 커널의 이름이고, 커널에 도구와 패키지를 묶어 배포하는 것을 [[Linux 배포판]]이라고 합니다. 서버의 대부분, 그리고 Docker 컨테이너 안은 거의 Linux입니다.
- **Windows**는 유닉스와 전혀 다른 길에서 왔습니다. 경로 구분자, 줄바꿈, 권한 모델, 프로세스 만드는 법이 모두 다른 이유입니다.

유닉스 계열 운영체제들이 서로 호환되도록 정한 표준이 [[POSIX]]입니다. "파일을 여는 함수는 `open`이고 인자는 이렇다" 같은 약속입니다. macOS와 Linux는 POSIX를 따르고, Windows는 따르지 않습니다. 그래서 Windows에서 유닉스 도구를 쓰려고 [[WSL]]을 만들었습니다. WSL2는 Windows 안에서 진짜 Linux 커널을 가벼운 가상 머신으로 돌립니다.

## 아이콘 대신 터미널로: 셸과 터미널

여기까지는 아이콘을 눌러 브라우저를 띄우는 길이었습니다. 그런데 이 책의 "직접 해보기"는 대부분 다른 길로 프로그램을 띄웁니다. 터미널에 `node`, `curl`, `ping`을 치는 길입니다. 이 길에서도 하는 일은 같습니다. 파일을 찾아 프로세스로 띄우고, 그 프로세스가 시스템 콜로 커널에 부탁합니다. 다만 그 사이에 세 운영체제의 차이가 가장 잘 드러납니다.

검은 창에 명령을 치는 것을 보통 "터미널을 쓴다"고 하지만, 사실 세 가지가 겹쳐 있습니다.

- **[[터미널]]** (터미널 에뮬레이터): 글자를 보여 주고 키보드 입력을 받는 창 프로그램. macOS의 터미널, iTerm2, Windows Terminal, VS Code의 터미널 패널입니다.
- **[[셸]]**: 그 창 안에서 내가 친 명령을 해석하고 프로그램을 실행하는 프로그램. zsh, bash, PowerShell, cmd입니다.
- **명령**: 셸이 실행하는 개별 프로그램. `ls`, `git`, `node`는 셸의 일부가 아니라 디스크에 있는 별개의 실행 파일입니다.

| | Windows | macOS | Linux |
| --- | --- | --- | --- |
| 기본 셸 | [[PowerShell]] (예전 cmd도 있음) | zsh (2019년 Catalina부터. 그전은 bash) | 대부분 bash |
| 파이프로 넘기는 것 | 객체 (PowerShell) | 텍스트 | 텍스트 |
| 스크립트 파일 | `.ps1`, `.bat`, `.cmd` | `.sh`, `.zsh` | `.sh` |
| 설정 파일 | `$PROFILE` | `~/.zshrc` | `~/.bashrc` |

자주 쓰는 명령은 이름만 다르고 하는 일은 같습니다.

| 하는 일 | macOS · Linux | Windows PowerShell | Windows cmd |
| --- | --- | --- | --- |
| 목록 보기 | `ls -la` | `Get-ChildItem` (`ls`, `dir`도 됨) | `dir` |
| 파일 내용 | `cat a.txt` | `Get-Content a.txt` (`cat`도 됨) | `type a.txt` |
| 글자 찾기 | `grep foo a.txt` | `Select-String foo a.txt` | `findstr foo a.txt` |
| 프로세스 목록 | `ps aux` | `Get-Process` | `tasklist` |
| 프로세스 끝내기 | `kill 1234` | `Stop-Process -Id 1234` | `taskkill /PID 1234` |
| 명령 위치 | `which node` | `Get-Command node` | `where node` |
| 네트워크 설정 | `ifconfig`(mac), `ip addr`(Linux) | `Get-NetIPAddress` | `ipconfig` |
| 환경 변수 보기 | `env` | `Get-ChildItem env:` | `set` |

셸이 명령을 실행하는 방법도 운영체제마다 다릅니다. macOS와 Linux의 셸은 자기 자신을 복제(`fork`)한 뒤 그 복제본을 새 프로그램으로 갈아 끼웁니다(`exec`). Windows는 `CreateProcess` 한 번으로 새 프로그램을 만듭니다. 6장에서 자세히 봅니다.

:::quiz npm-rm `package.json`의 `"clean": "rm -rf dist"`가 macOS와 Ubuntu CI에서는 되는데, Windows cmd를 쓰는 동료에게서만 실패합니다. 원인으로 가장 알맞은 것은?
- [ ] Windows 파일 시스템이 대소문자를 구분하지 않아서
- [ ] Windows에서는 npm이 스크립트를 실행하지 않아서
- [ ] Windows에서는 `dist`를 관리자만 지울 수 있어서
- [x] npm이 스크립트를 넘기는 셸(cmd)에 `rm` 명령이 없어서

cmd에는 `rm`이라는 명령이 없기 때문입니다. `npm run`은 스크립트 문자열을 운영체제의 기본 셸에 넘기는데, macOS와 Linux에서는 POSIX 셸과 `rm` 실행 파일이 있지만 Windows cmd에는 없습니다. 그래서 `rimraf`처럼 Node로 짠 도구를 씁니다.
:::

터미널에 `node`라고만 치면 셸은 어디에 있는 어떤 파일을 실행할까요?

## 환경 변수와 PATH

[[환경 변수]]는 프로세스마다 붙어 다니는 "이름=값" 목록입니다. 프로세스가 새 프로세스를 띄우면 자식은 부모의 환경 변수를 복사해 받습니다. 그래서 터미널에서 `export NODE_ENV=production`을 하면 그 터미널에서 실행한 Node 프로그램이 `process.env.NODE_ENV`로 읽을 수 있습니다.

가장 중요한 환경 변수는 [[PATH]]입니다. `node`라고만 쳐도 실행되는 건, 셸이 PATH에 적힌 디렉터리들을 앞에서부터 뒤져 `node`라는 실행 파일을 찾기 때문입니다. "command not found"나 "'node'은(는) 내부 또는 외부 명령… 이 아닙니다"는 PATH의 어느 디렉터리에도 그 파일이 없다는 뜻입니다.

![셸은 PATH의 디렉터리를 앞에서부터 하나씩 열어 보고, 처음 찾은 파일을 실행합니다. 그 뒤는 보지 않습니다](os-path.svg)

| | Windows | macOS · Linux |
| --- | --- | --- |
| PATH 구분자 | `;` (`C:\Windows;C:\Program Files\nodejs`) | `:` (`/usr/local/bin:/usr/bin:/bin`) |
| 지금 값 보기 | `$env:Path` | `echo $PATH` |
| 영구 설정 | 시스템 속성 → 환경 변수, 또는 `setx` | `~/.zshrc`, `~/.bashrc`에 `export` |
| 대소문자 | 이름의 대소문자를 구분 안 함 (`Path` = `PATH`) | 구분함 |

`.env` 파일은 운영체제 기능이 아닙니다. `dotenv` 같은 라이브러리나 Vite, Next.js가 파일을 읽어 `process.env`에 채워 주는 관례입니다. 서버에서는 Docker Compose의 `environment:`나 systemd의 `Environment=`가 같은 일을 합니다.

:::quiz path-order PATH가 `/opt/homebrew/bin:/usr/local/bin:/usr/bin`이고, `node` 실행 파일이 `/usr/local/bin`과 `/usr/bin` 두 곳에 있습니다. 터미널에서 `node`를 치면?
- [ ] 두 파일 가운데 버전이 더 높은 쪽이 실행된다
- [x] `/usr/local/bin/node`가 실행된다
- [ ] `/usr/bin/node`가 실행된다
- [ ] 이름이 겹쳐 셸이 오류를 낸다

`/usr/local/bin/node`가 실행됩니다. 셸은 [[PATH]]의 디렉터리를 앞에서부터 뒤져 처음 찾은 파일을 실행하고 멈춥니다. 버전은 보지 않으니, 엉뚱한 Node가 실행될 때는 `which -a node`로 순서를 확인합니다.
:::

:::quiz env-sibling 터미널 창 A에서 `export NODE_ENV=production`을 한 뒤, 미리 열어 둔 터미널 창 B에서 `node -e "console.log(process.env.NODE_ENV)"`를 실행하면? (설정 파일에는 NODE_ENV가 없습니다)
- [x] `undefined` — B는 A의 환경을 물려받은 자식이 아니라서
- [ ] `production` — 환경 변수는 컴퓨터 전체에 하나라서
- [ ] `production` — 같은 사용자의 프로세스끼리 공유해서
- [ ] 오류 — 다른 터미널의 변수는 sudo가 있어야 읽혀서

`undefined`가 나옵니다. [[환경 변수]]는 프로세스마다 따로 있고, 새 프로세스를 띄울 때 부모의 것을 복사해 줄 뿐입니다. A에서 바꾼 값은 A와 그 뒤에 A에서 띄운 자식에게만 보이고, 이미 떠 있는 B의 셸과 그 자식에게는 닿지 않습니다.
:::

이 페이지를 띄운 브라우저는 내 사용자 계정으로 돌고 있습니다. 그래서 내 다운로드 폴더에는 파일을 쓸 수 있지만, 시스템 파일은 못 바꿉니다. 누가 무엇을 할 수 있는지는 어떻게 정할까요?

## 사용자와 권한

운영체제는 사용자를 나눠 각자 할 수 있는 일을 제한합니다. 모든 것을 할 수 있는 관리자 계정이 있고, 평소에는 권한이 적은 계정으로 일하다가 필요할 때만 관리자 권한을 빌립니다.

| | Windows | macOS | Linux |
| --- | --- | --- | --- |
| 최고 권한 계정 | Administrator, SYSTEM | [[root]] (평소 잠겨 있음) | root (UID 0) |
| 잠깐 권한 빌리기 | [[UAC]] 확인 창, "관리자 권한으로 실행" | [[sudo]], 암호 입력 창 | sudo |
| root도 못 건드리는 곳 | 시스템 파일은 TrustedInstaller 소유 | [[SIP]]가 `/System` 등을 보호 | 기본은 없음 (SELinux, AppArmor로 추가) |
| 앱별 개인정보 권한 | 설정 → 개인 정보 | 화면 기록, 전체 디스크 접근 등 앱마다 허락 (TCC) | 데스크톱에 따라 다름 |

macOS에서 터미널이 "데스크탑 폴더에 접근하려고 합니다"라고 묻거나, 화면 녹화 앱이 권한을 요구하는 건 root 권한과 별개인 앱별 개인정보 보호 장치입니다. 서버에서는 웹 서버를 root로 돌리지 않고 전용 사용자로 돌리는 것이 기본입니다. 웹 서버가 뚫려도 그 사용자의 권한만큼만 피해가 나기 때문입니다.

## 패키지 관리자

프로그램을 설치하고 업데이트하고 지우는 일을 맡는 프로그램이 [[패키지 관리자]]입니다. 의존하는 다른 프로그램까지 알아서 설치해 줍니다.

| | Windows | macOS | Linux |
| --- | --- | --- | --- |
| 운영체제 패키지 관리자 | winget (기본 포함), Chocolatey, Scoop | Homebrew (따로 설치) | apt (Debian, Ubuntu), dnf (Fedora, RHEL), apk (Alpine) |
| 예 | `winget install OpenJS.NodeJS` | `brew install node` | `sudo apt install nodejs` |

npm, pnpm, pip는 운영체제가 아니라 언어의 패키지 관리자입니다. 둘이 겹치면 헷갈리기 쉬워서, Node 자체는 nvm이나 fnm 같은 버전 관리자로 설치하고 프로젝트 의존성은 npm으로 설치하는 경우가 많습니다.

## 파일 경로와 이름 규칙

파일 이름을 다루는 규칙도 운영체제마다 다릅니다. 8장에서 파일 시스템을 자세히 보기 전에 차이만 짚습니다.

| | Windows | macOS | Linux |
| --- | --- | --- | --- |
| 경로 예 | `C:\Users\me\project` | `/Users/me/project` | `/home/me/project` |
| 구분자 | `\` (대부분 `/`도 받아 줌) | `/` | `/` |
| 최상위 | 드라이브마다 따로 (`C:\`, `D:\`) | 하나의 `/` 아래 모두 | 하나의 `/` 아래 모두 |
| 대소문자 구분 | 안 함 (적은 대로 보존은 함) | 기본은 안 함 (APFS 기본 설정) | 함 |
| 쓸 수 없는 이름 | `CON`, `NUL`, `PRN` 등과 `< > : " \| ? *` | `:` (Finder에서) | `/`와 NUL 문자만 |

대소문자 차이는 프론트엔드에서 자주 사고를 냅니다. 파일 이름이 `Button.tsx`인데 `import Button from "./button"`이라고 쓰면, 대소문자를 구분하지 않는 Mac과 Windows에서는 잘 되지만 Linux인 CI 서버와 배포 서버에서는 "모듈을 찾을 수 없다"며 빌드가 깨집니다. Node에서 경로를 만들 때 문자열을 이어 붙이지 않고 `path.join`을 쓰는 것도 구분자 차이 때문입니다.

## 다시 장면으로: 클릭 한 번이 SSD에 닿기까지

이제 맨 앞 그림을 처음부터 끝까지 말로 할 수 있습니다. 마우스 버튼이 눌리면 마우스의 칩이 신호를 보내고, 컨트롤러가 인터럽트를 겁니다. CPU는 하던 일을 멈추고 커널의 인터럽트 핸들러와 마우스 드라이버를 돌려 "이 좌표에서 클릭"이라는 사건으로 만듭니다. 커널은 이 사건을 화면의 창을 관리하는 프로그램(macOS의 WindowServer, Windows의 win32k)에 넘기고, 그 프로그램이 지금 그 자리에 있는 창, 곧 브라우저에 전합니다.

브라우저는 체크박스를 켜고 `localStorage`에 기록을 씁니다. 브라우저도 SSD를 직접 만질 수 없으니, 결국 `write` 같은 시스템 콜로 커널에 부탁합니다. 커널은 권한을 확인하고, 파일 시스템이 어느 블록에 쓸지 정하고, SSD 드라이버가 그 장치의 명령으로 바꿔 내려보냅니다. 들어올 때는 인터럽트, 나갈 때는 시스템 콜입니다.

그런데 이 그림에서 아직 설명하지 않은 칸이 있습니다. "브라우저"라는 칸입니다. 브라우저 아이콘을 눌렀을 때 SSD에 있던 브라우저 파일은 어떻게 실행 중인 프로그램이 될까요? 그리고 이 페이지의 JS는 2장에서 본 기계어도 아닌데, 어떻게 CPU에서 돌까요? 5장이 이 질문에서 시작합니다.

## 한눈에 보는 세 운영체제

| | Windows | macOS | Linux |
| --- | --- | --- | --- |
| 커널 | NT (하이브리드) | XNU (하이브리드: Mach + BSD) | Linux (모놀리식 + 모듈) |
| 계보 | VMS의 영향을 받은 독자 설계 | 유닉스 (BSD) | 유닉스 같은 새 구현 |
| POSIX | 아니요 (WSL로 Linux를 돌림) | 예 (UNIX 인증) | 대부분 예 |
| 실행 파일 형식 | PE (`.exe`, `.dll`) | Mach-O | ELF |
| 기본 파일 시스템 | NTFS | APFS | ext4 (배포판에 따라 Btrfs, XFS) |
| 첫 프로세스 | smss.exe | launchd | systemd |
| 기본 셸 | PowerShell | zsh | bash |
| 줄바꿈 | CRLF | LF | LF |
| 주로 쓰는 곳 | 데스크톱, 게임, 회사 업무 | 데스크톱, 개발, 디자인 | 서버, 클라우드, 컨테이너, 임베디드, Android |

실행 파일 형식은 5장, 첫 프로세스는 3장과 6장, 파일 시스템은 8장에서 자세히 봅니다.

## 프론트엔드와 이어지는 곳

- `npm run`이 실행하는 스크립트는 셸 명령입니다. `rm -rf dist && vite build`는 macOS와 Linux에서는 되지만 Windows cmd에서는 `rm`이 없어 실패합니다. `rimraf`나 `cross-env` 같은 패키지가 존재하는 이유입니다.
- 브라우저 탭 하나가 죽어도 브라우저 전체가 살아 있는 건, 탭을 별도 프로세스로 띄워 운영체제의 보호 벽을 그대로 쓰기 때문입니다(6장).
- Node의 `os.platform()`은 `win32`, `darwin`(macOS 커널 이름에서 온 말), `linux`를 돌려줍니다. 플랫폼별로 다르게 동작해야 할 때 이 값을 봅니다.
- import 경로의 대소문자는 파일 이름과 정확히 맞춥니다. Mac에서 되고 CI에서 깨지는 빌드의 단골 원인입니다.

## 용어 정리

:::terms
- 운영체제 (operating system) — 하드웨어를 감싸 쓰기 쉬운 개념(파일, 프로세스, 소켓)으로 바꾸고, 자원을 여러 프로그램에 나누고, 서로를 보호하는 소프트웨어입니다.
- 커널 (kernel) — 운영체제의 핵심. 커널 모드에서 돌며 하드웨어를 직접 다루는 유일한 프로그램입니다.
- 사용자 공간 (user space) — 커널 바깥에서 일반 프로그램들이 도는 영역. 하드웨어에 직접 손댈 수 없습니다.
- 커널 모드 (kernel mode) — 모든 명령어와 메모리, 장치에 접근할 수 있는 CPU 실행 모드. x86의 링 0입니다.
- 사용자 모드 (user mode) — 권한이 제한된 CPU 실행 모드. 일반 프로그램은 여기서 돌고, 금지된 일을 하면 CPU가 커널을 부릅니다.
- 커널 패닉 (kernel panic) — 커널이 더 진행할 수 없는 오류를 만나 시스템을 멈추는 것. Windows에서는 파란 화면(BSOD)으로 보입니다.
- 시스템 콜 (system call) — 사용자 프로그램이 파일, 네트워크, 프로세스 같은 일을 커널에 부탁하는 정해진 창구입니다.
- 인터럽트 (interrupt) — 하드웨어가 CPU에 "일이 생겼다"고 알리는 신호. CPU는 하던 일을 멈추고 커널의 핸들러를 실행합니다.
- 인터럽트 핸들러 (interrupt handler) — 인터럽트가 오면 실행되는 커널의 코드. 키 입력을 읽거나 도착한 패킷을 받아 갑니다.
- 예외 (exception) — 0으로 나누기, 없는 메모리 접근처럼 실행 중인 명령어 때문에 CPU가 커널을 부르는 것입니다.
- 디바이스 드라이버 (device driver) — 특정 장치를 다루는 법을 아는 커널 쪽 코드. 커널의 공통 요청을 그 장치의 명령으로 바꿉니다.
- 모놀리식 커널 (monolithic kernel) — 파일 시스템, 네트워크, 드라이버를 모두 커널 안에 둔 구조. Linux가 대표적입니다.
- 마이크로커널 (microkernel) — 커널에는 최소 기능만 두고 드라이버와 파일 시스템을 사용자 공간 프로그램으로 뺀 구조. Mach, MINIX, QNX.
- 하이브리드 커널 (hybrid kernel) — 마이크로커널 구조에 성능을 위해 많은 기능을 다시 커널 안에 넣은 구조. Windows NT와 XNU.
- 커널 모듈 (kernel module) — 실행 중인 커널에 끼웠다 뺄 수 있는 코드 조각. Linux 드라이버가 주로 이 형태입니다.
- XNU — macOS와 iOS의 커널. Mach 마이크로커널, BSD 계층, IOKit을 합쳤습니다.
- Windows NT — Windows 2000, XP부터 11까지 이어지는 Windows의 커널과 구조. Windows Server도 같습니다.
- 유닉스 (Unix) — 1969년 벨 연구소에서 만든 운영체제. macOS와 BSD의 조상이고, Linux가 흉내 낸 대상입니다.
- Linux 배포판 (Linux distribution) — Linux 커널에 도구, 패키지 관리자, 기본 설정을 묶어 내놓은 운영체제. Ubuntu, Debian, Fedora, Alpine 등.
- POSIX — 유닉스 계열 운영체제의 공통 인터페이스 표준. 파일, 프로세스, 셸 명령의 동작을 정합니다. macOS와 Linux가 따릅니다.
- WSL (Windows Subsystem for Linux) — Windows 안에서 Linux를 돌리는 기능. WSL2는 실제 Linux 커널을 가벼운 가상 머신으로 실행합니다.
- 터미널 (terminal) — 글자를 보여 주고 키 입력을 받는 창 프로그램. 그 안에서 셸이 돕니다.
- 셸 (shell) — 사용자가 친 명령을 해석해 프로그램을 실행하는 프로그램. zsh, bash, PowerShell.
- PowerShell — Windows의 기본 셸. 명령 사이에 텍스트 대신 객체를 넘깁니다. macOS와 Linux용도 있습니다.
- 환경 변수 (environment variable) — 프로세스마다 붙어 있는 이름=값 목록. 자식 프로세스가 복사해 물려받습니다.
- PATH — 셸이 명령 이름으로 실행 파일을 찾을 때 뒤지는 디렉터리 목록을 담은 환경 변수입니다.
- root — 유닉스 계열의 최고 권한 사용자(UID 0). 모든 파일과 설정을 바꿀 수 있습니다.
- sudo — 다른 사용자(주로 root)의 권한으로 명령 하나를 실행하는 프로그램. 내 암호로 확인합니다.
- UAC (User Account Control) — Windows에서 관리자 권한이 필요한 일을 할 때 확인 창을 띄우는 기능입니다.
- SIP (System Integrity Protection) — root라도 macOS 시스템 파일을 바꾸지 못하게 막는 보호 장치입니다.
- 패키지 관리자 (package manager) — 프로그램을 의존성과 함께 설치, 업데이트, 삭제해 주는 도구. apt, Homebrew, winget, npm.
:::

## 직접 해보기

:::practice syscalls 프로그램 하나가 부르는 시스템 콜 엿보기
파일 하나를 읽는 Node 한 줄이 실제로 어떤 시스템 콜을 부르는지 봅니다. `open`(또는 `openat`), `read`, `close`를 찾아봅니다.

```sh Linux (또는 Docker의 Linux 컨테이너)
strace -f -e trace=openat,read,close node -e "require('fs').readFileSync('/etc/hostname')" 2>&1 | grep hostname -A2
strace -c node -e "1"      # 아무것도 안 하는 Node도 시스템 콜을 수백 번 부릅니다
```

```sh macOS
# 터미널 두 개를 엽니다. 하나에서:
sudo fs_usage -w -f filesys node
# 다른 하나에서:
node -e "require('fs').readFileSync('package.json')"
```

```text Windows
Sysinternals의 Process Monitor를 받아 실행하고, 필터에 "Process Name is node.exe"를 넣은 뒤
node -e "require('fs').readFileSync('package.json')" 를 실행해 CreateFile, ReadFile 줄을 찾습니다.
```
:::

:::practice path PATH가 명령을 찾는 과정 따라가기
`node`가 어느 파일인지, PATH에 어떤 디렉터리가 어떤 순서로 있는지 확인합니다. 같은 이름의 실행 파일이 두 곳에 있으면 어느 쪽이 이기는지도 봅니다.

```sh macOS · Linux
echo $PATH | tr ':' '\n'
which -a node
type ls cd       # ls는 파일, cd는 셸 내장 명령
```

```powershell Windows (PowerShell)
$env:Path -split ';'
Get-Command node -All
```
:::

:::practice case 파일 이름 대소문자 실험
내 컴퓨터의 파일 시스템이 대소문자를 구분하는지 확인합니다. 그리고 Linux 컨테이너에서는 어떻게 되는지 비교합니다.

```sh macOS · Linux
mkdir /tmp/case && cd /tmp/case
echo a > Button.txt
cat button.txt   # Mac은 보통 "a", Linux는 "No such file"
```

```powershell Windows (PowerShell)
Set-Content Button.txt a
Get-Content button.txt   # 대소문자를 구분하지 않아 읽힙니다
```
:::

:::practice versions 내 운영체제와 커널 버전 확인하기
운영체제 이름, 버전, 커널 버전을 확인하고, 커널 이름(Darwin, Linux, Windows NT)이 이 장의 계보 그림 어디에 있는지 찾아봅니다.

```sh macOS
sw_vers
uname -a        # Darwin Kernel Version ... (XNU)
```

```sh Linux
cat /etc/os-release
uname -r
```

```powershell Windows (PowerShell)
[System.Environment]::OSVersion
Get-ComputerInfo -Property OsName, OsVersion, WindowsVersion
```
:::

## 장 전체 문제

:::quiz two-doors "다 읽었어요"를 누른 순간부터 그 기록이 SSD에 쓰이기까지, CPU가 사용자 모드에서 커널 모드로 넘어가는 문을 순서대로 적은 것은?
- [ ] 시스템 콜 → 인터럽트
- [ ] 예외 → 시스템 콜
- [ ] 인터럽트 → 예외
- [x] 인터럽트 → 시스템 콜

인터럽트 → 시스템 콜입니다. 마우스가 눌림을 알리는 것은 하드웨어가 커널을 부르는 인터럽트이고, 브라우저가 기록을 디스크에 써 달라고 하는 것은 프로그램이 커널을 부르는 시스템 콜입니다. 들어올 때와 나갈 때 쓰는 문이 다릅니다.
:::

## 스스로 점검

:::qa 사용자 모드 프로그램이 디스크를 직접 읽을 수 없다면, `fs.readFile`은 어떻게 파일을 읽나요?
`read` 같은 시스템 콜로 커널에 부탁합니다. `syscall` 명령어가 CPU를 커널 모드로 바꾸고, 커널이 권한을 확인한 뒤 파일 시스템과 디스크 드라이버를 거쳐 읽고 결과를 돌려준 뒤 사용자 모드로 돌아갑니다.
:::

:::qa 무한 루프를 도는 프로그램이 있어도 다른 프로그램이 계속 돌 수 있는 이유는?
타이머 인터럽트 덕분입니다. 일정 시간마다 하드웨어 타이머가 인터럽트를 보내 CPU를 강제로 커널로 넘기고, 커널의 스케줄러가 다른 프로세스에 CPU를 줍니다.
:::

:::qa 시스템 콜, 인터럽트, 예외는 각각 누가 일으키나요? 공통점은?
시스템 콜은 프로그램이 일부러, 인터럽트는 하드웨어 장치가, 예외는 실행 중인 명령어가 문제를 만나서 일으킵니다. 셋 다 CPU를 사용자 모드에서 커널 모드로 넘겨 커널 코드를 실행하게 합니다.
:::

:::qa macOS 터미널 명령이 Linux와 거의 같고 Windows와는 다른 이유는?
macOS는 BSD 유닉스의 후손이고 POSIX를 따르며, Linux는 유닉스처럼 동작하도록 만든 운영체제라 같은 POSIX 명령과 셸을 씁니다. Windows는 유닉스와 다른 계보(NT)라 셸, 경로, 명령 체계가 따로 발전했습니다.
:::

:::qa Mac에서 잘 빌드되던 프로젝트가 GitHub Actions(Ubuntu)에서 "Cannot find module './components/button'"으로 깨집니다. 원인과 확인 방법은?
실제 파일 이름이 `Button.tsx`처럼 대소문자가 다를 가능성이 큽니다. macOS 기본 파일 시스템은 대소문자를 구분하지 않아 찾아지지만 Linux는 구분합니다. `git ls-files | grep -i button`으로 Git에 기록된 실제 이름을 확인하고 import를 맞춥니다.
:::

:::qa 웹 서버를 root가 아닌 전용 사용자로 돌리는 이유는?
웹 서버에 취약점이 있어 공격자가 코드를 실행하게 되더라도, 그 코드는 웹 서버 사용자의 권한만 갖게 되어 시스템 전체를 장악하지 못합니다. 피해 범위를 줄이는 최소 권한 원칙입니다.
:::
