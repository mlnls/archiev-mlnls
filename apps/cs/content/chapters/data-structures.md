1~4부는 컴퓨터와 네트워크가 데이터를 어떻게 나르는지였습니다. 5부는 그 데이터를 프로그램 안에서 어떻게 담고 다루는지입니다. 같은 일을 하는 코드라도 데이터를 어떤 모양으로 두느냐에 따라 1000배 넘게 빠르거나 느려집니다. 목록이 10개일 때는 차이가 안 보이다가 10만 개가 되면 화면이 멈추는 일, 프론트엔드에서도 자주 만납니다.

## 자료구조와 알고리즘

[[자료구조]]는 데이터를 담는 방식입니다. 같은 사용자 목록이라도 배열에 넣을지, ID를 키로 한 `Map`에 넣을지, 이름순 트리에 넣을지에 따라 "ID로 찾기", "이름순으로 보여 주기", "중간에 끼워 넣기" 같은 연산의 속도가 달라집니다.

[[알고리즘]]은 문제를 푸는 정해진 절차입니다. 정렬, 검색, 최단 경로 찾기 같은 것입니다. 알고리즘은 자료구조 위에서 돌고, 자료구조는 알고리즘이 빠르게 돌도록 고릅니다. 둘은 늘 함께 다닙니다.

## 얼마나 빠른가를 세는 법: 시간 복잡도

코드의 속도를 "0.3초"로 말하면 컴퓨터마다, 입력마다 다릅니다. 그래서 입력 크기 n이 커질 때 연산 횟수가 **어떤 모양으로** 늘어나는지로 말합니다. 이걸 [[시간 복잡도]]라고 하고, [[빅오 표기법]]으로 적습니다.

```js
function sum(arr) {            // n번 돌기 → O(n)
  let s = 0;
  for (const x of arr) s += x;
  return s;
}

function hasDuplicate(arr) {   // n × n번 → O(n²)
  for (let i = 0; i < arr.length; i++)
    for (let j = i + 1; j < arr.length; j++)
      if (arr[i] === arr[j]) return true;
  return false;
}
```

빅오는 가장 빨리 커지는 항만 남기고 상수는 버립니다. `3n² + 100n + 7`은 O(n²)입니다. n이 충분히 크면 나머지는 의미가 없어지기 때문입니다. 그리고 보통 가장 나쁜 경우(최악)를 말합니다.

| 복잡도 | 이름 | n = 10 | n = 1,000 | n = 1,000,000 | 예 |
| --- | --- | --- | --- | --- | --- |
| O(1) | 상수 | 1 | 1 | 1 | 배열 인덱스, `Map.get` |
| O(log n) | 로그 | 3 | 10 | 20 | 이진 탐색, 균형 트리 |
| O(n) | 선형 | 10 | 1,000 | 100만 | 배열 한 번 훑기, `includes` |
| O(n log n) | | 33 | 1만 | 2000만 | 좋은 정렬 |
| O(n²) | 제곱 | 100 | 100만 | 1조 | 이중 반복문 |
| O(2ⁿ) | 지수 | 1,024 | 끝나지 않음 | 끝나지 않음 | 모든 부분집합 |
| O(n!) | 팩토리얼 | 360만 | 끝나지 않음 | 끝나지 않음 | 모든 순서 |

JS가 1초에 단순 연산 수억 번쯤 한다고 치면, n이 100만일 때 O(n log n)은 0.1초 안쪽이지만 O(n²)은 몇 시간입니다. 2장에서 본 하드웨어 차이(수 배)보다 알고리즘 차이(수백만 배)가 훨씬 큽니다.

## JS 코드에 숨은 O(n)

반복문이 하나여도 O(n²)일 수 있습니다. 안에서 부르는 메서드가 O(n)이면 그렇습니다.

| 연산 | 복잡도 | 주의 |
| --- | --- | --- |
| `arr[i]`, `arr.push`, `arr.pop` | O(1) | |
| `arr.includes`, `indexOf`, `find`, `filter`, `some` | O(n) | 앞에서부터 다 훑음 |
| `arr.shift`, `unshift`, `splice(중간)` | O(n) | 뒤 원소를 전부 한 칸씩 옮김 |
| `[...arr]`, `arr.slice()`, `{...obj}` | O(n) | 통째로 복사 |
| `map.get`, `map.set`, `set.has` | 평균 O(1) | 해시 테이블 |
| `arr.sort` | O(n log n) | |

프론트엔드에서 흔한 숨은 O(n²)입니다.

```jsx
// 주문마다 사용자를 배열에서 찾음: 주문 n개 × 사용자 m명
orders.map((o) => <Row user={users.find((u) => u.id === o.userId)} />);

// 한 번 Map으로 만들어 두면 O(n + m)
const byId = new Map(users.map((u) => [u.id, u]));
orders.map((o) => <Row user={byId.get(o.userId)} />);
```

반복문 안에서 `[...acc, x]`로 배열을 계속 새로 만들거나, `reduce` 안에서 `{...acc}`를 펼치는 것도 매번 O(n) 복사라 전체가 O(n²)이 됩니다.

## 메모리도 셉니다: 공간 복잡도

알고리즘이 추가로 쓰는 메모리가 입력에 따라 어떻게 늘어나는지를 [[공간 복잡도]]라고 합니다. 위의 `Map`을 만드는 방법은 시간을 O(n²)에서 O(n)으로 줄이는 대신 O(m) 메모리를 더 씁니다. 메모리를 더 써서 시간을 사는 거래는 아주 흔합니다. 캐시(2장), 인덱스(21장), 메모이제이션(20장)이 모두 그렇습니다. 재귀는 깊이만큼 콜 스택(5장)을 쓴다는 것도 공간 복잡도에 들어갑니다.

## 평균, 최악, 그리고 분할 상환

같은 연산도 경우에 따라 비용이 다릅니다.

- **최악의 경우**: 가장 운이 나쁠 때. 보장이 필요할 때 봅니다.
- **평균**: 보통의 입력에서. 해시 테이블의 O(1)은 평균입니다.
- **[[분할 상환 분석]]**: 가끔 비싼 연산이 있지만 여러 번에 나눠 보면 한 번당 싼 경우. 아래의 동적 배열 `push`가 대표적입니다.

## 배열

[[배열]]은 같은 크기의 칸을 메모리에 빈틈없이 이어 붙인 구조입니다. i번째 칸의 주소는 `시작 주소 + i × 칸 크기`로 바로 계산되니, 몇 번째든 O(1)에 읽습니다. 연속된 메모리라 2장의 캐시 라인과 지역성을 가장 잘 살립니다. 대신 중간에 끼워 넣거나 빼려면 뒤의 원소를 모두 한 칸씩 옮겨야 해서 O(n)입니다.

크기가 고정된 배열은 꽉 차면 더 넣을 수 없습니다. 그래서 [[동적 배열]]은 꽉 차면 두 배 크기의 새 메모리를 잡고 통째로 옮깁니다. 옮기는 순간은 O(n)이지만 그런 일은 크기가 두 배가 될 때마다 한 번이라, n번 `push`의 총비용은 O(n), 한 번당 분할 상환 O(1)입니다. JS 배열, Python 리스트, Java의 ArrayList가 동적 배열입니다.

JS 배열은 조금 특별합니다. V8은 배열의 내용을 보고 내부 표현을 고릅니다.

- 정수만 있으면 정수 칸, 소수가 섞이면 실수 칸, 그 밖이면 객체를 가리키는 칸으로 빈틈없이 둡니다. 빠릅니다.
- `arr[1000000] = 1`처럼 구멍이 많아지면 해시 테이블(사전 모드)로 바꿔 버립니다. 느려집니다.
- 한 번 일반적인 표현으로 바뀌면 다시 빠른 표현으로 돌아가지 않습니다.

그래서 배열은 구멍 없이 앞에서부터 채우고, 한 배열에 타입을 섞지 않는 게 좋습니다. 숫자를 대량으로 다룬다면 1장의 `TypedArray`가 진짜로 연속된 메모리입니다.

## 연결 리스트

[[연결 리스트]]는 원소마다 "다음 원소가 어디 있는지"를 가리키는 노드를 이은 구조입니다. 메모리 여기저기에 흩어져 있어도 됩니다.

```text
head → [3 | •] → [7 | •] → [1 | •] → null
```

노드를 알고 있으면 그 뒤에 끼우거나 빼는 건 포인터 두어 개만 바꾸면 되니 O(1)입니다. 대신 k번째 원소를 찾으려면 앞에서부터 k번 따라가야 하니 O(n)이고, 노드가 흩어져 있어 캐시 미스가 많습니다. 그래서 실제로는 배열이 더 빠른 경우가 대부분입니다.

연결 리스트가 빛나는 곳도 있습니다. 운영체제 커널은 프로세스 목록이나 대기열을 연결 리스트로 관리하고, 아래에서 볼 LRU 캐시는 해시 테이블과 양방향 연결 리스트를 묶어 만듭니다. React의 Fiber 구조도 각 노드가 첫 자식, 다음 형제, 부모를 가리키는 연결 구조로 컴포넌트 트리를 표현해서, 렌더링을 중간에 멈췄다가 이어 갈 수 있습니다.

## 스택

[[스택]]은 마지막에 넣은 것을 먼저 꺼내는(LIFO) 구조입니다. 접시를 쌓고 맨 위부터 꺼내는 것과 같습니다. 넣기(push)와 꺼내기(pop)가 모두 O(1)이고, JS 배열의 `push`, `pop`으로 바로 씁니다.

- 5장의 콜 스택: 함수 호출이 쌓이고 끝나면 빠집니다.
- 되돌리기(Ctrl+Z): 한 일을 쌓아 두고 마지막 것부터 되돌립니다.
- 브라우저 뒤로 가기 기록.
- 괄호 짝 맞추기, 수식 계산, 19장의 깊이 우선 탐색.

```js
function balanced(s) {
  const pairs = { ")": "(", "]": "[", "}": "{" };
  const stack = [];
  for (const c of s) {
    if ("([{".includes(c)) stack.push(c);
    else if (c in pairs && stack.pop() !== pairs[c]) return false;
  }
  return stack.length === 0;
}
```

## 큐와 덱

[[큐]]는 먼저 넣은 것을 먼저 꺼내는(FIFO) 구조입니다. 줄 서기와 같습니다. 6장의 태스크 큐, 17장의 메시지 큐, 프린터 대기열, 19장의 너비 우선 탐색이 큐입니다.

JS에서 큐를 배열의 `push`와 `shift`로 만들면 함정이 있습니다. `shift`는 맨 앞을 빼고 나머지를 모두 한 칸씩 당기니 O(n)입니다. 큐에 원소가 많으면 느려집니다. 원소가 많다면 앞을 가리키는 번호를 따로 두거나, 원형 버퍼를 씁니다.

```js
class Queue {
  #items = []; #head = 0;
  push(x) { this.#items.push(x); }
  shift() {                       // O(1): 앞 번호만 옮김
    const x = this.#items[this.#head++];
    if (this.#head > 1024 && this.#head * 2 > this.#items.length) {
      this.#items = this.#items.slice(this.#head); this.#head = 0; // 가끔 앞부분 정리
    }
    return x;
  }
  get size() { return this.#items.length - this.#head; }
}
```

[[원형 버퍼]]는 고정 크기 배열의 끝과 처음을 이어 붙인 것처럼 쓰는 큐입니다. 읽는 위치와 쓰는 위치가 배열을 빙빙 돕니다. 메모리를 새로 잡지 않아 빠르고 크기가 예측 가능해서, 8장에서 본 네트워크 카드의 수신 칸, 오디오 버퍼, 로그 버퍼가 이렇게 생겼습니다.

양쪽 끝에서 모두 넣고 뺄 수 있는 큐를 [[덱]]이라고 합니다.

## 해시 테이블

[[해시 테이블]]은 키로 값을 평균 O(1)에 찾는 구조입니다. 프로그래밍에서 가장 많이 쓰는 자료구조일 것입니다.

1. 키를 **해시 함수**에 넣어 정수를 얻습니다. 같은 키는 늘 같은 정수가 나옵니다.
2. 그 정수를 배열 크기로 나눈 나머지를 칸 번호로 씁니다.
3. 그 칸에 키와 값을 둡니다. 찾을 때도 같은 계산으로 칸을 바로 찾아갑니다.

```text
"apple" → hash → 9135 → 9135 % 8 = 7 → 칸 7
"grape" → hash → 4122 → 4122 % 8 = 2 → 칸 2
"melon" → hash → 3255 → 3255 % 8 = 7 → 칸 7  ← 충돌!
```

서로 다른 키가 같은 칸에 떨어지는 것을 [[해시 충돌]]이라고 합니다. 피할 수 없으니 처리 방법이 있습니다. 같은 칸에 작은 목록으로 이어 두거나(체이닝), 빈 옆 칸을 찾아 넣습니다(개방 주소법).

칸이 너무 차면 충돌이 많아져 느려집니다. 원소 수 ÷ 칸 수를 [[적재율]]이라고 하고, 이게 일정 값(보통 0.75 안팎)을 넘으면 칸 수를 두 배로 늘리고 모든 원소를 다시 넣습니다. 동적 배열처럼 분할 상환 O(1)입니다.

평균 O(1)이지만 최악은 O(n)입니다. 모든 키가 한 칸에 몰리면 목록을 다 훑어야 하니까요. 공격자가 일부러 같은 칸에 떨어지는 키 수만 개를 보내 서버를 멈추게 하는 공격(해시 플러딩)이 실제로 있었고, 그래서 요즘 언어들은 실행할 때마다 해시 함수에 무작위 값을 섞습니다.

여기서 해시 함수는 14장의 암호학적 해시(SHA-256)와 목적이 다릅니다. 해시 테이블용 해시는 빠르고 고르게 퍼지기만 하면 되고, 암호학적 해시는 되돌리거나 충돌을 찾기 어려워야 합니다.

JS에서 해시 테이블로 쓸 수 있는 것은 두 가지입니다.

| | 객체 `{}` | `Map` |
| --- | --- | --- |
| 키 | 문자열과 심볼만 (숫자는 문자열로 바뀜) | 아무 값 (객체, 함수도) |
| 순서 | 정수 같은 키는 숫자순, 나머지는 넣은 순 | 넣은 순서 그대로 |
| 크기 | `Object.keys(o).length` (O(n)) | `map.size` (O(1)) |
| 함정 | `"__proto__"`, `"constructor"` 같은 키가 프로토타입과 섞임 | 없음 |
| 자주 넣고 빼기 | 느려질 수 있음 (히든 클래스가 계속 바뀜, 5장) | 그 용도로 만듦 |

데이터를 키로 찾는 용도라면 `Map`이 맞습니다. 객체는 모양이 정해진 레코드(`{ id, name }`)에 씁니다.

## 집합

[[집합]]은 중복 없이 "있다, 없다"만 관리하는 구조이고, 보통 해시 테이블로 만듭니다. JS의 `Set`입니다.

```js
const unique = [...new Set(tags)];              // 중복 제거 O(n)
const seen = new Set(selectedIds);
items.filter((it) => seen.has(it.id));          // O(n). seen 대신 배열.includes면 O(n²)
```

"배열에 있는지 반복해서 확인하는" 코드를 `Set.has`로 바꾸는 것은 가장 쉽고 효과가 큰 최적화입니다.

## LRU 캐시: 해시 테이블과 연결 리스트를 함께

캐시는 크기가 정해져 있으니 꽉 차면 무언가를 버려야 합니다. 가장 오래 쓰이지 않은 것을 버리는 정책이 LRU(Least Recently Used)입니다. "키로 O(1)에 찾기"(해시 테이블)와 "쓴 순서대로 줄 세우고 O(1)에 맨 뒤로 옮기기"(양방향 연결 리스트)를 합쳐 만듭니다. JS의 `Map`은 넣은 순서를 지키니, 지웠다 다시 넣으면 맨 뒤로 가는 성질로 간단히 만들 수 있습니다.

```js
class LRU {
  constructor(limit) { this.limit = limit; this.map = new Map(); }
  get(key) {
    if (!this.map.has(key)) return undefined;
    const v = this.map.get(key);
    this.map.delete(key); this.map.set(key, v);           // 방금 쓴 것으로 맨 뒤에
    return v;
  }
  set(key, v) {
    this.map.delete(key); this.map.set(key, v);
    if (this.map.size > this.limit) this.map.delete(this.map.keys().next().value); // 맨 앞(가장 오래됨)을 버림
  }
}
```

7장의 운영체제가 어떤 페이지를 디스크로 내릴지 고를 때, 브라우저가 메모리 캐시에서 무엇을 버릴지 고를 때도 LRU나 그 변형을 씁니다.

## 무엇을 골라야 하나

| 자료구조 | i번째 접근 | 찾기 | 맨 뒤에 넣기 | 맨 앞에 넣기·빼기 | 중간에 넣기·빼기 |
| --- | --- | --- | --- | --- | --- |
| 배열 (동적) | O(1) | O(n) | O(1)* | O(n) | O(n) |
| 정렬된 배열 | O(1) | O(log n) | O(n) | O(n) | O(n) |
| 연결 리스트 | O(n) | O(n) | O(1) | O(1) | O(1) (노드를 알면) |
| 해시 테이블 | — | O(1)* | O(1)* | — | O(1)* (키로) |
| 균형 이진 탐색 트리 (19장) | O(log n) | O(log n) | O(log n) | O(log n) | O(log n) |

별표(*)는 평균 또는 분할 상환 비용입니다.

## 프론트엔드와 이어지는 곳

- 서버에서 받은 목록을 ID로 자주 찾는다면 `{ ids: [...], byId: { ... } }`처럼 정규화해서 둡니다. Redux Toolkit의 `createEntityAdapter`가 이 모양입니다. 해시 테이블로 찾고, 배열로 순서를 지킵니다.
- 렌더링 안의 `find`, `filter`, `includes`를 반복문과 겹쳐 쓰고 있지 않은지 봅니다. 목록이 커지면 화면이 멈추는 주범입니다.
- 불변 업데이트(`[...arr, x]`, `{...obj}`)는 매번 O(n) 복사입니다. 대부분은 괜찮지만, 아주 큰 목록을 자주 바꾸면 Immer처럼 바뀐 부분만 새로 만드는 구조적 공유를 씁니다.
- 10만 줄 목록을 다 그리면 DOM 노드가 10만 개가 됩니다. 화면에 보이는 줄만 그리는 가상화(react-window, TanStack Virtual)는 렌더링을 O(n)에서 O(보이는 줄 수)로 바꿉니다.

## 용어 정리

:::terms
- 자료구조 (data structure) — 데이터를 담고 정리하는 방식. 어떤 연산이 빠르고 느린지가 구조에 따라 정해집니다.
- 알고리즘 (algorithm) — 문제를 푸는 유한하고 정해진 절차입니다.
- 시간 복잡도 (time complexity) — 입력 크기 n이 커질 때 알고리즘의 연산 횟수가 늘어나는 정도입니다.
- 빅오 표기법 (Big-O notation) — 가장 빨리 커지는 항만 남기고 상수를 버려 복잡도의 상한을 O(n²)처럼 적는 방법입니다.
- 공간 복잡도 (space complexity) — 입력 크기에 따라 알고리즘이 추가로 쓰는 메모리가 늘어나는 정도입니다.
- 분할 상환 분석 (amortized analysis) — 가끔 비싼 연산이 섞여 있어도 여러 번에 나눠 평균을 내 한 번당 비용을 따지는 분석입니다.
- 배열 (array) — 같은 크기의 칸을 메모리에 연속으로 둔 구조. 인덱스 접근이 O(1)이고 중간 삽입·삭제는 O(n)입니다.
- 동적 배열 (dynamic array) — 꽉 차면 더 큰 메모리로 옮겨 크기가 늘어나는 배열. 맨 뒤에 넣기가 분할 상환 O(1)입니다. JS 배열이 이렇습니다.
- 연결 리스트 (linked list) — 각 노드가 다음 노드를 가리키도록 이은 구조. 알고 있는 위치의 삽입·삭제는 O(1), 접근은 O(n)입니다.
- 스택 (stack) — 마지막에 넣은 것을 먼저 꺼내는(LIFO) 구조입니다.
- 큐 (queue) — 먼저 넣은 것을 먼저 꺼내는(FIFO) 구조입니다.
- 덱 (deque) — 양쪽 끝에서 모두 넣고 뺄 수 있는 큐입니다.
- 원형 버퍼 (ring buffer) — 고정 크기 배열의 끝과 처음을 이어 쓰는 큐. 네트워크 카드, 오디오, 로그 버퍼에 씁니다.
- 해시 테이블 (hash table) — 키를 해시 함수로 칸 번호로 바꿔 값을 평균 O(1)에 넣고 찾는 구조. JS의 `Map`, `Set`이 이렇습니다.
- 해시 충돌 (hash collision) — 서로 다른 키가 같은 칸 번호를 얻는 것. 체이닝이나 개방 주소법으로 처리합니다.
- 적재율 (load factor) — 해시 테이블의 원소 수를 칸 수로 나눈 값. 일정 값을 넘으면 칸을 늘리고 다시 배치합니다.
- 집합 (set) — 중복 없이 원소가 있는지 없는지만 관리하는 구조입니다.
- LRU (Least Recently Used) — 가장 오래 쓰이지 않은 것을 먼저 버리는 캐시 교체 정책입니다.
:::

## 직접 해보기

:::practice includes-vs-set includes와 Set.has 속도 재기
10만 개 배열에서 10만 번 찾기를 `includes`와 `Set.has`로 각각 해서 시간을 비교합니다. n을 1만, 10만으로 바꿔 가며 시간이 어떻게 늘어나는지(제곱으로, 선형으로) 표로 적습니다.

```js 브라우저 콘솔 또는 node
for (const n of [10_000, 100_000]) {
  const arr = Array.from({ length: n }, (_, i) => i);
  const set = new Set(arr);
  let t = performance.now(); let hit = 0;
  for (let i = 0; i < n; i++) if (arr.includes(n - i)) hit++;
  const a = performance.now() - t;
  t = performance.now();
  for (let i = 0; i < n; i++) if (set.has(n - i)) hit++;
  const b = performance.now() - t;
  console.log(n, "includes", Math.round(a), "ms / Set", b.toFixed(1), "ms");
}
```
:::

:::practice shift 배열 shift 큐와 번호 큐 비교하기
원소 10만 개를 큐에 넣고 모두 꺼내는 데 `arr.shift()`와 이 장의 `Queue` 클래스가 각각 얼마나 걸리는지 잽니다. 큐를 쓰는 BFS 같은 코드를 짤 때 어떤 쪽을 써야 하는지 결론을 적습니다.
:::

:::practice lru LRU 캐시 만들고 시험하기
이 장의 `LRU` 클래스를 크기 3으로 만들고, `set(a) set(b) set(c) get(a) set(d)` 순서로 했을 때 어떤 키가 버려지는지 먼저 예상한 뒤 확인합니다. 그리고 이 캐시를 `fetch` 결과를 담는 데 써 보고, 같은 URL을 다시 부르면 네트워크 탭에 요청이 안 생기는지 봅니다.
:::

// (1)
const names = users.map((u) => u.name).filter((n) => n.startsWith("김"));
// (2)
const result = items.reduce((acc, it) => [...acc, it.id], []);

## 스스로 점검

:::qa 직접 해보기 "코드의 복잡도 맞히기"의 네 코드는 각각 몇인가요?
(1) `map`과 `filter`가 각각 한 번씩 훑으니 O(n)입니다. (2) 매번 지금까지의 배열을 펼쳐 복사하니 1 + 2 + … + n = O(n²)입니다. (3) i가 매번 두 배가 되니 O(log n)입니다. (4) Map을 만드는 데 O(p), 댓글마다 O(1) 조회로 O(c), 합쳐서 O(p + c)입니다.
:::

:::qa 배열의 i번째 원소를 O(1)에 읽을 수 있는 이유와, 중간에 끼워 넣기가 O(n)인 이유는?
배열은 칸이 메모리에 연속으로 있어서 i번째 주소를 "시작 주소 + i × 칸 크기"로 바로 계산할 수 있습니다. 중간에 넣으려면 그 뒤의 원소들을 모두 한 칸씩 옮겨 자리를 만들어야 해서 최악에 n개를 옮깁니다.
:::

:::qa JS 배열의 `push`는 가끔 메모리를 통째로 옮기는데도 왜 O(1)이라고 하나요?
동적 배열은 꽉 차면 두 배 크기로 늘리니 옮기는 일은 크기가 두 배가 될 때마다 한 번뿐입니다. n번 push하는 동안 옮기는 총량이 n의 상수 배라서, 한 번당 분할 상환 비용은 O(1)입니다.
:::

:::qa 해시 테이블의 조회가 평균 O(1)인데 최악이 O(n)인 이유는? 실제로 이게 문제가 된 적이 있나요?
보통은 키들이 칸에 고르게 퍼져 칸마다 원소가 몇 개뿐이지만, 많은 키가 한 칸에 충돌하면 그 칸의 목록을 다 훑어야 합니다. 공격자가 일부러 충돌하는 키를 대량으로 보내 서버를 멈추게 하는 해시 플러딩 공격이 실제로 있었고, 그래서 언어들이 해시에 실행마다 무작위 값을 섞습니다.
:::

:::qa BFS에서 큐를 `arr.shift()`로 만들면 무엇이 문제인가요?
`shift`는 맨 앞을 빼고 나머지를 모두 한 칸씩 당기니 O(n)입니다. 노드가 많으면 꺼낼 때마다 O(n)이 들어 전체가 O(n²)이 됩니다. 앞 번호를 따로 두는 큐나 원형 버퍼로 꺼내기를 O(1)로 만듭니다.
:::
