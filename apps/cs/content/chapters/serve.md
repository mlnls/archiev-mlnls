![이 사이트를 이루는 서버들. 모든 요청은 Caddy 하나로 들어와 이름과 경로에 따라 이 책의 nginx, 블로그의 Next.js, API로 나뉩니다. 코드는 main에 머지되면 GitHub Actions가 이미지로 만들어 서버에 내보냅니다](serve-scene.svg)

웹 서비스 하나는 보통 역할이 다른 서버 여러 개가 함께 돌아가며 만들어집니다. 이 장은 그림 속 상자들, 정적 파일 서버와 API 서버와 리버스 프록시부터 봅니다. 그다음 이 사이트에는 아직 없지만 서비스가 커지면 붙는 서버들(로드 밸런서, CDN, 캐시, 큐)로 넓혀 가고, 마지막에 그림 아래쪽의 배포와 운영을 봅니다. 이 서버들은 각자 앞에서 배운 개념 하나씩을 크게 키운 것들이라, 읽다 보면 2부와 3부의 내용이 계속 다시 나옵니다.

## 정적 파일 서버

가장 단순한 서버는 디스크의 파일을 그대로 보내 주는 [[웹 서버]]입니다. 요청 경로를 파일 경로로 바꿔(`/assets/app.js` → `/usr/share/nginx/html/assets/app.js`), 파일이 있으면 내용과 함께 확장자에 맞는 MIME 타입(14장)을 붙여 보내고, 없으면 404를 보냅니다. nginx, Caddy, Apache가 대표적입니다.

정적 파일 서버가 빠른 이유는 앞의 장들에 다 있습니다.

- 자주 요청되는 파일은 운영체제의 페이지 캐시(8장)에 이미 올라가 있어 디스크에 가지 않습니다.
- nginx는 epoll(8장)로 연결 수만 개를 적은 프로세스로 받습니다.
- 파일을 사용자 공간으로 읽어 들였다가 소켓에 다시 쓰지 않고, `sendfile` 시스템 콜로 커널이 페이지 캐시에서 소켓으로 바로 보냅니다. 데이터를 복사하는 횟수를 줄여 CPU를 아낍니다.

이 사이트가 정적 파일 서버입니다. 빌드할 때 Node로 모든 장을 HTML로 만들어 두고, 서버에서는 nginx가 그 파일들을 보내기만 합니다. 요청마다 계산할 게 없으니 메모리 48MB짜리 컨테이너로도 충분합니다.

React나 Vue로 만든 SPA도 빌드 결과는 정적 파일입니다. 다만 `/posts/1` 같은 주소로 바로 들어오면 그런 파일이 없으니, 파일이 없을 때 `index.html`을 대신 보내도록 설정합니다(nginx의 `try_files $uri /index.html`). 14장에서 본 경로 라우팅의 서버 쪽 설정입니다.

페이지 캐시 덕분입니다(8장). 한 번 읽은 파일은 RAM에 남아 있고, nginx는 `sendfile`로 거기서 소켓으로 바로 보냅니다. HTML은 `no-cache`라 브라우저가 매번 확인 요청을 보내고, Caddy는 이 사이트에서 응답을 저장하지 않습니다.
:::

:::quiz spa-fallback Vite로 만든 SPA를 nginx에 올렸습니다. 첫 화면에서 링크를 눌러 `/posts/1`로 가면 잘 보이는데, 거기서 새로고침하면 404가 납니다. 고칠 곳은?

:::

## 동적 서버와 API

요청마다 내용이 달라야 하면 코드를 실행해 응답을 만드는 서버가 필요합니다. 로그인한 사용자의 글 목록, 검색 결과, 결제가 그렇습니다. 이런 서버는 대개 이런 구조입니다.

1. **라우팅**: 메서드와 경로를 보고 처리할 함수를 고릅니다. `GET /posts/:id` → `getPost`.
2. **미들웨어**: 모든 요청에 공통으로 할 일을 앞뒤에 끼웁니다. 로그, 인증 확인, 본문 파싱, CORS 헤더.
3. **처리**: 데이터베이스를 읽고 쓰고, 다른 서버를 부르고, 결과를 만듭니다.
4. **응답**: 상태 코드, 헤더, 본문(HTML이나 JSON)을 씁니다.

화면 없이 데이터만 주고받는 서버의 창구를 [[API]]라고 부릅니다. 웹 API를 설계하는 가장 흔한 방식이 [[REST]]입니다. 다루는 대상을 자원으로 보고 URL로 이름 붙인 뒤, 14장의 HTTP 메서드와 상태 코드를 그 뜻대로 씁니다.

| 하는 일 | 요청 | 응답 |
| --- | --- | --- |
| 글 목록 | `GET /posts?tag=cs` | `200` + 글 배열 JSON |
| 글 하나 | `GET /posts/42` | `200` 또는 `404` |
| 글 쓰기 | `POST /posts` + JSON 본문 | `201` + `Location: /posts/43` |
| 글 고치기 | `PATCH /posts/42` | `200` |
| 글 지우기 | `DELETE /posts/42` | `204` |

REST 말고도 클라이언트가 필요한 필드를 쿼리로 골라 받는 GraphQL, 함수 호출처럼 주고받는 RPC(gRPC, tRPC)가 있습니다.

HTML을 어디서 만드느냐에 따라 웹 앱을 그리는 방식도 나뉩니다.

| 방식 | HTML을 만드는 곳과 때 | 필요한 서버 |
| --- | --- | --- |
| CSR | 브라우저가 JS로 그림. 서버는 빈 HTML과 JS만 줌 | 정적 파일 서버 + API 서버 |
| [[SSR]] | 요청마다 서버가 HTML을 만들어 줌 | 늘 떠 있는 Node 서버 |
| [[SSG]] | 빌드할 때 모든 페이지의 HTML을 미리 만들어 둠 | 정적 파일 서버 (이 사이트) |
| ISR, 캐시된 SSR | 서버가 만든 HTML을 캐시해 두고 가끔 다시 만듦 | Node 서버 + 캐시 |

:::quiz ssg 이 책처럼 빌드할 때 모든 페이지의 HTML을 미리 만들어 두고, 서버는 파일만 보내는 방식을 표의 약자로 무엇이라 할까요?
= SSG

**SSG**(정적 사이트 생성)입니다. 요청마다 계산할 게 없으니 서버는 48MB짜리 nginx 컨테이너면 충분하고, CDN에 그대로 올릴 수도 있습니다. 대신 글을 고치면 다시 빌드해 배포해야 합니다.
:::

## 리버스 프록시

서버 앞에 서서 요청을 대신 받아 뒤의 서버에 넘기고, 받은 응답을 다시 클라이언트에 돌려주는 서버를 [[리버스 프록시]]라고 합니다. 클라이언트는 뒤에 무엇이 있는지 모르고 리버스 프록시하고만 대화합니다. 반대로 클라이언트 쪽에 서서 클라이언트 대신 바깥으로 요청을 내보내는 것은 [[포워드 프록시]]입니다. 회사 네트워크의 프록시나 VPN이 그쪽입니다.

![포워드 프록시는 클라이언트 쪽에 서서 대신 나가 주고, 리버스 프록시는 서버 쪽에 서서 대신 받아 줍니다. 어느 쪽이든 상대는 프록시만 봅니다](serve-proxy.svg)

리버스 프록시가 하는 일은 많습니다.

- **이름과 경로로 나눠 보내기**: `Host` 헤더(14장의 가상 호스팅)나 경로를 보고 어느 서버로 보낼지 정합니다.
- **TLS 종료**: HTTPS를 여기서 풀고 안쪽에는 HTTP로 넘깁니다(16장).
- **압축과 보안 헤더**: gzip, zstd 압축과 HSTS 같은 헤더를 모든 사이트에 한꺼번에 붙입니다.
- **느린 클라이언트 받아 주기**: 느린 휴대폰 회선이 응답을 천천히 받아 가는 동안 앱 서버가 붙잡혀 있지 않게, 프록시가 응답을 받아 두고 대신 천천히 보냅니다.
- **제한**: 요청 본문 크기 제한(413), 요청 수 제한(429).
- **원래 정보 전달**: 앱이 보기에는 모든 요청이 프록시에서 온 것이니, 프록시가 원래 사용자 IP와 프로토콜을 [[X-Forwarded-For]], `X-Forwarded-Proto` 헤더로 붙여 줍니다. 앱은 믿을 수 있는 프록시가 붙인 값만 믿어야 합니다. 사용자가 이 헤더를 직접 위조해서 보낼 수도 있으니까요.

이 사이트의 리버스 프록시인 Caddy 설정을 읽어 보면 위의 일이 그대로 보입니다.

```text deploy/Caddyfile.mlnl를 간추린 것
(mlnl_common) {
	encode zstd gzip                                   # 압축
	header Strict-Transport-Security "max-age=31536000" # HSTS
}

blog.도메인 {                                          # Host가 blog.… 이면 (인증서도 자동)
	import mlnl_common
	handle_path /api/* {                               # 경로가 /api/로 시작하면
		request_body { max_size 6MB }                  # 6MB 넘으면 413
		reverse_proxy mlnl-api:4000                    # API 컨테이너로
	}
	handle {
		reverse_proxy mlnl-blog:3000                   # 나머지는 블로그(Next.js)로
	}
}

cs.도메인 {
	import mlnl_common
	reverse_proxy mlnl-cs:80                           # 이 책(nginx)으로
}
```

:::quiz real-ip Caddy 뒤의 API 서버가 `req.socket.remoteAddress`로 요청한 사람의 IP를 기록합니다. 무엇이 찍힐까요?
- [ ] 사용자 노트북의 사설 IP (192.168.0.23)
- [ ] 사용자 집 공유기의 공인 IP
- [x] Caddy 컨테이너의 Docker 네트워크 주소
- [ ] 127.0.0.1

Caddy의 주소입니다. API가 맺은 TCP 연결의 상대는 사용자가 아니라 Caddy니까요. 원래 사용자의 IP는 Caddy가 붙여 주는 `X-Forwarded-For` 헤더에서 읽되, 믿을 수 있는 프록시가 붙인 값만 믿습니다.
:::

## 로드 밸런서

앱 서버 한 대로 요청을 감당하지 못하면 같은 앱을 여러 대 띄우고, 앞에서 요청을 나눠 줍니다. 이 일을 하는 것이 [[로드 밸런서]]입니다. 리버스 프록시가 뒤의 서버 여럿에 나눠 보내면 로드 밸런서가 됩니다.

| 나누는 방법 | 규칙 |
| --- | --- |
| 라운드 로빈 | 차례로 돌아가며 |
| 최소 연결 | 지금 연결이 가장 적은 서버로 |
| 가중치 | 큰 서버에 더 많이 |
| IP 해시 | 같은 사용자 IP는 늘 같은 서버로 |

로드 밸런서는 뒤의 서버들에 주기적으로 요청을 보내 살아 있는지 확인합니다. 이걸 [[헬스 체크]]라고 합니다. 응답이 없는 서버는 빼고, 살아나면 다시 넣습니다. 이 사이트의 컨테이너들도 Dockerfile의 `HEALTHCHECK`로 nginx가 응답하는지 확인하고, 배포 스크립트는 새 컨테이너가 healthy가 될 때까지 기다렸다가 안 되면 옛 이미지로 되돌립니다.

로드 밸런서가 보는 층에 따라 둘로 나뉩니다. L4 로드 밸런서는 12장의 TCP 연결 단위로 나누고(내용을 보지 않아 빠름), L7 로드 밸런서는 HTTP 요청을 열어 경로나 헤더를 보고 나눕니다(9장의 계층 번호가 여기서 쓰입니다). AWS의 NLB가 L4, ALB가 L7입니다.

서버를 여러 대 두려면 앱이 요청 사이의 상태를 자기 메모리에 들고 있으면 안 됩니다. 사용자의 다음 요청이 다른 서버로 갈 수 있으니까요. 세션은 데이터베이스나 Redis에 두고, 업로드 파일은 공유 저장소에 둡니다. 이 이야기는 24장 시스템 설계에서 이어집니다.

:::quiz l7 `/api/`로 시작하는 요청은 API 서버들로, 나머지는 프론트 서버들로 나누고 싶습니다. 필요한 로드 밸런서는?
- [ ] L4 로드 밸런서: TCP 연결만 보고 나누니까 충분하다
- [x] L7 로드 밸런서: HTTP 요청을 열어 경로를 봐야 하니까
- [ ] DNS 라운드 로빈: 이름마다 IP를 다르게 주면 된다
- [ ] 아무거나: 경로는 IP 헤더에 들어 있다

L7입니다. 경로는 HTTP 요청 안에 있어서 TCP 연결만 보는 L4로는 알 수 없습니다. 이 사이트의 Caddy가 `/api/*`를 API 컨테이너로 보내는 것도 L7에서 하는 일입니다.
:::

## CDN

[[CDN]](콘텐츠 전송 네트워크)은 세계 곳곳에 캐시 서버를 두고, 사용자와 가까운 곳에서 응답을 주는 서비스입니다. 9장에서 본 것처럼 빛의 속도는 줄일 수 없으니, 서울 사용자에게 미국 서버의 파일을 주는 대신 서울에 복사본을 둡니다.

1. 사용자가 `cdn.example.com/app.js`를 요청하면, DNS나 애니캐스트(11장, 13장)가 가장 가까운 CDN 서버(엣지)로 보냅니다.
2. 엣지에 캐시가 있으면 바로 줍니다(캐시 적중).
3. 없으면 원래 서버인 [[오리진]]에 받아 와서 사용자에게 주고, 14장의 `Cache-Control`에 맞춰 저장해 둡니다.

해시가 붙은 JS, CSS, 이미지, 폰트처럼 모두에게 같은 정적 파일이 CDN에 딱 맞습니다. CDN은 캐시 말고도 TLS를 사용자 가까이에서 풀어 핸드셰이크 왕복을 줄이고, 엄청난 양의 공격 트래픽(DDoS)을 흡수해 오리진을 보호합니다. Cloudflare, AWS CloudFront, Fastly, Akamai가 대표적이고, Vercel과 Netlify도 정적 파일을 자기 CDN으로 내보냅니다.

:::quiz cdn-fit CDN의 엣지에 캐시해 두기에 가장 알맞은 것은?
- [x] 이름에 해시가 붙은 `/assets/app.c81e….js`
- [ ] 로그인한 사용자의 장바구니 API 응답
- [ ] 결제를 만드는 `POST /payments`
- [ ] 관리자만 보는 통계 페이지

해시가 붙은 정적 파일입니다. 모든 사용자에게 똑같고 내용이 바뀌면 이름이 바뀌니, 세계 곳곳에 오래 복사해 둬도 문제가 없습니다. 사용자마다 다르거나 상태를 바꾸는 요청은 오리진이 직접 처리해야 합니다.
:::

## 데이터베이스 서버

데이터를 오래, 안전하게, 여럿이 함께 쓰려면 데이터베이스가 필요합니다. PostgreSQL이나 MySQL은 5432번, 3306번 포트에서 듣는 서버 프로세스이고, 앱 서버가 12장의 연결 풀로 미리 연결을 맺어 두고 SQL을 보냅니다. 데이터베이스는 인터넷에 절대 직접 열지 않습니다. 앱 서버와 같은 사설 네트워크에서만 접근하게 하고, 관리할 때는 SSH 포트 포워딩(15장)으로 들어갑니다. 데이터베이스가 안에서 어떻게 동작하는지는 6부(21, 22장)에서 봅니다.

이 사이트의 API처럼 작은 서비스는 별도 DB 서버 없이 SQLite 파일 하나를 Docker 볼륨에 두고 쓰기도 합니다(이 저장소는 SQLite를 이어 만든 libSQL을 씁니다). 서버 프로세스가 아니라 앱 안의 라이브러리로 동작하는 데이터베이스입니다.

## 캐시 서버

데이터베이스 조회나 외부 API 호출이 느리고 자주 반복된다면, 결과를 메모리에 잠시 저장해 둡니다. 여러 앱 서버가 함께 쓰는 메모리 저장소를 따로 두는데, 가장 많이 쓰는 것이 [[Redis]]입니다. 키-값을 메모리에 두는 서버라 조회가 1ms도 안 걸립니다.

가장 흔한 사용법은 [[캐시 어사이드]]입니다.

```js
async function getPost(id) {
  const cached = await redis.get(`post:${id}`);
  if (cached) return JSON.parse(cached);                          // 캐시 적중
  const post = await db.query("SELECT … WHERE id = $1", [id]);     // 미스면 DB에서
  await redis.set(`post:${id}`, JSON.stringify(post), { EX: 60 }); // 60초 동안 캐시
  return post;
}
```

어려운 건 데이터가 바뀌었을 때입니다. 글을 고쳤는데 캐시에 옛 글이 남아 있으면 사용자는 옛 글을 봅니다. 쓸 때 캐시를 지우거나, 만료 시간을 짧게 두거나, 잠깐 옛 데이터가 보여도 괜찮은 곳에만 캐시를 씁니다. "컴퓨터 과학에서 어려운 일은 캐시 무효화와 이름 짓기 두 가지뿐"이라는 말이 있을 정도입니다. Redis는 캐시 말고도 세션 저장, 요청 수 제한 계수기, 순위표, 간단한 작업 큐로도 씁니다.

## 메시지 큐와 백그라운드 작업

회원 가입 요청을 받았는데 환영 메일 보내기, 프로필 이미지 줄이기, 분석 기록 남기기까지 다 끝내고 응답하면 사용자는 몇 초를 기다립니다. 이런 일은 "할 일"로 적어만 두고 응답은 바로 보낸 뒤, 다른 프로세스가 나중에 처리하게 합니다.

할 일을 쌓아 두는 곳이 [[메시지 큐]]이고, 꺼내서 처리하는 프로세스가 [[워커]]입니다. 6장의 생산자-소비자 구조를 서버 여러 대로 넓힌 것입니다.

![API 서버는 오래 걸리는 일을 큐에 적어만 두고 바로 응답합니다. 워커들이 큐에서 하나씩 꺼내 처리합니다](serve-queue.svg)

- 보내는 쪽과 처리하는 쪽이 서로를 기다리지 않습니다. 워커가 잠깐 죽어도 일은 큐에 남아 있다가 살아나면 처리됩니다.
- 갑자기 일이 몰려도 큐에 쌓였다가 워커가 감당할 속도로 처리됩니다.
- 실패한 일은 몇 번 다시 시도하고, 계속 실패하면 따로 모아 둡니다(데드 레터 큐).

RabbitMQ, Apache Kafka, AWS SQS, Redis 기반의 BullMQ가 많이 쓰입니다. Kafka는 큐라기보다 엄청난 양의 이벤트를 순서대로 저장하고 여러 소비자가 각자 읽어 가는 로그에 가깝습니다. 이 사이트의 저장소에도 채용 공고를 모으는 일을 따로 하는 `employ-worker` 앱이 있습니다.

:::quiz mail-down 가입하면 환영 메일을 큐에 넣는 구조입니다. 메일 발송 서비스가 10분 동안 멈췄다면?
- [ ] 10분 동안 가입 요청이 모두 실패한다
- [ ] 메일 작업이 사라져 아무에게도 메일이 가지 않는다
- [x] 가입은 바로 성공하고, 메일 작업은 큐에 남았다가 서비스가 살아나면 다시 시도된다
- [ ] API 서버가 메일이 갈 때까지 응답을 미룬다

가입은 정상입니다. API는 할 일을 큐에 적고 바로 응답하니 메일 서비스와 상관없이 끝납니다. 워커는 실패한 작업을 다시 시도하고, 계속 실패하면 데드 레터 큐로 모아 둡니다.
:::

## 실시간 통신

HTTP는 클라이언트가 물어야 서버가 답합니다. 채팅, 알림, 협업 편집처럼 서버가 먼저 알려 줘야 하는 경우에는 방법이 몇 가지 있습니다.

| 방법 | 어떻게 | 특징 |
| --- | --- | --- |
| 폴링 | 몇 초마다 "새 소식 있어?" 요청 | 단순하지만 대부분 헛걸음이고 늦음 |
| [[롱 폴링]] | 요청을 보내 두면 서버가 새 소식이 생길 때까지 답을 미룸 | 늦지 않지만 연결을 계속 다시 맺음 |
| [[SSE]] (Server-Sent Events) | HTTP 응답 하나를 끝내지 않고 서버가 계속 이어 씀 | 서버 → 클라이언트 한 방향. 단순하고 HTTP 그대로. AI 챗봇의 글자가 흘러나오는 방식 |
| [[WebSocket]] | HTTP로 시작해 `101 Switching Protocols`로 바꾼 뒤 TCP 연결 위에서 양방향 메시지 | 양방향, 지연이 작음. 채팅, 게임, 협업 |

WebSocket과 SSE는 연결 하나를 오래 붙잡고 있습니다. 그래서 서버는 연결 수만큼 소켓(파일 디스크립터)과 메모리를 쓰고, 중간의 리버스 프록시와 로드 밸런서가 "오래 조용한 연결"을 끊지 않도록 시간 제한을 늘리거나 주기적으로 작은 핑을 보냅니다. 서버리스 함수(15장)가 이런 연결에 맞지 않는 이유이기도 합니다.

:::quiz stream-text AI 챗봇처럼 서버가 답을 몇 글자씩 이어서 흘려보내기만 하면 됩니다. 가장 단순한 방법은?
- [ ] 1초마다 폴링
- [ ] WebSocket
- [ ] 롱 폴링
- [x] SSE (Server-Sent Events)

SSE입니다. 서버에서 클라이언트로 한 방향이면 HTTP 응답 하나를 끝내지 않고 이어 쓰는 것으로 충분합니다. 양방향으로 자주 주고받아야 할 때 WebSocket을 씁니다.
:::

## 정해진 시간에 하는 일: 크론

매일 새벽 백업, 매시간 통계 집계, 매일 아침 8시에 공고 모으기처럼 정해진 시각에 할 일은 [[크론]]으로 돌립니다. 크론은 유닉스의 시간 예약 데몬이고, 시각은 다섯 칸으로 적습니다.

```text
┌ 분 (0-59)
│ ┌ 시 (0-23)
│ │ ┌ 일 (1-31)
│ │ │ ┌ 월 (1-12)
│ │ │ │ ┌ 요일 (0-6, 일요일=0)
0 8 * * *   매일 8시 0분     (이 사이트 API의 BATCH_CRON 값)
*/5 * * * * 5분마다
0 3 * * 1   매주 월요일 3시
```

| | Linux | macOS | Windows |
| --- | --- | --- | --- |
| 시간 예약 | `crontab -e`, systemd 타이머 | launchd의 `StartCalendarInterval` (cron도 있음) | 작업 스케줄러 (`schtasks`) |

서버의 시계는 보통 UTC입니다. "매일 8시"가 한국 시각 8시인지 UTC 8시(한국 17시)인지 꼭 확인합니다. 그리고 서버를 여러 대 두면 크론도 여러 대에서 동시에 돌아 같은 일을 두 번 할 수 있으니, 한 곳에서만 돌게 하거나 잠금을 겁니다(6장).

:::quiz cron-utc 서버 시계가 UTC입니다. 크론에 `0 8 * * *`를 적으면 한국 시각으로 매일 몇 시에 돌까요? (숫자만)
= 17 | 17시 | 오후5시

**17시**입니다. 한국 시각은 UTC보다 9시간 빠르니 UTC 8시는 한국 17시입니다. 한국 8시에 돌리려면 `0 23 * * *`(전날 UTC 23시)로 적거나, 크론의 시간대를 `Asia/Seoul`로 정합니다.
:::

## 파일과 미디어 저장

사용자가 올린 이미지와 동영상은 앱 서버의 디스크에 두면 곤란합니다. 서버를 여러 대로 늘리면 파일이 한 서버에만 있고, 서버를 새로 만들면 사라집니다. 그래서 파일은 [[오브젝트 스토리지]]에 둡니다. AWS S3, Cloudflare R2, Google Cloud Storage처럼 파일을 키(경로)로 넣고 꺼내는 거의 무한한 저장소입니다. 브라우저가 앱 서버를 거치지 않고 저장소로 바로 올리도록, 서버가 잠깐만 유효한 서명된 업로드 주소(presigned URL)를 만들어 주는 방식을 많이 씁니다.

컨테이너에서는 컨테이너를 지우고 새로 만들어도 남아야 하는 데이터를 [[볼륨]]에 둡니다. 볼륨은 컨테이너 바깥(호스트 디스크)에 있는 디렉터리를 컨테이너 안에 마운트(8장)한 것입니다. 이 사이트의 `docker-compose.yml`에서 API의 `data` 볼륨과 아카이브의 `archive` 볼륨이 그렇습니다. 볼륨에 있는 데이터는 따로 백업해야 합니다.

## 곁가지: 그 밖에 직접 돌릴 수 있는 것들

서버가 있으면 남이 제공하는 서비스를 내 서버에서 직접 돌릴 수도 있습니다. 이걸 [[셀프호스팅]]이라고 하고, GitHub의 awesome-selfhosted 목록에 수천 가지가 정리되어 있습니다.

| 분류 | 예 |
| --- | --- |
| 코드와 협업 | Gitea, Forgejo (GitHub 대신), Outline, Wiki.js |
| 개인 클라우드 | Nextcloud (파일 동기화), Immich (사진), Vaultwarden (비밀번호) |
| 미디어 | Jellyfin (영상), Navidrome (음악) |
| 네트워크 | WireGuard (VPN), AdGuard Home, Pi-hole (DNS로 광고 차단, 13장) |
| 지켜보기 | Uptime Kuma (사이트가 살아 있는지), Grafana, Prometheus |
| 분석 | Umami, Plausible (개인정보를 덜 모으는 방문 분석) |

메일 서버는 가능하지만 어렵습니다. 스팸 필터들이 개인 서버에서 온 메일을 잘 믿지 않아서, SPF, DKIM, DMARC를 DNS에 맞게 넣고(13장의 TXT 레코드) 서버 IP의 평판까지 관리해야 합니다. 그래서 보내는 메일은 보통 전문 서비스(SES, Resend)를 씁니다.

## 여러 서버를 함께 돌리기: Docker Compose

앱 서버, 데이터베이스, Redis, 워커, 리버스 프록시를 각각 `docker run`으로 띄우면 관리가 어렵습니다. [[Docker Compose]]는 여러 컨테이너의 이미지, 환경 변수, 네트워크, 볼륨, 재시작 규칙을 YAML 파일 하나에 적고 한 번에 띄웁니다.

```yaml deploy/docker-compose.yml를 간추린 것
services:
  mlnl-cs:
    image: ghcr.io/mlnls/archiev-mlnls/cs:latest   # 레지스트리의 이미지 (15장)
    restart: unless-stopped                        # 죽으면 다시 띄움
    mem_limit: 48m                                 # cgroups 메모리 제한 (7장, 15장)
    networks: [edge]                               # Caddy와 같은 네트워크. ports:가 없으니 바깥에 안 열림

  mlnl-api:
    image: ghcr.io/mlnls/archiev-mlnls/api:latest
    environment:
      SESSION_SECRET: ${SESSION_SECRET}            # 비밀 값은 서버의 .env에서
      ALLOWED_ORIGINS: https://blog.${SITE_DOMAIN} # CORS 허락 목록 (14장)
      BATCH_CRON: "0 8 * * *"                      # 크론
    volumes:
      - data:/data                                 # 볼륨

networks:
  edge:
    external: true                                 # 다른 프로젝트의 Caddy가 만든 네트워크
```

서버가 여러 대로 늘어나 컨테이너 수백 개를 여러 서버에 나눠 배치하고, 죽으면 다른 서버에 다시 띄우고, 부하에 따라 개수를 늘리고 줄이는 일까지 자동으로 하려면 [[오케스트레이션]] 도구가 필요합니다. Kubernetes가 대표적입니다. 작은 서비스에는 과하고, Compose나 PaaS로 충분한 경우가 많습니다.

## 배포: 코드가 서버에 닿기까지

코드를 고칠 때마다 손으로 서버에 들어가 빌드하고 재시작하면 실수가 생깁니다. 그래서 테스트, 빌드, 배포를 자동으로 잇습니다. 이걸 [[CI/CD]]라고 합니다. CI(지속적 통합)는 코드를 합칠 때마다 자동으로 테스트하고 빌드하는 것, CD(지속적 배포)는 통과한 것을 자동으로 서버에 내보내는 것입니다.

이 사이트의 배포 흐름은 이렇습니다(`.github/workflows/deploy.yml`, `deploy/deploy.sh`).

1. `main` 브랜치에 코드가 합쳐지면 GitHub Actions가 시작됩니다.
2. 바뀐 앱만 골라 테스트합니다.
3. 앱마다 Dockerfile로 `linux/amd64` 이미지를 만들고(2장), 커밋 해시를 태그로 붙여 `ghcr.io`에 올립니다.
4. 배포 전용 SSH 키로 서버에 접속합니다. 이 키는 `deploy.sh`만 실행할 수 있습니다(15장).
5. `deploy.sh`가 새 이미지를 받아 그 컨테이너만 새로 띄웁니다.
6. 새 컨테이너가 60초 안에 헬스 체크를 통과하지 못하면 옛 이미지로 되돌리고 실패를 알립니다. 이게 [[롤백]]입니다.

서비스를 멈추지 않고 새 버전으로 바꾸는 것을 [[무중단 배포]]라고 합니다. 서버가 여러 대면 한 대씩 바꾸거나(롤링), 새 버전 묶음을 옆에 통째로 띄워 두고 로드 밸런서의 방향만 한 번에 돌립니다(블루-그린). 옛 프로세스는 6장의 SIGTERM을 받아 처리 중인 요청을 마치고 끝나야 사용자가 오류를 보지 않습니다.

## 운영: 살아 있는지, 느려지지 않았는지

서버를 띄웠다고 끝이 아닙니다. 지금 잘 돌고 있는지 계속 알아야 합니다. 이걸 [[모니터링]]이라고 합니다.

- **로그**: 무슨 일이 있었는지의 기록. 요청, 오류, 중요한 동작을 남깁니다. 서버 여러 대의 로그는 한곳에 모아 검색합니다.
- **지표**: 시간에 따른 숫자. CPU, 메모리, 디스크, 초당 요청 수, 오류 비율, 응답 시간.
- **추적**: 요청 하나가 프록시, 앱, DB, 외부 API를 거치며 각 구간에서 얼마나 걸렸는지.
- **알림**: 오류 비율이나 응답 시간이 기준을 넘으면 사람에게 알립니다.

응답 시간은 평균보다 [[백분위수]]로 봅니다. p50(중앙값)은 절반의 요청이 이보다 빠르다는 뜻이고, p99는 100개 중 가장 느린 1개 수준입니다. 평균이 100ms여도 p99가 3초면, 페이지마다 요청을 수십 개 보내는 사용자는 거의 매번 3초짜리 하나를 만납니다. 그래서 "느리다"는 불만은 꼬리(p95, p99)에서 옵니다.

밖에서 1분마다 내 사이트에 요청을 보내 응답이 없으면 알려 주는 업타임 모니터(Uptime Kuma, UptimeRobot)는 가장 쉽고 효과가 큰 첫걸음입니다. 브라우저 쪽 오류는 Sentry 같은 도구로 모읍니다.

## 다시 장면으로: 4부를 마치며

맨 앞 그림은 이제 이렇게 읽힙니다. 가비아의 와일드카드 레코드가 모든 이름을 이 서버로 보내고, Lightsail의 방화벽을 지난 요청은 리버스 프록시 Caddy가 받습니다. Caddy는 인증서를 받아 TLS를 풀고, `Host`와 경로를 보고 정적 파일 서버(이 책의 nginx), SSR 서버(블로그의 Next.js), REST API(SQLite 볼륨과 크론을 가진 Node)로 나눠 보냅니다. 응답은 압축되고 HSTS가 붙어 돌아갑니다. 코드는 main에 머지되면 GitHub Actions가 테스트하고 이미지로 만들어, 배포 전용 키로 `deploy.sh`를 부르고, 헬스 체크를 통과하지 못하면 되돌립니다.

4부는 여기서 끝납니다. 이 페이지의 요청 하나가 브라우저를 떠나 서버에 닿고 응답이 돌아오는 길을 끝까지 따라왔습니다. 그런데 그 길의 양 끝에 있는 프로그램들은 데이터를 어떤 모양으로 들고 있을까요? 이 책의 빌드 스크립트는 용어 657개를 배열이 아니라 `Map`에 넣어 두고, 본문에서 `[[용어]]`를 만날 때마다 찾습니다. 왜 배열이 아니라 `Map`일까요? 5부는 서버와 브라우저 안의 프로그램이 쓰는 재료, 자료구조와 알고리즘으로 들어갑니다.

## 프론트엔드와 이어지는 곳

- 프론트엔드 빌드 결과는 정적 파일이니, CDN에 올리고 해시 파일은 오래, HTML은 짧게 캐시하는 것이 기본 배포입니다.
- 개발 서버의 `proxy` 설정은 작은 리버스 프록시입니다. 운영에서는 nginx, Caddy, 플랫폼의 rewrites가 같은 일을 합니다.
- 실시간 기능이 필요하면 단방향이면 SSE, 양방향이면 WebSocket을 고르고, 배포 환경(서버리스인지)이 오래 가는 연결을 받아 주는지 먼저 확인합니다.
- API 응답이 느리면 프론트에서 로딩을 꾸미기 전에, 서버 쪽에서 캐시나 백그라운드 작업으로 옮길 수 있는지 봅니다.

## 용어 정리

:::terms
- 웹 서버 (web server) — HTTP 요청을 받아 정적 파일을 보내거나 뒤의 앱으로 넘기는 서버 프로그램. nginx, Caddy, Apache.
- API (Application Programming Interface) — 프로그램끼리 기능을 주고받는 약속된 창구. 웹에서는 주로 HTTP로 JSON을 주고받는 서버 쪽 창구를 말합니다.
- REST — 자원을 URL로 나타내고 HTTP 메서드와 상태 코드를 그 뜻대로 써서 API를 설계하는 방식입니다.
- SSR (Server-Side Rendering) — 요청마다 서버가 HTML을 만들어 보내는 방식입니다.
- SSG (Static Site Generation) — 빌드할 때 모든 페이지의 HTML을 미리 만들어 두고 정적 파일로 내보내는 방식. 이 사이트가 이렇습니다.
- 리버스 프록시 (reverse proxy) — 서버 앞에서 요청을 대신 받아 뒤의 서버들에 나눠 넘기고 응답을 돌려주는 서버. TLS 종료, 압축, 라우팅을 맡습니다.
- 포워드 프록시 (forward proxy) — 클라이언트 쪽에서 클라이언트 대신 바깥 서버에 요청을 보내는 프록시입니다.
- X-Forwarded-For — 프록시가 원래 클라이언트의 IP를 뒤의 서버에 알려 주려고 붙이는 HTTP 헤더입니다.
- 로드 밸런서 (load balancer) — 들어온 요청이나 연결을 여러 서버에 나눠 보내고, 죽은 서버를 빼는 장치나 소프트웨어입니다.
- 헬스 체크 (health check) — 서버나 컨테이너가 정상적으로 응답하는지 주기적으로 확인하는 것입니다.
- CDN (Content Delivery Network) — 세계 곳곳의 캐시 서버(엣지)에서 사용자와 가까운 곳의 복사본을 주는 서비스입니다.
- 오리진 (origin server) — CDN이나 캐시 뒤에 있는 원래 서버. 캐시에 없는 것을 여기서 받아 옵니다.
- Redis — 데이터를 메모리에 두는 키-값 저장 서버. 캐시, 세션, 계수기, 큐로 씁니다.
- 캐시 어사이드 (cache-aside) — 먼저 캐시를 보고, 없으면 원본(DB)에서 읽어 캐시에 넣는 가장 흔한 캐시 사용법입니다.
- 메시지 큐 (message queue) — 보내는 쪽이 넣은 메시지나 할 일을 쌓아 두었다가 받는 쪽이 꺼내 처리하게 하는 중간 저장소입니다.
- 워커 (worker) — 큐에서 할 일을 꺼내 백그라운드에서 처리하는 프로세스입니다.
- 롱 폴링 (long polling) — 클라이언트의 요청에 서버가 새 소식이 생길 때까지 답을 미뤘다가 보내는 방식입니다.
- SSE (Server-Sent Events) — HTTP 응답을 끝내지 않고 서버가 계속 이벤트를 이어 써서 클라이언트에 보내는 단방향 방식입니다.
- WebSocket — HTTP로 시작해 프로토콜을 바꾼 뒤 TCP 연결 하나로 양방향 메시지를 주고받는 프로토콜입니다.
- 크론 (cron) — 정해진 시각이나 주기에 명령을 실행하는 유닉스의 예약 데몬. `0 8 * * *` 같은 다섯 칸 표기를 씁니다.
- 오브젝트 스토리지 (object storage) — 파일을 키로 넣고 꺼내는 거의 무한한 저장소. AWS S3, Cloudflare R2 등.
- 볼륨 (volume) — 컨테이너를 지워도 남도록 컨테이너 바깥에 두고 안에 마운트한 저장 공간입니다.
- 셀프호스팅 (self-hosting) — 남이 운영하는 서비스 대신 같은 기능의 소프트웨어를 내 서버에서 직접 돌리는 것입니다.
- Docker Compose — 여러 컨테이너의 이미지, 환경 변수, 네트워크, 볼륨을 파일 하나에 적어 함께 띄우는 도구입니다.
- 오케스트레이션 (orchestration) — 여러 서버에 컨테이너를 배치하고, 다시 띄우고, 개수를 늘리고 줄이는 일을 자동으로 하는 것. Kubernetes가 대표적입니다.
- CI/CD — 코드를 합칠 때마다 자동으로 테스트·빌드하고(CI), 통과한 것을 자동으로 배포하는(CD) 흐름입니다.
- 롤백 (rollback) — 새 버전에 문제가 있을 때 이전 버전으로 되돌리는 것입니다.
- 무중단 배포 (zero-downtime deployment) — 서비스를 멈추지 않고 새 버전으로 바꾸는 배포. 롤링, 블루-그린 방식이 있습니다.
- 모니터링 (monitoring) — 로그, 지표, 추적, 알림으로 서비스가 잘 돌고 있는지 계속 지켜보는 것입니다.
- 백분위수 (percentile) — 값을 정렬했을 때 그 비율 아래에 있는 값. 응답 시간의 p99는 가장 느린 1% 수준을 뜻합니다.
:::

## 직접 해보기

:::practice nginx nginx로 정적 사이트와 SPA 내보내기
아무 프론트엔드 프로젝트를 빌드하고 nginx 컨테이너로 내보냅니다. `/없는/경로`로 새로고침했을 때 404가 나는 것을 보고, `try_files`로 `index.html`을 돌려주게 고칩니다. 응답 헤더의 `Content-Type`도 확인합니다.

```sh 터미널 (Docker)
npm run build
cat > spa.conf <<'EOF'
server {
  listen 80;
  root /usr/share/nginx/html;
  location / { try_files $uri $uri/ /index.html; }
}
EOF
docker run --rm -p 8080:80 -v "$PWD/dist:/usr/share/nginx/html:ro" -v "$PWD/spa.conf:/etc/nginx/conf.d/default.conf:ro" nginx:alpine
curl -sI localhost:8080/assets/ | head -3
```
:::

:::practice proxy 리버스 프록시로 두 앱을 하나의 주소에
Node 서버 두 개를 서로 다른 포트에 띄우고, Caddy 하나로 `/api/*`는 하나에, 나머지는 다른 하나에 보내 봅니다. 뒤의 앱에서 `X-Forwarded-For` 헤더가 들어오는지 출력해 봅니다. 그다음 API 서버를 끄고 `/api/`를 요청해 502를 확인합니다.

```sh 터미널
node -e "require('http').createServer((q,s)=>s.end('front '+q.url+'\n')).listen(3001)" &
node -e "require('http').createServer((q,s)=>s.end('api '+q.url+' from '+q.headers['x-forwarded-for']+'\n')).listen(3002)" &
cat > Caddyfile <<'EOF'
:8080 {
  handle_path /api/* {
    reverse_proxy localhost:3002
  }
  reverse_proxy localhost:3001
}
EOF
caddy run --config Caddyfile &     # brew install caddy / winget install CaddyServer.Caddy / apt install caddy
curl localhost:8080/hello ; curl localhost:8080/api/posts
kill %2 ; curl -i localhost:8080/api/posts | head -1   # 502
```
:::

:::practice sse SSE와 WebSocket 맛보기
서버가 1초마다 시각을 보내는 SSE 엔드포인트를 만들고 브라우저에서 받아 봅니다. DevTools Network 탭에서 응답이 끝나지 않고 계속 이어지는 모습(EventStream 탭)을 확인합니다.

```js sse.mjs
import http from "node:http";
http.createServer((req, res) => {
  if (req.url !== "/events") {
    res.setHeader("Content-Type", "text/html; charset=utf-8");
    return res.end(`<pre id=o></pre><script>new EventSource("/events").onmessage = e => o.textContent += e.data + "\\n"</script>`);
  }
  res.writeHead(200, { "Content-Type": "text/event-stream", "Cache-Control": "no-cache" });
  const t = setInterval(() => res.write(`data: ${new Date().toLocaleTimeString()}\n\n`), 1000);
  req.on("close", () => clearInterval(t));
}).listen(3000, () => console.log("http://localhost:3000"));
```
:::

:::practice compose Compose로 앱과 Redis 함께 띄우기
Node 앱과 Redis를 Compose 파일 하나로 띄우고, 앱이 서비스 이름(`redis`)으로 Redis를 찾는 것(13장의 Docker 내장 DNS)을 확인합니다. 새로고침할 때마다 방문 수가 늘어나면 성공입니다. `docker compose down` 뒤에 다시 띄우면 숫자가 어떻게 되는지, 볼륨을 붙이면 어떻게 달라지는지도 봅니다.

```yaml compose.yaml
services:
  app:
    image: node:24-alpine
    command: node -e "const net=require('net');require('http').createServer((q,s)=>{const c=net.connect(6379,'redis');c.write('INCR visits\r\n');c.once('data',d=>{s.end('방문 '+d.toString().slice(1));c.end()})}).listen(3000)"
    ports: ["127.0.0.1:3000:3000"]
  redis:
    image: redis:7-alpine
```
:::

:::practice cron 크론 표기 읽고 쓰기
다음 일을 크론 다섯 칸으로 적어 봅니다: 평일 오전 9시, 매월 1일 자정, 15분마다, 매주 일요일 새벽 4시 30분. [crontab.guru](https://crontab.guru/)에 넣어 맞는지 확인하고, 내 서버의 시간대가 UTC라면 한국 시각으로는 언제인지도 적습니다. Linux나 macOS라면 `date -u`와 `date`를 비교해 봅니다.
:::

## 장 전체 문제

:::quiz api-path `blog.mlnl.cloud/api/posts`로 보낸 요청이 거치는 순서로 맞는 것은?
- [ ] Caddy → 가비아 DNS → mlnl-blog → mlnl-api
- [ ] 가비아 DNS → mlnl-blog → Caddy → mlnl-api
- [ ] 가비아 DNS → Caddy → mlnl-blog → mlnl-api
- [x] 가비아 DNS → Caddy (TLS 종료, 경로 확인) → mlnl-api

DNS로 IP를 얻고, Caddy가 TLS를 푼 뒤 `/api/*` 경로를 보고 블로그를 거치지 않고 API 컨테이너로 바로 보냅니다. Caddyfile의 `handle_path /api/*` 블록이 이 일을 합니다.
:::

:::quiz blog-down `mlnl-blog` 컨테이너 하나만 죽었습니다. 각 주소에서 보이는 결과로 맞는 것은?
- [x] `blog.mlnl.cloud`는 502, `cs.mlnl.cloud`는 정상
- [ ] 둘 다 502
- [ ] `blog.mlnl.cloud`는 연결 거부, `cs.mlnl.cloud`는 정상
- [ ] 둘 다 열리지 않다가 1분 뒤 함께 돌아온다

Caddy는 살아 있으니 연결과 TLS는 맺어지고, 뒤의 블로그에 닿지 못해 502를 돌려줍니다(14장). 이 책의 nginx는 다른 컨테이너라 영향이 없습니다. `restart: unless-stopped`이니 Docker가 블로그를 곧 다시 띄웁니다.
:::

## 스스로 점검

:::qa 리버스 프록시가 하는 일을 네 가지 이상 대 보세요. 이 사이트의 Caddy는 그중 무엇을 하나요?
이름과 경로로 뒤의 서버에 나눠 보내기, TLS 종료, 압축과 보안 헤더 붙이기, 느린 클라이언트 대신 받아 주기, 요청 크기와 횟수 제한, 원래 IP를 X-Forwarded-For로 전달하기가 있습니다. 이 사이트의 Caddy는 Host와 경로로 컨테이너에 나눠 보내고, 인증서를 자동으로 받아 HTTPS를 종료하고, zstd·gzip 압축과 HSTS 헤더를 붙이고, 블로그 API의 본문 크기를 제한합니다.
:::

:::qa 앱 서버를 두 대로 늘렸더니 로그인이 자꾸 풀립니다. 왜일까요?
세션을 각 앱 서버의 메모리에 저장하고 있어서, 로드 밸런서가 다음 요청을 다른 서버로 보내면 그 서버는 세션을 모르기 때문입니다. 세션을 Redis나 DB 같은 공유 저장소에 두어 앱 서버를 무상태로 만듭니다.
:::

:::qa CDN이 웹 페이지를 빠르게 만드는 이유를 RTT로 설명해 보세요.
사용자와 가까운 엣지 서버가 캐시된 파일을 주니 왕복 거리가 짧아 RTT가 줄고, TLS 핸드셰이크도 가까운 엣지에서 끝납니다. 연결, 핸드셰이크, 요청마다 드는 왕복 시간이 모두 줄어듭니다.
:::

:::qa 회원 가입 처리에서 환영 메일 보내기를 메시지 큐로 빼면 무엇이 좋아지나요?
가입 요청은 할 일을 큐에 넣고 바로 응답하니 사용자가 메일 발송을 기다리지 않습니다. 메일 서비스가 잠깐 느리거나 죽어도 일은 큐에 남아 워커가 나중에 다시 시도하고, 가입이 몰려도 워커가 감당할 속도로 처리됩니다.
:::

:::qa 평균 응답 시간이 100ms인데 사용자들은 느리다고 합니다. 무엇을 더 봐야 하나요?
p95, p99 같은 꼬리 응답 시간을 봅니다. 평균이 낮아도 느린 요청이 일부 있으면, 페이지 하나에 요청을 수십 개 보내는 사용자는 거의 매번 그 느린 요청을 만나 페이지 전체가 느려집니다.
:::
