## 바꿀 수 없는 레거시

수자원기술 홈페이지는 PHP 레거시였다.
CMS, 문의, 검색이 PHP로 돌아가서 정적 사이트로 바꿀 수도 없었다.

그 위에 영문판을 새로 열어야 했다.

## 영문판인데 소스는 국문판

영문판은 국문판과 같은 소스를 쓴다. 파일은 `www/kor/` 그대로다.
그런데 주소는 `/eng/`로 보여야 했다.

여기서 쓰는 게 rewrite다. redirect와 헷갈리기 쉬워서 정리하면 이렇다.

- **redirect**: 서버가 브라우저에게 "저 주소로 다시 가"라고 답한다. 주소창이 바뀐다
- **rewrite**: 서버가 안에서 주소만 바꿔 처리한다. 브라우저는 모른다. 주소창도 그대로다

그래서 `/eng/`로 들어온 요청은 Caddy가 안에서 `/kor/`로 바꿔 PHP에 넘긴다.
반대로 `/kor/`로 들어온 요청은 301로 `/eng/`에 보낸다. 같은 페이지가 두 주소로 보이지 않게.

![Caddy가 /eng/ 요청은 /kor/로 rewrite해 넘기고, /kor/ GET은 /eng/로 301, /kor/ POST는 그대로 넘기는 세 경우](rewrite.svg "Caddy가 요청을 나누는 세 가지 경우")

POST는 일부러 넘기지 않았다.
301을 받은 브라우저는 POST를 GET으로 바꿔 다시 보낼 수 있다. 그러면 문의 폼 내용이 사라진다.

```caddyfile Caddyfile
# 주소창에는 /eng/ 로 보이게 한다. 실제 파일은 www/kor/ 그대로 (국문 사이트와 같은 소스)
#   /kor/... 로 들어온 GET·HEAD → /eng/... 로 이동 (POST 는 폼 전송이 깨지지 않게 그대로 둠)
#   /eng/... → 서버 안에서 /kor/... 로 바꿔 web 에 넘김
```

## 머지하면 출시까지

배포도 손으로 하지 않게 만들었다. main에 머지하면 이 순서로 돈다.

![main 머지 후 바뀐 PHP 문법 검사, 배포, Caddy 설정 검사, 무중단 reload 순서로 진행하고, 중간에 실패하면 복구하는 흐름](pipeline.svg "머지부터 출시까지")

순서에도 이유가 있다.
PHP 문법 검사는 배포 전에, Caddy 설정 검사는 reload 전에 한다.
잘못된 파일이나 설정이 운영에 닿기 전에 걸러 내기 위해서다.

Caddy의 reload는 서버를 끄지 않고 설정만 갈아 끼운다. 받던 연결은 그대로 끝까지 처리한다.

## 서버는 한 대뿐

자동 확장이 없는 서버 한 대로 운영해야 했다. 그것도 버스트형 CPU다.

버스트형은 평소에는 CPU를 조금만 쓰면서 크레딧을 모으고, 바쁠 때 그 크레딧을 써서 더 빨리 돈다.
크레딧이 바닥나면 기본 성능으로 떨어진다.

이 서버가 얼마까지 버티는지 모르고 출시할 수는 없었다.

## 단계별로 부하 걸기

동시 접속 10명부터 200명까지, 단계마다 30초씩 부하를 걸었다.
초당 처리량과 응답 시간(p50 / 95 / 99)만이 아니라 서버 load, 메모리, 컨테이너별 CPU까지 같이 기록했다.

p50은 요청 절반이 그 안에 끝난 시간, p99는 100개 중 99개가 그 안에 끝난 시간이다.
평균은 느린 요청 몇 개를 가려 버린다. 그래서 p99를 같이 봤다.

실제 결과 파일에서 메인 페이지 부분만 옮기면 이렇다.

## 숫자 읽기

동시 접속을 20배 늘려도 처리량은 초당 약 50건에서 평평했다. 늘어난 건 기다리는 시간뿐이었다.

서버가 한 번에 처리할 수 있는 양에는 천장이 있다.
그 천장을 넘는 요청은 사라지지 않고 줄을 선다.

![요청이 Apache 대기열에 줄을 서고 처리는 초당 약 55건에서 막혀, 기다리는 시간이 줄 선 사람 수를 처리 속도로 나눈 값이 되는 모습](queue.svg "천장을 넘은 요청은 줄을 선다")

이건 리틀의 법칙(L = λ × W)으로 맞춰 볼 수 있다.
시스템 안에 있는 요청 수(L)는 처리 속도(λ)에 머무는 시간(W)을 곱한 값이다.
동시 50명을 초당 약 55건으로 나누면 0.9초쯤 나온다. 실측 p50 864ms와 맞았다.

실패가 0건이라고 괜찮은 건 아니었다.
Apache는 넘치는 요청을 버리지 않고 줄을 세운다. 그래서 실패는 0인데 200명에서 p99는 12초가 넘었다.
사용자에게 12초는 실패와 같다.

## 측정 타이밍에 한 번 속았다

부하가 끝난 뒤에 찍은 CPU는 0.5%였다. 부하가 걸린 동안 찍으니 70%였다.
CPU는 "지금"의 값이다. 부하가 끝나면 바로 내려간다.
측정은 부하가 걸려 있는 그 순간에 해야 한다.

## 공개 다음 날

인증 없이 원격 코드 실행이 가능한 PHP 취약점 PHP2Shell(CVE-2026-109618 · 109619, CVSS 9.2)이 공개됐다.

문제는 버전이었다.
사이트는 PHP 7.4였고, 공식 이미지는 7.4.33에서 멈춰 있었다. 지원이 끝난 버전이라 기다려도 패치된 이미지는 나오지 않는다.

그래서 두 가지를 동시에 했다.
당장 공격이 PHP에 닿지 못하게 막는 **완화**, 그리고 PHP 자체를 고치는 **수정**.

## 요청이 PHP에 닿기까지

완화를 하려면 요청이 어떤 길을 지나 PHP에 닿는지부터 알아야 했다.

요청은 Caddy → Apache → PHP 순서로 지나간다.
그리고 PHP는 스크립트를 실행하기 **전에** 요청 본문을 먼저 다 읽고 파싱한다. 업로드 파일이나 폼 데이터가 `$_POST`, `$_FILES`에 미리 들어 있는 이유다.

이 취약점은 요청 본문을 다루는 쪽을 노렸다.
그러니 본문이 크면 PHP에 닿기 전에 잘라야 한다.

![요청이 Caddy, Apache, PHP 본문 파싱, 스크립트 순서로 지나가고, 상한을 앞쪽에 걸어 PHP가 보기 전에 막으며, 스크립트의 ini_set은 이미 늦은 지점인 구조](limits.svg "상한을 거는 자리와 시점")

## 완화 네 겹

1. Caddy: 요청 본문 상한
2. Apache: `LimitRequestBody`
3. PHP: 본문 파싱 전에 적용되는 `php_admin_value`
4. 컨테이너: 메모리 상한 1g

```apache web/apache.conf
php_admin_value memory_limit -1
# 요청 본문 크기. Caddy 와 같은 값이며 크기를 밝히지 않은(chunked) 요청에도 적용된다.
LimitRequestBody 8388608

# CMS 업로드만 32M 까지
<Directory /var/www/html/cms>
    LimitRequestBody 33554432
    php_admin_value post_max_size 32M
    php_admin_value upload_max_filesize 30M
</Directory>
```

같은 값을 코드의 `ini_set`으로 걸면 소용이 없다.
`ini_set`은 스크립트 안에서 실행된다. 그때는 본문 파싱이 이미 끝났다.
설정은 "무엇"보다 "언제" 적용되는지가 중요했다.

## 수정 한 겹: 직접 빌드

완화만으로 끝내지 않고 PHP 자체를 고쳤다.
PHP 보안팀이 낸 7.4 백포트 패치를 받아, 이미지에 들어 있는 PHP의 원래 빌드 옵션(`php-config --configure-options`) 그대로 다시 빌드했다.
빌드 옵션이 같아야 확장 모듈이나 동작이 바뀌지 않는다.

```bash web/php-cve/rebuild-php.sh
[ "$(php -r 'echo PHP_VERSION;')" = "7.4.33" ] || { echo "PHP 7.4.33 이미지(php:7.4-*)에서만 쓴다"; exit 1; }
echo "$PATCH_SHA256  $PATCH" | sha256sum -c -

opts="$(php-config --configure-options | sed 's/--with-pear\b/--without-pear/')"
docker-php-source extract
cd /usr/src/php
patch -p1 --forward < "$PATCH"
eval "./configure $opts"
make -j"$(nproc)"
```

패치 파일은 sha256부터 검사한다. 받은 파일이 바뀌었으면 빌드하지 않는다.

## 패치가 들어갔는지 어떻게 알까

백포트는 버전을 올리지 않는다. 패치 전후 모두 버전 문자열이 7.4.33이다.
버전으로는 확인할 수 없었다.

그래서 패치가 새로 추가한 설정 `max_multipart_body_parts`를 마커로 삼았다.
이 설정이 있으면 패치가 들어간 PHP다. 없으면 빌드가 실패한다.

## 이미 들어왔다면?

패치는 앞으로의 공격을 막는다.
하지만 취약점이 공개되고 패치하기까지 사이에 이미 누가 들어왔는지는 따로 확인해야 했다.

원격 코드 실행 취약점으로 들어온 공격자는 보통 흔적을 남긴다.
다시 들어올 문(웹쉘)을 심거나, 업로드 폴더에 실행 파일을 두거나, 기존 PHP 파일을 고친다.

## 어디를 볼까

그래서 그 흔적이 남을 만한 곳 8개를 정해 점검했다.
공격 흔적, 웹쉘, 최근 바뀐 PHP 파일, 업로드 경로에 있는 스크립트 등이다.

업로드 경로는 원래 이미지나 문서만 있어야 하는 곳이다.
그런 곳에 `.php` 파일이 있으면, 그 자체가 이상 신호다.

## 점검 → 패치 → 재점검

점검을 한 번 하고 끝내지 않았다.
점검 → 패치 → 재점검을 한 세트로 돌렸다.

패치 전 점검은 "이미 들어왔는가"를 보고, 패치 후 재점검은 "패치하는 사이에 들어왔는가"를 본다.
