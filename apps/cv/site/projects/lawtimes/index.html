01문제와 결과

문제

  • 클라이언트 렌더링 범위가 넓어 SSR의 이점이 사라져 있었고, SPA 라우팅에서 GA4 페이지뷰가 빠지고 있었습니다.
  • 배포는 맥에서 크로스 빌드 → VPN 접속 → 베스천 SSH → 컨테이너 하나씩 교체 → git 싱크의 다섯 단계 손작업이었습니다.
  • EC2는 VPN IP만 받는데 GitHub 러너 IP는 매번 바뀌어서, “빌드 자동화”가 아니라 “못 들어오는 서버에 어떻게 배포하나”가 진짜 질문이었습니다.

결과

  • 머지 한 번이면 배포되고, 테스트 서버 교체는 정지부터 새 컨테이너 응답까지 약 8초입니다.
  • pem · VPN · 비밀번호를 사람끼리 주고받지 않고, 레포 권한만으로 배포됩니다.

02한 일

  1. 01

    렌더링

    SSR을 무력화하던 클라이언트 렌더링 범위를 좁히고 폰트를 dynamic subset으로 바꿨습니다.

  2. 02

    베스천 runner

    베스천에 self-hosted runner를 두고 GitHub으로 나가는 443 롱 폴링만 쓰게 해 VPN 규칙을 그대로 뒀습니다.

  3. 03

    빌드는 GitHub에서

    amd64 네이티브로 빌드하고, 버전은 최신 태그와 PR 라벨로 정했습니다.

  4. 04

    롤링 교체

    포트를 하나씩 교체하고, 60초 안에 응답이 없으면 그 포트만 이전 컨테이너로 되돌립니다.

  5. 05

    권한 최소화

    sudo 없는 전용 계정, main · dev workflow만 허용, 러너 키에는 command=로 배포 스크립트만 실행하게 하고 인자는 정규식으로 검사합니다. 베스천 job에는 Secret을 넘기지 않습니다.

03배운 것

  • set -e는 복구 단계까지 건너뜁니다. 실패하면 기존 컨테이너가 멈춘 채 끝나서 if ! …; then restore로 바꿨습니다.
  • 새 브랜치를 push하면 paths 필터가 비교할 커밋이 없어 아무 기록 없이 건너뜁니다.
  • 버전은 push한 순간 “쓴 것”입니다. 같은 번호로 다시 빌드하면 롤백을 보장할 수 없습니다.
  • 자동화는 실패 경로가 코드에 없으면 그냥 멈춥니다. 사람이 하던 판단까지 스크립트로 옮겼습니다.
