고칠 때마다 손으로 눌러 봤다

관리자 화면은 넓었다. 회원, 상품, 결제, 정산, 통계, 배달, 고객센터까지.
수정도 잦았다.

하나 고치면 어디가 깨졌는지 알 수 없어서, 매번 손으로 눌러 봐야 했다.

무엇을 테스트할까

테스트를 짜기 전에 정한 게 있다.
"이 함수가 무엇을 리턴하나"가 아니라 "관리자가 무엇을 하면 화면이 어떻게 되나"를 테스트한다.

관리자에게 중요한 건 버튼을 누르면 목록이 바뀌고, 저장하면 알림이 뜨는 것이다.
그래서 화면 단위로, 실제 사용 흐름대로 통합 테스트를 짰다.

서버 대신 MSW

화면 테스트에는 서버 응답이 필요하다.
그렇다고 화면 코드 안에 "테스트면 가짜 데이터" 같은 분기를 넣고 싶지는 않았다.

MSW는 요청이 나가는 길목에서 가로채서 대신 응답한다.
화면 코드는 실제로 fetch를 부르고, 실제 응답처럼 받는다. 테스트인 줄 모른다.

  • 도메인별로 fixture를 만들었다
  • alert · table · download처럼 자주 하는 확인은 공통 유틸로 뺐다
  • 테스트 이름은 "~하면 ~한다" 문장으로 썼다

마지막 규칙 덕분에 테스트 목록을 위에서부터 읽으면 그대로 요구사항 목록이 된다.

결과

테스트 파일 84개, 케이스 935개.
로컬에서 다시 돌린 175개는 약 10초에 모두 통과했다.

zod가 조용히 지운 필드

하나 배운 게 있다.
zod는 스키마에 없는 필드를 에러 없이 지운다. parse의 기본 동작이 그렇다.

관리자 스키마에 새 필드를 넣지 않으면, 서버가 그 값을 보내도 화면까지 오지 못하고 조용히 사라진다.
에러가 없으니 테스트로 잡으려면 "그 값이 화면에 보이는가"를 확인해야 한다.
