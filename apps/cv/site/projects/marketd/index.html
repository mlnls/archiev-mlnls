01문제와 결과

문제

  • 관리자, 사용자 앱, 웹뷰가 각자 다른 레포에 있어 앱-웹뷰 메시지 타입이 어긋나곤 했습니다.
  • 관리자 화면은 회원 · 상품 · 결제 · 정산 · 통계 · 배달 · 고객센터까지 넓고 수정이 잦아, 하나를 고치면 어디가 깨졌는지 손으로 확인해야 했습니다.
  • 이웃거래 채팅 사진(집 앞, 송장, 계좌 캡처)이 공개 버킷에 있어 주소만 알면 누구나 볼 수 있었습니다.

결과

  • 관리자 테스트는 “~하면 ~한다” 문장이라 요구사항처럼 읽히고, 로컬 재실행 175/175가 약 10초에 통과합니다.
  • 채팅 사진은 참여자만 60초 동안 볼 수 있고, 보내는 쪽 코드는 한 줄도 바꾸지 않았습니다.

02한 일

  1. 01

    모노레포

    pnpm workspace와 Turborepo로 레포를 합치고 앱-웹뷰 메시지 타입을 공통 패키지로 묶었습니다.

  2. 02

    배포 경로 분리

    Expo EAS Update로 웹뷰, 연결 로직, 바이너리의 배포 경로를 나눠 긴급 수정을 스토어 심사 없이 내보냈습니다.

  3. 03

    테스트 기반

    MSW로 서버 대신 목업 API를, 도메인별 fixture와 alert · table · download 공통 유틸을 만들었습니다.

  4. 04

    E2E는 골라서

    jsdom은 File을 멀티파트로 바꿀 때 파일명과 내용을 잃습니다. 전부 옮기지 않고 배너 이미지, 엑셀 업로드, 실제 달력, 체크박스만 Playwright로 옮겼습니다.

  5. 05

    서명 URL 이미지

    비공개 버킷과 60초 서명 URL로 바꾸며, 목록은 initialData로 · 소켓 메시지는 바로 발급받게 쿼리 하나로 두 경로를 처리했습니다.

  6. 06

    만료 대응

    이미 그린 이미지는 미리 갱신하지 않고, 깨지면 key당 한 번만 재발급합니다. 여러 장이 동시에 깨져도 요청은 한 번(cancelRefetch: false)입니다.

03배운 것

  • 서명은 “누가”를 모릅니다. URL을 가진 누구나 60초 동안 볼 수 있으니, 발급 API에서 참여자를 확인해야 합니다.
  • zod는 모르는 필드를 에러 없이 지웁니다. 관리자 스키마에 새 필드를 넣지 않으면 조용히 사라집니다.
  • 배포 순서도 설계입니다. 서버 배포 직후 PR을 머지하지 않으면 둘 다 깨집니다.
  • “Playwright를 썼다”가 아니라, 통합 테스트가 못 보는 지점만 골라 브라우저 테스트로 옮겼습니다.

04발표 자료
